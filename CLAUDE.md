# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ClawBox is **OpenClaw OS** — the operating system for [OpenClaw Hardware](https://clawbox.com/), a private AI assistant running on NVIDIA Jetson (Tegra/ARM). It manages the full device lifecycle: broadcasts a WiFi access point with captive portal for first-boot setup from any phone/laptop, transitions to the home network, then serves a Chrome OS-style desktop environment with built-in apps. The OpenClaw AI agent controls the entire device through MCP (Model Context Protocol) tools — making ClawBox an OS the AI can operate, not just a UI the user clicks through.

## Stack

Bun runtime (package management + builds), Node.js 22 (production runtime), Next.js 16 (App Router), React 19, TypeScript 5, Tailwind CSS v4. Optimized for local edge deployment on Jetson — `output: 'standalone'` in next.config.ts, no external CDN dependencies, fully offline-capable.

## Commands

- `bun run dev` — dev server on port 3000 at 0.0.0.0
- `bun run dev:privileged` — dev server on port 80 (requires root)
- `bun run build` — production build (generates `.next/standalone/`)
- `bun run start` — run standalone production server on port 80
- `bun run lint` — run ESLint
- `bun run test` — run Vitest unit tests
- `sudo bash install.sh` — full system install: installs bun, builds, configures avahi/mDNS, installs systemd services, starts AP and web server

## Architecture

### Routing

After setup completes, the root `/` serves a Chrome-like desktop environment (`src/app/page.tsx`) that includes a window manager, taskbar, and built-in apps. The setup wizard lives at `/setup`. Authentication is enforced via middleware — unauthenticated users are redirected to `/login`.

Next.js rewrites in `next.config.ts` proxy gateway paths (`/api/*`, `/assets/*`, favicons) to the OpenClaw gateway at `127.0.0.1:18789`. A catch-all route (`src/app/[...gateway]/`) handles remaining gateway paths.

Selecting the box's own voice (`{action:"select", choice:"local"}`) REPAIRS the wiring when Kokoro is installed but openclaw.json has no `tts-local-cli` entry (`src/lib/voice-local-wiring.ts` writes the same provider JSON install.sh does, asking `clawbox-tts.sh --provider-timeout-ms` for the timeout), and when the pick still cannot be honoured it settles on Auto and answers 200 with `fallback: { requested, reason: "not_installed" | "not_wired" }` instead of a 409 — the panels show that in amber. `tts/install` (owner-only, streamed like the Gemma install) runs install.sh's `openclaw_tts` root step for an absent Kokoro — and for an absent encoder too: `tts_ensure_ffmpeg` runs at the TOP of that step, ahead of the engine because it also has to reach the Hermes arm, which returns before the OpenClaw registration, and it WARNS rather than failing when apt cannot be reached (a box that cannot reach a mirror still has a working chat voice, and losing the whole voice install over one download would be the worse outcome). That same step is what every update run invokes, so it is the only route a box already in a customer's hands has to the fix. `openclaw_tts` is on the WEB root-step list for it and deliberately not on the UI list, which `install/run-step` serves to the MCP bearer too. `tts/warm` (POST, owner cookie AND same origin — spawning systemctl is the person's doing, not another site's page and not the MCP bearer the middleware also admits; deliberately NOT gated on the edition, since `install-voice.sh` writes the Kokoro unit on every SKU and both harnesses speak through the same script) asks systemd to bring the box's own voice up before anything needs it: `startUserEngine` (`src/lib/local-models.ts`) runs `systemctl --user start --no-block` for `KOKORO_UNIT` and nothing else (allow-listed, and never `enable` — that is Local AI's standing switch, and an engine the owner switched off for good must not come back at the next boot because a chat turn warmed it), answering 200 `{warm:true}` for a unit already up, 202 `{warming:true}` once systemd has the request, 409 `not_installed` where there is no unit and 502 `start_failed`. It exists because the Kokoro server holds the model on the GPU and stops itself after five idle minutes while nothing on the box brings it back, so the first utterance after a quiet spell pays a 13-19 s cold start and usually loses the race to the cloud voice; the two surfaces that KNOW a spoken reply is coming call it the moment the person acts — the chat's microphone button before it starts recording (only while the spoken-replies switch is on, so the recording, the transcription and the agent's turn all run while the model loads) and the Voice tab's "This box" pick, ahead of the write rather than after it, both fire-and-forget so a 409 cannot colour an action that worked. `stt` — speech input: `stt_primary` orders ClawBox cloud transcription and Whisper on the box for BOTH the chat microphone (`chat/transcribe`, which now falls through and reports `engine`) and channel voice notes (`tools.media.models[]`, OpenClaw 2's shared media-model list — audio rows tagged `capabilities: ["audio"]` — tried in order). - **Memory embedder**: `embed/status`, `embed/install`, and the proxy `local-ai/embed/v1/*` — the memory-search embedding model (Qwen3-Embedding-0.6B, Q8_0) on ClawBox's own llama.cpp, run as the SYSTEM unit `clawbox-embed.service` (`config/clawbox-embed.service`, `scripts/start-embed-server.sh`, numbers in `src/lib/embed-runtime-ids.ts`, pinned by `embed-server-pin.test.ts`). It replaced the copy ollama hosted, which measured 2.8 GB resident whenever the agent was in use because ollama launched it with a 2,048-token batch — `n_ubatch × n_vocab × 4 B` of compute buffer, 1.2 GB, for inputs that never exceeded 484 tokens. The unit runs `-c/-b/-ub 1024` with q8_0 KV (~2 GB predicted on the GPU; `EMBED_N_GPU_LAYERS=0` measured 1.4 GB CPU-only with queries FASTER and indexing 13× slower), under a cgroup cap from `config/clawbox-resource-limits.env`, and is a system unit precisely so it can carry one — the web server's unit has none, and a user unit would share the desktop's. OpenClaw's `memory.search` is pointed at the PROXY (`provider: openai-compatible`, `remote.baseUrl` = `/setup-api/local-ai/embed/v1`, `apiKey` = `data/.local-ai-token`), never at port 8081: the proxy is what wakes the unit on the first request (`ensureLocalAiReady("embed")`, `sudo systemctl start`) and stops it ten idle minutes later, and it has to be an always-listening endpoint because OpenClaw's embedding client retries a refused connection three times inside two seconds and then answers keyword-only. The proxy also restores the model's query instruction: OpenClaw's ollama adapter prefixed every search query with `"Instruct: Given a user query, retrieve relevant memory notes and documents\nQuery:"` and its openai-compatible adapter does not, so `memory.search.queryInputType/documentInputType` make it label each request and `src/lib/embed-query-instruction.ts` prefixes the query ones — without this recall quietly degrades while the index stays "healthy". `src/lib/embed-input-fit.ts` trims an input that would overflow the batch (OpenClaw chunks by CHARACTERS, so a 1,600-character CJK chunk can be 1,600 tokens) through llama-server's `/tokenize`, the way ollama's `truncate: true` did, instead of letting the document drop from the index. `ensureLocalAiReady("embed")` refuses the wake below `EMBED_WAKE_MIN_AVAILABLE_MB` (2,300) of MemAvailable — the unit's own cap cannot stop a wake from squeezing the gateway or a build — and `armIdleStopIfRunning("embed")` at web-server boot re-arms the idle stop for a unit that outlived a restart. Provisioning is `scripts/ensure-local-embeddings.sh` (the GGUF via `hf download`, then the config in ONE merged `config set … --strict-json --merge` — a per-key sequence was killed midway on the box, because the bearer write restarts the gateway and during an update that restart is a `systemctl stop` of the cgroup the script runs in — read back from the file before success is logged, then `memory index --force` because the provider change alters the index identity and vector search pauses until a rebuild), run by install.sh's `ensure_local_embeddings` after the web server is up and detached by `gateway-pre-start.sh` on every gateway start. The script and `gateway-pre-start.sh` both export `OPENCLAW_CONFIG_PATH`/`OPENCLAW_STATE_DIR` and `unset OPENCLAW_HOME` before any `openclaw` runs: the CLI reads `OPENCLAW_HOME` as the ACCOUNT home and puts its tree at `$OPENCLAW_HOME/.openclaw`, while ClawBox has always used that name for the `.openclaw` directory itself, and the updater exporting it into the pre-start made every CLI write land in a second tree at `~/.openclaw/.openclaw/` with a clean log. The updater passes `CLAWBOX_OPENCLAW_HOME` instead (never `OPENCLAW_HOME`), and pre-start's `remove_stray_state_tree` deletes such a nested tree when it carries neither a workspace nor credentials; `step_embed_model` caches the model as root first so a first request never downloads inside OpenClaw's 120 s batch budget. Ollama stays installed for its chat-provider backend (retired from every picker — and never offered or WRITTEN as a CHAT model: `inferConfiguredLocalModel` refuses an `ollama/…` id whose name says embed, `ai-models/configure`'s fallback writer asks `ollamaModelCanChat` before an `ollama/…` candidate goes into `agents.defaults.model.fallbacks`, and `chat/model` asks Ollama's `/api/show` capabilities (`completion` present) before an `ollama/…` model is listed, falling back to the name (`/embed/i`) when Ollama cannot be asked, because the migrated embedder `qwen3-embedding:0.6b` stayed declared under `models.providers.ollama.models` and `inferConfiguredLocalModel` took it for the picker's "Ollama Local" row on 2026-09-07; `local-ai/ollama` proxy, `ollama/*` routes, `setup/reset`'s model wipe are unchanged) but has no row on Settings → Local AI any more: the Memory search row IS the engine row ("Qwen 3 via llama.cpp"), `control: "none"` because the proxy owns the lifecycle, `managedBy: "clawkeep"` for the Memory Shard pointer. `post_update` stops ollama after the switch (stop, never disable) and `free_memory_for_build` stops the embed unit the way it stops ollama — and since TASK-724 both stops go through `pause_engine_unit`, which records whether the unit was RUNNING, with `resume_paused_engines` starting back exactly those and checking each after a settle (every one is `Type=simple`, so systemd calls it active the instant it forks). It runs at the end of `step_post_update` — the update's last act, and the stop whose missing start was the defect — and at the end of `do_rebuild` except when the caller announced `--reboot-follows`, since starting four model servers seconds before a reboot restores nothing that survives it. An update that stopped an engine and reported `completed` used to leave it stopped until something happened to ask for it; an engine the owner or the idle standby had already put away is still left alone, and `src/instrumentation.ts` now re-arms the ollama idle stop at web-server boot the way it already did the embedder's, because a root shell cannot arm a timer that lives in the web server.
- **Ollama** (chat-provider backend, no UI): `ollama/status`, `ollama/pull`, `ollama/search`, `ollama/delete` — local model management. `search` offers only sizes under the ollama.service memory cap (`OLLAMA_MAX_MODEL_PARAM_B` in `resource-limits.ts`, answered as `maxParamBillions`); `pull` follows the client's abort so a cancelled download stops. The runtime's idle standby (`systemctl stop`, never `disable`, ten minutes after the last proxied use) still applies through `local-ai-runtime.ts`.
- **Apps**: `apps/store`, `apps/install`, `apps/uninstall`, `apps/icon/[appId]`, `apps/settings`, `apps/skill-info` — app store integration. ClawHub namespaces skills as `@owner/slug` and `openclaw skills install` refuses a bare slug more than one publisher uses, so `install` resolves the publisher first (`src/lib/clawhub-url.ts` — GET clawhub.ai/api/v1/skills/<slug>): one owner installs; an ambiguous slug is settled only by the store listing's own `developer`, otherwise the route answers 409 `{ code: "ambiguous", matches: [{ ownerHandle, ref, url }] }` and the caller re-posts `{ appId, owner }` or `{ appId: "@owner/slug" }`; a slug ClawHub lacks is 404 `not_found`. Every install failure is a non-2xx with `ok: false`, an honest `code` and `retryable` (the CLI's trust gate is left alone — no `--acknowledge-clawhub-risk` — so a `review_required` release tells the owner to install it from the Terminal). Locally everything stays keyed by the bare slug, and the icon is downloaded only after the install succeeded. `install`, `uninstall` and the webapp registry (`src/lib/webapp-registry.ts`, behind webapp deploys) are the only writers of `installed_apps`/`installed_meta`; `uninstall` also drops the window's KV keys and `app_<id>_settings` on every edition, and — only where the edition HAS OpenClaw (`openclawSkillRoot()`, null on the hermes SKU alone) — the skill directory and `skills.entries.<id>` from openclaw.json. That split is why `uninstall` is deliberately the one app route without `openclawAppsGuard()`: the MCP `app_uninstall` tool posts to it on Hermes to remove a webapp whose store the UI has hidden, so it must stay reachable there without ever resolving a delete target under a workspace that edition does not have (TASK-551). Its answer carries `skillRemoved: true | false | null` (`null` = no skill half to report on: the hermes SKU, or a web app) so a caller can tell a removal from a no-op, and it refuses the whole uninstall — 503 `ok: false`, `retryable: true` — rather than dropping the desktop entry for a skill it could not reach, because half an uninstall leaves the owner nothing to retry from: `config_unreadable` when openclaw.json exists and cannot be read (nothing is touched — that is not the same as an edition that has none), `skill_remove_failed` when the folder is there and will not go (`fs.rm` deletes as it walks, so part of it may already be gone, the message says so, and the skill-info cache is rescanned before answering); the outer catch carries the same contract (`uninstall_failed`, 500) and reports `skillRemoved`, because everything after the skill delete can still throw over a folder that is already gone; an id that is not one plain path segment is 400 `invalid_app_id`, `retryable: false`, before anything is touched. Every id that reaches a path on these routes is REBUILT from the alphabet rather than tested and passed through (`safeAppId` in `src/lib/webapp-icon.ts`, `safeProjectId` behind `projectDir`/`webappPath` in `src/lib/code-projects.ts`, `safeSkillName` in `src/lib/openclaw-skill-info.ts`) — a `.test()` guard leaves the caller's string in play, and CodeQL rightly flags every path built from it (`js/path-injection`). The 1-64 `[A-Za-z0-9_-]` bound is a rule about what may ARRIVE: `install` applies it (as `zInstalledAppId`, `skill-info`, the webapps route and the icon route already did), `uninstall` deliberately does not, so an app installed before that bound existed can still be removed. Whether the app is a WEB APP — `installed_meta.webappUrl`, else the deployed `data/webapps/<id>` this uninstall removed — decides two things and neither is whether the skill half RUNS: an unreadable OpenClaw config does not refuse a web app (it has no skill half, so on a `dual` box a config belonging to the idle harness must not strand the agent's own pages), and an id the desktop knows as a web app answers `null` rather than `false`, since "there was no skill of that name on disk" is an absence report about something that never existed. One id can be both — `webapp_create` REPLACES `installed_meta[<id>]` for any id with no collision check — so the removal itself is never skipped; and on the one path where it CANNOT run (a web app the `installed_meta` KNOWS about, removed while that config is unreadable — one recognised only by its deployed directory is still refused, since the refusal is answered before anything is looked at) the answer carries `skillHalfChecked: false` beside `ok: true`, present only when false, because `null` there would claim there was no skill half when the route simply could not look — `app_uninstall` and the desktop's own toast both relay that as "its skills were not checked". The enable switch (`settings` `_setEnabled`) is a direct JSON write of `skills.entries.<id>.enabled` (the gateway hot-reloads it; the CLI cost 10–17 s per click), and `skill-info?appId=` reads `enabled` back from the same file — its list comes from `openclaw skills list --json` served stale-while-revalidate (`src/lib/openclaw-skill-info.ts`; the routes rescan behind an install/uninstall), answering 404 `not_installed` for a skill that is gone and 503 `skills_unavailable` when the CLI failed with nothing cached. `store?slug=` adds `ownerHandle` (and `clawhubMatches`) from ClawHub and rewrites `clawhubUrl` to the real page, or removes it. `icon/[appId]` persists to `data/icons/` only for installed apps and remembers an upstream 404 for an hour.
- **Files**: `files/` — file list, read, write, upload, mkdir, delete. Its `resolve` action answers `relPath` beside `absPath` — the browse-relative path the Files app navigates by — which is how the Coding Agent's "Open in Files" turns a project folder's absolute path into a Files window opened there (`dispatchOpenApp("files", { forceNew, meta: { path } })` → `FilesApp initialPath`). Uploads are bounded by what the box can spare, not by a size cap (large uploads are the point of the PUT path): `src/lib/bounded-body.ts` meters the body against a budget that re-measures free space on the DESTINATION filesystem every 64 MiB minus `DISK_FREE_RESERVE_BYTES` (`src/lib/disk-reserve.ts`, 512 MiB — the in-app update's build is what a full disk kills; project-import's reserve is the same constant), a chunked or understated body is cut at the reserve with 507 `disk_full` and the partial file unlinked, and the multipart POST carries Busboy limits (`files: 1`, `parts: 4`) with the attachments route's teardown discipline — busboy's `fileSize` TRUNCATES rather than errors, so the `limit` handler destroys the write and answers 507 instead of `ok: true` over a cut file; count limits answer 413 `too_many_parts`; a statfs that fails skips the reserve for that request rather than refusing every upload. The `[...path]` PUT (rename) and DELETE refuse a PROTECTED CONTAINER with 400 `protected_container` (`isProtectedContainer` in `src/lib/file-guard.ts`, judged on the typed path AND its `canonicalPath`): `data/` itself, the checkout, `~/.config` and the browse root — `isProtectedFilePath(DATA_DIR)` stays false so the listing keeps filtering entry by entry, but a rename of `data/` to `data-copy` used to move every credential store out from under the guard in one request.
- **Browser**: `browser/` — Chromium automation via CDP (launch, navigate, click, type, screenshot). WHICH Chromium it drives is the owner's setting, read for EVERY session: with the Coding Agent's real browser on (`coding_agent_real_browser`, absent means on) it uses the device's own window, brought up the way `browser/manage`'s open does, and falls back to a headless Chromium of its own only when that is impossible (a foreign Chromium on port 18800, a launch that failed); with it off it goes straight to the headless one and never touches the owner's screen. ### Middleware (`src/middleware.ts`)

Handles three concerns (plus one carve-out: `UI_LANGUAGE_READ` — a GET of `/setup-api/preferences?keys=ui_language`, path and query byte for byte — is answered with no session, because `/login` renders inside the same I18nProvider as the desktop and asks for the box's language on mount; answered 401 it fell back to the browser's language, so a box set to German greeted its owner in English (the sweep of 2026-09-07); the preferences route makes the same cut on its own side, `ANONYMOUS_READABLE_KEYS`, so nothing wider is ever told to an anonymous caller):
1. **Captive portal detection** — intercepts OS-specific detection URLs (Android, Apple, Windows, Firefox) and redirects to `http://10.42.0.1/`
2. **Authentication** — enforces session cookie auth, redirects unauthenticated users to `/login`
3. **The update lock** — while an update owns the box, desktop page navigations (`/` and `/app/*`) are redirected to `/updating`. An update runs `git reset --hard` and `git clean -fd` over the project while the desktop is still on screen and every app on it can write through `/setup-api`, so a window left open can save into a tree being rewritten underneath it. The flag is on DISK (`update_in_progress`, `src/lib/update-lock.ts`) rather than in the updater's memory, because middleware answers before any route handler is entered — it reads the same mtime-cached `data/config.json` snapshot it already reads for `setup_complete`, so the lock costs no extra I/O. `/setup-api` is deliberately NOT redirected (the updating page polls the status route, and an API answering a navigation redirect with HTML is the defect #304 fixed), nor is the gateway (the assistant keeps answering on it throughout). The check sits after the session check, so an expired session still gets `/login`. The acquisition is AWAITED at the top of `runUpdate`, scoped to the flow that contains the RESTART step (the OpenClaw-only flow reinstalls a package and bounces the gateway; locking the desktop for that would be over-reach), and a failure to take or release the lock is reported rather than swallowed — it never stops the update, because refusing to update a box over a courtesy lock is the worse outcome. The flag OUTLIVES the reboot on purpose — the release is in `launchUpdate`'s `finally`, which does not run when `do_rebuild` kills the server, so the desktop stays locked through `post_update`, `gateway_verify` and `verify_build_identity` — and cannot outlive a dead update, because `resumeContinuation` releases it at boot when there is nothing to resume. That boot release is also the only escape that works, so `/updating`'s stuck panel names a restart rather than offering a link back to the desktop, which the middleware would redirect straight back. The page gives every string an English floor (`tr(key, english)`): `I18nProvider` loads translations in an effect through a dynamic import, and this is the one screen guaranteed to be open while the box is offline — raw keys for the length of an outage is not an acceptable answer.

### Code Assistant (`src/lib/code-projects.ts`, `src/app/setup-api/code/`)

Enables the AI agent to build multi-file desktop webapps through an iterative coding workflow:

1. `code_project_init` — scaffold a project (index.html + style.css + app.js)
2. Write/edit files using `code_file_write` and `code_file_edit` (string-replacement edits)
3. Search code with `code_search`, inspect with `code_file_read`
4. `code_project_build` — inlines local CSS/JS into a single HTML file, deploys to `data/webapps/`, registers on the desktop

Projects live in `data/code-projects/<projectId>/`. Built webapps are deployed to `data/webapps/<projectId>/` and served at `/setup-api/webapps?app=<projectId>`. The desktop and the standalone `/app/[id]` page frame a webapp with the one sandbox in `src/lib/webapp-sandbox.ts` (`WEBAPP_IFRAME_SANDBOX`, never `allow-same-origin`): agent-written HTML must never run with the owner's session, which is what a same-origin frame gave it. A framed app therefore has an opaque origin and cannot fetch `/setup-api/kv` (or any `/setup-api` route) — it persists through the KV bridge instead: the guest snippet (`WEBAPP_KV_CLIENT_SNIPPET`, inlined into every `code_project_init` scaffold and quoted in the `clawbox_context` storage guide for one-file apps) defines `window.clawboxKv.get/set/delete/list`, which post `{ clawboxKv: { id, op, key, value } }` to the host; the host answers only the frame it opened, forces the `<appId>:` key namespace and does the KV call with the owner's session. A webapp written earlier against `fetch('/setup-api/kv')` has lost its persistence and must be rebuilt on the bridge. An app created or built without an icon gets one generated by ClawBox AI's image model when the box is linked (`src/lib/webapp-icon.ts`): fire-and-forget after `deployWebapp`/`buildProject` register the app, written atomically to `data/icons/<appId>.png` where the icon route already looks, never overwriting an existing icon, one picture per app and one generation at a time (a rebuild while the picture is being drawn joins it; a failure is not retried for a few minutes) — `withGenerationSlot` is box-wide, so app icons, a coding project's favicons and a run's own pictures all come out of the one per-UTC-day allowance rather than opening N upstream requests against it — dropped if the app was uninstalled meanwhile, and the open desktop is nudged with a `register_webapp` re-push so the icon appears without a reload.

A webapp always runs in a sandboxed iframe with an opaque origin (`src/lib/webapp-sandbox.ts`) — on the desktop and at `/app/installed-<id>` alike — so it can neither call the session-authenticated `/setup-api` nor reach the desktop around it. Its storage is `window.clawboxKv` (get/set/delete/list, Promises), a postMessage bridge the host page answers under the app's own `<appId>:` key namespace; the scaffold inlines the snippet into new projects and the `clawbox_context` storage guide tells the agent to use it. A webapp written before the bridge that fetches `/setup-api/kv` directly no longer persists anything (the call is cross-origin now and the cookie is not sent) — it has to be rebuilt on `window.clawboxKv`. Installed apps and their meta are written by the install/uninstall/webapp-registry routes only; the desktop no longer re-persists `installed_apps`/`installed_meta`, so an install or uninstall made by the agent or the API survives an open desktop (each remaining preference key is written on its own, only when its own state changes).

### System Integration (`scripts/`, `config/`)

- **`scripts/start-ap.sh`** / **`scripts/stop-ap.sh`** — create/tear down WiFi AP "ClawBox-Setup" on `wlP1p1s0` at `10.42.0.1/24`
- **`scripts/terminal-server.mjs`** — WebSocket PTY server on port 3006 (plain ESM JS, started with the web server's own Node — no npx, no transpiler)
- **`scripts/setup-optimizations.sh`** — Jetson GPU/memory tuning. Swap is TWO tiers since 2026-09-06: the board's stock `nvzramconfig` zram (one compressed device per core, half of RAM, priority 5 — a compression ratio, never capacity, since its pages live in RAM: measured 1.12 GB of pages in 0.35 GB, 3.47x) and `install.sh`'s `step_swapfile`, which puts an 8 GB file on the disk at priority 1, records it in `/etc/fstab` and runs on fresh installs (`step_system_config`) AND in-app updates (`step_post_update`). Priority 1 is the point: the kernel fills zram first and the file stays at 0 bytes until something genuinely large arrives — the case that killed an owner's update build on 2026-09-05 (OOM at 4.6 GB resident with the desktop session up). It is idempotent, adopts an existing `/swapfile` without re-making it, falls back to 4 GB and then to nothing when the disk cannot spare the room (`CLAWBOX_SWAPFILE_SIZE_GB`, `CLAWBOX_SWAPFILE_RESERVE_GB`), stands down in test mode because a container cannot `swapon`, and never fails the install
- **`scripts/gateway-pre-start.sh`** — gateway pre-startup hooks, and the two halves of the agent's introduction. It seeds `config/clawbox-bootstrap.md` as the workspace's `BOOTSTRAP.md`: OpenClaw adopts a bootstrap file that is already on disk verbatim, which is the supported way to ship one and survives a reinstall of the npm package, and ours is needed because the stock ritual asks what to call the ASSISTANT and never asks the owner's name — with the Settings field gone, that first conversation is the only thing on the device that asks, and it records the answer in `USER.md` and in `ui_user_name` through `preferences_set`. The seed is for a GENUINELY fresh workspace only: "no `BOOTSTRAP.md`" is not the test, because on an introduced box the file is absent precisely BECAUSE the ritual finished, so every trace of a working agent (`USER.md`, `IDENTITY.md`, `SOUL.md`, `AGENTS.md`, `MEMORY.md`, `memory/`) must be absent too. It is also the one write here that may create the workspace, since a factory reset empties `~/.openclaw` wholesale and the gateway would otherwise make the directory on the first turn and seed the stock ritual first. The second half pays back the deferred language: the owner's pick is stored but not written to the persona (see `language-persona.ts`), so this re-applies it under the same two conditions the route uses, at the first gateway start after the introduction is over — byte-for-byte the transformation `writeLanguagePersona()` performs, rewriting nothing when the files already say it, so every later reboot is a no-op. `scripts/setup-shared-identity.sh` and `scripts/clawbox-identity-sync.sh` wait on the same test before copying the canonical identity into an OpenClaw workspace, because on the dual SKU that copy suppressed the ritual exactly as the language write did elsewhere; a switch made before the first hello is picked up by the next sync instead.
- **`scripts/kokoro-*.sh`** / **`scripts/kokoro-server.py`** / **`scripts/openclaw/clawbox-tts.sh`** — voice/TTS integration. There is ONE `kokoro-server.py` now: the `scripts/openclaw/` copy nothing deployed is deleted (`install-voice.sh` has always copied the top-level one into the workspace, so the second could only drift, and it had already missed a fix), and the surviving one unlinks `/tmp/kokoro-server.sock` on its idle shutdown — `os._exit` runs no cleanup, so the file outlived every idle exit and the cheap `[ -S … ]` "is the server up?" test kept answering yes for a socket nothing was listening on. `clawbox-tts.sh` reads its ~2.6 GB memory guard on the COLD path only, immediately before the CUDA load the guard protects: in front of the resident server it refused requests that allocate nothing like that, and on this board — ollama keeps its model resident for five minutes after every agent turn, leaving ~2.8 GB — that meant every spoken reply following a chat message went to the cloud voice while the box's own engine was up and idle. After paying for a cold start it asks systemd for `kokoro-server.service` (`warm_kokoro_server`, `--no-block`, unconditionally rather than behind the socket test that was lying, and best-effort AFTER the caller's audio is on disk so it can never turn a good utterance into a failed one), because nothing else on the box restarts a server that stops itself every five idle minutes The Unix socket is bound under `umask 0177` and chmod 0600 (it was 0666 — every legitimate client is the clawbox user, and root bypasses the mode), every accepted connection is checked with `SO_PEERCRED` (uid must be the server's or 0), and a request must name an `output` that is an absolute `.wav` regular file (never a symlink) owned by the server's uid directly under `/tmp` (`resolve_output`; both real clients mktemp the WAV there first), written through `O_NOFOLLOW` — a caller could otherwise have the server truncate any clawbox-owned file with WAV bytes (`openclaw.json`, `data/config.json`). `whisper-server.py` carries the socket half only: its `audio` field is a READ path the gateway hands in from wherever it downloaded a voice note. `install-voice.sh` `try-restart`s both user units after deploying the scripts so a resident server does not keep the old socket until its idle exit.

- **`config/clawbox-root-step.sh`** ExecStarts nothing under `/home/clawbox` either, since TASK-733. The rule the sweep enforces is a MECHANISM, not a list of verbs: root must never read a byte out of the clawbox-writable tree and then run it — `install` and `cp` into a root-owned path count exactly as much as `exec`, `bash` and `source` do, and are worse, because the copy becomes the file root runs on every later dispatch. `config/clawbox-root-manifest.sh` keeps a root-owned **mirror** of the paths it records — `install.sh`, `scripts/`, `config/` — at `/var/lib/clawbox/root-exec-mirror` (`--mirror`, `--mirror-path`), the dispatcher execs `$MIRROR/install.sh` for EVERY step, and install.sh resolves `scripts/`/`config/` from `$SRC_DIR` (the directory it was started from, `$PROJECT_DIR` on every path but a dispatched step) so the scripts it hands to `bash` as root and the units it installs into `/etc` come from the mirror too. The exempt self-updating family — `bootstrap_updater`, `post_update`, `rebuild_reboot`, all three web-startable — could never be manifest-verified (an update rewrites the recorded files), so what makes them safe is WHEN the mirror is restaged: only from a tree that still matches the record, and `install.sh` may re-anchor that record only when it is itself running out of the tree or has just hard-reset it (`root_exec_may_anchor`). Outside those two moments the record is brought forward but never re-written — a re-write is a second walk of a directory the clawbox account owns, after the `--verify` that authorised it has already returned. The bootstrap's repair of an unanswering manifest helper obeys the same rule: it installs `config/clawbox-root-manifest.sh` into libexec and runs it as root only where root is already executing that checkout. `install_root_libexec` installs the new dispatcher only after the mirror is staged, which is the fleet-rollout ordering — see `docs/root-exec-mirror.md` for what an old-build box does on its first update. `git` over the checkout runs as its OWNER, never root (`use_tree_owner_for_git`), because `.git/hooks` and `.git/config` are clawbox-writable and git executes both. `src/tests/unit/root-exec-mirror.test.ts` fails if a step joins the exempt family without going through the mirror. `harness_swap` (the edition swap, 2026-09-07) is on `WEB_ROOT_STEPS` — and on `DISPATCH_STEPS`, `ALLOWED_STEPS` and the run-root-step allow-list — and deliberately NOT on `UI_ROOT_STEPS`, which `install/run-step` serves to the MCP bearer, nor in the self-updating family; like `set_timezone` it is VALUE-gated by a file the route writes, `data/harness-swap.env`, read by `read_configured_harness_swap` (a plain file only, `TARGET_EDITION` exactly `openclaw` or `hermes`, `REQUESTED_AT` within the hour; parsed, never sourced), and the sub-steps it re-execs with `CLAWBOX_EDITION=<target> CLAWBOX_ALLOW_EDITION_CHANGE=1` (`hermes_install`, proved runnable BEFORE `edition_lock` flips anything so an unrunnable Hermes leaves a working OpenClaw box, then `hermes_edition`; or `openclaw_install`, proved, → `edition_lock` → `gateway_setup` → `openclaw_patch` with the gateway proved listening by the installer's own `wait_for_gateway_port` — never `openclaw_config`, whose one swap-relevant write, the Telegram bot, is the carry-over's) come out of the mirror like every other dispatch. The boundary is the timezone step's: the capability belongs to the clawbox ACCOUNT — anything running as clawbox can write the file and start the unit — so the value gate is what root checks, and the worst outcome is a swap of the box's edition the owner did not ask for: loud, because the desktop reloads onto the other harness and the card names it, and reversible with the same button.
