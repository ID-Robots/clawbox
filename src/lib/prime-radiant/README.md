# Prime Radiant — `src/lib/prime-radiant/`

The server-side layer of Prime Radiant, the "living wiki": a git-backed vault
of Markdown pages with structured claims, read by OpenClaw's bundled
`memory-wiki` plugin in isolated mode and kept healthy by its own lint. Every
module here is SERVER ONLY unless it says "pure".

## Layout on disk

```
<box data dir>/prime-radiant/        (or $PRIME_RADIANT_DIR)
  vault/                              git repo, branch main, memory-wiki layout
    index.md  AGENTS.md  .gitignore       (.gitignore names memory-wiki's own files)
    golden.json                           the golden questions (golden.ts): versioned with the pages, never a page
    entities/  concepts/  syntheses/  sources/
    WIKI.md  inbox.md  reports/  _views/  _attachments/  .openclaw-wiki/   memory-wiki's, never pages
  prime-radiant.sqlite                state: claim_registry, review_items, runs, costs, ingest_jobs, ingest_files,
                                      claim_embeddings, judged_pairs,
                                      deferred_claims, pass_state, stale_claims, golden_scores, golden_results
  settings.json                       ingest (exclude, parallel, nightly folders), cost-rate overrides, nightly
                                      schedule, Opus tier, contradiction pass, search index limit, domains, golden
                                      check, daily questions (absent = defaults)
  dream-worktree/                     the nightly pass's checkout of its dream/YYYY-MM-DD branch (only while it runs)
  uploads/<batch>/                    dropped documents waiting for their ingest (removed when it ends, 24 h TTL)
  dead-letter/<job>/                  dropped documents that still failed, kept for a retry (30 days)
  tmp/<job>/                          a job's private extraction scratch (removed when it ends)
```

## Modules

| Module | What it is for |
| --- | --- |
| `paths.ts` | `primeRadiantRoot()`, `vaultDir()`, `stateDbPath()` (read at call time); `safePagePath(input)` rebuilds a caller's page path or answers null; `isKnowledgePage(rel)` tells pages from bookkeeping (`index.md`, `reports/`, `.openclaw-wiki/`, …) and from memory-wiki's files (`isPluginOwnedPath`). |
| `schema.ts` (pure) | The page contract: `PageFrontmatter` (optional `version_of`: the page this one is a version of; optional `as_of`: the day a metric page's figures were true on — a value that is no date counts as none, never an error), `Claim` (optional `valid_from` / `valid_until` / `as_of`, ISO dates or datetimes, the period running forwards, and `historical`), the enums, `validateFrontmatter(raw)`, `hasVerification(fm)`, `folderForType(type)`. Unknown keys are kept. |
| `frontmatter.ts` (pure) | `parsePage(text)` → `{ ok, frontmatter, body }` or `{ ok: false, errors }`; `serializePage(fm, body)` is deterministic (an unchanged page re-serialises to the same bytes); `pageSummary(body)` (HTML comments — a managed block's marker, a note across several lines — are scanned out first and are never the summary; an unclosed `<!--` stays text). The body comes back without memory-wiki's managed blocks (`stripManagedBlocks`). YAML via js-yaml's CORE schema (no implicit dates). |
| `claims.ts` (pure) | The global claim-id namespace `<domain>/<entity>/<fact>`: `isClaimId`, `makeClaimId`, `slugify` (lowercase kebab ASCII, also every page path: Cyrillic transliterated first by `transliterateCyrillic` — Bulgarian's official system, щ `sht`, ъ `a`, ь `y`, ю `yu`, я `ya`, a word-final `-ия` `ia`, plus the Russian, Ukrainian, Belarusian, Serbian and Macedonian letters Bulgarian lacks —, accents folded, the rest dropped, `x` when nothing is left), `buildClaimIndex(pages, ledgerRetired)`, `claimCollisions`, `retiredReuse`, `assertClaimIdAvailable` (throws `ClaimIdError` `invalid`/`taken`/`retired`), `allocateClaimId`, `retireClaimsOnPage`. A retired id is never reused. |
| `redact.ts` (pure) | `redactText(text, { maskEmails, maskPhones })`, `redactPath(path, { homeDir })`, `scanSecrets(text)`. Deterministic `[REDACTED:<KIND>]` placeholders; an IBAN is found by its country's registered length (`IBAN_LENGTHS`) and replaced whole, spaced or not, glued to the word before (`IBAN…`) or after, valid by mod-97 or of exactly its country's shape; card Luhn validation, never the digits of an IBAN-shaped word; Unix timestamps are never cards. Apply to text AND paths before any network call. |
| `links.ts` (pure) | `extractLinks(body)` (wikilinks and relative Markdown links, code ignored), `createLinkResolver(pages)`, `buildLinkGraph(pages, indexBody)` → inbound/outbound/indexed; `isContentPage(rel)` (concepts/, entities/, syntheses/) and `contentReach(graph)` → `orphans` (content pages no OTHER content page links to — index.md lists every page, so a listing there, or a link from `_views/`, a report or a source page, does not count) and `isolated` (no content link in or out either), one pass over the links; the connect stats, the lint `orphan` rule and the Map's `inbound` all use it; a page's former path (a path-shaped alias, `isPathAlias` / `pathAliases`: rename.ts keeps a renamed page's old path in its `aliases`) resolves to it, after a page actually at that path, and its former file name does too, after every current path, name and title; `linkDensity(graph)` (meaningful links per page: for each content page the other content pages linked either way, once — median, mean, `atTarget` against `LINKS_PER_PAGE_TARGET` 5; what Status shows), `rewriteLinks(body, retarget)` (each link with its parts — `#heading`, `\|alias`, `#fragment`, `"title"` — handed to `retarget`, code left alone; a page merge re-points links with it) and `relativeHref(fromPage, toPage)`. |
| `lexical.ts` (pure) | `buildLexicalIndex(docs)` → `neighbours(path, k, minSimilarity, skip?)` and `hasText(path)`: TF-IDF cosine over a page's own words (title, claims, summary) through an inverted index in typed arrays — only pages sharing a word are scored, a word on more than `maxDocumentFrequency(pages)` pages (50…400) is left out, a page asks with its `LEXICAL_QUERY_TERMS` (48) heaviest words — so a vault of 20k pages costs a few MB and no n² matrix. `lexicalTokens` (Latin and Cyrillic words, lowercased; stopwords, bare numbers and words under 3 letters dropped); same-domain neighbours ranked ×`SAME_DOMAIN_BOOST` (1.25), ties by path. |
| `connect.ts` | The connect pass (`planConnections` pure, `runConnectPass` writes it in commits of 400): entity links (and entity pages for names that recur), similar pages by embedding (the vault index's page vectors) — by words (`lexical.ts`, cosine ≥ `LEXICAL_MIN_SIMILARITY` 0.2) for a page the index holds no vector for —, shared rare entities, dated hubs over one-per-thing leaves; then REACHABILITY: a content page linking to no other content page gets its nearest pages by words (the best one down to `LEXICAL_FLOOR` 0.05 when none clears the bar), and one no other content page links to joins its nearest page's "Similar pages" (by vector, then words; at most `MAX_INBOUND_ADDS` 3 a page, only while that page's block still fits its budget with everything it held). One managed block a page, replaced whole; a verified page is never rewritten. Stats: `orphansAfter`, `isolatedAfter`, `pagesLexical`, `unlinkable` (pages whose words tie them to nothing, left as they are). A leaf the structure pass filed (`record.hub`) is its record hub's: never rolled into a connect hub, never "similar" to its hub's other leaves; the structure pass's own pages are not re-linked. |
| `records.ts` (pure) | Record leaves — a page per invoice, credit note, receipt, bank transfer, shipment (waybill), customs declaration or ad platform receipt (`RECORD_TYPES`): `classifyRecord(path, fm, { ownCompany, assign })` → `{ type, month, day, counterparty, amount, ref, via, by }` or null. Order: a `record` frontmatter a person or the model set (`record.by` other than `rules`), the TITLE's document words (English and Bulgarian, most specific first: credit note before invoice, ad receipt before receipt, customs before shipment; never a page ABOUT such documents, `identifiers.ts` `topicTitle`), then the CLAIMS (the kind most facts name beside a reference). A month is required (title day/month, a `date` field, a claim's `as_of`/`valid_from`, the first date in a fact). Amount: a "total"/"amount due"/"общо" claim, else the one amount the facts agree on (`amountsIn`, `parseAmountNumber`: either decimal style); counterparty: a company with a legal suffix (`companyNames`, document words and codes before it dropped), never the owner's company. `recordHubKey` (`<type>/<month>`, what pairing.ts reads), `totalsByCurrency` (in cents), `formatAmount`. |
| `structure.ts` | The structure pass (`planStructure` pure, `runStructurePass` writes it in commits of 400, new pages and their index.md lines first; `dryRun` answers `would`). 1. MONTHLY RECORD HUBS: one `synthesis` page per record type × month with at least two leaves — summary, totals per currency, by counterparty, a table of the leaves (date, Markdown link, counterparty, amount), previous/next month and the domain hub; a month over `HUB_PART_LEAVES` (40) gives each counterparty with `COUNTERPARTY_HUB_MIN` (5) leaves a hub of its own under it, and a list too long for `HUB_TABLE_BUDGET` is cut into parts; a connect hub of the same title is taken over. Each leaf gets `record: { type, month, hub, by }` and a block linking its hub, its counterparty's entity page, its neighbours in the hub and its counterparty's previous and next record (any type, any month). 2. DOMAIN HUBS: one per configured domain with pages (none configured: the domains with three pages or more) — what it covers, key facts (owner-verified first, never a leaf's or the pass's own), open review items, top entities, record hubs. 3. THE ROOT: one page for the owner's company (settings `structure.company`, else "Company overview") linking every domain hub, the latest hub per record type, the register and the top entities. 4. ENRICHMENT: the top `enrichTop` (25) entities by inbound links (counted without the pass's own pages and blocks, so a re-run plans the same) get up to `ENRICH_MAX_CLAIMS` (5) claims `origin: structure` — role, who they appear with, totals (`as_of` the last record), first and last seen — under lint's claim cap, never a retired or taken id, never on a verified page. 5. THE DECISIONS REGISTER: `decision` pages and claims of type decision (date, decider, source), newest first; past `REGISTER_ROWS` older years go to pages of their own. Managed blocks `<!-- prime-radiant:hub:start/end -->` (a page of its own) and `<!-- prime-radiant:record:start/end -->` (a leaf), replaced whole; text outside them is kept byte for byte (a marker a person left without its partner is dropped first, the text around it kept, so the next rewrite never runs from it into their text); an unchanged vault plans no write; a verified page is never rewritten (`skippedVerified`). Pages are found again by their `structure` frontmatter (`kind`, `type`, `month`, `counterparty`, `part`, `domain`, `year`), whatever their path. Stats include `linksMedianBefore/After` (links.ts `linkDensity`). Measured on a 10,000-page synthetic vault: the plan 0.6–0.7 s; on disk the first night writes 8,770 pages in 22 commits in 32–44 s, the second writes nothing in 1.7 s; median meaningful links per page 1 → 5 (`prime-radiant-structure-bench.test.ts`). |
| `structure-run.ts` | The pass on a vault: the open review items, the retired-id ledger and the settings around `runStructurePass` (`runStructure`), and the capped cheap-model fallback (`classifyWithModel`): record-like dated pages the rules could not type (`modelCandidates`: identifiers.ts `recordPage`, a date, no type) — at most `structure.modelFallback` (25) a run, one Flash call, titles and facts redacted, recorded with `recordCost` (`structure-classify`); a type becomes `record.by: model` on the leaf, "none" is remembered in `pass_state` until the page changes (`changeKey`: the path and a SHA-256 digest of the page's own title and facts, kept on the box); offline or a dry run never asks. |
| `node-summary.ts` | The summaries pass's pure plan (`planSummaries`): every node's 1–3 sentence `summary` (frontmatter) written from its NEIGHBOURHOOD — its own claims (the structure pass's enrichment among them), the lead line of its text (never the connect stub), its neighbours' claims that name it, the owner-verified claims of linked entities, the hubs that list it, the pages linked with it (entities first) and the sources it shares with them; owner-verified first; a neighbour of a stricter privacy tier lends nothing. The facts' digest is the neighbourhood hash: unchanged, the page is skipped. `checkSentences` is the check step: a sentence stands only when it cites facts of the node and every number, name and content word in it is in them (markup and redaction placeholders refused); verified-citing sentences first, 3 at most, 400 characters. `factsSummary` composes one from the facts' own words. Order: entities → hubs → concepts, the most linked first; record leaves, verified pages, `secret-ref` pages, a person's `summary` and a duplicate's page (its canonical one has it) are skipped. |
| `node-summary-run.ts` | The summaries pass on a vault (`runSummaries`, nightly step 4c and the `summaries` maintenance action): the cheap model writes the first `summaries.maxPages` (150) of the plan, 8 a call, facts redacted; each call's worst case is checked against what is left of `summaries.capUsd` (0.25) BEFORE it is made, recorded with `recordCost` (`node-summaries`). The rest get the facts' summary; a model summary whose neighbourhood changed waits for the model; a page whose every model sentence was rejected is marked `tried` and not asked again until its neighbourhood changes. Duplicate entities come back as `mergeSuggestions` (edit.ts `previewMerge`, the merge tool's dry run), wrong domains as `domainMismatches`. A dry run asks nothing and writes nothing (`would`). A page edited since the plan is left as the person left it. |
| `summary-meta.ts` | What a page's `summary_meta` says (`by: summaries`, `method: model / facts`, the neighbourhood `hash`, a `digest` of the text — a different text is a person's edit, theirs from then on —, `at`, `from`: per sentence the claim ids / page paths / sources it came from, `tried`), `generatedSummary(fm)` for the page header and the page list, and the summary call's marker (`NODES (JSON):`) the stub model answers. |
| `entity-hygiene.ts` | Pure. `findDuplicateEntities`: entity pages for one name — a `-2` copy, a Latin/Cyrillic pair, a punctuation variant — by a transliteration-tolerant `nameSkeleton`; the canonical page is a verified one, else one without a `-N` suffix, else the most linked. `suggestDomain` / `domainMismatches`: the domain a role the entity is the SUBJECT of names ("… is the COO" → an operations domain, when that domain exists), else a clear majority (60 %, of 5 or more) of its linked pages. Both feed lint (`duplicate-entity`, `domain-mismatch`, warnings) and the summaries pass. |
| `graph.ts` | The Map's graph: `getVaultGraph()` → `{ revision, truncated, nodes: [{ id, title, domain, degree, links, inbound, sources }], edges: [[a, b, w]] }` (`inbound`: content pages linking to the node; 0 on a content page is an orphan, which the MCP Map lists as unconnected) with numeric indexes. Edges are links either way (w 1, via `buildLinkGraph`) and shared sources (w 0.5): a source's pages are tied in a ring to their next `SOURCE_RING` (2) pages — five or fewer are all tied — and no page takes more than `MAX_SOURCE_EDGES` (6), so a big source never makes a clique; a linked pair keeps its link. O(pages + links + source mentions). Kept per `vaultRevision()` (HEAD, plus size and time of any uncommitted change), one build shared by concurrent requests; `buildVaultGraph(pages, revision)` is the pure core. |
| `graph-layout.ts` (pure) | The Map's force layout, run in a Web Worker: `seedPositions` (each domain around its own point on a Fibonacci sphere), a flat-array Barnes-Hut `Octree` (θ 1.2, O(n log n) a tick), `createLayout` / `tick` / `isSettled` (d3-force's link, many-body and centring forces, cooling alpha; 2D for the flat fallback), `writePositions` into a reused `Float32Array`. Nothing allocated per tick. |
| `graph-communities.ts` (pure) | `louvain(n, ends, weights)` (deterministic, communities numbered largest first, a lone page its own), `modularity`, and `graphInsights` → orphans (no link in or out; a shared source is not a link), hubs (by degree) and bridges (pages whose links reach the most other communities). |
| `lint.ts` (pure over a snapshot) | `lintVault(snapshot, { scope, ledgerRetired, staleClaims, domains, now })` → `LintReport`. Over-cap findings carry a `split` (`suggestSplit`: by headings, else by paragraphs; the page stays the hub). Four rules have `blocksCommit`. |

| `ingest-upload.ts` | Dropped files: `stageUpload` (batch id and file name rebuilt from their alphabets — a name keeps letters of any script, NFC, at most 200 bytes —, written `wx`, metered, 9 MiB a file because the middleware keeps only the first 10 MiB of a body, a body shorter than its declared length refused), `stagedBatch`, `pruneStaleBatches`. A dropped file's label (its page's source, what the model sees) is the name it was dropped under, redacted like a path, numbered `notes (2).md` when an earlier document already goes by it — never the staging path. |
| `shard-index.ts` | The vault as a built-in Memory Shard source, on Shard's engine (its chunker, embedding client, embedder choice and memory budget): `<root>/shard-index.sqlite`, built from `main` (`ls-tree` + blobs, the blob id as the change key — a `dream/` branch never reaches search). `pageIndexUnits` (pure: body chunks led by the title + one unit per claim, redacted before embedding), `rankVaultHits` (pure: one hit per page/claim, `VERIFIED_BOOST` added to a verified one, the score clamped to `MAX_SCORE` (1) so it merges fairly with the owner's documents while the order keeps the unclamped lift), `vaultIndexingAllowed()` (Memory Shard switched on AND the vault initialised — every run checks it and does nothing otherwise; switching Memory Shard on starts a whole-vault catch-up run), **`reindexPrimeRadiantPaths(paths)`** (the incremental hook: re-embeds the named pages whose blob moved, drops the ones `main` lost; runs serialised per vault and coalesced), `reindexPrimeRadiantVault()` (whole tree), `scheduleReindexAfterCommit` (what `vaultOperation` calls after a commit on `main`, fire and forget), `searchPrimeRadiant(q, limit)` → hits `{ source, path, id, kind, type, title, snippet, score, similarity, verified }`, `vaultIndexStatus()` (with `withoutPageVector`: pages on `main` the last run left without a page vector; `usedBytes`, `limitBytes`, `maxChunks`, `cappedPages`, `migrationPending` — the status route shows them in MB as `index`). 8-BIT VECTORS (`vector-q8.ts`): int8 codes + one float32 scale a vector (1,029 bytes at 1,024-d), on disk and in the search cache; a float32 store from an earlier build is converted in place by the next run (`migrateVaultVectors`: batches, no re-embedding, same identity; a row's format is its blob length, so it resumes after a crash) and read as it is until then. The chunk budget is the owner's `search.indexLimitMb` over those real bytes (160 MB ≈ 163k chunks); `vaultIndexLimitChanged()` clears the `capped` marks and queues a whole-tree run that fills to a raised limit or trims to a lowered one. PAGE VECTORS FIRST: when the chunk budget (`vaultMaxChunks`) is full, `planVaultChunks` (pure) gives every page its page chunks, then shares what is left between claims up to one level (the pages with most claims give theirs up first; a verified claim is kept longest) — a run drops claim chunks over a page's share to make room for a new page's vector, and a whole-tree run gives them back once there is room (an incremental run never reads a page it was not given, so there such a page asks for no more claims than it holds); the plan places, and the run re-embeds, the pages that end up no bigger first and the ones that grow after them, so room a shrinking page frees is there in the same run; `capped` (no room even for page chunks; a limit lowered below the page chunks of the pages kept caps the biggest of them first) is what still asks for a whole-tree scan, `partial` counts pages holding fewer claims than they have. An embedder change rebuilds the store whole; a run the embedder refused marks it for a whole-tree scan next time. RECORD LEAVES: a page row carries its `hub` (the leaf's `record.hub`; the column is added in place to an older store, no rebuild), a leaf's link block is not embedded, and a leaf never outranks its hub — `rankVaultHits` puts it just under the hub (score no higher) and `searchPrimeRadiant` brings in the hub's best page chunk when a leaf was found without it. |

## Routes (`src/app/setup-api/prime-radiant/`)

Every route needs a session through `requireSession`; who may call it is listed per endpoint below (owner-only unless it says otherwise — `POST review` also takes the MCP bearer). All are `force-dynamic`, `Cache-Control: no-store`, failures as `{ error, code }`. The GETs NEVER create the vault (no folder, no repository, no state database, no config write); the app calls `POST init` when status says `initialised: false`. There is no boot hook.

- `POST init` — `ensureVault()` + `ensureMemoryWikiWiring()` + `repairPluginWritesOnce()`, idempotent: `{ created, plugin: { state, …, wrote }, repair: { ran, cleaned, removed, commit } | null }`. The app also sends it, in the background, when an initialised vault's wiring still `needs-write` (keys a newer ClawBox added). Owner cookie AND same origin (the MCP bearer gets 403 `owner_only`, a cross-site page 403 `cross_origin`), because it writes openclaw.json. 500 `vault_unavailable` when the vault cannot be made, `wiring_failed` when the vault is made and the config write failed.
- `GET status` — `initialised`, the vault's counts, git head, memory-wiki wiring state (reported, never written), lint summary, `links` (median meaningful links per content page against the target of 5; the app shows it beside the counts), the search index (`index`) and the golden questions' accuracy (`golden`: `goldenStatus`, null when it cannot be read). Not initialised → zero counts, `git: { branch: null, head: null, commits: 0 }`, a clean lint.
- `GET pages?type&domain&status&verified&q&offset&limit` — page list, no bodies (`{ total: 0, pages: [] }` with no vault).
- `GET graph` — the Map's graph (see `graph.ts`), kept per vault revision. No vault → `{ revision: null, truncated: false, nodes: [], edges: [] }`, nothing created.
- `GET pages/<path>` — one page: frontmatter or its errors, body, summary, backlinks, links, scoped lint. Not a page, or no vault → 404.
- `PATCH pages/<path>` `{ title?, summary?, body?, status?, domain?, owner?, privacy?, stale_after?, as_of?, sources? }` — `editPage` (edit.ts): `{ path, commit, changed, findings }`, ONE commit `edit: <path>` (none when nothing differed). The page is read alone; a change of metadata only (`status`, `domain`, `owner`, `privacy`, `stale_after`, `sources`) is linted with `lint: "pages"` and not re-embedded in Memory Shard's index (what it embeds is the title, body and claims). A page a person verified is refused to the assistant (409 `verified`); 404 `not_found`, 409 `invalid_page` / `lint_blocked`. The owner, or the assistant through the MCP bearer (`writerGuard`). `DELETE pages/<path>` removes the page and its index line, one commit `delete: <path>`.
- `POST pages/bulk` `{ edits: [1..500 of { path, domain?, owner?, privacy?, status? }], dry_run? }` — `bulkEditPages` (edit.ts): metadata on many pages as ONE commit `bulk: N pages` that Undo reverses whole → `{ changed, unchanged, refused: [{ path, code, error }], commit, dryRun }`. Each page is read alone under the lock and only its frontmatter is rewritten (the body stays byte for byte); a page its own PATCH would refuse is listed in `refused` with that code (`not_found`, `invalid` — a bad value, an unknown field, a page named twice —, `invalid_page`, `verified` for the assistant, `lint_blocked` when its new frontmatter breaks a blocking rule) and the others still change. Linted with `lint: "pages"`, never re-embedded. `dry_run: true` answers the same, commits nothing — except that, like a merge's, it runs no vault-wide lint: a page index.md does not list whose claim id another page already carries passes the dry run and is refused `lint_blocked` by the real one. 400 `invalid` for the request's own shape (no edits, more than 500, an unknown field), 413 past 512 KB, 412 `not_initialised`. The same writers as PATCH; the `[...path]` route's POST like the merge, so no `bulk/` folder shadows a page at `bulk.md`.
- `POST pages/merge` `{ into, from: [1..20], dry_run?, keep_into_body? }` — `mergePages` (edit.ts): the `from` pages folded into `into` as ONE commit `merge: <from, …> -> <into>` that Undo reverses whole. Claims move with their ids, text and verification untouched (a verified one that cannot move intact refuses the merge, 409 `verified`, naming it; over `LIMITS.maxClaims` 409 `too_many_claims`; a retired id 409 `retired`); `sources` and `retiredClaimIds` are unioned, the titles and aliases become `into`'s `aliases`, its privacy rises to the strictest; `into`'s body stays byte for byte (`keep_into_body`, default true — a link there to a `from` page refuses the merge, 409 `into_links`), and with `keep_into_body: false` a summary it lacks closes its body as a "Merged from" line (never a deprecated page's) and its links to a `from` page become plain text; every other `[[link]]` (`|alias`, `#heading`) and Markdown link to a `from` page, index.md's too, leads to `into`; merging FROM a deprecated page is fine; the `from` pages and their index lines go; the claim registry and the waiting review items about a moved claim follow it (none is resolved). `dry_run: true` answers the same, commits nothing. Into a deprecated page 409 `deprecated`; into itself 400. The owner, or the assistant through the MCP bearer (`writerGuard`); it is the `[...path]` route's POST, so no `merge/` folder shadows a page at `merge.md`.
- `GET lint?path=…&paths=a,b` — lint report for those pages, or the whole vault (an empty report with no vault).
- `POST ingest` `{ folders: string[] }` (1–20, the folder picker's rule — `resolveFolderInsideBrowseRoot`, shared with Memory Shard) or `{ upload: <batch> }` → 202 `{ job }`. Owner cookie AND same origin. 409 `busy` (`runningId`), 412 `no_credential`, 404 `folder_not_found` / `unknown_batch` (with `index`), 400 `folder_refused` (ClawBox's own output) / `invalid`.
- `GET ingest` → `{ running, jobs }` (recent, newest first; nothing created on a fresh box).
- `GET ingest/<id>` → `{ job, deadLetter: [{ seq, label, error, attempts, bytes }] }`; 404 `not_found`. Never creates anything.
- `DELETE ingest/<id>` — stop: 202 `{ stopping: true, job }`, 409 `not_running`, 404. Owner cookie AND same origin.
- `POST ingest/preview` `{ folders: string[] }` → `{ preview: { documents, skips, topFolders, codeProjects, truncated, limit, notes } }`: what `POST ingest` would read, by the same folder rule and settings. Owner cookie AND same origin. 400 `invalid` / `folder_refused`, 404 `folder_not_found` (with `index`).
- `POST ingest/<id>/retry` — a job over that job's dead letters → 202 `{ job }` (`kind: "retry"`, `retryOf`). 409 `nothing_to_retry` / `busy`, 412 `no_credential`, 404. Owner cookie AND same origin.
- `GET ingest/<id>/events` — SSE: `job` (tallies), `file` (`{ seq, label, status, pages?, reason? }`), `end` (final job, then the stream closes). A finished job answers `job` + `end` at once; a 15 s comment keeps proxies open; 404 for an unknown id.
- `POST ingest/upload?name=<file>[&batch=<id>]` — one dropped document as the raw body → `{ batch, name, bytes }`. Owner cookie AND same origin. 400 `invalid_name` / `empty`, 404 `unknown_batch`, 409 `batch_full`, 413 `too_large`, 507 `disk_full`.
- `GET search?q=…&limit=…` — the vault through Memory Shard's engine: `{ initialised, indexing, index, results }`, hits as `searchPrimeRadiant` answers them. No vault → `initialised: false`, nothing created. A vault with no index (or one built for another embedder, or an unfinished run) queues a whole-vault run in the background; while there is no usable index it answers `indexing: true` with no results. 503 `search_failed` when the query cannot be embedded.

Memory Shard's own search (`GET /setup-api/clawkeep/memory/search`, the edition with no OpenClaw) merges these hits with the owner's documents by score; on OpenClaw the memory-wiki plugin is what the agent searches the vault through.

- `GET review?status=open|later|resolved|all&kind&claimId&offset&limit` → `{ total, counts, items }`. `POST review` `{ kind?, claimId?, pages?, candidates?, note? }` → 201 `{ item }` (200 `created: false` when the same question waits): the owner OR the MCP bearer (the assistant may flag a fact), same origin, 412 `not_initialised`.
- `POST review/<id>/resolve` `{ action: "pick", candidate } | { action: "new", text, page? } | { action: "later" } | { action: "dismiss" }` → `{ item, commit, retired }`. Owner cookie AND same origin (a verification is a person's word). 404, 409 `already_resolved` / `no_claim` / `verify_failed` / `lint_blocked`, 400 `invalid`.
- `GET golden` → `{ questions, skipped, verdicts, score }` (`skipped`: entries of `golden.json` that cannot be read; each question's latest verdict by id; `score` as `goldenStatus`). `POST golden` `{ question, expected, domain, owner?, claimId?, page? }` → 201 `{ question, commit }`; `PATCH golden/<id>` (`null` clears owner, claimId or page) and `DELETE golden/<id>` → `{ question, commit }`. The owner, or the assistant through the MCP bearer (`writerGuard`). 400 `invalid`, 404 `not_found`, 409 `too_many` / `unreadable` / `lint_blocked`, 412 `not_initialised`. The GET never creates anything.
- `GET daily?owner=` → `readDailyQuestions` (without `owner`: who has questions waiting). Read-only, never creates anything; 400 `invalid` for an owner name over 80 characters.
- `GET history/<page>?limit` → `{ path, commits }`; `GET diff?commit=<sha>[&from=<sha>][&path=<page>]` → `{ from, to, path, commit, files, diff, truncated }`.
- `POST revert` `{ commit, path? }` → `{ reverted, commit, changed }`. Owner cookie AND same origin. 409 `conflict` / `lint_blocked` (with `findings`) / `nothing_to_revert` / `dirty`; 500 `commit_failed` with what git said, and whether putting the vault back worked.
- `GET settings` → `{ settings, defaults, limits, nightly: { nextRunAt }, rates, opusSource }` (`opusSource`: `api_key`, `subscription` or `none` — `detectOpusSource`, bounded to 3 s and `none` past it; `limits.opusMaxPages`); `PUT settings` (a patch; folders by the folder picker's rule; re-arms the timer). Owner cookie AND same origin; the assistant through the MCP bearer too, except the cost rates, the Opus model and `verification.outbound` (403 `owner_only`).
- `GET costs?since&runId` → the cost summary (estimates; the app shows only its token counts), with `notMeasured: [{ operation: "embedding", reason: "no_usage_reported" }]`: the contradiction pass's claim embeddings cost something the embedder does not report, so they are in no total.
- `POST maintenance` `{ action, dryRun? }` (owner; the assistant only `connect`): `rejudge-reviews`, `version-groups`, `reindex`, `connect`, `migrate-frontmatter`, `structure` (the structure pass; a dry run answers `would` at once and never asks the model, a real run 202 in the background), `summaries` (the summaries pass, likewise; its answer carries `mergeSuggestions` and `domainMismatches`; the assistant may run its dry run) and `classify-records` (read only: leaves by type and month, the pages the model fallback would be asked). `GET maintenance` → `{ running, last }`.
- `GET nightly` → `{ running, nextRunAt, runs }`. `POST nightly/run` → 202 `{ run }` (409 `busy`, 412 `not_initialised`); `{ merge: "dream/…" }` merges a held night (409 `open_items` / `not_merged`). Owner cookie AND same origin.

## The app

`src/components/PrimeRadiantApp.tsx` (and its `PrimeRadiant*.tsx` tabs) is the desktop face of these routes; it is the one caller of `POST init`, once, when `GET status` says `initialised: false`. Its strings are `primeRadiant.*` in `src/lib/prime-radiant-translations.ts`. A refusal's `code` is what the app words in the owner's language (`primeRadiant.error.<camelCode>`), so a new code a screen should explain needs a key there too; the English `error` stays the floor.

Six tabs (`TABS` in `prime-radiant-ui.ts`; the ids are stable, the words changed): **Map** (`map`, below), **Pages** (`browse`: the list with one search field — typing filters by title or path, Enter or "Search inside pages" runs `GET search` and shows the hits above the list — and each page with its History, opened from the page with Back to it), **Review** (`review`: the open questions, then the Checks), **Questions** (`questions`, `PrimeRadiantQuestions.tsx`: the golden questions' accuracy — % correct, its change and a trend line, also beside the counts in the header — the golden questions with their last verdicts, added, edited and deleted in place, and one owner's daily questions in their language with the language picker and the owner's switch for the assistant sending them, off by default; then Question settings: the nightly golden check on or off, its nightly cap, and the daily questions an owner gets), **Add** (`ingest`) and **Settings** (`settings`, ending with Model usage). The app shows **no money**: `GET costs` and the runs' estimates stay on the server for the record, and the screens show tokens only (`formatTokens`, `useTokensByRun` in `PrimeRadiantUsage.tsx` — per import, per night including the import it ran, and in all). The Opus tier's per-night cap is a dollar figure on the wire, so Settings does not offer it; a save sends back the box's own value.

### The Map (start page)

A vault with pages opens on **Map** (`src/components/PrimeRadiantMap.tsx`, loaded lazily); an empty one opens on Pages and its call to add documents. The Map fetches `GET graph` and draws it with the modules in `src/components/prime-radiant-map/` — no graph or 3D library:

- `layout-engine.ts` runs `graph-layout.ts` + `graph-communities.ts` behind a message protocol: the seed positions first (the map draws at once), then the communities and Insights, then positions as it cools, each into one of two `Float32Array`s the page hands back (transferred, never copied, never flooded). `layout.worker.ts` wires it to a Web Worker; `layout-port.ts` falls back to the same engine on the page, in slices, where a worker cannot start.
- `renderer-gl.ts` is raw WebGL2: one instanced draw for every node (round, shaded, sized by degree, coloured by domain or community, with a state byte for hidden / dimmed / matched / selected / hovered) and one `GL_LINES` draw for every edge, both reading the same position buffer. `renderer-2d.ts` is the still 2D canvas used without WebGL2 or under `prefers-reduced-motion`.
- `view.ts` owns the camera (orbit, wheel and pinch zoom, right-drag or two-finger pan, a slow turn until touched), a render loop that only runs while something moves and never while the page is hidden, `devicePixelRatio` capped at 2, and picking through a screen-cell grid rebuilt once per view change (never a walk over every node per pointer move).
- The component adds the search (matches lit, the camera flies to them; Enter steps through them), the domain legend with toggles, labels for the top 20 hubs and the selected page, the hover tooltip, the Insights strip, and a screen-reader list of the 300 most connected pages. Double-click (or Enter) opens a page in Pages, whose Back returns to the Map with the page still picked out. Colours lead with ClawBox orange and a soft grey (then sky, amber, teal, rose, lime, violet…); edges are a neutral grey that fades as they multiply. A reopened Map on the same revision draws where it was left without laying out again.

Measured on a laptop CPU (`graph-layout.ts`, θ 1.2): 5,000 nodes / 20,000 edges ≈ 10 ms a tick, settled in about 3 s; 20,000 / 80,000 ≈ 60 ms a tick. The page's frame rate does not depend on it — the layout is off its thread.

## Building on it

- The ingest writer adds pages with `vaultOperation("ingest: <what>", async (tx) => { … tx.writePage(path, fm, body) … })`, allocating ids with `allocateClaimId` against `buildClaimIndex` of a snapshot read under the lock, after `redactText`/`redactPath` on everything sent to a model. Later passes calling the model go through `flashClient()` + `completeWithRetry` and record every call with `recordCost`.
- Settle a fact through `verifyClaim` (or `resolveReviewItem`), never by editing a claim's text in place.
- Anything that moves `main` calls `notifyVaultChanged(changed)` afterwards.
- A model call outside the ingest goes through `flashClient()` / `resolveOpusClient()` and records itself with `recordCost` under its run id.
