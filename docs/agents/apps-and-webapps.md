# Apps, web apps and the Code Assistant

The app store and installed apps, the web apps the agent builds (iframe sandbox, KV bridge, legacy storage), `/apps/<id>/` server apps, `clawbox.json`, and publishing ClawBox apps to the ClawBox Store and installing them from it. Read it when you touch `apps/*`, `webapps/*`, `code/*`, `app-proxy.ts`, `webapp-*.ts`, `code-projects.ts`, `store-*.ts`, `tar-gz.ts` or `AppStore.tsx`.

## Setup API Routes (`src/app/setup-api/`)

- **Apps**: `apps/store`, `apps/install`, `apps/uninstall`, `apps/icon/[appId]`, `apps/settings`, `apps/skill-info` — app store integration. ClawHub namespaces skills as `@owner/slug` and `openclaw skills install` refuses a bare slug more than one publisher uses, so `install` resolves the publisher first (`src/lib/clawhub-url.ts` — GET clawhub.ai/api/v1/skills/<slug>): one owner installs; an ambiguous slug is settled only by the store listing's own `developer`, otherwise the route answers 409 `{ code: "ambiguous", matches: [{ ownerHandle, ref, url }] }` and the caller re-posts `{ appId, owner }` or `{ appId: "@owner/slug" }`; a slug ClawHub lacks is 404 `not_found`. Every install failure is a non-2xx with `ok: false`, an honest `code` and `retryable` (the CLI's trust gate is left alone — no `--acknowledge-clawhub-risk` — so a `review_required` release tells the owner to install it from the Terminal). Locally everything stays keyed by the bare slug, and the icon is downloaded only after the install succeeded. `install`, `uninstall` and the webapp registry (`src/lib/webapp-registry.ts`, behind webapp deploys) are the only writers of `installed_apps`/`installed_meta`; `uninstall` also drops the window's KV keys and `app_<id>_settings` on every edition, and — only where the edition HAS OpenClaw (`openclawSkillRoot()`, null on the hermes SKU alone) — the skill directory and `skills.entries.<id>` from openclaw.json. That split is why `uninstall` is deliberately the one app route without `openclawAppsGuard()`: the MCP `app_uninstall` tool posts to it on Hermes to remove a webapp whose store the UI has hidden, so it must stay reachable there without ever resolving a delete target under a workspace that edition does not have (TASK-551). Its answer carries `skillRemoved: true | false | null` (`null` = no skill half to report on: the hermes SKU, or a web app) so a caller can tell a removal from a no-op, and it refuses the whole uninstall — 503 `ok: false`, `retryable: true` — rather than dropping the desktop entry for a skill it could not reach, because half an uninstall leaves the owner nothing to retry from: `config_unreadable` when openclaw.json exists and cannot be read (nothing is touched — that is not the same as an edition that has none), `skill_remove_failed` when the folder is there and will not go (`fs.rm` deletes as it walks, so part of it may already be gone, the message says so, and the skill-info cache is rescanned before answering); the outer catch carries the same contract (`uninstall_failed`, 500) and reports `skillRemoved`, because everything after the skill delete can still throw over a folder that is already gone; an id that is not one plain path segment is 400 `invalid_app_id`, `retryable: false`, before anything is touched. Every id that reaches a path on these routes is REBUILT from the alphabet rather than tested and passed through (`safeAppId` in `src/lib/webapp-icon.ts`, `safeProjectId` behind `projectDir`/`webappPath` in `src/lib/code-projects.ts`, `safeSkillName` in `src/lib/openclaw-skill-info.ts`) — a `.test()` guard leaves the caller's string in play, and CodeQL rightly flags every path built from it (`js/path-injection`). The 1-64 `[A-Za-z0-9_-]` bound is a rule about what may ARRIVE: `install` applies it (as `zInstalledAppId`, `skill-info`, the webapps route and the icon route already did), `uninstall` deliberately does not, so an app installed before that bound existed can still be removed. Whether the app is a WEB APP — `installed_meta.webappUrl`, else the deployed `data/webapps/<id>` this uninstall removed — decides two things and neither is whether the skill half RUNS: an unreadable OpenClaw config does not refuse a web app (it has no skill half, so on a `dual` box a config belonging to the idle harness must not strand the agent's own pages), and an id the desktop knows as a web app answers `null` rather than `false`, since "there was no skill of that name on disk" is an absence report about something that never existed. One id can be both — `webapp_create` REPLACES `installed_meta[<id>]` for any id with no collision check — so the removal itself is never skipped; and on the one path where it CANNOT run (a web app the `installed_meta` KNOWS about, removed while that config is unreadable — one recognised only by its deployed directory is still refused, since the refusal is answered before anything is looked at) the answer carries `skillHalfChecked: false` beside `ok: true`, present only when false, because `null` there would claim there was no skill half when the route simply could not look — `app_uninstall` and the desktop's own toast both relay that as "its skills were not checked". The enable switch (`settings` `_setEnabled`) is a direct JSON write of `skills.entries.<id>.enabled` (the gateway hot-reloads it; the CLI cost 10–17 s per click), and `skill-info?appId=` reads `enabled` back from the same file — its list comes from `openclaw skills list --json` served stale-while-revalidate (`src/lib/openclaw-skill-info.ts`; the routes rescan behind an install/uninstall), answering 404 `not_installed` for a skill that is gone and 503 `skills_unavailable` when the CLI failed with nothing cached. `store?slug=` adds `ownerHandle` (and `clawhubMatches`) from ClawHub and rewrites `clawhubUrl` to the real page, or removes it. `icon/[appId]` persists to `data/icons/` only for installed apps and remembers an upstream 404 for an hour.
- **Code**: `code/` — code project management (init, file ops, search, build/deploy) — `search` is substring only: a body with `regex` is answered 400 `regex_unsupported` rather than compiled, because a caller-supplied pattern ran on the request thread with cost exponential in the LINE (`(a+)+$` over 26 characters was 10 s on the Orin), nothing on the device sent it, and the OpenClaw agent's `grep` tool is a killable child with a deadline.
- **Other**: `vnc/`, `webapps/`, `mascot-lines/`. `webapps?app=<id>` also answers for the host:port redirect STUBS written before `/apps/<id>/` existed: a stub whose project declares a `port` in its clawbox.json is migrated through `registerServerApp` (listener check included) so its icon opens a path rather than a host, and one whose port is silent is answered with the box's own sentence — the same `listenerRefusal` the proxy speaks — instead of the browser's blank ERR_CONNECTION_REFUSED page. A stub whose port still answers is served untouched: it works on the LAN today, and taking it away would be the regression.

## ClawBox Store: publishing and installing ClawBox apps

A ClawBox app is a Coding Agent project with a `clawbox.json` at its root (see `clawbox-manifest.ts` below). The ClawBox Store lists two kinds of entry: ClawHub skills (installed through the OpenClaw CLI, unchanged) and ClawBox apps another box published, which the portal lists with `source: "clawbox"` under the category `clawbox-apps` ("ClawBox Apps") together with `kind`, `version`, `packageUrl`, `sha256`, `size` and `iconUrl`. The portal decides who may publish: until the Developer plan opens it answers 403 `coming_soon` for everyone but its admins.

**Publish** (`src/lib/store-publish.ts`, `POST /setup-api/apps/publish`, the Coding Agent's **Publish to ClawBox Store**, MCP `app_publish`):

- `packProject(projectDir)` makes a gzip'd tar (`src/lib/tar-gz.ts`, written in-tree — the box needs little of tar and must refuse most of it) of the project folder. Never packed: `node_modules`, `.git`, `.next`, `dist`, `build` and `.clawbox` at any depth, `.env*`, `*.pem`, `*.key`, `data/secrets*`, and symlinks (never followed: one to `~/.ssh` would publish it). Files `.gitignore` ignores are left out through `git ls-files --cached --others --exclude-standard` when the folder is the root of its OWN repository; a code project sits inside ClawBox's checkout, whose `.gitignore` ignores the whole data folder, so there the root `.gitignore`'s simple patterns are applied by the walk instead (negations are not honoured — it can only leave out more). `clawbox.json` is always packed and must parse (`parseClawboxManifest`); the package is capped at 50 MB packed (10,000 files, 256 MB read).
- The slug is the manifest's `slug` (lowercase a-z, 0-9, inner dashes, ≤ 64), else derived from its `name` (`slugFromName`, accents folded), else from the folder; the dialog lets the owner change it. The version is three numbers (`1.0.0`, or the patch after the Store's own record of the slug — `GET /setup-api/apps/publish?projectId=` answers `suggestedVersion`).
- The call goes to `{portal}/api/store/publish` with the box's portal token (`resolveClawaiToken`, `Authorization: Bearer claw_…`). `{portal}` is `PORTAL_WEB`, else the origin of `CLAWBOX_AI_PROXY_URL`, else clawbox.com (`storePortalBase`). Up to 4 MB the package rides in the request (multipart `metadata` JSON + `package`); above it the box asks `/api/store/publish/upload` for a client token for `store/apps/<slug>/<version>.tgz` (`blob.generate-client-token`), uploads with `@vercel/blob/client` `put(…, { access: "private", multipart: true })` and publishes by `packageUrl`. `@vercel/blob` is a `serverExternalPackages` entry in `next.config.ts`, loaded from `node_modules` at run time: bundled, it brings undici's optional `node:sqlite` cache store, which Turbopack compiles into the throwing stub `scripts/check-bundled-builtins.sh` refuses.
- `mapPublishResponse` turns every portal answer into ONE typed outcome the route, the dialog and the MCP tool share: 201/200 `{ app, created }` → `{ ok: true, app, created, storeUrl }`; 403 `coming_soon` (with `upgradeUrl`, made absolute on the portal); 400 `invalid` with `field`; 409 `slug_taken`; 413 `package_too_large`; 503 `store_unavailable` (also `package_storage_unavailable` and a token error's 503); the token errors `{ error: { message, type, code } }` on 401/403 → `token_rejected`. Box-side codes: `not_linked` (no portal token), `not_found`, `no_manifest`, `unreachable`, `upstream`, `failed`. The route never answers 401 (the desktop reads that as "signed out"): `not_linked` and `token_rejected` are 409.
- The route is the OWNER's: their session from the box's own pages (`isSameOriginRequest`) or the MCP bearer — another ClawBox user gets 403 `owner_only`. A project is found through the Coding Agent's own listing by its folder name, so nothing else can be packed. GET answers `linked`, `canPublish` (the portal's `GET /api/store/publish`), the owner's apps in the Store, and for a project its name, slug and next version.
- UI (`src/components/StorePublishDialog.tsx`, opened from the project row's storefront button and the run page for any project with `app`): not linked → "Connect your ClawBox account first" with **Open Settings** (AI section); `canPublish: false` or a `coming_soon` answer → "Publishing is coming soon with the Developer plan", the portal's message and **Open the website** (`upgradeUrl`); otherwise the form (name from the manifest, read-only; slug; version; description; icon URL), and on success a toast plus a **View in the Store** link (a toast's action is allowlisted to Settings, so the link lives in the dialog).

**Install** (`src/lib/store-install.ts`, `POST /setup-api/apps/install { appId, source: "clawbox" }`; an install that names no source and that ClawHub does not know is retried as a ClawBox app when the Store's record says it is one):

- The record is read from the Store by the route (`{portal}/api/store/apps/<slug>`), never taken from the caller, and checked (`clawboxStoreAppFrom`). The package is downloaded server side (https anywhere, or the portal's own origin; the portal token goes to the portal origin only; 50 MB cap, streamed) and refused whole — 422 `sha256_mismatch`, nothing written — unless its SHA-256 equals the listing's, the `X-ClawBox-Package-SHA256` header (when sent) agrees and the size matches.
- It is unpacked into the owner's Coding Agent project folder as `<slug>` (409 `no_project_folder` when none is set, as the import says; 409 `exists` for a folder of that name the Store did not make). `readTarGz` refuses links, devices, absolute paths and `..` (422 `invalid_package`), caps the unpacked size and file count, and a package whose manifest sits one folder down is taken from inside it. The folder is CLAIMED with a non-recursive `mkdir`, gets `.clawbox/store-app.json` (the Store's receipt: slug, version, sha256) and a repository of its own with one commit (`ensureRepository`, the import's).
- Registered per its manifest: a `port` goes through `registerOrStartServerApp` (started with its `start` when nothing listens, then `/apps/<slug>/`); a `webapp`/`site` with an `index.html` is bundled into one page (`bundleFolderHtml`, the code-project build's inlining) and deployed as a desktop web app; anything else (a `tool`, a page that still needs a build) gets a small page saying where its files are. A server app with a `start` whose folder has a `package.json` that declares dependencies and no `node_modules` (a package never carries them) first gets its dependencies installed by `installAppDependencies` (`src/lib/app-server-start.ts`, which every start runs too, so Install again recovers an older install: bun for a bun lockfile or `packageManager`, npm for a `package-lock.json`, else bun when it is on the PATH, 10 minutes at most), and a failed install starts nothing and answers `registered: false` with e.g. `bun install failed: <its last lines>`. A listing icon that is a PNG becomes the app's icon. A server that will not start answers `ok: true, registered: false` with the reason: the files stay, the Store does not mark the app installed, and Install again only retries the registration (the receipt says the folder is the Store's).
- Uninstall removes the project folder only when it carries the receipt for exactly that id (`src/lib/store-install-receipt.ts`, loaded on demand so the uninstall route does not pull the installer in), BEFORE the web app and the desktop entry; a folder that will not go is 503 `project_remove_failed`, and the answer carries `projectRemoved: true` when it went. A server app's running process is not stopped by the uninstall.
- The Store app (`AppStore.tsx`) shows the category first (`mergeStoreCategories` in `src/lib/store-categories.ts`: named and counted even before the portal's category list carries it, never twice, absent when there is no ClawBox app at all), a "ClawBox app" badge, no star for an unrated one, and posts `source: "clawbox"` for such an install; the desktop's in-memory meta keeps the install's `webappUrl` so the new icon opens its window at once.

## Server Libraries (`src/lib/`)

- **`clawbox-manifest.ts`** — `clawbox.json`, the file that makes a folder a ClawBox APP (the owner's "a special file like package.json", 2026-09-05): `{ name, description?, kind?: server|webapp|site|tool, port?, start?, stripBasePath?, slug? }` (`slug` is the app's ClawBox Store id, present on the parsed manifest only when valid; `manifestSlug` derives one otherwise), parsed strictly (`parseClawboxManifest` never repairs; no name → null) and read best-effort. The projects listing carries it as `app` (a "ClawBox app" chip on the row, Open for a project with a port even before it is on the desktop), the GitHub import flags a repository that carries one at its root (one `search/code` query over the listing's owners; null when GitHub will not say), and a run's settle registers a project whose manifest names a `port` on the desktop (`registerProjectApp` → `registerServerApp`: the stub HTML that sends the frame to `/apps/<id>/`, the port into meta.json, `registerWebappInPreferences` with `webappUrl: /apps/<id>/`, a `register_webapp` nudge).
- **`app-proxy.ts`** — `/apps/<id>/…`, see the CSP note above: `resolveAppProxyTarget` (a registered app whose listener is the project's own), `listenerOwnedBy`, `isDocumentRequest` (the middleware asks the same question), `registerServerApp`, `APP_PROXY_CSP`, `appProxyAllowOrigin` (the CORS that sandbox makes necessary — the module script and `crossorigin` stylesheet of every ES-module app are fetched from the opaque origin `null`, so the proxy answers for the origin it imposes, echoing `null` and never `*`, never with credentials, and ONLY for the asset types that are CORS-fetched by construction: script, stylesheet, font, wasm, svg. `Origin: null` proves nothing on its own — any page on the web can send it from a sandboxed iframe, and over plain HTTP no second header tells them apart (Chrome sends `Sec-Fetch-*` only to secure contexts and an opaque-origin document has no referrer) — so an app's JSON, HTML and text answers get no CORS header and stay unreadable to another origin). The relay also drops `content-encoding` and `content-length` when Node's `fetch` has already decompressed the body and asks the app for `identity` in the first place: forwarding the app's `gzip` with the plain bytes told the browser to gunzip text that was already text, which is the OTHER reason the window was blank. The proxy's timeout is on the app's HEADERS only (`HEADERS_TIMEOUT_MS`); a body streams until the client goes away. Next's trailing-slash redirect is off (`skipTrailingSlashRedirect`) so `/apps/<id>/` reaches the proxy as typed; the middleware keeps that redirect for page paths.
- **`webapp-sandbox.ts`** / **`webapp-kv-bridge.ts`** — the webapp iframe contract. A webapp is HTML the agent wrote, served from the ClawBox origin; framed with `allow-same-origin` it ran with the OWNER's session and could reach every owner-only route and script the desktop. `WEBAPP_IFRAME_SANDBOX` (never `allow-same-origin`) is the one sandbox both the desktop window in `page.tsx` and the standalone `/app/[id]` page use. What the opaque origin loses is persistence, and the bridge gives it back without the origin: the guest snippet (`WEBAPP_KV_CLIENT_SNIPPET`, `window.clawboxKv = { get, set, delete, list }`) posts `{ clawboxKv: { id, op, key, value } }` to `window.parent`; the host (`attachWebappKvBridge()`, mounted once per page) attributes it to an `iframe[data-webapp-id]` by `event.source` identity, forces the `<appId>:` key prefix (any other prefix is refused), performs the `/setup-api/kv` call itself and answers `{ clawboxKvResult }` to that frame only. `WEBAPP_DOCUMENT_CSP` is the same sandbox as a RESPONSE header for a webapp opened top-level (`launch: "window"`, a chat link, a share link in a tab — a first-class document on the authenticated origin otherwise); it is shipped by the `/setup-api/webapps{/}?` headers() entry in `next.config.ts` placed AFTER the general one, because a route handler's Content-Security-Policy never reaches the wire when the config already set the key, and Next compiles a source under strict matching so the trailing-slash form has to be named — pinned through Next's own matcher in `desktop-csp-header.test.ts` and by `webapp-sandbox.test.ts`. A top-level open now has an opaque origin: no localStorage/IndexedDB, no KV bridge; nothing on the box writes `launch` or `public` today. An app built before v4.0 against `fetch('/setup-api/kv')` or `localStorage` is carried by the legacy-storage layer on top of the bridge (ops `legacyKv`/`legacyLocalStorage`, see the Code Assistant section below).
- The desktop's CSP (`next.config.ts`) allows `frame-src 'self' blob: http: https:`: an app the coding agent serves on its own port used to be reached on the box's own host at that port, at whatever address the owner typed, and `'self'` alone showed "This content is blocked" over a running app. The webapp iframe sandbox (`webapp-sandbox.ts`) is what protects the desktop, not that list. Since 2026-09-05 such an app is reached THROUGH the box instead: **`/apps/<id>/…`** (`src/app/apps/[id]/[[...path]]/route.ts`, `src/lib/app-proxy.ts`) proxies to `127.0.0.1:<port>` — the port from the app's `data/webapps/<id>/meta.json` (written by `registerServerApp`) or the project's `clawbox.json` — so the desktop icon works on the LAN, over mDNS, through a Cloudflare tunnel and after the tunnel's address changes (a redirect to `location.hostname:<port>` was dead the moment the tunnel restarted, the owner's report). The path reaches the app unchanged, so an app built for this serves under the base path `/apps/<id>` (Next.js `basePath`, Vite `base`; a manifest may say `stripBasePath: true` instead). ONLY a REGISTERED app is proxied (its `meta.json` carries the port and the project folder, written by `registerServerApp` at a run's settle or from the project page's **Add to desktop** → `POST coding-agent/projects/desktop`), and every registration and every proxied request first checks that the port's LISTENER is the project's own — a process of this user whose `/proc/<pid>/cwd` is inside the project folder, read through `ss -ltnp` (`listenerOwnedBy`, verdicts cached 30 s, refusals 3 s) — because the proxy forwards unauthenticated requests and a manifest is a file a run or an imported repository can write: one naming port 2375 would otherwise have put the Docker API on the tunnel. The containment is the RESPONSE's `Content-Security-Policy: sandbox …` (`APP_PROXY_CSP`, no allow-same-origin, on EVERY proxied response whatever its type says) rather than the iframe attribute — a sandboxed frame's navigation carries no cookie and the document needs the owner's — so the desktop and `/app/[id]` frame a same-origin `/apps/` URL WITHOUT the attribute (`isProxiedAppUrl`); the middleware lets the app's own non-document requests through without a cookie (its documents still need one), which exposes the app's routes to whoever has the address the way its port on 0.0.0.0 is exposed on the LAN; `production-server.js` routes `/apps/<id>/` upgrades (a dev server's HMR) to the same port; the desktop's CSP header is scoped to `/((?!apps/).*)` so a dev server's eval'd source maps are not refused. The `clawbox_context` storage guide now tells a run to write the manifest, serve under the base path, and never put a host or port in a link.
- **`code-projects.ts`** — code project management: CRUD, file ops (write/edit/delete/search), build/bundle to webapp.

## Code Assistant (`src/lib/code-projects.ts`, `src/app/setup-api/code/`)

Enables the AI agent to build multi-file desktop webapps through an iterative coding workflow:

1. `code_project_init` — scaffold a project (index.html + style.css + app.js)
2. Write/edit files using `code_file_write` and `code_file_edit` (string-replacement edits)
3. Search code with `code_search`, inspect with `code_file_read`
4. `code_project_build` — inlines local CSS/JS into a single HTML file, deploys to `data/webapps/`, registers on the desktop

Projects live in `data/code-projects/<projectId>/`. Built webapps are deployed to `data/webapps/<projectId>/` and served at `/setup-api/webapps?app=<projectId>`. The desktop and the standalone `/app/[id]` page frame a webapp with the one sandbox in `src/lib/webapp-sandbox.ts` (`WEBAPP_IFRAME_SANDBOX`, never `allow-same-origin`): agent-written HTML must never run with the owner's session, which is what a same-origin frame gave it. A framed app therefore has an opaque origin and cannot fetch `/setup-api/kv` (or any `/setup-api` route) — it persists through the KV bridge instead: the guest snippet (`WEBAPP_KV_CLIENT_SNIPPET`, inlined into every `code_project_init` scaffold and quoted in the `clawbox_context` storage guide for one-file apps) defines `window.clawboxKv.get/set/delete/list`, which post `{ clawboxKv: { id, op, key, value } }` to the host; the host answers only the frame it opened, forces the `<appId>:` key namespace and does the KV call with the owner's session. A webapp built BEFORE v4.0 keeps its data through the legacy-storage layer (TASK-1150; `src/lib/webapp-legacy-storage*.ts`): v4.0 moved no data when it boxed the apps, so every app that had saved through `fetch('/setup-api/kv')` (free-form keys — the guide's own example paired id `todo-list` with `todo:items`) or the origin's `localStorage` opened on EMPTY storage. The `webapp-legacy-storage` boot migration (awaited, once) COPIES each old KV key an app's own code names (`isAttributedKey` over its string literals) into that app's namespace — `<appId>:<key>`, a key already under `<appId>:` staying where it is — only where the namespace is empty, never a ClawBox-owned key (`isClawboxOwnedStorageKey`: `clawbox*`, `clawai*`, `openclaw*` — the Control UI's gateway token — `hermes*`, `ui:`) or another installed app's namespace, never through a symlinked folder or file; reads every copy back, deletes nothing (a rollback to v3.9 still finds the originals), and writes `data/webapp-legacy-storage.json`, whose existence is what switches the layer on — an app is never served with the layer before its data has moved, so it cannot save an empty first screen over it. The census is the apps present at that boot. Serving `index.html` of an app that uses the old APIs then puts `webapp-legacy-storage-shim.ts` first in the page: `fetch('/setup-api/kv…')` is answered through the bridge (op `legacyKv`, v3.9's statuses and shapes), and the `localStorage` an opaque origin THROWS on is replaced by a working one seeded from `<appId>:localStorage:*` (not for a `public` app, which gets memory-only storage), its changes sent in order (op `legacyLocalStorage`). Both ops go to `/setup-api/webapps/storage` (same-origin, confined to the app the desktop attributes the frame to). A browser's OLD localStorage is brought over by `WebappFrame` (the one frame both pages draw) before the frame loads — only keys the census recorded the app's code naming, only where the app has nothing yet, each key once from whichever browser comes first, the browser's copy untouched. An app created or built without an icon gets one generated by ClawBox AI's image model when the box is linked (`src/lib/webapp-icon.ts`): fire-and-forget after `deployWebapp`/`buildProject` register the app, written atomically to `data/icons/<appId>.png` where the icon route already looks, never overwriting an existing icon, one picture per app and one generation at a time (a rebuild while the picture is being drawn joins it; a failure is not retried for a few minutes) — `withGenerationSlot` is box-wide, so app icons, a coding project's favicons and a run's own pictures all come out of the one per-UTC-day allowance rather than opening N upstream requests against it, with a run's own picture (`priority: "request"`) served ahead of icon jobs still waiting and bounded only by what is really ahead of it, so the project icon a run queues at start never makes its first picture "busy" (TASK-1355) — dropped if the app was uninstalled meanwhile, and the open desktop is nudged with a `register_webapp` re-push so the icon appears without a reload.

A webapp always runs in a sandboxed iframe with an opaque origin (`src/lib/webapp-sandbox.ts`) — on the desktop and at `/app/installed-<id>` alike — so it can neither call the session-authenticated `/setup-api` nor reach the desktop around it. Its storage is `window.clawboxKv` (get/set/delete/list, Promises), a postMessage bridge the host page answers under the app's own `<appId>:` key namespace; the scaffold inlines the snippet into new projects and the `clawbox_context` storage guide tells the agent to use it. A webapp written before the bridge that fetches `/setup-api/kv` directly no longer persists anything (the call is cross-origin now and the cookie is not sent) — it has to be rebuilt on `window.clawboxKv`. Installed apps and their meta are written by the install/uninstall/webapp-registry routes only; the desktop no longer re-persists `installed_apps`/`installed_meta`, so an install or uninstall made by the agent or the API survives an open desktop (each remaining preference key is written on its own, only when its own state changes).
