# ClawKeep backups

ClawKeep's wizard and restore rules, its backup boundary around `openclaw backup create`, what it leaves out and the links it skips. Read it when you touch `clawkeep/` or the ClawKeep components.

## Frontend (`src/components/`)

### Built-in Apps

- ClawKeep's "What's in a backup" list sits behind a question-mark button beside the title (`BackupContentsInfo`, testids `clawkeep-contents-toggle` / `-popover`; Escape or a click elsewhere closes it), not in a card of its own.
- **`ClawKeepWizard.tsx`** / **`ClawKeepArt.tsx`** / **`ClawKeepPairChallengeCard.tsx`** — ClawKeep's first-run wizard (intro with the artwork → pair through the device-code loop → passphrase → schedule, then `POST /setup-api/clawkeep/setup { setupComplete: true }`), shown by `ClawKeepApp` while the status says `setupComplete: false` AND the box is not paired; "Not now" marks setup done without pairing. The pair-code card is shared with the dashboard. ClawKeep's RESTORE (`clawkeep/clawkeep/restore.py`) never lets the manifest choose the destination: a pre-pass over every asset, before anything is staged or moved, requires each `sourcePath` to be absolute, normalised and one of the roots THIS box declares — Hermes' `ASSETS` matched by kind (entry and sqlite pinned), OpenClaw's answered by `openclaw backup create --dry-run --json` under the same environment clawkeep spawns the CLI with — and the symlink allowance for absolute link targets is derived from those vetted targets, not the manifest (a hostile snapshot in the account's shared R2 prefix could name `/home/clawbox/.ssh`); extraction refuses a link member whose resolved target leaves the staging root and re-checks the real parent of every member so nothing is written THROUGH a link the archive created (Python 3.10.12 has `tarfile.data_filter`; the check is explicit either way). `restore`, `unpair`, `snapshots/delete|label|lock`, `encryption` (POST and DELETE) and `reset-state` are owner-only AND same-origin (403 `owner_only`, `kind: "owner_only"`); `backup` is deliberately not, because the `backup_now` MCP tool posts it with the bearer.
- **ClawKeep BACKUP on OpenClaw** (TASK-1000): `openclaw backup create` stays the archiver and the authority; `clawkeep/clawkeep/backup_guard.py` is ClawKeep's boundary around it — a dry-run pre-flight refuses two sources claiming one archive path before the core runs; symlinks the core would refuse that an explicit rule calls regenerable (package-manager `node_modules`/pnpm-store links, OpenClaw's `plugin-skills` and legacy `plugin-runtime-deps` links, `.cache` links, a stale Chromium `SingletonSocket`) are journalled (`detached-links.json`), set aside for the build and put back after it (or by the next run), under an `archive.lock` so overlapping runs cannot interleave; every other outward link is left alone and the failure names it. An ENOENT inside the backup is a bounded race (`EXIT_ARCHIVE_BUSY`=11); a SQLite database whose ONLY damage is its indexes is `REINDEX`ed by `sqlite_recovery.py` after a copy is kept through the online-backup API (`sqlite-recovery/`, newest 3) and proven by a full `integrity_check` — anything else stops the run as `EXIT_ARCHIVE_DB_DAMAGED`=12 with the file untouched; duplicates and outward links end as `EXIT_ARCHIVE_CONFLICT`=13. The bridge maps them to `archive_busy` / `database_damaged` / `archive_conflict`. Hermes' own archiver snapshots each file in one read (a file truncated mid-read used to misalign the tarball), records a vanished file or folder as skipped, and writes each member name once. The pytest suites never plan against the real box: `tests/conftest.py` stubs the pre-flight and points `CLAWKEEP_DATA_DIR` at a temp dir.
- **ClawKeep leaves the box's own backups out** (TASK-1301): measured on OpenClaw 2026.9.4, `backup create` carries `<state>/backups/**` byte for byte and has no exclude option (no flag, no `backup` key in `openclaw config schema`; it only refuses to write its OWN output inside a source path), so a customer's 20 GB of local archives took snapshots from 2.5 GB to 13 GB and the account over quota. `clawkeep/clawkeep/own_backups.py` is the rule — a regular file in `<state>/backups/` with an archive suffix, or anywhere with OpenClaw's own `<timestamp>-openclaw-backup.tar.gz[.enc]` name; path and name only — and the mechanism: one `rename(2)` into `<data>/set-aside/run-*/` (else a `.clawkeep-set-aside/` beside the asset) on the SAME filesystem and outside every planned root, never a copy (no such place → the file stays in and is warned about), journalled in `set-aside-files.json` (fsynced with its directory) before anything moves, put back in the build's `finally`, before the next build and on the hourly idle tick (`backup_guard.put_back_interrupted`, non-blocking on `archive.lock`), never over a file that took its name (`<name>.clawkeep-returned`), never through a folder that became a link. `backup_guard.scan` is the pre-flight's ONE walk — refused links and archive-named files together — and no plan means no walk and nothing set aside. The run writes `last_left_out_*` and `last_large_archive*` (carried archives ≥ 256 MiB, five named) to state.json BEFORE the upload; the status carries them as `leftOutCount/Bytes` and `largeArchives/Count/Bytes`, the dashboard draws the left-out line and `LargeArchivesCard`, the "What's in a backup" popover lists the rule under Not included (`clawkeep.contents.openclaw.excludeBackups`, all ten locales), and `backup_status` adds a note for each without quoting a file name.
- **ClawKeep skips links the archiver refuses** (TASK-1304): OpenClaw 2026.9.4's `backup create` refuses, WHILE WRITING, any symlink whose target is outside its declared assets ("Archive symbolic link target must be relative" / "… is outside the declared backup assets") and has no exclude option, so one absolute link in a workspace failed every backup after the long archive step. `backup_guard.scan`'s one walk now finds every link the core's rule refuses (`_link_refused`: an absolute target whose real path is outside every asset or does not exist, a relative one that lands outside) and `detach_links` sets ALL of them aside for the build in one pass (journalled in `detached-links.json`, put back in the `finally`, never followed) — not only the managed ones; an asset root is never detached. An absolute link whose real target is inside an asset is left alone: the core stores it as the relative link. Non-managed ones are the run's `skipped_links` (first `LISTED_SKIPPED_LINKS`=20 as `~/…` path + link text, all counted): `Archive.skipped_*` → `state.json` `last_skipped_links/_count` before the upload → status `skippedLinks/skippedLinkCount` → the dashboard's "Backup finished · N symbolic link(s) skipped" line (only once `lastHeartbeatStatus` is ok) and `SkippedLinksCard`, the popover's Not included line (`clawkeep.contents.openclaw.excludeLinks`), and `backup_status` (five named, `maxChars` 6,000, never quoted in a note). The heartbeat stays `ok`; no path goes to the portal. The snapshot's sidecar-manifest record gets `skippedLinkCount` in the clear and `skippedLinks` SEALED with the backup passphrase (`crypto.seal_text`, base64 of the same `openssl enc`), which `restore` opens back (best effort, encrypted snapshots only) into `skippedLinks/skippedLinkCount` of its report and `RestoreResultCard` names — nothing is recreated from it. The net: when the core still refuses a link the rule let through, `_refused_again` detaches it plus every link of its shape under a stricter reading (`_absolute_refused`: every absolute link; `_relative_refused`: the real target must exist inside) and rebuilds, at most `MAX_LINK_REBUILDS`=2; after that, or with no dry-run, the refusal stands as `EXIT_ARCHIVE_CONFLICT`. `tests/fake_openclaw.py` stores an absolute-inside link relative and `FAKE_OPENCLAW_NO_ABSOLUTE=1` plays a stricter core.
