# Desktop

The desktop shell: windows, shelf, launcher, tray, mascot and pets, notices and toasts, monitor mode, battery, desktop state, screenshots, the x64 desktop session and the performance suite. Read it when you touch `page.tsx`, `Chrome*`, `Mascot.tsx`, `desktop-*`, `monitors*`, `visible-interval.ts` or any desktop poll.

## Setup API Routes (`src/app/setup-api/`)

- **Battery**: `system/battery` (`src/app/setup-api/system/battery/route.ts`) — GET → `BatteryStatus` from `battery.ts` (see Server Libraries), exactly as `readBattery()` returns it, for the shelf's `BatteryIndicator.tsx`. OWNER-ONLY through `requireSession` with no bootstrap carve-out and no non-owner scope: a signed-out page is 401, a non-owner 403 `owner_only`, and the indicator draws nothing on either. Every box's desktop asks it — Jetsons and battery-less desktops too — so a box that is not x64 (`os.arch()`), has no battery, or fails to read one answers 200 `{ available: false }`, never a 500; no child process and no cache (a charger plugged in shows on the next poll), `Cache-Control: no-store`. The caller polls once a minute and only while the page is visible — keep it that way, never a faster poll. Tests: `src/tests/routes/system/battery.test.ts`.
- **Desktop state**: `desktop/state` (TASK-1306) — the signed-in user's open windows, one file per ClawBox user in `data/desktop-state/` (`src/lib/desktop-state-store.ts`; the name rebuilt from `[a-z0-9_-]` with `~<hex>` for anything else, 0600, atomic per write; removed with the user by `removeUser`). GET answers `{ user, state }`, PUT `{ state }` (same-origin, 256 KiB) stores what `sanitizeDesktopState` (`src/lib/desktop-state.ts`, shared with the desktop) rebuilds field by field: the windows bottom to top, geometry, minimized/maximized/snapped and the restore rect, `meta`, a Terminal's tabs with their session ids, the focused window — and drops the setup wizard's window and any window of a built-in app this build no longer has (`RETIRED_APP_IDS`: `projects`, the Files app's Projects view removed by TASK-1556), so such a window is never drawn, counted or saved again. The user is always the SESSION's (the MCP bearer and test mode are the owner), and it is the one `/setup-api` path a non-owner may WRITE (`NON_OWNER_API_OWN_STATE` in `non-owner-scope.ts`, GET/HEAD/PUT). An owner with no file yet gets the old `desktop_open_windows` preference back once, minimized as before; the desktop no longer writes that preference. The desktop (`page.tsx` + `src/lib/desktop-state-client.ts`) restores it exactly on load — clamped into a smaller desktop (`clampRectToViewport`), left as saved on a phone — writes every change to this browser's localStorage under the user's name at once and to the device 400 ms after it settles (a `keepalive` PUT on `pagehide`), and restores this browser's copy when the device is unreachable or never got the last save. Closing a window by hand ends its terminals' sessions.
- **Monitors** (monitor mode): `monitors`, `monitors/brightness` — the desktop spread over a ROW of monitors as one page, on a box whose display is the labwc "ClawBox Desktop" session (`scripts/x64-migration/kiosk/clawbox-desktop-*`; never a Jetson today). GET `monitors` answers `available: false` with a 200 everywhere else and runs nothing: `src/lib/monitors.ts` acts only with `/etc/clawbox/kiosk.env` present AND `$XDG_RUNTIME_DIR/clawbox-monitor-mode` holding a PID whose `/proc/<pid>/comm` is `labwc` (the session script writes its own PID there just before `exec labwc`; the cage kiosk also answers wlr-randr and must never be driven). The owner gets the whole status (monitors with their modes, the order left to right, `main`, the row's `box`, `mirror`, a trial's `pending.deadline`); another signed-in user the positions-only `desktopViewOf` (it is on `NON_OWNER_API_READS`). POST `{ action: "apply", layout }` (owner cookie AND same origin) puts a layout on screen ON TRIAL — `readLayoutRequest` (`src/lib/monitors-layout.ts`) rebuilds every value from the compositor's own lists, never passes one through — and it is undone after `REVERT_AFTER_MS` (20 s) unless `{ action: "keep" }` saves it in `data/monitors.json`; `{ action: "revert" }` undoes it now. The trial is armed BEFORE wlr-randr runs and re-armed once the layout is on screen; an undo the compositor refuses is retried every 3 s and given up after `MAX_REVERT_ATTEMPTS`, after which the reconciler puts the saved layout back. Refusal codes: `owner_only`, `cross_origin`, `invalid_body`, `invalid_action`, the layout's own (`invalid`, `unknown_monitor`, `unknown_mode`, `invalid_scale`, `invalid_transform`, `none_enabled`, `main_disabled`), `unavailable` 503, `nothing_pending` 409, `apply_failed`, `apply_uncertain` (wlr-randr ran out of time — the layout may be on screen, on trial), `save_failed`, `revert_failed`. A variable refresh rate the compositor refuses costs only itself (the layout is applied again without it, the monitor is listed in `refusedAdaptiveSync` and its switch is not offered again). The reconciler (`startMonitorReconciler`, from `src/instrumentation.ts`, every 3 s) re-applies the saved layout when the session, the connected set, the lid or any output's actual state changes; a monitor never seen goes on at the right end at its preferred mode, at least one output is always on, and a built-in panel stays off while the lid is shut (`lidClosed()`, ACPI). A GET runs no wlr-randr of its own while a read begun in the last `STATUS_READ_REUSE_MS` (1.5 s, half the reconciler's interval, timed on `performance.now()`: on the wall clock, which NTP steps, a step back kept every read "recent" for the step's length, each GET handed the newest look and only the reconciler's own 3 s look keeping it from going stale; a trial's `deadline` stays a wall-clock time, because the client reads it as one) can answer it — the reconciler's, another GET's, or one still on its way (`readCompositorShared`) — because every GET used to spawn one, every 5 s from the desktop and again from Settings, on top of the reconciler's own every 3 s. The reconciler, Apply, Keep and Revert always read fresh, and `putOnScreen` forgets every read before wlr-randr runs and again once it has answered (`forgetReads`, a generation number), so no GET is answered from before a change ClawBox put on screen; one the box did not make (a monitor plugged in) reaches a GET at most 1.5 s later than it used to. Every apply resizes the desktop's Chrome --app window over the row through its DevTools port (`spanDesktopWindow`, every CDP call time-boxed). `monitors/brightness` is DDC/CI through `ddcutil` where it is installed and a monitor answers (`src/lib/monitor-brightness.ts`: one queue, the latest value per bus wins, connector → bus from `ddcutil detect --terse`); a monitor that cannot is absent from the GET, and nothing installs ddcutil.

## Server Libraries (`src/lib/`)

- **`battery.ts`** — `readBattery({ root?, arch? })` → `BatteryStatus`: `{ available: false }`, or `{ available: true, percent, state, acOnline, minutesLeft }` with `state` one of `charging`/`discharging`/`full`/`not_charging`/`unknown`. Read from sysfs `/sys/class/power_supply/*`: a `type` Battery supply's `capacity` and `status`, a Mains/USB supply's `online` for `acOnline` (null when none reports it). Two gates, both answering `{ available: false }`: x64, which is `os.arch() === "x64"` — the process architecture, as `system-info.ts` reports it; `edition-source.ts` says which ASSISTANT a box runs (openclaw/hermes/dual), not which hardware, so there is no edition flag for this — and any other arch (every Jetson) never even lists the directory; and a battery, left after skipping a peripheral's own (`scope` Device: a mouse, a headset) and an empty bay (`present` 0) — so every desktop PC answers it too. Several batteries are one pack: the percent weighted by energy when all report it (else the mean of the capacities), and any charging or discharging battery decides the state. `minutesLeft` is to empty while discharging and to full while charging, from `energy_now`/`energy_full`/`power_now`, else `charge_now`/`charge_full`/`current_now` (a signed rate counts by its size); null in any other state, when the rate is missing or zero, or past 48 h. It never throws — an unreadable file is a missing attribute, anything worse `{ available: false }` — so the route never answers 500 for the ordinary state of most boxes. The directory is the `root` option, else `CLAWBOX_POWER_SUPPLY_DIR`, else `/sys/class/power_supply` (`DEFAULT_POWER_SUPPLY_DIR`): `vitest.config.ts` points the env at a path that does not exist, so the suite run on an x64 laptop never reads its real battery, and tests that want one pass `root` to a fixture tree (`src/tests/unit/battery.test.ts`).
- **`window-snap.ts`** — where a dragged surface lands against a screen edge, shared by `ChromeWindow` and the mascot chat, and `DESKTOP_GAP`: the ONE margin the desktop's floating surfaces keep from the edges and from each other. It is one number because the two are measured against each other — `page.tsx` adds it to the chat panel's width to build the strip windows reserve — and kept apart they drifted to 10 px and 12 px, which is exactly the lopsidedness visible when both are on screen. A window that fills the desktop takes no gap at all: a SNAPPED window is deliberately flush, and since 2026-09-30 a MAXIMIZED one is too (the owner's ask: no small paddings around the windows), so the constant is the docked chat's margin and the room a window opened or centred beside it keeps from the panel.
- **`desktop-screens.ts`** / **`use-desk-screens.ts`** / **`use-monitor-layout.ts`** — the page's half of monitor mode: the monitors in the page's own CSS pixels (`screensFromStatus`; null — the plain one-screen desktop — for every page that is not the spread window, a mirrored layout, or a viewport whose ratio is not the row's), polled every 5 s from `/setup-api/monitors` only in an app window (`display-mode` not `browser`) and not while the page is HIDDEN (a tick that fell due then is read on the visible edge; a resize or a layout change from Settings is read at once either way). The first `available: true` also marks the page as that session's window (`setMonitorSessionWindow`, read through `isMonitorSessionWindow()` by `isBoxOwnScreen()`, see `visible-interval.ts`): kept apart from the screens, which are null for one monitor on, a mirrored row or a viewport not yet the row's size — all of them still the session's window — kept through a failed read or a 5xx as the layout is, and cleared on unmount; an answer that lands after the unmount marks nothing. With screens, `window-snap.ts` maximizes and snaps on the monitor under the window (`workArea`, `maximizedRect`; a shared edge never snaps), the shelf, launcher, tray, chat, mascot, notices, toasts and icons sit on the MAIN monitor (`mainInsets`), each monitor gets its own wallpaper, and `ChromeWindow` moves a window WITH its monitor when the layout changes (`followLayout`, and `rejoinLayout` after a one-screen interlude). Without screens every function answers exactly what it did before.
- **`visible-interval.ts`** — `setVisibleInterval(tick, ms, { hiddenMs? })`, an interval that stops asking the box while nobody can see the answer: a tick that falls due while the page is HIDDEN (a phone's background tab, a laptop tab left open on the LAN or over the tunnel — Chrome throttles hidden timers to one wake-up a minute only after five minutes, and not every browser does) is skipped, and asked once, at once, on the edge back to visible, so what the owner returns to is at least as fresh — the rule the chat's polls already kept (`installPendingRefresh`). Timed on `monotonicNow()` (exported here, `performance.now()`), since the box has no RTC and its wall clock jumps at NTP sync — `use-clawbox-login.ts`, the ClawKeep status helper and the Coding Agent's GitHub minute time their windows on it too, while the verdict and "ago" clocks stay on `Date.now()` because they are compared with the box's own wall-clock stamps. `hiddenMs` is for a poll that carries EVENTS which expire rather than state that can be re-read; it may be a FUNCTION, asked at every hidden tick (where the page is shown can change after mount), and a hidden run falls on the interval's own BEAT: `beats = ceil(every / ms)` — rounded up, so a cadence that is not a whole number of intervals is never run sooner (5 s on a 2 s beat is every third tick, as it was) — a value no longer than `ms` (`beats <= 1`) runs every tick outright, and any other runs once `beats * ms - ms / 2` has passed since the last run. Half a beat to spare, because a browser fires a repeating timer on its own schedule rather than `ms` after the last callback: a run that was late stamped its time late, the tick due `every` later landed a few ms short of it, and judged exactly the ring's 20 s became 22 s and a cadence no slower than visible ran every other tick (`visible-interval.test.ts` drives 100 jittered beats). The box's own screen CAN be hidden: in the cage kiosk the desktop is one tab of the kiosk's Chrome, hidden whenever the owner is on another of its tabs, and the monitor session's app window is hidden while minimised. `isBoxOwnScreen()` asks that, each place by its own answer rather than by how the page is displayed — `kioskBarInset() > 0` (the kiosk bar has set its height on this page; 0 in every other browser), or `isMonitorSessionWindow()` (`desktop-screens.ts`: the monitor session answered `available: true` to THIS page, which a box without one — every Jetson — never does) — on every call, never cached, because the kiosk bar and the monitors' answer both arrive after the page has mounted. It used to be any `display-mode` but `browser`, and the desktop installed as an app on a phone or a laptop (`public/manifest.json` is `standalone`) and a tab put in full screen (F11, the shelf's own button) are app display modes too: a hidden phone read the ring every 2 s — the battery cost the hidden cadence exists to save — and reads it every 20 s now. (An installed app or a full-screen tab on another device pointed at the internal x64 machine while it runs monitor mode still keeps 2 s, since the box answers it `available: true` as well — never a shipped box.) Only the notice ring uses it: `page.tsx`'s `ringHiddenPollMs()` keeps `RING_POLL_MS` (2 s) there and `RING_HIDDEN_POLL_MS` (20 s, inside its entries' minute) everywhere else, because the ring's entries act on the box's screen while the desktop is away (an `open_app` for an external app or a `launch: "window"` web app is a new kiosk tab, and the update lock on its answer takes the screen to `/updating`) and slowed to 20 s they arrived up to 20 s after the agent said "I've opened it". Both of the box's own Chromes — the cage kiosk's launcher (`install-kiosk-tabs.sh` merges it in) and the monitor session's (`clawbox-desktop-browser`) — carry `IntensiveWakeUpThrottling` in their ONE `--disable-features` list (Chrome reads only the last such flag): Chrome wakes a chain of timers in a page hidden for more than five minutes only once a MINUTE, which left the 2 s ring about as rare as a ring entry lives (60 s), so an "open this app" or the move to `/updating` could be missed rather than late. Only that feature, never `--disable-background-timer-throttling`: a hidden page keeps Chrome's ordinary one wake-up a second (see `scripts/x64-migration/README.md`). `page.tsx`'s ring (2 s), Telegram pairing (20 s) and version (30 min) polls and the power prompt's safety poll use it; `use-clawbox-login.ts`, the ClawKeep status polls and `use-monitor-layout.ts` keep the same rule in their own code, and the Coding Agent's live poll skips its hidden ticks (its Team card's board poll and a team run's members poll are `setVisibleInterval`s outright) (its visible edge already re-read everything). Those get no exemption on the box's own screen: what they feed is state drawn on the desktop itself, re-read the moment it is shown, and nothing they bring acts on the screen meanwhile.
- **`use-desktop-clock.ts`** — the desktop's clock (the shelf's time, the power menu's time and date) as a store of its own, read through `useSyncExternalStore` by the labels that show it (`ShelfClock`, `TrayClock`). It was state of the desktop ROOT, ticking every second, so every new minute re-rendered every window, the chat and the mascot to change one text node; now it re-renders the labels. ONE ticker for every label on screen, so the shelf and an open power menu turn the minute in the same frame; it runs only while a label is mounted and notifies only when the text changes, and still every second, because a clock jump at NTP sync has to reach the screen within a second. Formatted with `toLocale*String` on every tick rather than a cached `Intl.DateTimeFormat`, which would keep the zone it was built in after Settings or `TimezoneAdopter` changed the box's. `desktop-shell-equality.ts` is the same idea for the root's own state: a pairing poll or a rubber-band move that brings back what is already held keeps the old array or Set, so React bails out instead of re-rendering the desktop.
- **`pending-actions.ts`** — the owner-notice ring: KV key `ui:pending-actions`, a JSON array of `{ id, ts, ...action }` newest last that every open desktop polls and NO reader deletes or rewrites (the single slot it replaced, `ui:pending-action`, was consumed by the first desktop to poll it, so every other screen missed the notice). `pushPendingAction(action, id?)` is the one in-process writer — the coding finish card, `notifyOwner()`, the web-app icon nudge, the power-approval notice — and prunes entries older than 60 s and beyond 20; the MCP tools and `clawbox notify` post the legacy key to `/setup-api/kv`, which folds the value into the ring. A desktop reads it every 2 s while the page is visible and every `RING_HIDDEN_POLL_MS` (20 s) while it is hidden — slowed, not paused like the other polls, because an entry is gone after a minute — and at once on the way back (`setVisibleInterval`'s `hiddenMs`); on the box's own screen (`isBoxOwnScreen()`: the kiosk tab, the monitor session's app window) it keeps the 2 s while hidden, because there its entries open pages the owner is looking at (see `visible-interval.ts`). `src/lib/power-approval.ts` pushes `{ type: "power_approval" }` (id `power-approval:<id>:asked` or `:settled`) when a restart or shutdown request is raised — before its Telegram round trips — answered (on any desktop or in Telegram) or run out, the last now on time with nobody asking (an `unref`'d expiry timer, judged by the same wall-clock test as every reader, that waits until `expiresAt` plus `EXPIRY_SLACK_MS` (250 ms) but never longer than `EXPIRY_LOOK_MAX_MS` (60 s) before it looks, and looks again under the same cap while the request is still live: `expiresAt` is a wall-clock time and the timer runs on the monotonic one, and a clock stepped back further than a timer can hold (~24.8 days — a date set far ahead by hand, then corrected by NTP) overflowed it to 1 ms with a `TimeoutOverflowWarning`, so the web server re-armed on 1 ms timers and flooded the journal until the clock caught up; capped, a normal two-minute request is looked at twice and a clock stepped forward is noticed within a minute — `power-approval-expiry.test.ts`); never awaited and never thrown, so a decision cannot wait on or fail over it. The notice carries nothing of the request — the ring is a file the MCP bearer reads and the agent writes, so a forged one can only make a desktop ask — and the desktop answers it by firing `POWER_APPROVAL_EVENT`, on which `PowerApprovalPrompt` asks the owner-only `system/power/approval` route at once (a notice landing while an ask is out is asked again once it lands), under a 60 s safety poll that waits while the page is hidden. The prompt used to ask every 5 s, on every owner desktop, all day, for a request that almost never exists.
- **`hermes-pets.ts`** — the mascot's pets (Settings → Appearance → Mascot pet; `PetPicker.tsx`, `pet-client.ts`, the `pets`, `pets/select`, `pets/sprite`, `pets/thumb` routes). Two arms behind one API, chosen per call by `hasHermesHarness()`: on a Hermes harness the store is Hermes' own (`$HERMES_HOME/pets`, `display.pet.*` through the CLI, so the TUI and `hermes pets` agree with the desktop); on OpenClaw — since 2026-09-07, the owner's "add the mascots when we are on openclaw" — the same layout under ClawBox's own `data/pets`, the curated sheet fetched by `installPetDirect` (never bundled: Petdex art stays its authors', downloaded by the owner's own pick onto their own device), and the pick in the config store under `mascot_pet`. The GET answers `placeholder: "crab" | "egg"` — what the desktop wears with NO pet: the crab wherever ClawBox's own harness runs (openclaw, dual), the egg on a Hermes-only box, because the crab is ClawBox's brand and not a stand-in on someone else's harness — and `Mascot.tsx` reaches `EggMascot` only on `"egg"`; the picker's first tile shows the crab under `settings.mascot.petCrab` on a crab box and "None" on Hermes. A server that predates pets answers no `supported: true`, and every fail-open path in `pet-client.ts` keeps the crab.

## Frontend (`src/components/`)

### Desktop Environment

- **`ChromeShelf.tsx`** — app launcher taskbar with pinned icons; the phone bar draws Settings and every OPEN app in a scrolling middle row (`shelf-mobile-apps`) — it computed that list for a year and never drew it, so an app switched away from on a phone could not be reached again (the sweep of 2026-09-07). Its fill is `SHELF_FILL`, a flat `rgba(17, 24, 39, 0.8)`, not frosted glass (see `scripts/perf/desktop-perf.mjs`; `kiosk/extension/bar.js` wears the same fill on the desktop and `kiosk-extension.test.ts` holds the two together), and the phone bar (under 768 px) is `PHONE_BAR_FILL`, 0.93: the icon grid scrolls UNDER that bar, and at 0.8 the tiles' white labels showed through as faint but readable text where the blur had left a soft glow — 0.93 is where a label's brightest step (17.9/255) meets the glass's own strongest glow (17.8/255), measured in Chromium over the four built-in wallpapers at every offset of a row, portrait and landscape; more opaque only darkens it further from the glass's tone (`chrome-shelf.test.tsx` pins both). `kiosk-extension.test.ts` also pins the extension's VERSION, because Chrome re-reads an unpacked extension's files only when `manifest.json`'s `version` moves (see `scripts/x64-migration/README.md`): `RELEASES` lists every version with a sha256 of every file in `kiosk/extension` (the manifest's `version` left out, CRLF normalised), the files on disk must match the newest entry and the manifest carry its version, and a changed file fails with the hash to record. An entry is FROZEN once its version is committed — a kiosk may already be running those files under that number, and a hash rewritten in place is the very unloaded change the list exists to catch — so a later change is a version bump and a new entry, APPENDED; until then the newest entry belongs to the uncommitted change still making that version and is re-recorded as it changes, and the failure message offers both (1.5.3 is the flat fill). Its clock is `ShelfClock` on `use-desktop-clock.ts`. Its fullscreen button (`shelf-fullscreen-button`, both bars) is drawn only while there is a fullscreen to ENTER, in a browser that can be asked for one (`useCanRequestFullscreen`: an iPhone's Safari cannot), and never turns into an exit button: `useIsFullscreen()` (`src/lib/use-is-fullscreen.ts`) is `document.fullscreenElement` — the only fact that answers in the monitor session's `--app` window, which stays `display-mode: standalone` in fullscreen — or `display-mode: fullscreen` (F11, the cage kiosk's `--kiosk`) while the page is the whole window (`pageFillsWindow`: outer/inner ratios equal on both axes, since a Mac's green-button fullscreen keeps its toolbar and still matches the query). Its ClawKeep shield is `useClawkeepShieldStatus` (`src/hooks/`), and every GET of `/setup-api/clawkeep` the page makes goes through ONE helper there: a look joins a request already out unless it has been out `JOIN_MAX_MS` (15 s, on `monotonicNow()` — on the wall clock a step back kept a stuck request joinable, the shield and the window both waiting on it, for the step's length), a look after an action (`refreshClawkeepStatus`) always sends anew, and an answer older than one already handed out is dropped. So with the ClawKeep window open (10 s, 3 s while a backup runs) the shield takes the window's answers and asks for itself only after 5 s without one, while the window shows only the answers it asked for (an error it shows clears on its own next look, as before); both wait while the page is hidden, the box's own screen included, since the shelf is not on screen then either. On the box `getStatus()` (`src/lib/clawkeep.ts`) makes the data directory once per process instead of on every read — a read that then fails is run again the old way, mkdir first, so a broken path answers the same error — and `which()` walks PATH with `stat`/`access` instead of spawning `which` (a shell and its children every 5 s), still never cached, so an install shows at the next poll
- The desktop pushes an OBJECT with a marker field (`{ clawbox: true }`) as its history entry and knows its own entry by that field: it pushed the string "clawbox" for a year, and Next 16's router writes its own `__NA` field onto the pushed state, which throws on a string — so a client-side arrival at `/` (the standalone page's "Back to Desktop" link) landed on Next's error page and the browser's Back button never closed a window (the sweep of 2026-09-07).
- **`ChromeLauncher.tsx`** — app discovery context menu (its ids for installed apps carry the `installed-` prefix; "Add to desktop" un-hides such an app by its raw id and never writes it into `desktop_apps`, which holds built-in ids only). `OFF_DESKTOP_BY_DEFAULT` in `page.tsx` is what keeps a built-in app out of the default grid without hiding it: `vnc`, because the box's own X session is a diagnostic on a headless appliance, and now `system_update`, a page the owner visits twice a year and already reaches from Settings, the About tile and the desktop's own new-version notice. "Add to desktop" puts either back permanently.
- **`ChromeWindow.tsx`** — the draggable, resizable desktop window with title bar controls. A window OPENED beside a docked chat is fitted to the strip left of the panel (`fitWindowSize(size, rightInset)`, two `DESKTOP_GAP`s in) so its Minimize/Maximize/Close stay reachable; a window already on the desktop keeps its size when the chat docks, as documented below. A mousedown on the title bar refuses its focus-moving default whether or not the window is maximized, so a click on Restore (like one on Maximize) leaves the keyboard in the window's content — a terminal swallowed every keystroke after Restore until it was clicked again (the sweep of 2026-09-07)
- **The `+` tile (2026-11-01)** — the cell after the last desktop icon (`slotAt(allIconIds.length, iconGeometry)` in `desktop-icon-layout.ts`) holds a semi-transparent orange `+` tile ("New app", `desktop-create-app-tile`), owner only. It is NOT an icon: no `data-desktop-icon-id`, never dragged, selected, saved in `icon_grid` or given a context menu, hidden while an icon is dragged; a phone's grid height counts it (`gridCellCount`). A press reads `coding-agent/status` and opens the Coding Agent app while its wizard is unfinished or its switch is off (`dispatchOpenApp("coding")`), the Create planner otherwise (`openNewAppCard`) — the chat's `+` gate. **`PopoutWindow.tsx`** — ChromeWindow without Minimize for windows an app or the chat opens beside itself (the planner, a run's whole goal); ChromeWindow's `onMinimize` is optional for it. See coding-agent-ui.md.
- **`SystemTray.tsx`** — the power menu, not a row of status indicators (it draws no WiFi, battery or Telegram indicator; the shelf's battery is `BatteryIndicator.tsx`): opened by the shelf's power button, and by a non-owner's click on the clock (the owner's opens Settings → System), it shows the date and time, the internet line (`tray.internet`/`tray.noInternet`, asked every 15 s while the menu is open), who is signed in on a multi-user box, Restart / Shut down for the owner and Lock (Switch user); the shelf clock and the menu's date are formatted in the desktop's UI locale (`useT().locale`, with the browser's region for that language when its list has one — `clockLocaleTag`), not the browser's, both through `useDesktopClock()`; the menu's `TrayClock` is mounted only while the menu is open, and the panel is `rgba(17, 24, 39, 0.98)` with no backdrop blur
- **`BatteryIndicator.tsx`** — the laptop's battery in the shelf's tray (v4.3): `ChromeShelf` mounts it just left of the clock (`shelf-tray-button`) in both tray branches — the desktop bar, and the phone bar except in portrait, where the clock is hidden too. It asks `GET /setup-api/system/battery` once at mount and then every 60 s through `setVisibleInterval` — nothing while the page is hidden, once at once on the way back — and never faster. Draws a glyph and the percentage (`shelf-battery`): `battery_0_bar`…`battery_6_bar` by sevenths, so a level below full never draws as full, `battery_full` when full and `battery_charging_full` while charging — every one in the bundled `material-symbols-rounded.ttf` subset. The `title`/`aria-label` give percent and state, the time left (or until full) when the route could compute it, and "Battery low"; all `tray.battery*` keys, in all ten locales. Discharging at ≤ 20 % it turns amber (`data-low="low"`), at ≤ 10 % red (`critical`). It renders nothing — and stops polling for good — on `available: false` (a Jetson, a desktop), a non-OK answer (401 signed out, 403 a non-owner), a network error, or a body that breaks the contract. The reply type is `BatteryStatus` from `@/lib/battery` by `import type`, erased at build, so the client bundle never takes in the sysfs reader. Tests: `src/tests/components/battery-indicator.test.tsx`.
- **`Mascot.tsx`** — animated crab mascot with personality states. A walk is a Web Animation built from the walk's own formula (`walkKeyframes`: `WALK_KEYFRAMES`, 120, evenly spaced points plus the moments it crosses a lane edge — within a hundredth of a pixel of the frame-drawn walk): as a requestAnimationFrame loop it cost 37–53 ms of main thread and 60 style recalcs a second, as an animation ~1 ms and none, and it no longer stutters when the main thread is busy. Every interrupt (a grab, a new action, sleep, a frenzy, the chat opening, a key tap, unmounting, the page going away) reads the body's place off the animation's clock, and whatever must react mid-walk — a resize, a new lane or monitor layout, a turn or a hop, the root element re-created, a pet's bubble — hands the walk to the old frame loop at that moment; a browser without Web Animations walks in frames. The resting animations are stepped (`AMBIENT_FPS`, see `scripts/perf/desktop-perf.mjs`) from the moment the mascot is drawn and not while it is hidden. Its position is stored once it has stood still for `POSITION_SETTLE_MS` (1 s), never per frame and never unchanged — a walk is one POST after it ends, not two a second — and one not yet stored goes out on `pagehide` as a `keepalive` write; while the mascot is not drawn (hidden, the egg, pets still loading) an action stands at idle and looks again in 2–6 s instead of running a walk nobody sees. The root's `will-change` is `transform` alone: its glow `filter` switches between values and never animates. Asleep it never opens its eyes: `sleep` is drawn on the `waiting` row, whose frame 3 has the crab's eyes open, so a pet steps only the frames its `pet.json` names in `sleepFrames` (`vibrant-clawd`: `[0, 1, 2]`, spread over the row's 1100 ms loop) — taken whole or not at all by `normaliseSleepFrames` (non-empty integers inside the row; checked on load, on the wire and against the row's measured frames) — and a pack without them holds the row's first frame; the fail-open still wears `clawbox-crab-sleep.png`, cut by `scripts/generate-crab-still.mjs` at the idle still's scale and foot line.
- Phone layout — no separate mobile UI: at phone widths `page.tsx` (`isMobile`) uses `ChromeShelf`'s mobile branch plus `ChromeLauncher`, and windows go fullscreen with the page's own header

A notice may carry an ALLOWLISTED destination (`src/lib/notify-action.ts`, e.g. `{ open: "settings", section: "email" }`): its body — icon and text, everything but the X — is then a button that opens Settings on that section through `dispatchOpenSettingsSection` and dismisses the toast, which is how the email-approval notice reaches the queue. `/setup-api/kv` strips the destination from a notice posted through the legacy slot, so the agent-driven `ui_notify` and `clawbox notify` can never make a toast clickable
- Top-right notices — the finished-run card, the update card, the What's new in 4.3 card, the ClawBox AI offer and a Telegram access request — all leave on their own after `NOTICE_AUTO_HIDE_MS` (`src/lib/use-auto-hide.ts`, `useAutoHide(keys, onExpire)`): a key keeps its clock across re-renders, a hand dismissal clears it, and none of the timeouts is recorded as a dismissal (the update card and the What's new card are back after a reload; a timed-out pairing request stays off the desktop for the session only and is still in Settings → Telegram).
- **`ChromeWindow.tsx`** — the desktop window. A docked chat (`rightInset > 0`) only narrows the desktop: windows keep their own size and place and every control, and a MAXIMIZED window fills the desktop EDGE TO EDGE with square corners, exactly as a snapped one does — `left: 0`, `top: 0`, `100%` (less `rightInset`) wide, the viewport less the shelf and the safe-area inset tall — since 2026-09-30 and on every device, the owner's ask ("remove the small paddings around clawbox windows"; until then it kept `DESKTOP_GAP` on every side with its corners); beside a docked chat it ends at the chat's left edge, so the one margin left on screen is the chat's own; `maximizeSignal` maximizes it on request. The window's `DOCK_GAP` and the chat's own `CHAT_PANEL_GAP` were two numbers for one margin and drifted apart, so both are that constant now (`CHAT_PANEL_GAP` is re-exported under its old name because `page.tsx` reserves the strip with it), and the docked panel's bottom carries the safe-area inset a maximized window already subtracted from its height. (The fill-the-pane layout that once replaced every window's geometry while the chat was docked is gone at the owner's request.) A restored window (TASK-1306) takes `initialMaximized`, `initialSnapped` (laid out again as that zone of THIS desktop) and `initialRestore` (where Restore goes back to), and `onModeChange` reports every later change of mode with the rect it goes back to; the root carries `data-window-id`, `data-active`, `data-maximized`, `data-snapped`. It is `memo()`ed and its drag listeners read `onGeometryChange`/`onModeChange` through refs, so they are installed once per window; a press that moves nothing or a drop where the drag began reports no geometry (`reportedRef`), a snap drop is reported once, as its mode change, and a touch the browser cancels ends the drag where it stands and snaps nothing. A snap drop works out its zone before any style is written and reads the computed style once, so the 200 ms glide starts at the drop point on every monitor; the zone's corner is then written by a layout effect after the commit that turns the glide on (`snapLandingRef`), because the drop writes the drop point onto the element and React writes only a style that differs from the one it LAST rendered — where the window stood before the drag — so a zone whose corner was that same spot (a window at the top-left snapped to the left half) took the zone's size and stayed at the drop point. How the drag itself moves the window is under `scripts/perf/desktop-perf.mjs`.
- **`ScreenshotApp.tsx`** / **`ScreenshotEditor.tsx`** / **`ScreenshotOverlay.tsx`** — the Screenshot app (`screenshot`, TASK-1475): capture the desktop (full screen, a dragged region, a clicked window, optional 3 s / 5 s delay), annotate, save. `ScreenshotOverlay` is mounted ONCE by the desktop (owner only), so `Print Screen` / `Ctrl+Shift+S` (full screen) and `Shift+Print Screen` / `Alt+Shift+S` (region) (`src/lib/screenshot/shortcuts.ts`) work with the window closed — but never while the focus is in a text field, an editable element or a terminal (`isTypingTarget`, TASK-1491) — and the shelf's tray carries a Screenshot button (`ShelfScreenshotButton` in `ChromeShelf.tsx`, drawn only while the desktop's overlay is mounted) that sends the overlay the same `requestCapture` event the app's own buttons do; a finished capture waits in `src/lib/screenshot/session.ts` for the window to take it (a bitmap cannot ride a window's string `meta`), and the Files app's Annotate hands a picture over the same way. The capture does NOT depend on `getDisplayMedia`: over plain http the page is not a secure context and `navigator.mediaDevices` is undefined, so the default engine is the app's own renderer, `src/components/screenshot/dom-capture.ts` — the live DOM is cloned with its stylesheets and the fonts it has loaded into an SVG `foreignObject` and drawn to a canvas; `<canvas>` pixels (the terminal — whose WebGL addon is created with `preserveDrawingBuffer` for exactly this — and the noVNC screen behind Browser / Remote Desktop) are read with `drawImage` and laid in as the element's background, same-origin frames are rendered recursively, scroll offsets, form values and the current frame of running animations are written onto the clone, and a scroll container is clipped with the gutter its live scrollbar took (a scrollbar the live page did not draw re-wrapped every line). A frame is replaced by a `<div>` stand-in: even in an SVG image an `<iframe>` paints its own empty document over anything behind it. What no page script may read — a sandboxed, opaque-origin frame (every installed web app) and a plugin document (the PDF viewer) — is drawn as a labelled "Not captured" tile and NAMED in the editor's notice, never left blank; where the context is secure the notice offers the browser's own capture (`display-capture.ts`) instead. Not reproduced: `backdrop-filter` blur and `:hover`. The editor keeps the picture and its annotations apart (`EditorDoc` in `src/lib/screenshot/annotations.ts`, undo / redo in `history.ts`), so the saved file comes from the same drawing code that painted the editor (`src/components/screenshot/render.ts`); blur and pixelate throw the detail away when the area is shrunk, they do not cover it. Saves go through `/setup-api/screenshots` (owner only, same-origin writes): ONE validated name segment into `<Files root>/Screenshots`, never overwriting, the bytes checked to be the PNG or JPEG the extension claims, capped at `MAX_SCREENSHOT_BYTES` (9 MiB — under the 10 MiB at which Next cuts a proxied body short without failing it). Copy to the clipboard needs a secure context and says so where there is none. No "Send to chat": the chat only takes attachments staged by its own route.

## System Integration (`scripts/`, `config/`)

- **`scripts/x64-migration/kiosk/clawbox-desktop-session`** / **`clawbox-desktop-browser`** / **`clawbox-desktop-span.mjs`** / **`install-desktop-session.sh`** and **`kiosk/labwc/rc.xml.in`** — the internal x64 machine's "ClawBox Desktop" session (labwc, not install.sh's): the desktop as a Chrome --app window laid over every monitor (`span.mjs` keeps it the row's size over CDP; its `--watch` reads wlr-randr every 2 s but runs the full pass — attach to every desktop page Chrome lists and run a script in it, a page the size of every monitor together — only when the row is not the size the last full pass spread the window over, the desktop's pages in `/json/list` are not the ones that pass asked (`shellSignature`: same pages, same order, same addresses), the browser target, on one DevTools socket kept open between looks, says (`Browser.getWindowBounds`, which the browser process answers alone) the window is not `normal` at the row's size, or any of that cannot be answered — a dead socket is dropped and the next shortcut opens another — and at least every 30 s regardless, counted on `performance.now()` (a wall clock stepped back held the full pass — the shortcut's safety net — off for the step's length): `createWatcher`, `FULL_PASS_MS`; so the steady state costs the desktop's own page nothing, no session attached to it and no script run in it, while a monitor plugged in or a window Chrome put back maximized is still fixed in the same look), pages it opens as native Chrome windows above it, `IntensiveWakeUpThrottling` in the launcher's one `--disable-features` list (the window can be hidden — minimised or covered — and the notice ring must still be read every 2 s, see `visible-interval.ts`; the watchdog's re-launch uses the same flags), the shelf margin on the main monitor only (from `data/monitors.json`'s `applied`; every output while mirrored). The owner's own additions live in `~/.config/clawbox-desktop/`: `keybinds.xml` (`<keybind>` elements spliced after the session's own; left out while it is not well-formed) and an executable `autostart`. `install-guake.sh` (run by the session installer unless `--no-guake`) adds the drop-down terminal there: Guake on Win+Down in the ClawBox Terminal's look (`kiosk/guake/`: its dconf settings, and a GTK stylesheet scoped to `#guake-terminal` for the dark tab strip and scrollbar).
- **`scripts/perf/desktop-perf.mjs`** — the desktop's performance suite: drives the LIVE desktop over its Chrome's DevTools port (idle, pointer sweep, a drag of its own Files window, every app opened and closed) and reports main-thread time, style recalcs, layouts, paints, compositor draws, rAF frame stats, long tasks, per-process CPU and (with `--gpu`, where `intel_gpu_top` carries `cap_perfmon`) GPU busy; `--out` saves a run and `--compare a.json b.json` prints before → after. What it found and what fixed it, by cause. A free-running CSS animation makes Chrome produce frames at 60 Hz for as long as it runs, so the mascot's RESTING animations are paused and stepped by a timer (`AMBIENT_FPS` in `Mascot.tsx` — a step only WRITES `currentTime`, to animations looked up once per commit and picked by `animationName`, because reading an animation's state between two writes flushes style: the sleeping crab ran 67 recalcs a second and the power stance 102, about 15 now), the pet sprite and the egg step their frames by timers (`petFrameTransforms`, `EGG_IDLE_STEPS`) rather than CSS animations over `background-position`, the team tree's dashes are stepped the same way (`FLOW_FPS`), and the mascot's walk is a Web Animation instead of a frame loop. Animating a PAINT property is a style recalc and a repaint every frame, so the ClawKeep shield's glow (on the shelf, and the System Update hero while updating) crossfades two static halo copies (`::before`/`::after`, the glyph from `--glow-glyph`) by opacity instead of animating `filter: drop-shadow`, the ClawBox AI offer shield's ring and the recording microphone's are discs that scale out from under them instead of an animated `box-shadow`, and the indeterminate progress bar (ClawKeep, the App Store) is two fixed-width pieces that only translate. Chromium cannot redraw part of a `backdrop-filter`: a change under ANY pixel of a blurred surface re-blurs all of it, at the rate the change runs — 1920×162 of damage a frame for a resting crab whose feet reach into the shelf, 1920×56 at 60 Hz for the shield's pulse — so the shelf is a flat `rgba(17, 24, 39, 0.8)` (and so is the kiosk bar over the desktop; the phone bar, which the icon grid scrolls under, is 0.93 — see `ChromeShelf.tsx`), the launcher and power-menu panels went from 0.95 with a blur to 0.98 without, every full-screen scrim dropped its blur and went one step darker (60→65%, 70→75%, 85→90%), and the opaque menus lost a blur nobody could see. A dragged window moves by a compositor offset on a layer of its own: the offset is the `translate` PROPERTY, not `transform` — the open and restore animations hold `transform` with fill-mode forwards and an animation outranks an inline style, so a window grabbed while still opening did not follow the pointer and then jumped, and `translate` composes with them — and `will-change: transform` is taken at the first move that actually moves the window, not at the press, so a click on a title bar promotes nothing; both are cleared on mouseup, touchend and touchcancel. The desktop root re-rendered every window, the chat and the mascot for any change of its state, so each window is a memoised `DesktopWindow` handed stable per-window callbacks over `memo(ChromeWindow)`, the launcher (with `launcherApps` and `openAppStable`), the tray, the toast host, the power prompt and the tier celebration are memoised, the clock is a store of its own (`use-desktop-clock.ts`), a poll that answers what is already held keeps it (`desktop-shell-equality.ts`, `same-plain-data.ts`), and the icon drag and the rubber band write styles directly rather than through state. Every gesture that moves the page outside React — a window's drag, the chat's drag and its two resizes, the icon drag, the rubber band — takes a pointer or touch the SYSTEM cancels (an edge swipe, a palm, a call coming in) as an end of its own — unhandled, a cancel left the moved DOM and React's state apart and the listeners armed, so the next touch anywhere went on with the gesture — and none snaps on it, since the owner never let go: a window ends where it stands; the chat's drag commits the place it stands (which is also what keeps its window-size listener, reading `pos` null, from writing the anchored `left` over a dragged `top`); its floating resize, with no snap to leave out, ends as a release — the size on screen, remembered; the docked panel keeps the width the last move wrote and tells the desktop, so the strip reserved beside it agrees; a dragged icon glides HOME, from where the last move put it (a cancel promises no point) to the cell React still has for it — an icon has no place outside a cell, and a drag-and-drop called off puts the item back — and a cancelled hold opens no long-press menu (so iOS is given no cause to cancel one: the icon's button carries `-webkit-touch-callout: none` and its picture is `draggable={false}`); the rubber band comes down, its selection already made on the moves; and a cancelled press on the mascot (`handlePointerCancel`, also on `lostpointercapture`, which a normal release fires too after `pointerup` and then finds nothing to do) is never a tap — moved, it is dropped through physics as a release drops it; held off the ground (caught mid-throw, or on an icon) it finishes its fall; otherwise the loop it interrupted comes back, the next action or, asleep, the nap's own end — and its picture is `draggable={false}` under `-webkit-touch-callout: none` for the same iOS reason. What an idle desktop asks the box is in `visible-interval.ts`, `use-clawbox-login.ts`, the shelf's shared ClawKeep poll, the notice ring (which now also carries power approvals), the monitors GET and `kv-store.ts`; and what it writes to the journal in `scripts/access-log.js`.
