# Settings app

Every Settings section: Providers and the ClawBox AI pitch, Local AI, Harness tiles and the swap dialog, Voice, System (and its Users tab), System Update, About. Read it when you touch `SettingsApp.tsx` or a panel it hosts.

## Frontend (`src/components/`)

- **Background tasks** (`src/lib/background-tasks.ts`, the inventory in `docs/design/background-tasks/INVENTORY.md`) — long work Settings starts that must not care whether Settings is open. A task is a promise of the web server, never of the request: its record (weighted steps, headline, byte progress, a 200-line log ring, how it ended) is persisted to `data/background-tasks.json`, a second start in a group with a live task (running OR queued) follows that one, and the starting route answers `backgroundTaskResponse(id)` — the same NDJSON every install route spoke (`{status}`, `{completed,total}`, ONE `{success}`/`{error}`), whose first line names `taskId`. On it: the llama.cpp, Whisper-engine and Kokoro installs, the memory-model download (`embed/install`, whose "Download again" moves the old copy aside and puts it back if the new one never arrives) and the Whisper size download. Work that can stop safely says `cancellable` and honours `ctx.signal` — `POST /setup-api/background-jobs/tasks {id, action:"cancel"}` (a person's browser, same origin) ends it `cancelled`, never `failed`; only the size download is, by SIGTERM to the fetcher's process group. A root step is followed through `ctx.rootStep(step, {finishes})`, which records the run (step, dispatch time, systemd `InvocationID`), so a web server that restarts mid-step ADOPTS the task and follows the same unit to its real ending (`followRootStepRun`); an adopted run ends well only on systemd's own word for its invocation (PID 1's `INVOCATION_ID=` lines; a run from another boot, or one systemd said nothing about, closes `interrupted`), and what a kind does at its ending whoever sees it lives in `src/lib/background-task-finishers.ts` (the memory model: check it is there, settle the aside copy, stop the embedder); a kind with no hooks closes on `finishes`, else `interrupted`, because the work after the unit died with the old process. A reader whose stream is cut short after naming its task follows it again (`readTaskStream`, about 2.5 min of backoff) rather than calling it failed. The progress view is ONE component, `BackgroundTaskProgress.tsx`: the desktop's corner card (`BackgroundTaskCards.tsx`) draws it, and so does Settings inline under the control that started it (`BackgroundTaskInline`: the Local AI rows, the memory-model card, the Whisper size rows, the Voice tab's repair). Every one of those re-attaches on mount — `findRunningBackgroundTask([kind])`, then `followBackgroundTask(id)` through the reader it already had — and a card that unmounts stops READING (`useStreamedInstall` aborts its stream), never the work. Strings `backgroundTasks.*`, all ten locales. **The install queue (TASK-2128):** every Install is accepted at once — no `busy` refusal for "another install is running". A spec may name `lanes` and `needs` (`src/lib/background-task-queue.ts`, `decideQueue`): a task that shares a lane with running work, or with one queued ahead of it, or that the box lacks the memory/disk for beside what the running work said IT needs (MemAvailable, `statfs`, the 512 MiB disk reserve; with nothing running it always starts), is created `queued` with `queuedBehind` (the task it really starts after: the nearest one ahead in its lane, else the running one) and `status` "Queued — starts after <label>"; `pump()` starts the next one whenever a task ends (done, failed, cancelled, interrupted), in the order pressed. Local AI's lanes are `src/lib/local-ai-install-queue.ts`: Kokoro, the Whisper engine and Gemma share `local-ai-system` (each a root step pip-installing into the clawbox user's site, a CUDA build, a write of the agent's config), the Whisper engine and every size download share `whisper-cache`, the memory-model download holds none. A queued task is LIVE everywhere (`isLiveBackgroundTask` / client `isLiveTask`): followed, drawn (its own corner card, `schedule` icon, no close button), never pruned or dismissed, and always cancellable — Cancel ends it `cancelled` at once and the one behind it moves up. Its stream's lines carry `queued: true, behind: {kind, label}`, then `queued: false` when it starts; the Local AI row keeps that as a fact and says it at render time (`queuedLine`). The closure of a queued task lives in the registry's `specs` map; a restart finds the record still `queued` and REBUILDS the work from its kind and `meta` through `src/lib/background-task-starters.ts` (which is why each install's work lives in a lib module — `kokoro-install.ts`, `whisper-install-tasks.ts`, `embed-install-task.ts`, `llamacpp-install-task.ts` — never in its route); a kind it cannot rebuild closes `interrupted` with `QUEUE_LOST_MESSAGE`. `src/instrumentation.ts` calls `resumeBackgroundTasks()` at boot, so adoption and the queue move on with no browser open. `ctx.waited` says the work sat in the queue: the Whisper installs measure the disk again then. Root-step plumbing — su's and PAM's session lines, sudo's command log, systemd's own unit lines (`src/lib/journal-noise.ts`) — is never a headline or a failure reason: `followLoop` shows the newest line that is not noise and hands the rest to `onLog`, and `ctx.status` demotes any to the log. Running work with no Cancel says "This step can't be stopped half-way" where the button would be (`backgroundTasks.notCancellable`).
