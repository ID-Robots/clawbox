# Updates, install and system integration

The in-app update (routes, lock, resume, what's new), `install.sh` steps, systemd units, root steps and the root-exec mirror, the setup AP and the production server. Read it when you touch `update/*`, `updater.ts`, `install.sh`, `config/*.service`, a root step or `production-server.js`.

## Setup API Routes (`src/app/setup-api/`)

- **Update**: `update/run`, `update/status` — git-based system updates. `update/run` starts the update for a person's click (or the first-boot wizard); the agent's MCP bearer gets 202 `pendingApproval` instead and the update runs only after the owner's Confirm, as on the chat path `update/request` (MCP `update_run`); `update/openclaw` refuses the bearer with 403. The on-device tests start an update as the owner (`board_owner_api` in `scripts/nano-tests/lib.sh`). The lock holder (`update-lock.ts`) records the STEP the run is on at every boundary, so a run cut short is reported by `resumeContinuation` as "the box restarted — or lost power — while "X" was running" (holder from another boot) or "the web server was replaced while "X" was running" (same boot), with the step list showing where it stopped and `update_interrupted_detail` `{cause, step}` written beside `update_interrupted_at`; a fresh `startUpdate()` then CONTINUES from that step (`resumeFromInterruption` → `interruptedStepIndex`); the network probe comes BEFORE the record is cleared, so a resume refused for want of WiFi keeps its position; the run's persisted warnings travel with it — and the failed panel's **Resume update** button (`update.resume`, or `update.startAgain` when no step is known; all ten locales; `onResume` on `UpdateProgressCard`, offered only for a verdict that starts with the prefix) is the gesture that starts it. Dismiss takes both records so the next run starts from the top, and a record with no stamp resumes nothing. The holder also carries `failed` — the non-failFast steps the run had walked past as failed — so the verdict keeps them red and the resume starts no later than the first of them, never painting a failure green. The list carries no `performance_mode` step (off since 2026-09-17, owner's ruling — the update leaves the power profile alone) and no `verify_build_identity` step (off the same day: it compared HEAD to the build's stamp AFTER `post_update`, whose bootstrap self-refresh `reset --hard`s the checkout to `origin/<branch>`, so a commit pushed mid-update failed a run that was fine; install.sh's `do_rebuild` still runs `scripts/verify-build-identity.sh` right after `bun run build`, and CI runs it on every PR). `step_openclaw_install` opens with `recover_parked_openclaw_core`: a promotion cut short between its two renames leaves the old tree at `lib/node_modules/.openclaw-previous` and no live tree, and that is put back before the core is probed (a present live tree instead drops such leftovers); the promotion checks every launcher move by hand because it is called as `… || return 1` (errexit off in its body), and the `--version` gate refuses a launcher that answers NOTHING whatever the target, comparing the version only for a numeric pin. The assistant-down sentence covers `openclaw_install`, `openclaw_patch` and `gateway_setup` (`ASSISTANT_DOWN_STEP_IDS`): the first stops the gateway and leaves it stopped, the last is what starts it again when openclaw_install left it stopped (a gateway still running is left to `gateway_verify`: `gateway_setup_restart_wanted`). `gateway_verify` then starts a gateway the update's own quiesce stopped with one plain restart (its unit's ExecStartPre), unless the doctor verdict in `data/openclaw-migration-status.json` does not cover the installed core or is over 30 days old, the gateway journal names a blocker or says nothing, or the unit is not cleanly stopped; it takes the full repair (pre-start outside the unit, plugin repair, `doctor --fix`, which records a fresh verdict when it completes and marks the recorded one due when it does not) in those cases, and after that start when it does not come up, when the chat is not served, or when that run's own journal (`_SYSTEMD_INVOCATION_ID`, read once the chat has answered) names a blocker or cannot be read; every way in logs `running the full repair: <gate>`, and a gateway still on the run gateway_setup left (`/run/clawbox/gateway-left-running`) is restarted the same plain way. Every verdict starts with `INTERRUPTED_MESSAGE_PREFIX`, which is what `isInterruptedVerdict` recognises. `step_openclaw_install` STAGES the core: `npm install -g` into `$NPM_PREFIX/.openclaw-stage`, the `--version` gate on the staged launcher (it must answer, and answer the pinned version — a zero-length launcher answers nothing with exit 0), then `promote_staged_openclaw_core` flushes the stage (`flush_core_to_disk`, `sync -f`), renames the live tree aside, renames the stage in, moves the launcher links, flushes again and drops the old tree — because a global npm install has no core on the box for its whole length, and on 2026-09-16 the boxes stopped seconds after npm exited 0 and were left with 5,346 zero-length files in a complete tree (ext4 delayed allocation), `openclaw.mjs` and `package.json` among them.
- **What's new**: `whats-new` — the desktop's "What's new in 4.3" card (`WhatsNewCard.tsx`, `use-whats-new.ts`; TASK-1059, re-keyed for 4.1 by TASK-1195 and for 4.2 and 4.3 the same way). POST `{ release: "4.3" }` records the dismissal in the box's store, so it holds on every browser; a tab still showing the 4.2 card posts `"4.2"` and is refused 400, so it cannot dismiss 4.3 unseen. Same-origin only, and the body is bounded. The docs link (`WHATS_NEW_DOCS_URL`) and the UTM-tagged portal link (`WHATS_NEW_PLANS_URL`) are one constant each. The card's highlight keys are `WHATS_NEW_HIGHLIGHTS` in `whats-new.ts`, shared with `/updating` (below).
- **Update what's new**: `update/whats-new` (TASK-1205) — GET, read-only, never a 500: the version the running update installs and the Highlights of its notes, for the "What's new" panel beside the update screen's step list (`UpdateWhatsNewPanel.tsx`, `use-update-whats-new.ts`, `src/lib/update-whats-new{,-server}.ts`); that screen (`UpdateRunView`, so the System Update window, Settings → System Update and `/updating` alike) draws a target on the release line this build's catalogue describes from that catalogue, whatever the answer's source (read notes too: they are English text without pictures, the catalogue is the same release in the owner's language) — beside its steps as the release's showcase (`UpdateWhatsNewShowcase.tsx`, TASK-2121: every catalogue highlight one at a time over its `fullImage`, a live demo in the screenshot's own % space, chips, ←/→, a 7.5 s auto-advance held on hover/focus, prefers-reduced-motion, every picture loaded once when it is drawn so it keeps working while the box restarts; narrow — under 704 px of its own, as on a phone or in Settings' 672 px pane, or on a viewport under 1024 px wide or 501 px tall (`SHOWCASE_NARROW_PX`, `SHOWCASE_COMPACT_VIEWPORT`) — the text sits over a taller stage (1:1 on a phone, 4:3 up to the two columns) on which the screenshot is drawn 880–960 px wide and panned to each demo by a camera of its own (demo text 10–11 px, its toasts a band across the stage's foot), the text is sized by the longest title and body so the stage stays put, the chips are one sideways-scrolling row under a thumb (wrapped with a mouse), a swipe turns it and a tap holds it, and `UpdateRunView` puts it under the steps on a phone held sideways), beside a failed run as one card; notes for another line are cards without pictures. The version is the package.json of the ref the updater hard-syncs to (`resolveUpdateBranch` → `origin/<branch>`, read with `git show`, never a fetch — root is fetching and resetting that checkout during the run), or the checkout's own once THIS run's `bootstrap_updater` has completed; the notes are `RELEASE-NOTES-<version>.md` at that ref, then in the checkout, then the GitHub release body for `v<version>` (5 s timeout, asked at most once a minute per version after a miss), all through ONE parser (`parseReleaseHighlights` in `src/lib/release-highlights.ts`: the `## Highlights` section's top-level bullets, plain text, capped at seven). An answer read from notes is cached in `data/update-whats-new.json` keyed by version, so the server that comes back after the rebuild has it; `update/run` fires `prefetchUpdateWhatsNew` (never awaited) the moment an update starts. `source: "none"` is drawn by the CLIENT as this build's own localized `WHATS_NEW_HIGHLIGHTS` when the target is on `WHATS_NEW_RELEASE`'s line — decided against the client's constant because the page outlives the server that answered it — else one generic line and the release page; the panel is never empty and never delays the status poll.
- **The update screen (TASK-2111)** — ONE screen from the click to the desktop. The System Update app (its window and Settings → System Update) and `/updating` both draw `UpdateRunView` and follow the run with `useUpdateRun` (`src/components/UpdateRunView.tsx`: the status poll, adopt, start/Resume, dismiss, reload on the first answer that names the run after an outage). `/updating` calls it with `hold`: it asks at once and keeps asking whatever the box answers or fails to, never gives up on `idle`, and leaves for `/` only on a `completed`/`idle` answer WITHOUT the middleware's `x-clawbox-update-lock` header — "Update complete" for 3 s first — so it cannot bounce off a desktop the middleware would send straight back. While the box does not answer, the view keeps the last progress but says the device is not answering and hides the running step's last log line.
- **Weekly update check (TASK-2260)**: `update/weekly-check`, `update/chat-command`. Every Monday at 10:00 on the box's clock plus a fixed per-box jitter of up to an hour (`src/lib/update-notice-schedule.ts`), the box runs the updater's OWN check (`getVersionInfo` with the cache dropped) and, when the branch it follows has something newer, tells the owner ONCE per version (`lastNotifiedTarget` in `data/update-notice.json`): one Telegram message on the box's own bot (the harness's token, read by `readActiveTelegramBot`, Bot API on both editions because `hermes send` carries no buttons) with the version, up to three Highlights from `readUpdateWhatsNew` and an inline **Update** button; with no bot or nobody reached, a desktop notice (`notifyOwner`, `OPEN_UPDATE_SETTINGS`). Nothing newer: nothing is sent. A week is settled by name (its Monday's date), so a restart never checks twice and a box that was off across the slot checks once at its next start that week (`BOOT_DELAY_MS` in, `src/lib/update-notice-scheduler.ts`); a check that could not reach the remote retries hourly inside the week. Words in the box's language (`updateNotice.*`, edition-translations). `update/weekly-check` is the owner's switch in Settings → System Update (GET for any session; POST `{ enabled }` owner-only, the bearer is refused; ON by default, config key `update_weekly_check`, read when the slot fires). `update/chat-command` takes `/update` and the button's tap from the harness hooks (`update-commands.mjs` `before_dispatch` on OpenClaw, where a tap arrives as the synthetic message `callback_data: clawbox-update`; `update_commands.py` on Hermes — `pre_gateway_dispatch` for `/update` and a `register_telegram_handler` callback handler scoped to `^clawbox-update$`, because Hermes drops callback data it has no handler for). The route REQUIRES the bearer, weighs the sender against the arriving harness's Telegram allowlist in the owner's private chat only, and answers after it has replied to the hook. A stranger is claimed and refused on OpenClaw (where the core's own sender check normally stops him first); on Hermes he is handed back (`outcome: "not_owner"`) to Hermes' own auth, which refuses him before any command runs — claiming him left Hermes' typing indicator running in his chat. The button only ASKS: an owner's tap is `requestPowerApproval("update")` — the question `update/request` asks for the bearer — and the update runs only on Confirm (desktop or approvals bot). Both hooks fail CLOSED for `/update`: each harness has its own `/update` that would update the harness underneath ClawBox's pin. Lab boards: `CLAWBOX_TELEGRAM_API_ROOT` (loopback only, `telegram-owner-send.ts`) points ClawBox's sends at a local Bot API stub, and `CLAWBOX_UPDATE_NOTICE_BOOT_DELAY_MS` shortens the catch-up delay.

## Server Libraries (`src/lib/`)

- **`updater.ts`** — multi-step system update orchestration (internet check → git fetch → checkout → build → restart). Its version check (`getVersionInfo`, behind `update/versions`) is two git round-trips to origin (the tag `ls-remote`, the pinned branch's fetch) plus the release-remote check, run in one concurrent round except that the pinned branch's fetch follows the `ls-remote` (two anonymous requests in a row, not a burst). There is deliberately no `git fetch --tags origin`: nothing reads local tags, and that fetch (every branch plus every tag's history) put its 20 s timeout in front of `/setup-api/update/status`, which the setup wizard's update step waits on; an answer that saw origin is cached for `VERSION_INFO_GOOD_TTL` (30 min — the desktop asks every 30 min and each open Settings tab asks too, and at the old 60 s TTL nearly every poll paid the 1.6–2.3 s), a refusal for `TARGET_VERSION_CACHE_TTL` (60 s), and `?force=1`, a finished update or a change of the update branch (`system/update-branch`) drops both (`invalidateVersionCache`). Its OpenClaw half follows the step list's own predicate (`openclawIsAbsent`, which drops `openclaw_install`): on `openclaw` and on `dual` — whichever harness is active, since a full update keeps both at their pins — it reports the core and the pin; on `hermes` it is `{ current: null, target: null, updateAvailable: false }` even when a Settings → Harness swap from OpenClaw left the old core on disk, because no update touches that core and the swap back installs and doctors the pin first. The desktop's "Update available" card and System Update both ask `shipsOpenclaw` (`src/lib/version-utils.ts`) before naming OpenClaw. The payload reads the edition lock once per answer, and the cache answers only for the edition it was made on, so a harness swap is a miss at once.
- **How an update ends (`step_rebuild_reboot`)** — a reboot only when something needs a boot (owner's ruling 2026-11-04, after the closing reboot hung a box for 12 h). `update_reboot_reasons` prints one reason per line from exactly three signals: Ubuntu's `/var/run/reboot-required` (+ `.pkgs`; the L4T kernel, initrd and bootloader postinsts set it on a JetPack upgrade, as libc6, systemd, dbus, libssl3 and network-manager do), `/boot/{Image,initrd,extlinux/extlinux.conf,dtb/*}` with a ctime after `/proc/stat` btime (ctime, because dpkg restores the archive's mtime) or a `uname -r` with no `/lib/modules/<release>`, and the ClawBox marker `/run/clawbox/reboot-required` (no update step writes one today). It is asked after the redeploy and before `do_rebuild` (a reason means `--reboot-follows` + `reboot`), and once more after the build on the restart arm. With no reason `restart_services_after_update` restarts every ACTIVE `clawbox-*` service and starts every ENABLED one that is not running (what the boot did), each in one `systemctl --no-block` call, proved by active + a new InvocationID that is still the same after a settle (`ENGINE_SETTLE_S`) — every unit gets that settle look however the wait ends — within `CLAWBOX_RESTART_WAIT_S` (90) seconds of one-second looks plus settles, never the clock, except `clawbox-gateway` (post_update quiesces it, gateway_verify starts it), `clawbox-root-update@*`, boot-time one-shots, and `clawbox-ap`, which is never started and restarted only when it runs and `ap_sources_changed` (git, from the replaced build's stamp) says its unit or scripts changed, and then queued after `clawbox-setup` (which is `After=` it) and proved by `step_post_update` (`report_update_ap_restart`, from the invocation kept in `/run/clawbox/update-ap-restart`; `CLAWBOX-WARN[ap-not-restarted]` otherwise), because `ap-watchdog.sh` stands down once setup is complete; `clawbox-performance` is restarted to re-apply the profile, the Hermes gateway goes through `hermes_gateway_refresh_after_install 1`, and `clawbox-setup` restarts last, resuming the continuation. The units that do not come back are ONE `CLAWBOX-WARN[service-not-restarted]` naming them all (the updater keeps one card per code), kept with one `CLAWBOX-WARN[engine-not-resumed:rebuild]` for the engines `resume_paused_engines` could not bring back (`ENGINE_NOT_RESUMED`) in `/run/clawbox/update-restart-warnings` and re-stated by `step_post_update` (`relay_update_restart_warnings`), because nobody reads the rebuild step's journal. Test mode is unchanged: no decision, `clawbox-setup` restart. Tests: `install-update-reboot-decision.test.ts`.
- **Harness downgrade guard (`harness-downgrade.ts`, `harness-downgrade-backup.ts`)** — a switch that would install an OLDER OpenClaw or Hermes than the one that wrote the box's data is refused before anything changes. For example, OpenClaw 2026.10.6 moves agent databases to schema 25 and 2026.10.3 refuses them, so a beta → main switch used to leave the gateway stopped. `assessHarnessDowngrade` is pure and refuses only on proof:
  - a database newer than the target declares (`OPENCLAW_STATE_SCHEMA_BY_VERSION` and `OPENCLAW_AGENT_SCHEMA_BY_VERSION` in updater.ts, both held to the published package by `harness-contract`; `readAgentSchemaVersions` in openclaw-state-store.ts);
  - an OpenClaw pin numerically older than the installed core;
  - a Hermes pin older by release name or by `merge-base --is-ancestor`.

  The guard runs in four places:
  1. the `system/update-branch` route answers 409 `code: "harness_downgrade"` and keeps the pin. When clearing the pin would fall back to an older branch, it writes the pin back;
  2. `runUpdate`'s pre-flight (target pins read off `origin/<branch>` by `readPinsAtBranch`, Hermes only when the run syncs) sets `UpdateState.errorCode`/`downgrade`. The pre-flight asks again at the `openclaw_install` boundary;
  3. install.sh's `harness_downgrade_guard`, asked twice, each time after a fetch and before a reset. First in the bootstrap block at the top of the file: its `reset --hard origin/<branch>` and its re-exec of the target's own install.sh come before anything else a run does, and an older branch's install.sh has no guard. That covers a bare `sudo CLAWBOX_BRANCH=main bash install.sh` and a dispatched update step whose pre-flight could not reach origin. Then again in `sync_repo_to_update_target`, for runs the bootstrap does not refresh. The constants are not parsed yet in the bootstrap, so the guard takes the checkout, the clawbox home and the edition as arguments;
  4. `openclaw-db-maintenance.py preflight` before the staged core is promoted. On a newer database it exits 3, the stage is dropped and the gateway restarted.

  `SystemUpdateApp` localises the refusal from the detail (`update.harnessDowngrade.*`, ten locales). The override is `allowHarnessDowngrade: true` on update/run or update-branch. It backs up first (ClawKeep `runBackup` when paired, else `openclaw backup create --verify --no-include-workspace` / `hermes backup` into `~/clawbox-harness-backups/<stamp>/`), then writes `data/harness-downgrade.json` (versions + backup dir, 12 h). For exactly that core, the helper moves the newer databases into `<backup>/openclaw-newer-schema/` and the older core starts fresh. Every run clears that file before its pre-flight, and an override run writes its own after its backup. The guards act on version proof only while the harness has a database on disk (OpenClaw state/agent, Hermes `state.db`): with none, there is nothing an older version could fail to open. The upgrade e2e relies on this when it moves `~/.openclaw` aside to build its main baseline.

## System Integration (`scripts/`, `config/`)

- **OpenClaw fast path (`openclaw_refresh_fast_path_check` in install.sh)** — `step_openclaw_install` returns before stopping the gateway only when the core answers the target, every ClawBox-managed plugin (`@openclaw/*` ones at the target, `clawbox-email-directives` at the checkout's copy) is at its version and `plugins list --json` reports no error, orphan or consent diagnostic, no plugin repair is open in `data/plugin-repair.json`, `OPENCLAW_REFRESH_MARKER` (`/etc/clawbox/openclaw-refresh`, written at the end of a finished full path and dropped as one starts) records the target, and `clawbox-gateway.service` is active/running and listening. Anything else is the full path, unchanged; one `OpenClaw refresh: fast path (…)` / `full path (…)` line says which and why. Never inside `step_openclaw_setup`. Force: `CLAWBOX_FORCE_OPENCLAW_REFRESH=1`. The update quiesces the gateway before `openclaw_install`, so `runUpdate` first dispatches `openclaw_install_fast` (step def `fastPathStep`, `rootStepTookFastPath` in updater.ts) with the gateway up: it takes the fast path or changes nothing, and only its own fast-path journal line skips the quiesced full step. The OpenClaw-only update (repair) never asks it.
- **Schema migrations and free disk (`openclaw_migration_disk_preflight` in install.sh)** — `step_openclaw_install` asks `scripts/openclaw-db-maintenance.py preflight` (as the clawbox account, the script handed to python on stdin) whether the disk can hold the migration the core brings: the STAGED core's `openclaw.schemaVersions` against each database's `user_version`, six times the databases it would migrate plus 1 GiB (the 9.x -> 10.x migration of a ~10 GB box needed 30-56 GB). A refusal (exit 3) comes before the promotion — the stage is removed, the gateway is started again on the core it had, and the step's `Error:` line is the helper's sentence with both sizes — and a core already at the pin is asked again before `doctor --fix` (refused there, the gateway stays stopped, as for any migration blocker). Doctor's verdict is recorded with `record-doctor`; both land in `data/openclaw-migration-status.json`, which the gateway pre-start refreshes at every start (see harness-openclaw.md). The updater's wait for `openclaw_install` on the appliance grows with the OpenClaw databases (`openclawInstallTimeoutFor`: 5 min + 5 min per started GiB, capped at the desktop's 110 min under the root unit's 7,200 s ceiling): with the flat five minutes a 40-minute migration was reported failed while it ran on, and the gateway came back with every agent degraded. `gateway_verify` and `gateway_restart` end with `warnIfOpenclawDatabasesDegraded`, so an update over agents the migration did not reach says so instead of a green Completed.
- **The fast path asks doctor's record too** — the refresh marker proves the full path FINISHED for the target, not that nothing moved under the core since: the start guard puts back a pre-update copy of a database the core refused, and a restore brings older ones, so a database can be behind the core's schema while the marker still names the target, and only the full path's `doctor --fix` migrates it. So on an OpenClaw 2 target `openclaw_refresh_fast_path_check` also requires `data/openclaw-migration-status.json` (read as the clawbox account, right after the marker and before systemd and the plugin list) to name the target as `doctor.core` with `doctor.verdict` `complete`, and as `core` with `state` `ok` (no database behind or newer, no incomplete doctor, no blocked preflight). A missing, unreadable or stale record is doubt: the full path runs, `record-doctor` writes the record, and the next update takes the fast path. An OpenClaw 1 pin (no doctor on its full path) is not asked. Suite: `install-openclaw-fast-path.test.ts`.
- **The llama.cpp pin (`step_llamacpp_runtime` in install.sh, TASK-2166)** — every box runs llama-server built from `LLAMACPP_COMMIT`, and the in-app updater's LAST step (`llamacpp_runtime`, after `gateway_verify`/`hermes_edition`, not on either kind of PC) is what moves a box that already has one: the old gate rebuilt only a missing or CPU-only binary, so boxes kept whatever they were born with through every pin move (a field box on May's build could not start its memory embedder). The record is the binary's own `--version` short hash (probed as clawbox, never root — its libraries are clawbox-writable; `ldd` runs as clawbox too), not a stamp file. A rebuild never touches the live tree: cmake bakes an absolute RUNPATH, so the source build goes into `~/llama.cpp/build-<commit12>-<cuda|cpu>` (fetched by commit from the URL — a shallow or `git init` checkout reaches it too — and no "build whatever is checked out" fallback), a prebuilt is staged as `build.clawbox-next` and swapped with the live `build/` only once it reports the pin; `activate_llamacpp_server` renames the copy over `/usr/local/bin/llama-server`, proves the INSTALLED copy starts and puts the previous one back if not, and only then are the unreferenced trees pruned and a failed `clawbox-embed.service` reset. A box that could not rebuild keeps its working binary and says so with `CLAWBOX-WARN[llamacpp-not-rebuilt]`; the step fails only when no llama-server that starts is left. One build at a time (`flock` on `/run/lock/clawbox-llamacpp-build.lock`, shared with `llamacpp_install`), one compile job per GiB available, no clock limits. Tests: `install-llamacpp-runtime.test.ts`. The pin moves only with the chat server's load mode: newer llama.cpp (5f490d7 among them) defaults to `auto`, which pins ~2 GB of the model in host memory on an Orin, so install.sh seeds `LLAMACPP_LOAD_MODE=mmap` into a Jetson's `.env` (never on a PC) and `scripts/start-llamacpp.sh` passes a value every pinned build accepts as `LLAMA_ARG_LOAD_MODE`, falling back to `mmap` on a Jetson (`/etc/nv_tegra_release`) when the key is missing, empty or refused — never `LLAMA_ARG_*` in `.env` itself, which `clawbox-embed.service` loads too (`llamacpp-speculative-decoding.test.ts`). An update swaps the binary but leaves a running chat server on the old one until it next starts.
- **`scripts/start-ap.sh`** / **`scripts/stop-ap.sh`** — create/tear down WiFi AP "ClawBox-Setup" on `wlP1p1s0` at `10.42.0.1/24`
- **`scripts/setup-optimizations.sh`** — Jetson GPU/memory tuning. Swap is TWO tiers since 2026-09-06: the board's stock `nvzramconfig` zram (one compressed device per core, half of RAM, priority 5 — a compression ratio, never capacity, since its pages live in RAM: measured 1.12 GB of pages in 0.35 GB, 3.47x) and `install.sh`'s `step_swapfile`, which puts an 8 GB file on the disk at priority 1, records it in `/etc/fstab` and runs on fresh installs (`step_system_config`) AND in-app updates (`step_post_update`). Priority 1 is the point: the kernel fills zram first and the file stays at 0 bytes until something genuinely large arrives — the case that killed an owner's update build on 2026-09-05 (OOM at 4.6 GB resident with the desktop session up). It is idempotent, adopts an existing `/swapfile` without re-making it, falls back to 4 GB and then to nothing when the disk cannot spare the room (`CLAWBOX_SWAPFILE_SIZE_GB`, `CLAWBOX_SWAPFILE_RESERVE_GB`), stands down in test mode because a container cannot `swapon`, and never fails the install. The Jetson power profile (`scripts/clawbox-power-mode.sh`, applied by `config/clawbox-performance.service` at boot and by `step_performance_mode` on a full install — never by an in-app update, which leaves the profile alone since 2026-09-17 and lets its closing service restart or reboot apply it again) is PERFORMANCE by default since 2026-09-15 — the pinned `nvpmodel` MAXN + `jetson_clocks` that TASK-455 measured at 7.21 W / ~58 C idle and 74.8 C median Tj under sustained 3B inference — with balanced as the owner's opt-out in Settings → System → Desktop & Power, and `store_clock_state` refusing to snapshot clocks that are already pinned, so an update over a box the pre-TASK-455 unit pinned cannot leave `--balanced` restoring the pinning.
- **`production-server.js`** — Node.js HTTP + WebSocket proxy wrapper (Bun doesn't support `http.Server` upgrade events) ; it also loads `scripts/proxy-peer.js` (see `auth.ts` above) and the access log (`scripts/access-log.js`: one `[access]` line per request in the persistent journal, `CLAWBOX_ACCESS_LOG=0` turns it off, `CLAWBOX_ACCESS_LOG_STATIC=1` adds the build assets it skips), which FOLDS a repeated poll — a GET or HEAD under `/setup-api/` from the same client and host to the same route with the same query-parameter NAMES (`quietPollKey`, `quietTarget`: the names sorted and each once, the values dropped, so `files?path=a` and `files?path=b` count together — keyed on the whole target, browsing folders or a run's evidence filled the 256-entry table with one-off reads and pushed the desktop's steady polls out of it — while `kv`, `kv?key` and `kv?prefix` stay three calls; the line written still carries its own request's full sanitised target) is written the first time and then once every `QUIET_REPEAT_LOG_MS` (10 min) with `quiet=N` for the repeats left out in between, while an error, an abort or an answer that took `QUIET_MAX_DURATION_MS` (1 s) or more is always written, and so is the first quiet answer after one — because an idle desktop's polls had been ~110 lines a minute, 97% of the unit's journal, pushing real diagnostics out of its 200 MB cap within days (`CLAWBOX_ACCESS_LOG_POLLS=1` writes every line again). No WRITE is folded: `POST /setup-api/kv` was, for the mascot's position save, but the same POST is how `ui_notify`, `clawbox notify` and a web app's KV-bridge save arrive, only the body tells them apart and the logger never reads a body (it observes; reading the stream would compete with Next for it), so the fold hid agent actions behind a count — a KV save is a line, one per settled mascot move. A count no later line will carry gets a line of its own, `[access] - GET /setup-api/kv?key - ip=… host=… quiet=N` (`formatQuietCountLine`: `-` for status and duration, so it reads apart from a request, and the request named as it was counted): when its entry is evicted to make room (`MAX_QUIET_KEYS`, written just before the line that took its place); on a sweep every `QUIET_REPEAT_LOG_MS` of the entries nobody has ASKED for in a whole window (judged on the last ask, not the last line, or a poll still going was split in two whenever the sweep landed between its window and its next repeat — a stopped one's count lands one to two windows after its last request; the timer is `unref`'d, armed by the first entry and stopped when the table empties, so a box nobody polls gets no wake-ups); and when the server emits `close` (production-server.js's SIGTERM path) or, through ONE process `exit` listener however many servers are attached, when that close outran its grace — never a SIGTERM or `beforeExit` handler of its own, which would be a second say in the shutdown production-server.js owns — so every request is a line or counted on one; and, at MCP-server startup, `mcp/clawbox-mcp.ts` reads `CLAWBOX_MCP_TOKEN` into the api cache and deletes it from `process.env` so a `bash` child cannot `printenv` the device bearer (hygiene, not a boundary: the child runs as the same user that owns `data/.mcp-token`).
- **`config/clawbox-ap.service`** — systemd oneshot service for WiFi AP — it, `clawbox-ap-watchdog.service` (root, fired every 20 s by its timer), the NM failover dispatcher hook, `recover.sh`/`step_recover` and the first-boot VNC unit ExecStart the ROOT-OWNED copies under `/usr/local/libexec/clawbox/` (`install_root_libexec`, which runs at the top of `step_systemd_services` ahead of the unit copy) and load `EnvironmentFile=-/etc/clawbox/network.env` (root-owned, written by `step_network_setup` beside the `data/` copy), never the clawbox-owned tree or `data/network.env`: the tree is `chown -R clawbox` after every update, so a root unit executing or sourcing it was a zero-privilege clawbox → root path (security scan #21 and the #8 residual); `ap-watchdog.sh` takes `START_AP` from `CLAWBOX_START_AP` (default the libexec copy, the WAITER precedent) and keeps `CLAWBOX_ROOT` only for the `data/` files it parses; the tree copies stay for the unprivileged callers (`src/lib/network.ts`, the hotspot route). `clawbox-heartbeat.service` runs as `User=clawbox` for the same reason (its EnvironmentFile is clawbox's own token file). `src/tests/unit/root-steps.test.ts` pins the class-wide rule: no root unit's Exec*/EnvironmentFile under `/home/clawbox`.
- **`config/clawbox-root-step.sh`** ExecStarts nothing under `/home/clawbox` either, since TASK-733. The rule the sweep enforces is a MECHANISM, not a list of verbs: root must never read a byte out of the clawbox-writable tree and then run it — `install` and `cp` into a root-owned path count exactly as much as `exec`, `bash` and `source` do, and are worse, because the copy becomes the file root runs on every later dispatch. `config/clawbox-root-manifest.sh` keeps a root-owned **mirror** of the paths it records — `install.sh`, `scripts/`, `config/` — at `/var/lib/clawbox/root-exec-mirror` (`--mirror`, `--mirror-path`), the dispatcher execs `$MIRROR/install.sh` for EVERY step, and install.sh resolves `scripts/`/`config/` from `$SRC_DIR` (the directory it was started from, `$PROJECT_DIR` on every path but a dispatched step) so the scripts it hands to `bash` as root and the units it installs into `/etc` come from the mirror too. The exempt self-updating family — `bootstrap_updater`, `post_update`, `rebuild_reboot`, all three web-startable — could never be manifest-verified (an update rewrites the recorded files), so what makes them safe is WHEN the mirror is restaged: only from a tree that still matches the record, and `install.sh` may re-anchor that record only when it is itself running out of the tree or has just hard-reset it (`root_exec_may_anchor`). Outside those two moments the record is brought forward but never re-written — a re-write is a second walk of a directory the clawbox account owns, after the `--verify` that authorised it has already returned. The bootstrap's repair of an unanswering manifest helper obeys the same rule: it installs `config/clawbox-root-manifest.sh` into libexec and runs it as root only where root is already executing that checkout. `install_root_libexec` installs the new dispatcher only after the mirror is staged, which is the fleet-rollout ordering — see `docs/root-exec-mirror.md` for what an old-build box does on its first update. `git` over the checkout runs as its OWNER, never root (`use_tree_owner_for_git`), because `.git/hooks` and `.git/config` are clawbox-writable and git executes both. `src/tests/unit/root-exec-mirror.test.ts` fails if a step joins the exempt family without going through the mirror. `harness_swap` (the edition swap, 2026-09-07) is on `WEB_ROOT_STEPS` — and on `DISPATCH_STEPS`, `ALLOWED_STEPS` and the run-root-step allow-list — and deliberately NOT on `UI_ROOT_STEPS`, which `install/run-step` serves to the MCP bearer, nor in the self-updating family; like `set_timezone` it is VALUE-gated by a file the route writes, `data/harness-swap.env`, read by `read_configured_harness_swap` (a plain file only, `TARGET_EDITION` exactly `openclaw` or `hermes`, `REQUESTED_AT` within the hour; parsed, never sourced), and the sub-steps it re-execs with `CLAWBOX_EDITION=<target> CLAWBOX_ALLOW_EDITION_CHANGE=1` (`hermes_install`, proved runnable BEFORE `edition_lock` flips anything so an unrunnable Hermes leaves a working OpenClaw box, then `hermes_edition`; or `openclaw_install`, proved, → `edition_lock` → `gateway_setup` → `openclaw_patch` with the gateway proved listening by the installer's own `wait_for_gateway_port` — never `openclaw_config`, whose one swap-relevant write, the Telegram bot, is the carry-over's) come out of the mirror like every other dispatch. The boundary is the timezone step's: the capability belongs to the clawbox ACCOUNT — anything running as clawbox can write the file and start the unit — so the value gate is what root checks, and the worst outcome is a swap of the box's edition the owner did not ask for: loud, because the desktop reloads onto the other harness and the card names it, and reversible with the same button.

First, `hand_over_checkout` hands back a checkout with root-owned leftovers whole, with the sync's own `chown -R "$PROJECT_DIR"`. It never chowns by name below the checkout, because a link at `data/` would redirect that chown. - **`config/clawbox-build-heal.service`** / **`config/clawbox-build-heal.sh`** (TASK-1316) — a root oneshot at every boot. It heals the one state the web server cannot leave by itself: a web build that starts root steps in a way the box no longer allows. There are two cases. `stale-build` is a pre-TASK-539 build (plain `systemctl start clawbox-root-update@…`, which only the polkit `manage-units` grant authorises) over a tree that uses the launcher. `root-contract-missing` is a launcher build with no launcher or no sudoers line. A healthy boot compares the build stamp with `HEAD` (git as the tree's owner) and exits. A heal dispatches the PINNED step `heal_build` through the root dispatcher, so it runs out of the mirror, only while the tree matches the record. The step rebuilds from the tree on disk (no fetch, no reset), runs `step_systemd_services`, restarts `clawbox-setup` and only then `step_polkit_rules`. Attempts are bounded: 2 per tree commit and reason, recorded in `/var/lib/clawbox/build-heal.state`. The step is on no launcher or UI list. `step_polkit_rules` keeps the old grant while the build on disk does not contain the launcher path (the same script's `--build-uses-launcher`). It never re-adds the grant. `step_rebuild_reboot` calls it AFTER `do_rebuild`, not before: running it before the rebuild is what stranded a customer's box when that rebuild failed. `startRootStep` throws `RootStepUnavailableError` for a launcher that is missing, not granted or too old. Its message names the one repair command. `scripts/preserve-local-edits.sh` runs before every update reset — the bootstrap block, `sync_repo_to_update_target` (which now also `clean -fd`s) and updater.ts via `src/lib/local-edits.ts`. It saves `tracked.patch` + `untracked/` to `/home/clawbox/clawbox-local-edits/<UTC stamp>/` (newest 5 kept), or to `git stash`. It raises `CLAWBOX-WARN[local-edits-saved]`. If neither place can hold the edits, it refuses the reset. When the newest save already holds every edit byte for byte, it names that save instead of writing another, so one update leaves one save. updater.ts runs the copy its BUILD carries (next.config.ts `env` bakes the text in; `bash -c`), never only the tree's: by the restart step the tree is the update target, which may predate the script. A missing helper never stops an update — with no copy anywhere, the edits go to `git stash`. See `docs/update-launcher-transition.md`, which also carries the manual recovery for a box stranded before this shipped.

The helper installs it to `/etc/apparmor.d/bwrap-userns-restrict` (root:root 0644) and runs `apparmor_parser -r` only when `/usr/bin/bwrap` exists, the sysctl reads 1, `apparmor_parser` exists and no OTHER file under `/etc/apparmor.d` attaches a profile to bwrap (a file of that name that does not open with `# ClawBox: ` is left alone); a byte-identical file is one log line, a refused load is rolled back, and a failure is a warning, never a failed install.
