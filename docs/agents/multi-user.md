# Multi-user ClawBox OS

Linux-account users, session identity, the owner-only default, login, user admin and the per-user Terminal. Read it before you add a route (owner-only is the default) or touch sessions, `/login` or users.

## Multi-user ClawBox OS (TASK-1256)

Every ClawBox user is a real Linux account. The **owner** is the install user (`getSystemUsername()`, now `src/lib/owner-username.ts`), is never stored anywhere and can never be removed; every OTHER user is one entry in data/config.json's `clawbox_users` (`{ username, createdAt, sv }`, parsed by `src/lib/session-identity.ts`) plus one account in the `clawbox-users` group. A box with no entry is the single-user box it always was — no migration, the owner stays the administrator, and `/login` renders the single password field unchanged.

- **Session identity** — the `clawbox_session` payload is `{ exp, gen, u?, sv? }`. `identityFromClaims` (`src/lib/session-identity.ts`, mirrored in CJS by `scripts/session-cookie.js` for WebSocket upgrades, one table tests both) decides who a verified cookie speaks for: no `u` → the owner (every pre-multi-user cookie), `u` = owner → the owner, `u` = a registered user with the registry's `sv` → that user, anything else → nobody. Removing a user drops the entry and re-creating the name mints a new `sv`, so either revokes that user's cookies everywhere; a `session_generation` bump still revokes everyone's. `readSessionClaims` in `auth.ts` returns the verified payload; `createSessionCookie(duration, secret, gen, { u, sv? })`.
- **Every signed-in user gets the owner's desktop** — every built-in and installed app, Files, the browser, the coding agent, the app store, the remote desktop, Prime Radiant, Memory Shard and Settings. `requireSession` and `hasValidSession` admit any signed-in person (the MCP bearer as before); `hasPersonSession`/`personSession` (`src/lib/owner-session.ts`) are the "a person, not the agent" gate the desktop's routes use; `hasOwnerSession` is the strict owner check, kept for the gateway token (`gateway-proxy.ts`). Middleware step 4a' applies `nonOwnerVerdict` (`src/lib/non-owner-scope.ts`), now a DENY-list of the three exceptions: **the owner's chat** (each user has their own, below; the harness consoles that list every conversation — `OWNER_ONLY_APP_IDS` `openclaw`/`hermes`, `/app/openclaw`, `/app/hermes`, the gateway's catch-all pages and `/api`/`/assets`/`/__openclaw__`/`/avatar` — stay the owner's, except `/api/chat/media/outgoing/<own key>/…`), **secrets in clear** (`/setup-api/gateway` with the token; `gateway/ws-config` answers a user `token: ""`, `relayed: true`; public-link URLs carry `tokenMasked`), and **the owner's account** (`system/credentials`, `credentials/verify`, `setup/reset` — `requireSession(req, { ownerOnly: true })`). A refusal is 403 `owner_only` (never 401). Picture paste into the Terminal stays the owner's: a user's shell cannot read the owner's file.
- **Per-user chat** — `src/lib/chat-scope.ts` (CJS copy `scripts/chat-scope.js`): a user's OpenClaw main is `agent:<agentId>:clawbox-user-<name>`, tabs `agent:<agentId>:clawbox-utab-<12hex>-<name>`; Hermes main `desktop-user-<name>`, tabs `desktop-utab-<12hex>-<name>` (id first so a `-` in a name cannot alias another user's key). `mayUseChatKey` holds every chat route to the caller's keys (`chat/history`, `chat/images`, `hermes/chat`, `chat/tabs` — one inventory per person, `data/chat-tabs/<name>.json` — and `spoken-history`); `chat-scope-server.ts` resolves the caller and binds Hermes session ids to the transcript key that opened them (`data/hermes-chat-sessions.json`). A user's gateway socket is answered by `scripts/gateway-user-relay.js` in `production-server.js`: the relay connects with the box's token and its own paired device key (`data/.gateway-user-relay-device.json`), returns the hello with the user's main key and no device token, passes only keyed requests on the user's keys (plus `commands.list`, `approval.resolve`, `question.resolve`, a filtered `question.list`) and only events about their sessions. Creating the first user sets `tools.sessions.visibility: "tree"` natively when it was unset/`all`; removing a user deletes their sessions (`sessions.delete`), transcripts and tab list (`src/lib/user-chats.ts`). `ChatPopup`/`ChatApp` take `chatUser` and mount only once `/users/me` has answered.
- **Owner-only is the default** (this bullet predates per-user desktops: `requireSession` without `ownerOnly` admits every signed-in user, `src/lib/route-auth.ts`; the per-user desktop bullet above is the current rule) — `hasOwnerSession`, `route-auth`'s `hasValidSession` and `requireSession` all mean THE OWNER now; a non-owner session gets **403 `owner_only`** (never 401, which the desktop reads as "signed out"). `requireSession(req, { allowNonOwner: true })` opts a route in (`terminal/shells`, the non-owner preference keys). Middleware step 4a' applies `nonOwnerVerdict` (`src/lib/non-owner-scope.ts`), an ALLOW-list: the desktop page, `/updating`, `/app/terminal`, GET `users/me`, `setup/status`, `terminal/shells`, `update/status`, `preferences?keys=` of `NON_OWNER_READABLE_PREF_KEYS` (`ui_language`, `terminal_settings`) and static media; every other page redirects to `/`, everything else 403s. The desktop (`page.tsx`) folds `NON_OWNER_APP_IDS` (`terminal`) into `harnessHiddenAppIds` and suppresses the chat, mascot, ClawKeep shield and power buttons for a non-owner.
- **Scoped per user**: sign-in (own Linux password), the session, the Terminal. **Owner-only for non-owners** (documented, not yet scopable): Settings, the assistant/gateway and chat (runs as the owner with the device's MCP tools), Files (Node fs as the owner), the coding agent, app store, VNC (`/novnc-ws` is `ownerOnly` in `production-server.js`), power, preferences writes. One route states that rule in code rather than by documentation: `GET/POST /setup-api/coding-agent/settings` (coding-agent.md) admits the owner's cookie OR the MCP bearer and answers any other signed-in user 403 `owner_only` — the coding team's settings are about the owner's agent and the owner's accounts.
- **Login** — `POST /login-api` takes an optional `username`; none (or the owner's name) is the owner's `unix_chkpwd` login. A registered user is verified by `verifyUserPassword` (`src/lib/clawbox-users.ts`): `sudo -n /usr/local/libexec/clawbox/clawbox-user-helper.sh verify` with `user\npassword` on STDIN — the helper runs unix_chkpwd as root and answers only for `clawbox-users` members (never root/admins). An unknown name is refused like a wrong password and runs nothing. Buckets: `global` + `cf:<ip>` as before, plus `user:<name>` for an EXISTING account only, capped at `SHARED_BUCKET_MAX_LOCK_MS` (anyone can charge it). `GET /login-api/users` (anonymous) is the picker: `{multiUser:false}` on a single-user box, the names on the LAN, `users: null` over the tunnel (the page then asks for a username).
- **Users admin** — `GET/POST/DELETE /setup-api/users` (any person's cookie AND same-origin for writes; never the MCP bearer; nobody removes the owner or themselves; the listing's `signIn` says whether the sign-in helper answers, with the repair command when not) and `GET /setup-api/users/me` (any signed-in user). Create/remove are root steps on `WEB_ROOT_STEPS` (never the UI list): `user_add` reads `data/.user-add-input` (`user:password`, 0600, like chpasswd) and runs `useradd --create-home --user-group --groups clawbox-users` then `chpasswd` (rolling the account back on failure), makes the new home 0750 and drops the "other" bits on the owner's home; `user_remove` reads `data/.user-remove-input` and removes only a `clawbox-users` member with uid ≥ 1000 that is not in an admin group (`pkill -u`, `userdel --remove`). `removeUser` drops the registry entry FIRST (sessions end before the account is touched) and restores it under a new `sv` if userdel fails. Names follow `src/lib/username-rules.ts` (`[a-z_][a-z0-9_-]{0,31}`, reserved system/admin/ClawBox names and `systemd-`/`_`/`clawbox` prefixes) and must not exist as a Linux account or group (`getent`, execFile). The UI is Settings → System → Users (`UsersPanel.tsx`), drawn for the owner only since TASK-2130 (settings.md); a non-owner sees no Users tab, while the route above still admits their cookie.
- **Terminal** — the PTY server (`scripts/terminal-server.mjs`) refuses any connection without `x-clawbox-terminal-token`, the per-boot `CLAWBOX_TERMINAL_TOKEN` `production-server.js` generates before Next boots; only the proxy adds it, after the cookie check, so another local account cannot dial 127.0.0.1:3006 for the owner's shell. For a non-owner the proxy also sets `x-clawbox-terminal-user` (client copies of both headers are stripped) and the PTY runs `sudo -n clawbox-user-helper.sh shell <user>` — `runuser` as that user, login shell, own home, clean env; their shell/cwd settings are not applied. Without the env var (`next dev`) the old loopback rule applies and no other user's shell can be requested.
- **Privilege surface** — one new NOPASSWD grant, `/usr/local/libexec/clawbox/clawbox-user-helper.sh` (no argument spec; verbs and the username validated in root-owned code), installed root-owned by `install_root_libexec`; the terminal call site is declared in `check-sudoers-coverage.sh`'s `DECLARED_ARGV`. On an install-x64.sh PC the launcher's `WEB_ROOT_STEPS` carries `user_add`/`user_remove`, `scripts/x64-migration/clawbox-x64-root-step.sh` implements both (install.sh's rules), and `install-x64.sh --step root_step_contract` installs the helper and its own drop-in `/etc/sudoers.d/clawbox-x64-users`; the integration .deb forwards both steps to that dispatcher out of its mirror.
- **Failures say why** — `createUser`/`removeUser` map a refused launcher (`RootStepUnavailableError`) and a dispatcher too old for the step to `root_step_unavailable` with `repairCommand`, a killed step to `create_timeout`/`remove_timeout`, and otherwise read THIS run's journal for the step's last `Error:` line (`detail`, the password cut out) — `user_exists`, `password_rejected`, `create_failed`. `checkUserPassword` answers `ok`/`wrong`/`unavailable`; `/login-api` answers a box that cannot check a second user's password 503 `signin_unavailable` on the LAN (an unknown name's 401 over the tunnel). Every code has its own `users.*`/`login.*` string in every locale.

## Updates are the owner's, on every box (TASK-2435)

"Update available", What's new and every update action answer a user other than the owner **403 `owner_only`** on every box: middleware refuses them `/setup-api/update/**` and `system/update-branch` (`UPDATE_API_TREE` in `src/lib/non-owner-scope.ts`), except `GET update/status`, which the `/updating` lock screen every user is sent to polls. `system_update` joined `OWNER_ONLY_APP_IDS`, so the System Update app and Settings → System Update are hidden from them. The desktop asks `update/versions` and `whats-new` only for the owner (`desktopNoticePolicy`, `src/lib/org-mode.ts`). The agent's MCP bearer is unchanged: it never starts an update, it asks the owner (`update/run` → `requestPowerApproval`).

## Organisation mode (`org_mode`, TASK-2435)

For a ClawBox that serves a company's staff: the owner is the administrator, everyone in `clawbox_users` is a member of staff. **Off unless the owner turns it on**, so a home box (single-user or not) behaves as before. The switch is `org_mode` in data/config.json; only a literal `true` counts (`orgModeFrom`). The owner moves it in Settings → System → Users (`OrgModeCard.tsx`) or `POST /setup-api/settings/org-mode {orgMode}` (owner's cookie and same-origin only — never another user, never the bearer; `GET` answers `{orgMode, canChange}`). `/users/me` carries `orgMode` to every desktop. `src/lib/org-mode.ts` is the one table (pure); `src/lib/org-mode-server.ts` reads and writes it.

With it on, a member of staff gets:

- **Chat, Files and Settings** — desktop, shelf and launcher (`ORG_USER_APP_IDS`; every other built-in app and every installed app hidden, `orgHiddenAppIds` in `page.tsx`). No ClawKeep shield, no restart/shutdown in the tray, no coding-run cards, "create an app" or email drafts in the chat (`orgMember` prop of `ChatPopup`), and no poll of a route that refuses them (`boxApis` in `page.tsx`; the notice ring polls `/users/me`, not `kv`).
- **Their own Settings only** — Appearance (language, wallpaper, look) and Account (their own password) (`ORG_USER_SETTINGS_SECTIONS`, `sectionShown` in `SettingsApp.tsx`); a link to any other section opens Appearance. Their preference writes land in their own map (`prefs_by_user`, `src/lib/user-preferences.ts`) and their reads are the box's preferences with theirs on top, so their three-icon desktop never rewrites the owner's grid, app list or wallpaper. The map entry goes with the account (`removeUser`).
- **An allow-list on the server** — middleware hands a member of staff only what `orgMemberVerdict` names (chat, `hermes/chat`, files, their desktop state and preferences, `users/me` and `users/me/password`, spoken replies, and READS of the box's state and AI the desktop and chat draw from); everything else under `/setup-api` is 403 `owner_only` — the terminal, coding agent, stores (`apps/*`, `plugins`, `webapps`), ClawKeep, Prime Radiant, Memory Shard, agent browser, VNC, kiosk, monitors, provider/model changes, system (`power`, `power-profile`, `timezone`, …), network (`wifi/*`, `network/*`, `tunnel/*`), users, channels (`email/*`, `telegram/*`, `whatsapp/*`, `discord/*`), background jobs, updates, `kv`. `middleware-org-mode.test.ts` holds the audit's list route by route (member 403, owner through); the member's tray, desktop and Settings ask none of them (no internet line, no monitor layout, no timezone adoption). Any other page redirects to `/?notice=owner-only`. A path with a `.`/`..` segment once decoded is refused, so `files%2f..%2fterminal` cannot reach a hidden route through an allowed tree. Nothing the owner shares reaches them: `openclaw_shared_with_users` is overridden, and `mayHaveGatewayToken` never hands them the gateway token. `chat/media` serves them the media tree but not the agent's workspace (`isOrgMemberRequest`, `src/lib/org-mode-server.ts`); `hermes/compress` takes only the caller's own conversation (`hermesSessionFor`), on every box. A project app's requests under `/apps/<id>` that carry a member's cookie are refused (middleware step 2b, and the upgrade in `production-server.js`); the sandboxed document's own requests carry none. Unlike the home-box rule (a deny-list), a route added later is the owner's on an organisation box until it is named here.
- **Sockets** — `production-server.js` refuses them every upgrade but their own chat (`USER_CHAT_WS_PATH`, still relayed): the Terminal, `/novnc-ws` and the gateway root answer 403 (`orgModeRefusesUpgrade`, `scripts/org-mode.js`, pinned to the TS by `org-mode.test.ts`), and a Terminal or remote desktop they had open closes on the next recheck once the switch goes on (`orgMemberWatch`).
- **The login page** asks for a username instead of listing the staff (`/login-api/users` answers `users: null`, as over the tunnel, and also when the switch cannot be read — `readOrgModeStrict`, over `config-store`'s tri-state `getKnown`); the owner may leave it empty. On any multi-user box the password field says "Password", not "System password".
- **No ClawBox AI offers, for anyone** — the desktop's "Free backup with ClawBox AI" card, the chat's portal welcome and What's new's plan section (`readPlanCta` answers `NO_PLAN_CTA`) are hidden for the owner too. The desktop card also waits for a known viewer (`desktopNoticePolicy` fails closed when `/users/me` could not answer). Settings → Users' "What other users can do" follows the switch (`users.scopeNoteOrg`).

The owner keeps everything, connecting and changing cloud AI providers included. The agent's MCP bearer keeps its tools: it is the box's assistant, not a member of staff. A member of staff's chat runs on their own limited assistant (next section); Files is still the owner's home folder (secrets carved out by `file-guard.ts`), as on a home box.

## A member of staff's own, limited assistant (TASK-2444, TASK-2445)

With `org_mode` on, a member of staff's chat turns run on an assistant of their OWN, held to a staff tool policy by the runtime itself (not hidden in the UI), with a memory nobody else reads. The owner's assistant is unchanged; with the switch off nothing here applies. One table, `config/org-staff-policy.json`, read by `src/lib/org-staff-policy.ts` (TS), `scripts/org-staff-policy.js` (the relay's CJS mirror — `org-staff-policy.test.ts` runs one case table through both) and the two guard plugins.

- **What staff get** — chat, attachments (PDF/Word/Excel through the staged files), search over their own memory (on OpenClaw also the Memory Shard folders the owner indexed: `memory.search.extraPaths` is global and the core has no per-agent subtraction), and files written into their own folder. **No** web search/fetch, browser, outbound messages (email, Telegram, WhatsApp, Discord, `message`), automations/cron, sub-agents or the coding agent, image/video/music generation or TTS, shell/exec, file writes outside their folder, gateway/config/plugin/power/update tools, any of the device's MCP tools, learned skills (`skill_workshop`, Hermes' `skill_manage`, background review, curator), Prime Radiant or Memory Shard writes. No M365 integration exists on the box yet; a sandboxed Python for calculations is a follow-up.
- **OpenClaw: one agent each** — `src/lib/org-staff-agents.ts` keeps `agents.entries["clawbox-staff-<name>"]` (`tools.profile: "full"` with the table's `allow`/`deny`, `elevated` off, `skills: []`, no sub-agents) for every user while the switch is on, and its workspace `<OpenClaw home>/staff/<name>` (0700, outside the Files carve-out) is their memory (`MEMORY.md`, `memory/`, their own index in their agent's database) and their folder, seeded with their own `USER.md` and the owner's persona. A roster that did not exist gets the owner's agent pinned beside them, `agents.ownership: "explicit"` and `agents.defaults.systemAgent.agentId` (unbound channel traffic and heartbeats stay the owner's), recorded in `org_staff_roster`. The switch off (or the last user going) removes the staff agents through the core's own `agents.delete` (files kept; a config unset only when the gateway cannot be asked), each on its own; those three stay — they name the agent and workspace the core already resolved. Applied hot through the gateway by `settings/org-mode` (awaited), `users` POST, `gateway/ws-config` for a member, and user removal (which also deletes the workspace and the agent directory).
- **The relay** (`scripts/gateway-user-relay.js`, `staffAgent`) hands a member the hello `agent:clawbox-staff-<name>:clawbox-user-<name>` and passes only keys on that agent; a turn goes out only while `staffReadyReader` finds the agent in openclaw.json with the staff policy AND `clawbox-staff-guard` enabled and installed (fail closed: "being set up"); `chat.send` keeps only `sessionKey/message/idempotencyKey/attachments/thinking/timeoutMs` (never delivered); `/new` (alone) and `/reasoning` are the only commands and no inline directive (`/model x` mid-sentence, `! cmd`) passes (`staffMessageVerdict`); `sessions.patch` carries only thinking/reasoning level and label — a model the chat sends beside the level is dropped, a model or tool override alone refused; `commands.list` is asked of their agent and cut to the two commands. The owner turning the switch closes an open member socket so the next hello is right.
- **`clawbox-staff-guard`** (`scripts/openclaw-plugins/`, installed by `gateway-pre-start.sh` with the table beside it) — `before_tool_call`: for a staff agent only, any tool outside the table is refused, `write`/`edit`/`apply_patch` must stay in their folder (symlinks resolved, `apply_patch` headers read when the host gives no `derivedPaths`), `read`/`pdf`/`view_image` in their folder or `media/chat-attachments` (a read naming no file is refused; an inline `data:` picture passes), nothing on the web.
- **Hermes: one profile each** — `src/lib/hermes-staff-profile.ts` keeps `~/.hermes/profiles/clawbox-staff-<name>` (the dashboard hosts a named profile per session: `profile` on `session.create`/`session.resume`/`slash.exec`/`session.compress`, `-p` on the CLI). Its config.yaml is the owner's with `platform_toolsets.cli` and `agent.disabled_toolsets` from the table, no `mcp_servers`, built-in memory on (no external provider, no write approval), background review and curator off, `terminal.cwd` = `workspace/` (their folder) and `gateway.standalone: true` (the messaging multiplexer never starts the owner's bots for it); `.env` and `auth.json` link to the owner's, SOUL.md is copied. Their `memories/`, `state.db` (so `session_search` sees only their chats) and skills are the profile's. `hermes/chat` refuses a member's other commands 403 `staff_command_refused`, a profile it could not prepare (or a box whose `clawbox_staff_guard` is not installed and enabled) 503 `staff_profile_unavailable`, a non-owner on a box whose switch cannot be read 503 `org_mode_unknown` (`orgMemberStrictOf`), drops the composer's model/provider and the slim `-t` toolsets, and answers every approval `deny`; a session the dashboard does not answer in the member's profile (`info.profile_name`) is refused, not run on the launch profile. **`clawbox_staff_guard`** (`scripts/hermes-plugins/`, installed and enabled by `register-mcp.sh` with the table and the staging directory) — `pre_tool_call`: on a staff profile home only, the same allow-list and folder rule, a relative path rewritten absolute inside the folder (`modify`).
- **Spoken replies** (`tts/speak`, allowed by `orgMemberVerdict`) follow the owner's Voice setting as before: the owner decides whether replies are spoken and with which voice. The agent's own `tts` tool is denied to staff on both runtimes.
- **Tests** — `org-staff-policy.test.ts`, `gateway-user-relay-staff.test.ts`, `org-staff-agents.test.ts`, `openclaw-staff-guard-plugin.test.ts` and `hermes-staff-profile.test.ts` (each with the two-member memory case: A's fact stays in A's folder/profile, B is refused it, the owner's MEMORY.md is untouched), `routes/hermes-chat-staff.test.ts`; on a board, `scripts/nano-tests/tests/56-org-mode-staff.sh` on both runtimes.

**A user's own password** (Settings → Account, every non-owner on any box): `POST /setup-api/users/me/password {currentPassword, password}` (a person's cookie and same-origin; the owner is answered 409 — theirs is `system/credentials`). The route checks the current password first (the helper's `verify`), then ends every other session (a new `sv`; this browser re-signed), and only then changes the password, so a password never changes while older sessions stay valid — a version that cannot be stored changes nothing (500 `sessions_not_ended`). The whole change holds `src/lib/password-change-lock.ts` (process store): `/login-api` answers that account 409 `password_changing` while it runs, and refuses a sign-in whose check began before a change and finished after it (the per-account epoch moved), so the old password cannot mint a cookie under the new session version. `changeUserPassword` (`src/lib/clawbox-users.ts`) runs the helper's `passwd` verb (`sudo -n clawbox-user-helper.sh passwd`, user/current/new on STDIN): root checks the current password with `unix_chkpwd` and only then pipes ONE `user:password` record to chpasswd, for a `clawbox-users` member only. Exit 7 is a wrong password (400 `wrong_password`, never 401), 65 a new password outside 8–256 characters, 66 chpasswd refusing; a helper from before the verb (64) or no grant is 503 `password_change_unavailable` until the box updates (`install_root_libexec` installs the helper). Wrong guesses are charged to the login's own durable per-account bucket (`user:<name>`, `src/lib/login-rate-limit.ts`, capped at `SHARED_BUCKET_MAX_LOCK_MS`), so this door and `/login-api` share one limit that outlives a restart; a locked account is answered 429 without asking the helper, and only one guess per account is in flight at a time. `rotateUserSessionVersion` reads the registry with `getKnown` (an unreadable store throws, never `get`'s empty reading) and is tried twice; every answer after it carries the re-signed cookie. A lock the shared bucket reports but cannot store (a full table) is held in the process too. Creating a user clears whatever an earlier account of that name left (`prefs_by_user`, `ui_language_by_user`) before the account exists, and refuses the create if it cannot.
