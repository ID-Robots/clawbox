# Multi-user ClawBox OS

Linux-account users, session identity, the owner-only default, login, user admin and the per-user Terminal. Read it before you add a route (owner-only is the default) or touch sessions, `/login` or users.

## Multi-user ClawBox OS (TASK-1256)

Every ClawBox user is a real Linux account. The **owner** is the install user (`getSystemUsername()`, now `src/lib/owner-username.ts`), is never stored anywhere and can never be removed; every OTHER user is one entry in data/config.json's `clawbox_users` (`{ username, createdAt, sv }`, parsed by `src/lib/session-identity.ts`) plus one account in the `clawbox-users` group. A box with no entry is the single-user box it always was — no migration, the owner stays the administrator, and `/login` renders the single password field unchanged.

- **Session identity** — the `clawbox_session` payload is `{ exp, gen, u?, sv? }`. `identityFromClaims` (`src/lib/session-identity.ts`, mirrored in CJS by `scripts/session-cookie.js` for WebSocket upgrades, one table tests both) decides who a verified cookie speaks for: no `u` → the owner (every pre-multi-user cookie), `u` = owner → the owner, `u` = a registered user with the registry's `sv` → that user, anything else → nobody. Removing a user drops the entry and re-creating the name mints a new `sv`, so either revokes that user's cookies everywhere; a `session_generation` bump still revokes everyone's. `readSessionClaims` in `auth.ts` returns the verified payload; `createSessionCookie(duration, secret, gen, { u, sv? })`.
- **Every signed-in user gets the owner's desktop** — every built-in and installed app, Files, the browser, the coding agent, the app store, the remote desktop, Prime Radiant, Memory Shard and Settings. `requireSession` and `hasValidSession` admit any signed-in person (the MCP bearer as before); `hasPersonSession`/`personSession` (`src/lib/owner-session.ts`) are the "a person, not the agent" gate the desktop's routes use; `hasOwnerSession` is the strict owner check, kept for the gateway token (`gateway-proxy.ts`). Middleware step 4a' applies `nonOwnerVerdict` (`src/lib/non-owner-scope.ts`), now a DENY-list of the three exceptions: **the owner's chat** (each user has their own, below; the harness consoles that list every conversation — `OWNER_ONLY_APP_IDS` `openclaw`/`hermes`, `/app/openclaw`, `/app/hermes`, the gateway's catch-all pages and `/api`/`/assets`/`/__openclaw__`/`/avatar` — stay the owner's, except `/api/chat/media/outgoing/<own key>/…`), **secrets in clear** (`/setup-api/gateway` with the token; `gateway/ws-config` answers a user `token: ""`, `relayed: true`; public-link URLs carry `tokenMasked`), and **the owner's account** (`system/credentials`, `credentials/verify`, `setup/reset` — `requireSession(req, { ownerOnly: true })`). A refusal is 403 `owner_only` (never 401). Picture paste into the Terminal stays the owner's: a user's shell cannot read the owner's file.
- **Per-user chat** — `src/lib/chat-scope.ts` (CJS copy `scripts/chat-scope.js`): a user's OpenClaw main is `agent:<agentId>:clawbox-user-<name>`, tabs `agent:<agentId>:clawbox-utab-<12hex>-<name>`; Hermes main `desktop-user-<name>`, tabs `desktop-utab-<12hex>-<name>` (id first so a `-` in a name cannot alias another user's key). `mayUseChatKey` holds every chat route to the caller's keys (`chat/history`, `chat/images`, `hermes/chat`, `chat/tabs` — one inventory per person, `data/chat-tabs/<name>.json` — and `spoken-history`); `chat-scope-server.ts` resolves the caller and binds Hermes session ids to the transcript key that opened them (`data/hermes-chat-sessions.json`). A user's gateway socket is answered by `scripts/gateway-user-relay.js` in `production-server.js`: the relay connects with the box's token and its own paired device key (`data/.gateway-user-relay-device.json`), returns the hello with the user's main key and no device token, passes only keyed requests on the user's keys (plus `commands.list`, `approval.resolve`, `question.resolve`, a filtered `question.list`) and only events about their sessions. Creating the first user sets `tools.sessions.visibility: "tree"` natively when it was unset/`all`; removing a user deletes their sessions (`sessions.delete`), transcripts and tab list (`src/lib/user-chats.ts`). `ChatPopup`/`ChatApp` take `chatUser` and mount only once `/users/me` has answered.
- **Owner-only is the default** (this bullet predates per-user desktops: `requireSession` without `ownerOnly` admits every signed-in user, `src/lib/route-auth.ts`; the per-user desktop bullet above is the current rule) — `hasOwnerSession`, `route-auth`'s `hasValidSession` and `requireSession` all mean THE OWNER now; a non-owner session gets **403 `owner_only`** (never 401, which the desktop reads as "signed out"). `requireSession(req, { allowNonOwner: true })` opts a route in (`terminal/shells`, the non-owner preference keys). Middleware step 4a' applies `nonOwnerVerdict` (`src/lib/non-owner-scope.ts`), an ALLOW-list: the desktop page, `/updating`, `/app/terminal`, GET `users/me`, `setup/status`, `terminal/shells`, `update/status`, `preferences?keys=` of `NON_OWNER_READABLE_PREF_KEYS` (`ui_language`, `terminal_settings`) and static media; every other page redirects to `/`, everything else 403s. The desktop (`page.tsx`) folds `NON_OWNER_APP_IDS` (`terminal`) into `harnessHiddenAppIds` and suppresses the chat, mascot, ClawKeep shield and power buttons for a non-owner.
- **Scoped per user**: sign-in (own Linux password), the session, the Terminal. **Owner-only for non-owners** (documented, not yet scopable): Settings, the assistant/gateway and chat (runs as the owner with the device's MCP tools), Files (Node fs as the owner), the coding agent, app store, VNC (`/novnc-ws` is `ownerOnly` in `production-server.js`), power, preferences writes. One route states that rule in code rather than by documentation: `GET/POST /setup-api/coding-agent/settings` (coding-agent.md) admits the owner's cookie OR the MCP bearer and answers any other signed-in user 403 `owner_only` — the coding team's settings are about the owner's agent and the owner's accounts.
- **Login** — `POST /login-api` takes an optional `username`; none (or the owner's name) is the owner's `unix_chkpwd` login. A registered user is verified by `verifyUserPassword` (`src/lib/clawbox-users.ts`): `sudo -n /usr/local/libexec/clawbox/clawbox-user-helper.sh verify` with `user\npassword` on STDIN — the helper runs unix_chkpwd as root and answers only for `clawbox-users` members (never root/admins). An unknown name is refused like a wrong password and runs nothing. Buckets: `global` + `cf:<ip>` as before, plus `user:<name>` for an EXISTING account only, capped at `SHARED_BUCKET_MAX_LOCK_MS` (anyone can charge it). `GET /login-api/users` (anonymous) is the picker: `{multiUser:false}` on a single-user box, the names on the LAN, `users: null` over the tunnel (the page then asks for a username).
- **Users admin** — `GET/POST/DELETE /setup-api/users` (any person's cookie AND same-origin for writes; never the MCP bearer; nobody removes the owner or themselves; the listing's `signIn` says whether the sign-in helper answers, with the repair command when not) and `GET /setup-api/users/me` (any signed-in user). Create/remove are root steps on `WEB_ROOT_STEPS` (never the UI list): `user_add` reads `data/.user-add-input` (`user:password`, 0600, like chpasswd) and runs `useradd --create-home --user-group --groups clawbox-users` then `chpasswd` (rolling the account back on failure), makes the new home 0750 and drops the "other" bits on the owner's home; `user_remove` reads `data/.user-remove-input` and removes only a `clawbox-users` member with uid ≥ 1000 that is not in an admin group (`pkill -u`, `userdel --remove`). `removeUser` drops the registry entry FIRST (sessions end before the account is touched) and restores it under a new `sv` if userdel fails. Names follow `src/lib/username-rules.ts` (`[a-z_][a-z0-9_-]{0,31}`, reserved system/admin/ClawBox names and `systemd-`/`_`/`clawbox` prefixes) and must not exist as a Linux account or group (`getent`, execFile).
- **Terminal** — the PTY server (`scripts/terminal-server.mjs`) refuses any connection without `x-clawbox-terminal-token`, the per-boot `CLAWBOX_TERMINAL_TOKEN` `production-server.js` generates before Next boots; only the proxy adds it, after the cookie check, so another local account cannot dial 127.0.0.1:3006 for the owner's shell. For a non-owner the proxy also sets `x-clawbox-terminal-user` (client copies of both headers are stripped) and the PTY runs `sudo -n clawbox-user-helper.sh shell <user>` — `runuser` as that user, login shell, own home, clean env; their shell/cwd settings are not applied. Without the env var (`next dev`) the old loopback rule applies and no other user's shell can be requested.
- **Privilege surface** — one new NOPASSWD grant, `/usr/local/libexec/clawbox/clawbox-user-helper.sh` (no argument spec; verbs and the username validated in root-owned code), installed root-owned by `install_root_libexec`; the terminal call site is declared in `check-sudoers-coverage.sh`'s `DECLARED_ARGV`. On an install-x64.sh PC the launcher's `WEB_ROOT_STEPS` carries `user_add`/`user_remove`, `scripts/x64-migration/clawbox-x64-root-step.sh` implements both (install.sh's rules), and `install-x64.sh --step root_step_contract` installs the helper and its own drop-in `/etc/sudoers.d/clawbox-x64-users`; the integration .deb forwards both steps to that dispatcher out of its mirror.
- **Failures say why** — `createUser`/`removeUser` map a refused launcher (`RootStepUnavailableError`) and a dispatcher too old for the step to `root_step_unavailable` with `repairCommand`, a killed step to `create_timeout`/`remove_timeout`, and otherwise read THIS run's journal for the step's last `Error:` line (`detail`, the password cut out) — `user_exists`, `password_rejected`, `create_failed`. `checkUserPassword` answers `ok`/`wrong`/`unavailable`; `/login-api` answers a box that cannot check a second user's password 503 `signin_unavailable` on the LAN (an unknown name's 401 over the tunnel). Every code has its own `users.*`/`login.*` string in every locale.
