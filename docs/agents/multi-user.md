# Multi-user ClawBox OS

Linux-account users, session identity, the owner-only default, login, user admin and the per-user Terminal. Read it before you add a route (owner-only is the default) or touch sessions, `/login` or users.

## Multi-user ClawBox OS (TASK-1256)

Every ClawBox user is a real Linux account. The **owner** is the install user (`getSystemUsername()`, now `src/lib/owner-username.ts`), is never stored anywhere and can never be removed; every OTHER user is one entry in data/config.json's `clawbox_users` (`{ username, createdAt, sv }`, parsed by `src/lib/session-identity.ts`) plus one account in the `clawbox-users` group. A box with no entry is the single-user box it always was — no migration, the owner stays the administrator, and `/login` renders the single password field unchanged.

- **Session identity** — the `clawbox_session` payload is `{ exp, gen, u?, sv? }`. `identityFromClaims` (`src/lib/session-identity.ts`, mirrored in CJS by `scripts/session-cookie.js` for WebSocket upgrades, one table tests both) decides who a verified cookie speaks for: no `u` → the owner (every pre-multi-user cookie), `u` = owner → the owner, `u` = a registered user with the registry's `sv` → that user, anything else → nobody. Removing a user drops the entry and re-creating the name mints a new `sv`, so either revokes that user's cookies everywhere; a `session_generation` bump still revokes everyone's. `readSessionClaims` in `auth.ts` returns the verified payload; `createSessionCookie(duration, secret, gen, { u, sv? })`.
- **Every signed-in user gets the owner's desktop** — every built-in and installed app, Files, the browser, the coding agent, the app store, the remote desktop, Prime Radiant, Memory Shard and Settings. `requireSession` and `hasValidSession` admit any signed-in person (the MCP bearer as before); `hasPersonSession`/`personSession` (`src/lib/owner-session.ts`) are the "a person, not the agent" gate the desktop's routes use; `hasOwnerSession` is the strict owner check, kept for the gateway token (`gateway-proxy.ts`). Middleware step 4a' applies `nonOwnerVerdict` (`src/lib/non-owner-scope.ts`), now a DENY-list of the three exceptions: **the owner's chat** (each user has their own, below; the harness consoles that list every conversation — `OWNER_ONLY_APP_IDS` `openclaw`/`hermes`, `/app/openclaw`, `/app/hermes`, the gateway's catch-all pages and `/api`/`/assets`/`/__openclaw__`/`/avatar` — stay the owner's, except `/api/chat/media/outgoing/<own key>/…`), **secrets in clear** (`/setup-api/gateway` with the token; `gateway/ws-config` answers a user `token: ""`, `relayed: true`; public-link URLs carry `tokenMasked`), and **the owner's account** (`system/credentials`, `credentials/verify`, `setup/reset` — `requireSession(req, { ownerOnly: true })`). A refusal is 403 `owner_only` (never 401). Picture paste into the Terminal stays the owner's: a user's shell cannot read the owner's file.
- **Per-user chat** — `src/lib/chat-scope.ts` (CJS copy `scripts/chat-scope.js`): a user's OpenClaw main is `agent:<agentId>:clawbox-user-<name>`, tabs `agent:<agentId>:clawbox-utab-<12hex>-<name>`; Hermes main `desktop-user-<name>`, tabs `desktop-utab-<12hex>-<name>` (id first so a `-` in a name cannot alias another user's key). `mayUseChatKey` holds every chat route to the caller's keys (`chat/history`, `chat/images`, `hermes/chat`, `chat/tabs` — one inventory per person, `data/chat-tabs/<name>.json` — and `spoken-history`); `chat-scope-server.ts` resolves the caller and binds Hermes session ids to the transcript key that opened them (`data/hermes-chat-sessions.json`). A user's gateway socket is answered by `scripts/gateway-user-relay.js` in `production-server.js`: the relay connects with the box's token and its own paired device key (`data/.gateway-user-relay-device.json`), returns the hello with the user's main key and no device token, passes only keyed requests on the user's keys (plus `commands.list`, `approval.resolve`, `question.resolve`, a filtered `question.list`) and only events about their sessions. **A user's reset** — the core resets a session only for a caller with `operator.admin`, which the user's socket never declares (`RELAY_SCOPES`), so the relay runs it on a one-shot socket of its own that does (`runAdminReset`, `RESET_SCOPES`), given the key (after the same ownership check) and the reason only: the chat's `sessions.reset`, and a TYPED `/new` or `/reset` (TASK-2520 — the chat sends it as the text of a `chat.send`, which the core answered "You are not authorized to reset this session"). `typedResetCommand` reads the command as the core does (bare, `/new message`, `/new: message`, a new line; never `/reset soft`, which travels as it is); after the reset a bare command is answered with the core's own notice (`resetNoticeFrames`: the ack, then a final "New session started." / "Session reset.") and a message after the command goes out as an ordinary `chat.send` on the USER's socket — nothing the user typed reaches the admin socket, a model named after `/new` is sent as text, and a failed reset fails the send. One reset per chat socket at a time. Creating the first user sets `tools.sessions.visibility: "tree"` natively when it was unset/`all`; removing a user deletes their sessions (`sessions.delete`), transcripts and tab list (`src/lib/user-chats.ts`). `ChatPopup`/`ChatApp` take `chatUser` and mount only once `/users/me` has answered.
- **Owner-only is the default** (this bullet predates per-user desktops: `requireSession` without `ownerOnly` admits every signed-in user, `src/lib/route-auth.ts`; the per-user desktop bullet above is the current rule) — `hasOwnerSession`, `route-auth`'s `hasValidSession` and `requireSession` all mean THE OWNER now; a non-owner session gets **403 `owner_only`** (never 401, which the desktop reads as "signed out"). `requireSession(req, { allowNonOwner: true })` opts a route in (`terminal/shells`, the non-owner preference keys). Middleware step 4a' applies `nonOwnerVerdict` (`src/lib/non-owner-scope.ts`), an ALLOW-list: the desktop page, `/updating`, `/app/terminal`, GET `users/me`, `setup/status`, `terminal/shells`, `update/status`, `preferences?keys=` of `NON_OWNER_READABLE_PREF_KEYS` (`ui_language`, `terminal_settings`) and static media; every other page redirects to `/`, everything else 403s. The desktop (`page.tsx`) folds `NON_OWNER_APP_IDS` (`terminal`) into `harnessHiddenAppIds` and suppresses the chat, mascot, ClawKeep shield and power buttons for a non-owner.
- **Scoped per user**: sign-in (own Linux password), the session, the Terminal. **Owner-only for non-owners** (documented, not yet scopable): Settings, the assistant/gateway and chat (runs as the owner with the device's MCP tools), Files (Node fs as the owner), the coding agent, app store, VNC (`/novnc-ws` is `ownerOnly` in `production-server.js`), power, preferences writes. One route states that rule in code rather than by documentation: `GET/POST /setup-api/coding-agent/settings` (coding-agent.md) admits the owner's cookie OR the MCP bearer and answers any other signed-in user 403 `owner_only` — the coding team's settings are about the owner's agent and the owner's accounts.
- **Login** — `POST /login-api` takes an optional `username`; none (or the owner's name) is the owner's `unix_chkpwd` login. A registered user is verified by `verifyUserPassword` (`src/lib/clawbox-users.ts`): `sudo -n /usr/local/libexec/clawbox/clawbox-user-helper.sh verify` with `user\npassword` on STDIN — the helper runs unix_chkpwd as root and answers only for `clawbox-users` members (never root/admins). An unknown name is refused like a wrong password and runs nothing. Buckets: `global` + `cf:<ip>` as before, plus `user:<name>` for an EXISTING account only, capped at `SHARED_BUCKET_MAX_LOCK_MS` (anyone can charge it). `GET /login-api/users` (anonymous) is the picker: `{multiUser:false}` on a single-user box, the names on the LAN, `users: null` over the tunnel (the page then asks for a username).
- **Users admin** — `GET/POST/DELETE /setup-api/users` (any person's cookie AND same-origin for writes; never the MCP bearer; nobody removes the owner or themselves; the listing's `signIn` says whether the sign-in helper answers, with the repair command when not) and `GET /setup-api/users/me` (any signed-in user). Create/remove are root steps on `WEB_ROOT_STEPS` (never the UI list): `user_add` reads `data/.user-add-input` (`user:password`, 0600, like chpasswd) and runs `useradd --create-home --user-group --groups clawbox-users` then `chpasswd` (rolling the account back on failure), makes the new home 0750 and drops the "other" bits on the owner's home; `user_remove` reads `data/.user-remove-input` and removes only a `clawbox-users` member with uid ≥ 1000 that is not in an admin group (`pkill -u`, `userdel --remove`). `removeUser` drops the registry entry FIRST (sessions end before the account is touched) and restores it under a new `sv` if userdel fails. Names follow `src/lib/username-rules.ts` (`[a-z_][a-z0-9_-]{0,31}`, reserved system/admin/ClawBox names and `systemd-`/`_`/`clawbox` prefixes) and must not exist as a Linux account or group (`getent`, execFile). The UI is Settings → System → Users (`UsersPanel.tsx`), drawn for the owner only since TASK-2130 (settings.md); a non-owner sees no Users tab, while the route above still admits their cookie.
- **Terminal** — the PTY server (`scripts/terminal-server.mjs`) refuses any connection without `x-clawbox-terminal-token`, the per-boot `CLAWBOX_TERMINAL_TOKEN` `production-server.js` generates before Next boots; only the proxy adds it, after the cookie check, so another local account cannot dial 127.0.0.1:3006 for the owner's shell. For a non-owner the proxy also sets `x-clawbox-terminal-user` (client copies of both headers are stripped) and the PTY runs `sudo -n clawbox-user-helper.sh shell <user>` — `runuser` as that user, login shell, own home, clean env; their shell/cwd settings are not applied. Without the env var (`next dev`) the old loopback rule applies and no other user's shell can be requested.
- **Privilege surface** — one new NOPASSWD grant, `/usr/local/libexec/clawbox/clawbox-user-helper.sh` (no argument spec; verbs and the username validated in root-owned code), installed root-owned by `install_root_libexec`; the terminal call site is declared in `check-sudoers-coverage.sh`'s `DECLARED_ARGV`. On an install-x64.sh PC the launcher's `WEB_ROOT_STEPS` carries `user_add`/`user_remove`, `scripts/x64-migration/clawbox-x64-root-step.sh` implements both (install.sh's rules), and `install-x64.sh --step root_step_contract` installs the helper and its own drop-in `/etc/sudoers.d/clawbox-x64-users`; the integration .deb forwards both steps to that dispatcher out of its mirror.
- **Failures say why** — `createUser`/`removeUser` map a refused launcher (`RootStepUnavailableError`) and a dispatcher too old for the step to `root_step_unavailable` with `repairCommand`, a killed step to `create_timeout`/`remove_timeout`, and otherwise read THIS run's journal for the step's last `Error:` line (`detail`, the password cut out) — `user_exists`, `password_rejected`, `create_failed`. `checkUserPassword` answers `ok`/`wrong`/`unavailable`; `/login-api` answers a box that cannot check a second user's password 503 `signin_unavailable` on the LAN (an unknown name's 401 over the tunnel). Every code has its own `users.*`/`login.*` string in every locale.

## Updates are the owner's, on every box (TASK-2435)

"Update available", What's new and every update action answer a user other than the owner **403 `owner_only`** on every box: middleware refuses them `/setup-api/update/**` and `system/update-branch` (`UPDATE_API_TREE` in `src/lib/non-owner-scope.ts`), except `GET update/status`, which the `/updating` lock screen every user is sent to polls. `system_update` joined `OWNER_ONLY_APP_IDS`, so the System Update app and Settings → System Update are hidden from them. The desktop asks `update/versions` and `whats-new` only for the owner (`desktopNoticePolicy`, `src/lib/org-mode.ts`). The agent's MCP bearer is unchanged: it never starts an update, it asks the owner (`update/run` → `requestPowerApproval`).

## Organisation mode (`org_mode`, TASK-2435)

For a ClawBox that serves a company's staff: the owner is the administrator, everyone in `clawbox_users` is a member of staff. **Off unless the owner turns it on**, so a home box (single-user or not) behaves as before. The switch is `org_mode` in data/config.json; only a literal `true` counts (`orgModeFrom`). The owner moves it in Settings → System → Users (`OrgModeCard.tsx`) or `POST /setup-api/settings/org-mode {orgMode}` (owner's cookie and same-origin only — never another user, never the bearer; `GET` answers `{orgMode, canChange}`). `/users/me` carries `orgMode` to every desktop. `src/lib/org-mode.ts` is the one table (pure); `src/lib/org-mode-server.ts` reads and writes it.

With it on, a member of staff gets:

- **Chat, Files and Settings** — desktop, shelf and launcher (`ORG_USER_APP_IDS`; every other built-in app and every installed app hidden, `orgHiddenAppIds` in `page.tsx`). No ClawKeep shield, no restart/shutdown in the tray, no coding-run cards, "create an app" or email drafts in the chat (`orgMember` prop of `ChatPopup`), and no poll of a route that refuses them (`boxApis` in `page.tsx`; the notice ring polls `/users/me`, not `kv`).
- **Their own Settings only** — Appearance (language, wallpaper, look) and Account (their own password) (`ORG_USER_SETTINGS_SECTIONS`, `sectionShown` in `SettingsApp.tsx`); a link to any other section opens Appearance. Their preference writes land in their own map (`prefs_by_user`, `src/lib/user-preferences.ts`) and their reads are the box's preferences with theirs on top, so their three-icon desktop never rewrites the owner's grid, app list or wallpaper. The map entry goes with the account (`removeUser`).
- **An allow-list on the server** — middleware hands a member of staff only what `orgMemberVerdict` names (chat, `hermes/chat`, files, their desktop state and preferences, `users/me` and `users/me/password`, spoken replies, and READS of the box's state and AI the desktop and chat draw from); everything else under `/setup-api` is 403 `owner_only` — the terminal, coding agent, stores (`apps/*`, `plugins`, `webapps`), ClawKeep, Prime Radiant, Memory Shard, agent browser, VNC, kiosk, monitors, provider/model changes, system (`power`, `power-profile`, `timezone`, …), network (`wifi/*`, `network/*`, `tunnel/*`), users, channels (`email/*`, `telegram/*`, `whatsapp/*`, `discord/*`), background jobs, updates, `kv`. `middleware-org-mode.test.ts` holds the audit's list route by route (member 403, owner through); the member's tray, desktop and Settings ask none of them (no internet line, no monitor layout, no timezone adoption). Any other page redirects to `/?notice=owner-only`. A path with a `.`/`..` segment once decoded is refused, so `files%2f..%2fterminal` cannot reach a hidden route through an allowed tree. Nothing the owner shares reaches them: `openclaw_shared_with_users` is overridden, and `mayHaveGatewayToken` never hands them the gateway token. `chat/media` serves them the media tree but not the agent's workspace (`isOrgMemberRequest`, `src/lib/org-mode-server.ts`); `hermes/compress` takes only the caller's own conversation (`hermesSessionFor`), on every box. A project app's requests under `/apps/<id>` that carry a member's cookie are refused (middleware step 2b, and the upgrade in `production-server.js`); the sandboxed document's own requests carry none. Unlike the home-box rule (a deny-list), a route added later is the owner's on an organisation box until it is named here.
- **Sockets** — `production-server.js` refuses them every upgrade but their own chat (`USER_CHAT_WS_PATH`, still relayed): the Terminal, `/novnc-ws` and the gateway root answer 403 (`orgModeRefusesUpgrade`, `scripts/org-mode.js`, pinned to the TS by `org-mode.test.ts`), and a Terminal or remote desktop they had open closes on the next recheck once the switch goes on (`orgMemberWatch`).
- **The login page** asks for a username instead of listing the staff (`/login-api/users` answers `users: null`, as over the tunnel, and also when the switch cannot be read — `readOrgModeStrict`, over `config-store`'s tri-state `getKnown`); the owner may leave it empty. On any multi-user box the password field says "Password", not "System password".
- **No ClawBox AI offers, for anyone** — the desktop's "Free backup with ClawBox AI" card, the chat's portal welcome and What's new's plan section (`readPlanCta` answers `NO_PLAN_CTA`) are hidden for the owner too. The desktop card also waits for a known viewer (`desktopNoticePolicy` fails closed when `/users/me` could not answer). Settings → Users' "What other users can do" follows the switch (`users.scopeNoteOrg`).

The owner keeps everything, connecting and changing cloud AI providers included. The agent's MCP bearer keeps its tools: it is the box's assistant, not a member of staff. A member of staff's chat runs on their own limited assistant (next section); Files serves them their own Linux home and the shared folder only (TASK-2377, below).

## A member of staff's own, limited assistant (TASK-2444, TASK-2445)

With `org_mode` on, a member of staff's chat turns run on an assistant of their OWN, held to a staff tool policy by the runtime itself (not hidden in the UI), with a memory nobody else reads. The owner's assistant is unchanged; with the switch off nothing here applies. One table, `config/org-staff-policy.json`, read by `src/lib/org-staff-policy.ts` (TS), `scripts/org-staff-policy.js` (the relay's CJS mirror — `org-staff-policy.test.ts` runs one case table through both) and the two guard plugins.

- **What staff get** — chat, attachments (PDF/Word/Excel through the staged files), search over their own memory (on OpenClaw also the Memory Shard folders the owner indexed: `memory.search.extraPaths` is global and the core has no per-agent subtraction, so an owner reviews those roots — the wizard's and any set by hand — before turning organisation mode on), and files written into their own folder. **No** web search/fetch, browser, outbound messages (email, Telegram, WhatsApp, Discord, `message`), automations/cron, sub-agents or the coding agent, image/video/music generation or TTS, shell/exec, file writes outside their folder, gateway/config/plugin/power/update tools, any of the device's MCP tools, learned skills (`skill_workshop`, Hermes' `skill_manage`, background review, curator), Prime Radiant or Memory Shard writes. The one exception to "no MCP tools" is what the owner grants (TASK-2377, below): on OpenClaw a granted server's read-only tools, with the member's own credential; never `clawbox__*`. A sandboxed Python for calculations is a follow-up.
- **OpenClaw: one agent each** — `src/lib/org-staff-agents.ts` keeps `agents.entries["clawbox-staff-<name>"]` (`tools.profile: "full"` with the table's `allow`/`deny`, `elevated` off, `skills: []`, no sub-agents) for every user while the switch is on, and its workspace `<OpenClaw home>/staff/<name>` (0700, outside the Files carve-out) is their memory (`MEMORY.md`, `memory/`, their own index in their agent's database) and their folder, seeded with their own `USER.md` and the owner's persona. A roster that did not exist gets the owner's agent pinned beside them, `agents.ownership: "explicit"` and `agents.defaults.systemAgent.agentId` (unbound channel traffic and heartbeats stay the owner's), recorded in `org_staff_roster`. The switch off (or the last user going) removes the staff agents through the core's own `agents.delete` (files kept; a config unset only when the gateway cannot be asked), each on its own; those three stay — they name the agent and workspace the core already resolved. Applied hot through the gateway by `settings/org-mode` (awaited), `users` POST, `gateway/ws-config` for a member, and user removal (which also deletes the workspace and the agent directory).
- **The relay** (`scripts/gateway-user-relay.js`, `staffAgent`) hands a member the hello `agent:clawbox-staff-<name>:clawbox-user-<name>` and passes only keys on that agent; a turn goes out only while `staffReadyReader` finds the agent in openclaw.json with the staff policy AND `clawbox-staff-guard` enabled and installed (fail closed: "being set up"); `chat.send` keeps only `sessionKey/message/idempotencyKey/attachments/thinking/timeoutMs` (never delivered); `/new` (alone) and `/reasoning` are the only commands and no inline directive (`/model x` mid-sentence, `! cmd`) passes (`staffMessageVerdict`); their `/new` is then run as the relay's reset of their own agent's session, like any user's (above) — `/new <anything>` and `/reset` stay refused, before any reset; `sessions.patch` carries only thinking/reasoning level and label — a model the chat sends beside the level is dropped, a model or tool override alone refused; `commands.list` is asked of their agent and cut to the two commands. The owner turning the switch closes an open member socket so the next hello is right.
- **`clawbox-staff-guard`** (`scripts/openclaw-plugins/`, installed by `gateway-pre-start.sh` with the table beside it) — `before_tool_call`: for a staff agent only, any tool outside the table is refused, `write`/`edit`/`apply_patch` must stay in their folder (symlinks resolved, `apply_patch` headers read when the host gives no `derivedPaths`), `read`/`pdf`/`view_image` in their folder or in `media/chat-attachments` on a file staged for THEM — the attachment owner record `data/chat-media-owners.json` (`src/lib/chat-media-owners.ts`, the rule of `isMediaOwnedBy`; its path is written beside the plugin as `clawbox-paths.json`), so another member's upload is refused by its path and a file with no record is nobody's (a read naming no file is refused; an inline `data:` picture passes), nothing on the web.
- **Hermes: one profile each** — `src/lib/hermes-staff-profile.ts` keeps `~/.hermes/profiles/clawbox-staff-<name>` (the dashboard hosts a named profile per session: `profile` on `session.create`/`session.resume`/`slash.exec`/`session.compress`, `-p` on the CLI). Its config.yaml is the owner's with `platform_toolsets.cli` and `agent.disabled_toolsets` from the table, no `mcp_servers`, built-in memory on (no external provider, no write approval), background review and curator off, `terminal.cwd` = `workspace/` (their folder) and `gateway.standalone: true` (the messaging multiplexer never starts the owner's bots for it); `.env` and `auth.json` link to the owner's, SOUL.md is copied. Their `memories/`, `state.db` (so `session_search` sees only their chats) and skills are the profile's. `hermes/chat` refuses a member's other commands 403 `staff_command_refused`, a profile it could not prepare (or a box whose `clawbox_staff_guard` is not installed and enabled) 503 `staff_profile_unavailable`, a non-owner on a box whose switch cannot be read 503 `org_mode_unknown` (`orgMemberStrictOf`), drops the composer's model/provider and the slim `-t` toolsets, and answers every approval `deny`; a session the dashboard does not answer in the member's profile (`info.profile_name`) is refused, not run on the launch profile. **`clawbox_staff_guard`** (`scripts/hermes-plugins/`, installed and enabled by `register-mcp.sh` with the table and the staging directory) — `pre_tool_call`: on a staff profile home only, the same allow-list and folder rule, a relative path rewritten absolute inside the folder (`modify`); a Tool Search `tool_call` is judged by each tool it names (`{name, arguments}` or a `calls` batch); a staged attachment opens only for the member it was staged for, by the same owner record (`mediaOwners` in its `clawbox-paths.json`). A member's turn reads its record and billing rows from their profile's own `state.db` (`withHermesStateHome`, `src/lib/harness/hermes-turn-record.ts`), and `hermes/session-size` measures only their own conversations. Hermes keeps one plugin manager per profile home and scans only `<home>/plugins` for it (`hermes_cli/plugins.py` `_plugin_managers_by_home`), so a guard in the owner's `~/.hermes/plugins` alone never sees a member's calls: each staff profile's `plugins/clawbox_staff_guard` is a link to the installed one and its config enables it, made before the profile is first served.
- **Spoken replies** (`tts/speak`, allowed by `orgMemberVerdict`) follow the owner's Voice setting as before: the owner decides whether replies are spoken and with which voice. The agent's own `tts` tool is denied to staff on both runtimes.
- **Tests** — `org-staff-policy.test.ts`, `gateway-user-relay-staff.test.ts`, `org-staff-agents.test.ts`, `openclaw-staff-guard-plugin.test.ts` and `hermes-staff-profile.test.ts` (each with the two-member memory case: A's fact stays in A's folder/profile, B is refused it, the owner's MEMORY.md is untouched), `routes/hermes-chat-staff.test.ts`; on a board, `scripts/nano-tests/tests/56-org-mode-staff.sh` on both runtimes.

## Files per member of staff (TASK-2377)

With `org_mode` on, the Files API serves a member of staff ONLY their own Linux home and one shared folder — server-side, on every route (`files` listing, search, upload POST/PUT, mkdir, move, the selection ZIP and its ticket, `files/[...path]` download, folder ZIP, rename, delete). `src/lib/files-scope.ts` is the fence every route resolves through (`fenceFor`); `src/lib/files-scope-server.ts` (`filesFenceFor`) decides whose:

- **The owner, the agent's MCP bearer (no person) and every user of a home box** get the owner's browse root exactly as before — the owner's half of the fence is the route's old `safePath`, pinned by `safe-path-containment.test.ts` against beta's predicate.
- **A member of staff** gets a virtual top folder with two entries: `Home/…` — their own home (`getent passwd`, `userHomeDir`) — and `Shared/…` — `<owner home>/Shared`, created when missing, read and written by every member and the owner (the owner sees it as an ordinary folder in their home). Every listing answers `view: "member"`, and the Files app then offers Home, Shared and `Home/Documents|Downloads|Desktop` as its places (created in their home on first use). Nothing can be written at the virtual top (400 `virtual_root`), and neither root can be renamed, moved or deleted (400 `protected_container`).
- **Containment, twice**: a request is resolved under its root lexically (`..`, absolute paths, NUL and any other top name refused) and again with every link resolved (`canonicalPath`), so a symlink left in a home that leads into the owner's home, another member's home or `/etc` is neither listed, searched, zipped, downloaded, moved nor written through; the secret-store inventory (`isProtectedFilePath`) applies inside their own home too (`~/.ssh` …). A selection-ZIP ticket is redeemed only in the view that issued it (`ZipTicket.scope`).
- **Reaching the home**: the web server runs as the owner, and a member's home is 0750 theirs. The first request whose home it cannot open asks the root-owned helper's `home_access` verb (`grantHomeAccess`, username on STDIN; `config/clawbox-user-helper.sh`), which lays a POSIX ACL for the calling owner account (`$SUDO_USER`) on that home — `u:<owner>:rwx` on it, `rwX` on what is in it, a default ACL `u:<owner>:rwx,u:<member>:rwx` on every directory so what either side creates stays usable by both — never following a link (`setfacl -P`, `find` without `-L`, `-xdev`). A helper from before the verb, a filesystem without ACLs or no `setfacl` answers 503 `home_unavailable` (asked again after a minute) — never the owner's home instead. A home that holds or sits inside the owner's home is refused the same way.
- **A non-owner whose switch cannot be read** is answered 503 `org_mode_unknown` (`readOrgModeStrict`), and a request carrying a session cookie whose identity could not be resolved 503 `session_unknown` — never the owner's home. Paths split on `/` only, as the owner's rule (a backslash is part of a name on Linux).
- **Checked again at the open**: for a member, the file a download, an upload (PUT and multipart) or a ZIP entry actually OPENED is judged by its descriptor (`/proc/self/fd/<n>`, `openInMemberView`, `zipEntries`' `allowed`), so a path component swapped for a link between the fence's check and the open carries nothing out of their view; a write opens without truncating, is judged, then truncates, and a file it created outside the view is removed again; a failed upload is taken back by the path its descriptor was judged at (`unlinkInMemberView`), never by the path as typed. Node has no `openat`/`unlinkat`, so a parent swapped DURING the open could still create (and the open then removes) an empty file outside the view — a race with no actor on an organisation box, where a member has no shell and nothing they drive creates a link. Directory operations (listing, rename, delete, move) remain checked at resolve time — on an organisation box a member has no shell and nothing they can drive creates a link in their home.
- **Chat paths stay theirs**: `chat/media` serves a member only staged media recorded as theirs, `chat/attachments` stages uploads only, and `hermes/chat` / the staff guards open only their own staged files — no chat route reads a path in anyone's Files roots.

Tests: `files-scope.test.ts` (the fence: traversal, absolute paths, links out of Home to the owner's home, another member's home and `/etc`, `.ssh`, roots), `routes/files/member-scope.test.ts` (owner vs member vs bearer, org mode on/off/unreadable, every route, Shared shared, the ticket, the helper asked once); on a board, `56-org-mode-staff.sh` step 5.

## Staff MCP tools with each member's own credential (TASK-2377, G2)

The owner can let members of staff use some of the box's MCP servers — a document search that filters by each person's bearer, a Microsoft 365 gateway — with every call carrying THAT member's credential, never the owner's or another member's. **OpenClaw only**; on Hermes members of staff get no MCP tools (the staff profile is written with no `mcp_servers` and `clawbox_staff_guard` refuses every tool outside the staff table; the grant route answers 409 `unsupported_harness` there).

- **The owner's setting** — Settings → System → Users, "Tools for members of staff" (`StaffMcpCard.tsx`, `users.staffMcp.*` in all ten locales) over `GET|POST /setup-api/settings/staff-mcp`: owner's cookie only (another user, the agent's bearer: 403 `owner_only`), writes same-origin only (403 `cross_origin`). `POST {servers: {<name>: {header?}}}` is the granted list, whole — a name that is not a server's, an unknown server, the box's own `clawbox`, a relay entry or a server staff cannot use is 400; `POST {username, server, credential|null}` sets or clears one member's credential (1–4096 characters, no control characters). Only a Streamable HTTP server whose URL carries no userinfo or query, over HTTPS (plain HTTP only to a literal loopback address — `127.x.x.x` or `[::1]`, never a NAME such as `localhost`, which is whatever the resolver says — `insecure` otherwise), can be granted (`staffServerVerdict`): a stdio server runs as the owner with the owner's environment, SSE speaks a second endpoint, and a credential in the URL is the owner's. The credential travels in the header the owner names (`Authorization` by default, `Bearer ` added to a bare token; transport, cookie and session headers refused).
- **Applied, or not yet** — every change syncs the staff agents at once; when the config write or the guard's grants file fails, the POST still answers 200 with `applied: false` and the card says the change is saved but not active, with a Try again that posts the grants once more (any later sync — a member opening their chat — retries too). While the grants file cannot be written, or the store cannot be planned from, the sync writes NO relay entry into openclaw.json (revocations still go through): fail closed.
- **The store** — `data/staff-mcp.json` (`src/lib/staff-mcp.ts`), 0600, written whole by rename under one lock: the grants, each member's credentials and each member's relay token. It is never answered to anyone but the owner, and to the owner only masked (`••••` + the last four characters of a long value). Its maps have no prototype, so a user or server named `constructor` is never read as set. Removing a user removes their credentials and relay token (`forgetStaffMcpUser`, before the roster sync), and creating an account clears whatever an earlier account of that name left (`forgetStaffMcpUserStrict`, the create refused if it cannot — any error but ENOENT on the store is a failure). A credential write re-checks, under the store's own lock, that the SAME account still exists (username, `createdAt` and its random session version `sv`, so a removed-and-recreated name is a different account even within one clock tick), and the clean-ups always go through that lock, so a credential never lands for an account removed or replaced meanwhile. A store that cannot be read grants nothing.
- **How identity travels** — OpenClaw 2026.10.9 sends one fixed header set per `mcp.servers` entry and has no per-agent MCP config (its per-requester identity is OAuth through a public gateway origin only). So each member gets an entry of their OWN per granted server they have a credential for (`planStaffMcpEntries`): `cbstaff-<8 hex of the username>-<server>` (within the core's 30-character provider-safe server prefix; the server part becomes 8 hex when too long), `transport: "streamable-http"`, the URL of ClawBox's loopback relay `/setup-api/staff-mcp/<server>` (`getLocalAiProxyRootUrl()`), `Authorization: Bearer <that member's relay token>`, and the owner's own `toolFilter`. `syncStaffAgents` writes them with the roster (`planStaffRoster`'s `mcp` input): `<entry>__*` in THAT member's `tools.allow` (`staffAgentEntry`), `cbstaff-*` added to the `tools.deny` of every agent that is not a member's (so the owner's agents neither list nor call them; taken away again with the last grant), and every `cbstaff-*` entry nobody is granted any more unset. The owner's own entry for the server is untouched and the owner's agent keeps using it with the owner's headers. Members without a credential get no entry — no tools from that server.
- **The relay** (`src/lib/staff-mcp-relay.ts`, middleware lets `/setup-api/staff-mcp` through like the local-AI proxies; the route checks its own token): names the member by the relay token (constant time; none → 401), serves only while `org_mode` reads true, the member is still a registered user, the server is still granted and still a usable Streamable HTTP server in openclaw.json, and the member has a credential (otherwise 403/404 and nothing reaches the server); sends the request on with exactly the member's credential header plus the transport's own (`content-type`, `accept`, `mcp-session-id`, `mcp-protocol-version`, `last-event-id`) — never the relay token, the owner's headers or a cookie — and follows no redirect. **Tools**: the owner's include/exclude, then never a tool whose name carries a sending or writing verb (`send`, `write`, `create`, `update`, `delete`, `upload`, `move`, `share`, `reply`, `forward`, `run`, … — `staffToolAllowed`), nor one the server itself marks `destructiveHint: true` or `readOnlyHint: false`: `tools/list` answers are filtered (JSON or SSE — and every SSE stream, a resumed GET included, event by event), and a `tools/call` of anything else is answered with a JSON-RPC error (`-32601`) without reaching the server. A call is judged by what the server LISTED: every listed tool is remembered with its annotations (the refused ones too), a call naming a tool this relay has not seen listed (after a restart) makes it ask the server's list first with the member's credential, and a tool the server does not list at all is refused. A name run together without separators is read too (`sendmail`, `deletefile`: a word beginning with a verb of four letters or more). The owner can narrow a grant, never widen it to a sender. **What it cannot see**: a credential of the owner's carried in the server URL's PATH (`https://host/mcp/<key>`) — userinfo and query strings are refused, but a path is a path; such a server must not be granted, since every member's call goes to that URL.
- **The guard** — `clawbox-staff-guard` refuses a staff agent's MCP call unless its server (`<server>__<tool>`, or Tool Search's `tool_call` with `mcp:<server>:<tool>` / `<server>__<tool>`) is listed for that agent in `staff-mcp-grants.json` beside the installed plugin (written by `syncStaffAgents` before the config, 0600; missing or unreadable grants nothing); `clawbox__*` and every other server are refused; and any OTHER agent's call to a `cbstaff-` entry is refused (it carries a member's token). `gateway-pre-start.sh`'s install probe proves those cases on the installed copy. The prefix is `config/org-staff-policy.json`'s `mcpEntryPrefix`; `project-mcp-servers.ts` never lists a `cbstaff-` entry, so no coding run is handed a member's relay token.
- **Tests** — `staff-mcp.test.ts`, `routes/staff-mcp-relay.test.ts` (a real stub server echoing the credential: A's, B's, none, a withdrawn grant, a removed user, org mode off, the owner's headers never sent, the list filtered, a sender refused before the server), `routes/settings-staff-mcp.test.ts`, the MCP cases in `org-staff-agents.test.ts` and `openclaw-staff-guard-plugin.test.ts`; on a board, `56-org-mode-staff.sh` step 6 (`scripts/nano-tests/board/org-mode-staff-mcp.mjs`) on both runtimes.

## The owner resets a user's password (TASK-2377)

Settings → System → Users → **Reset password** (`UserPasswordReset.tsx`) posts `POST /setup-api/users/password {username, password}`: the owner's cookie and our own page only (another user or the bearer 403 `owner_only`, another site 403 `cross_origin`); the owner's own account 409 `owner_password`; an unknown user 404; the same 8–256-character rule as Account. Under the same `password-change-lock.ts` as a user's own change, the user's session version is rotated FIRST — every session of theirs ends, and if that cannot be stored nothing changes (500 `sessions_not_ended`) — and only then does the helper's `setpasswd` verb (`resetUserPassword`; user and new password on STDIN, `clawbox-users` members only, one record to chpasswd; 7 not a ClawBox user, 65 bad password, 66 chpasswd failed) set the password. A helper from before the verb answers 503 `password_change_unavailable` until the box updates. Tests: `routes/users-password-reset.test.ts`, `clawbox-users.test.ts`.

**A user's own password** (Settings → Account, every non-owner on any box): `POST /setup-api/users/me/password {currentPassword, password}` (a person's cookie and same-origin; the owner is answered 409 — theirs is `system/credentials`). The route checks the current password first (the helper's `verify`), then ends every other session (a new `sv`; this browser re-signed), and only then changes the password, so a password never changes while older sessions stay valid — a version that cannot be stored changes nothing (500 `sessions_not_ended`). The whole change holds `src/lib/password-change-lock.ts` (process store): `/login-api` answers that account 409 `password_changing` while it runs, and refuses a sign-in whose check began before a change and finished after it (the per-account epoch moved), so the old password cannot mint a cookie under the new session version. `changeUserPassword` (`src/lib/clawbox-users.ts`) runs the helper's `passwd` verb (`sudo -n clawbox-user-helper.sh passwd`, user/current/new on STDIN): root checks the current password with `unix_chkpwd` and only then pipes ONE `user:password` record to chpasswd, for a `clawbox-users` member only. Exit 7 is a wrong password (400 `wrong_password`, never 401), 65 a new password outside 8–256 characters, 66 chpasswd refusing; a helper from before the verb (64) or no grant is 503 `password_change_unavailable` until the box updates (`install_root_libexec` installs the helper). Wrong guesses are charged to the login's own durable per-account bucket (`user:<name>`, `src/lib/login-rate-limit.ts`, capped at `SHARED_BUCKET_MAX_LOCK_MS`), so this door and `/login-api` share one limit that outlives a restart; a locked account is answered 429 without asking the helper, and only one guess per account is in flight at a time. `rotateUserSessionVersion` reads the registry with `getKnown` (an unreadable store throws, never `get`'s empty reading) and is tried twice; every answer after it carries the re-signed cookie. A lock the shared bucket reports but cannot store (a full table) is held in the process too. Creating a user clears whatever an earlier account of that name left (`prefs_by_user`, `ui_language_by_user`) before the account exists, and refuses the create if it cannot.
