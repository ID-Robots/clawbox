# Setup API routes and middleware

The `/setup-api/*` route families no feature file owns (WiFi, System, Preferences, KV, Gateway) and the middleware (captive portal, authentication, the update lock). Read it when you add or change a route under `src/app/setup-api/` or touch `src/middleware.ts`; a feature's own routes are in its area file.

The other route families are written up with their feature: `ai-models/*`, `providers/*` and `ollama/*` in [ai-providers.md](ai-providers.md); `tts` and `stt` in [voice.md](voice.md); `embed/*` in [memory-shard.md](memory-shard.md); `prime-radiant/*` in [prime-radiant.md](prime-radiant.md); `apps/*`, `code/` and `webapps/` in [apps-and-webapps.md](apps-and-webapps.md); `files/` in [files.md](files.md); `system/battery`, `desktop/state` and `monitors` in [desktop.md](desktop.md); `browser/` in [browser.md](browser.md); `harness/*` in [harness-swap.md](harness-swap.md); `hermes/plugins/reload` in [harness-hermes.md](harness-hermes.md); `telegram/*` and `discord/*` in [channels.md](channels.md); `email/*` in [email.md](email.md); `setup/*` in [setup-wizard.md](setup-wizard.md); `update/*` and `whats-new` in [update-and-install.md](update-and-install.md); `coding-agent/*` in [coding-agent.md](coding-agent.md); users in [multi-user.md](multi-user.md).

## Setup API Routes (`src/app/setup-api/`)

50+ Next.js Route Handlers namespaced under `/setup-api/` to avoid conflicts with the OpenClaw gateway's `/api/*`:

- **WiFi**: `wifi/scan`, `wifi/connect`, `wifi/status`, `wifi/ethernet` — WiFi and Ethernet management
- **System**: `system/info`, `system/stats`, `system/power`, `system/credentials`, `system/hotspot`, `system/desktop`, `system/power-profile` — system info, power control, password, hotspot config, desktop/headless toggle, Jetson power profile + memory guards. `system/power-profile`'s PERFORMANCE mode (`nvpmodel` MAXN + `jetson_clocks`, `scripts/clawbox-power-mode.sh`) is the DEFAULT since 2026-09-15 (owner's ruling): the script's `DEFAULT_MODE` resolves an absent or invalid `/etc/clawbox/power-mode` to `performance`, `persistedPowerIntent()` in `src/lib/system-profile.ts` falls back the same way, `step_performance_mode`'s `--apply` on every full install — and `clawbox-performance.service` at every boot, the reboot that ends every in-app update included — is what turns it on for a box already in the field. The in-app update itself does NOT touch the power profile since 2026-09-17 (owner's ruling): the `performance_mode` step is off `UPDATE_STEPS` — it had pinned the clocks one step ahead of the npm install on 2026-09-16, when three field boxes went dark inside `openclaw_install` and stayed dark until power-cycled, then for a few hours unpinned for the update's length instead — so the box keeps the profile it booted with and the closing reboot applies the persisted or default one again; `update_owns_the_box` in install.sh stays for a hand-run `--step performance_mode` while an update is in flight, which unpins (`clawbox-power-mode.sh --restore`, the unit's ExecStop verb, persisting nothing) rather than pins. Balanced is the owner's opt-out — persisted by `--balanced`, returned by `read_mode` untouched, so it survives every update. `system/timezone` (owner-only, same-origin; one transition at a time through an in-process queue, because TimezoneAdopter fires it from every open tab and two overlapping zones once let a root step read the other request's env file while the process took its own) is the box's zone in three places — the OS through the `set_timezone` root step, each harness's own key, and since F-B of the Memory Shard sweep the RUNNING web server too: behind a landed OS leg it calls `applyProcessTimeZone` (`src/lib/timezone.ts`, a validated `process.env.TZ`, which Node honours at runtime) and re-reads both schedulers (`clawkeep-scheduler`, `clawkeep-memory-scheduler` — their `setHours` is in the PROCESS zone, so a server started in UTC armed "Tue 04:30" at 07:30 local until it restarted), and `src/instrumentation.ts` seeds the same zone at boot, awaited and before either scheduler arms, only when `timezone_applied` equals `timezone`
- **Gateway**: `gateway/`, `gateway/health`, `gateway/ws-config` — gateway proxying with HTML injection
- **Preferences**: `preferences/` — persistent user preferences (language, installed apps, etc.; `?keys=ui_language` alone is readable with no session, see the middleware's `UI_LANGUAGE_READ`) — a POST naming an `installed_*` key is refused 403 `owner_only` unless `hasOwnerSession` (cookie, never the MCP bearer): `installed_meta[id].launch = "window"` makes the desktop `window.open` the app's URL top-level, and the middleware admits the bearer to this route like any other — without that in-handler check a bearer holder could have planted an entry; with it, bearer access to the route does not reach the `installed_*` keys; install/uninstall and `webapp-registry.ts` write the store directly and the desktop reads the prefix, so no legitimate caller loses anything.
- **KV Store**: `kv/` — key-value store for UI state

All dynamic API routes use `export const dynamic = "force-dynamic"` to prevent caching.

## Middleware (`src/middleware.ts`)

Handles three concerns (plus one carve-out: `UI_LANGUAGE_READ` — a GET of `/setup-api/preferences?keys=ui_language`, path and query byte for byte — is answered with no session, because `/login` renders inside the same I18nProvider as the desktop and asks for the box's language on mount; answered 401 it fell back to the browser's language, so a box set to German greeted its owner in English (the sweep of 2026-09-07); the preferences route makes the same cut on its own side, `ANONYMOUS_READABLE_KEYS`, so nothing wider is ever told to an anonymous caller):
1. **Captive portal detection** — intercepts OS-specific detection URLs (Android, Apple, Windows, Firefox) and redirects to `http://10.42.0.1/`
2. **Authentication** — enforces session cookie auth, redirects unauthenticated users to `/login`
3. **The update lock** — while an update owns the box, desktop page navigations (`/` and `/app/*`) are redirected to `/updating`. An update runs `git reset --hard` and `git clean -fd` over the project while the desktop is still on screen and every app on it can write through `/setup-api`, so a window left open can save into a tree being rewritten underneath it. The flag is on DISK (`update_in_progress`, `src/lib/update-lock.ts`) rather than in the updater's memory, because middleware answers before any route handler is entered — it reads the same mtime-cached `data/config.json` snapshot it already reads for `setup_complete`, so the lock costs no extra I/O. `/setup-api` is deliberately NOT redirected (the updating page polls the status route, and an API answering a navigation redirect with HTML is the defect #304 fixed), nor is the gateway (the assistant keeps answering on it throughout). The check sits after the session check, so an expired session still gets `/login`. The acquisition is AWAITED at the top of `runUpdate`, scoped to the flow that contains the RESTART step (the OpenClaw-only flow reinstalls a package and bounces the gateway; locking the desktop for that would be over-reach), and a failure to take or release the lock is reported rather than swallowed — it never stops the update, because refusing to update a box over a courtesy lock is the worse outcome. The flag OUTLIVES the reboot on purpose — the release is in `launchUpdate`'s `finally`, which does not run when `do_rebuild` kills the server, so the desktop stays locked through `post_update` and `gateway_verify` — and cannot outlive a dead update, because `resumeContinuation` releases it at boot when there is nothing to resume. That boot release is also the only escape that works, so `/updating`'s stuck panel names a restart rather than offering a link back to the desktop, which the middleware would redirect straight back. The page gives every string an English floor (`tr(key, english)`): `I18nProvider` loads translations in an effect through a dynamic import, and this is the one screen guaranteed to be open while the box is offline — raw keys for the length of an outage is not an acceptable answer.
