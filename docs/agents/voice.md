# Voice

Speech output (TTS: ClawBox cloud or Kokoro on the box) and input (STT: cloud or Whisper) on every edition, spoken replies and hold-to-talk. Read it when you touch the `tts`/`stt` routes, `voice-*`, `stt-*`, `tts-*`, `chat-hold-to-talk.ts` or the Kokoro and Whisper scripts.

## Setup API Routes (`src/app/setup-api/`)

- **Voice**: `tts` — speech output, on EVERY edition: which engine speaks first (ClawBox cloud or Kokoro on the box), the voice each engine speaks with (`{action:"voice"}` — the local one is the file `clawbox-tts.sh` reads, the cloud one is the harness's own key). Writes go to whichever harness will actually speak, chosen by `getActiveHarness()` so the dual SKU writes the one that is talking: OpenClaw's `tts.providers.<cloud>.voice` via its CLI, or Hermes' native `tts.*` block via `hermes config set` (`src/lib/hermes-tts.ts` — "ClawBox cloud" is `tts.provider: openai` with `tts.openai.base_url` on the ClawBox AI proxy, "This box" is `tts.providers.clawbox-local`, a `type: command` provider wrapping the same `clawbox-tts.sh`; Hermes' factory `edge` is Microsoft's cloud voice and is never offered or kept). Only spoken replies on CHANNELS are OpenClaw-only, reported as `channels.supportedOnEdition` the way `stt` reports its own channel half; beside it `channels.voiceNoteReady` (`ffmpegPresent()` in `src/lib/local-models.ts` — the PATH walked rather than a shell spawned, since this is read on every Voice-tab load, failing closed and never cached because the whole point is that it flips the moment the voice install has run) answers the same question about THIS box: a channel voice note is Opus and Kokoro speaks WAV, so OpenClaw's Local CLI provider forces the `opus` format for that target and converts our WAV with `ffmpeg -c:a libopus`, and on a box without ffmpeg the local attempt throws for EVERY Telegram voice note and the gateway falls through to the cloud voice — invisibly, because the Voice tab, Local AI and the gateway's own status all still say the box speaks for itself. Two fields rather than one folded fact, because "this edition has no channels" and "this box cannot encode a voice note" have different fixes. The route also carries the sample language (the desktop's UI language until the owner picks one; only `{action:"language"}` persists a pick). Every refusal carries a stable `code` beside its English `error`, and the status carries the privacy notice as a fact (`disclosure: {kind, providers}`) beside the worded `warning`. No screen renders either any more — the chat's yellow cloud-TTS banner was removed at the owner's request and `CloudTtsWarning.tsx` deleted with it — but the two fields and `src/lib/tts-cloud-warning.ts` stay, because they are the route's contract and what its tests pin, so a surface asked for the notice again words the chain in the owner's language instead of deriving it a second time. `tts/sample` answers the WAV for the Voice tab's player: on OpenClaw it speaks typed text with ONE engine and voice — deliberately not the fall-through chain, because an audition of the cloud voice that quietly played Kokoro would be the wrong answer — and on a Hermes box it goes through Hermes' own `POST /api/audio/speak`, which resolves the same `tts.provider` the tab just wrote, so the sample and the box's real replies cannot disagree; on OpenClaw, when `clawbox-tts.sh` refuses, its stated reason reaches the owner (the memory guard as `local_memory` with the numbers), never its install hint or a path; on Hermes the refusal comes back through the harness, said in the words of the engine the owner pressed play on. `stt` — speech input: `stt_primary` orders ClawBox cloud transcription and Whisper on the box for BOTH the chat microphone (`chat/transcribe`, which now falls through and reports `engine`) and channel voice notes (`tools.media.models[]`, OpenClaw 2's shared media-model list — audio rows tagged `capabilities: ["audio"]` — tried in order). Microsoft's bundled Edge TTS is switched off at boot on any box with its own voice (`ensureMicrosoftTtsExcluded`), so the speech chain is exactly cloud → Kokoro. `tts/speak` (`{text}`) speaks a chat REPLY through the chain — the engine the Voice tab put first, then the other (`src/lib/voice-speak.ts`, shared with `sample`) — with the Markdown lifted off (`src/lib/speech-text.ts`) and capped, naming the engine that spoke in `X-ClawBox-Voice-Engine`; on the OPENCLAW edition it is what the desktop chat asks for on every reply to a question the owner asked there, because the gateway speaks none of them: a turn from that surface reaches it as text (the recording is transcribed on the box), so `tts.auto: "inbound"` never sees the `inboundAudio` its own guard requires — measured on 2026.8.1's `maybeApplyTtsToPayloadCore` — which is why `spokenReplyTrigger` there is `'chat'` and not `'harness'`. On HERMES the same clip is made inside the turn instead, by `speakHermesReply` in `hermes/chat/route.ts` (`spokenReplyTrigger: 'box'`), and the chat asks for nothing; `tts/speak` still serves that edition for a SPOKEN question's reply, through Hermes' own speech route. Either way the clip is played at once when the question was SPOKEN and left on the bubble to press when it was typed, and the route is refused while the spoken-replies switch is off. That switch (`{action:"autoReply", enabled}`, owner-only, `autoReply` in the status, `voice_auto_reply` in the config store, OFF by default since 2026-09-15 — only a stored `true` speaks — `src/lib/voice-reply.ts`) writes OpenClaw's `tts.auto` as `inbound`/`off` so a channel voice note is answered with a voice note and a typed CHANNEL message never is; the desktop chat is the other half and is not the gateway's to answer at all (see `tts/speak` above); the boot repair `ensureVoiceAutoReplyMode` seeds the mode once on a box that predates the switch, and flips the previous build's own `inbound` seed to `off` once when no answer is stored (recording `voice_auto_reply: false`, so it runs once) — never over an answer the owner stored or a hand-set `always`/`tagged`. Under it sits "Auto-play every spoken reply" (`{action:"autoPlayAll", enabled}`, the same owner-only and same-origin gate, `autoPlayAll` in the status, `voice_auto_play_all` in the config store, OFF unless a stored `true`). It belongs to the desktop chat alone and writes nothing to any harness, so a typed CHANNEL message still gets a typed answer. When it is on, the reply to a TYPED question in the chat plays by itself, exactly as a spoken question's reply does: the clip the reply came with, or the one the chat owes it, through the same queue and with the same `chat.tapToHearReply` fallback. It applies only to the owner's own turn landing live in the tab and conversation that asked (the one-shot `askedTurnKeyRef`), and never on a tab return, a history load or a reconnect. The owner must also be at the chat (popup open, tab visible) both when the reply lands and when its sound would start; otherwise the clip stays on the bubble to press. A `/setup-api/tts` read that a `VOICE_SETTINGS_CHANGED_EVENT` overtook loses to the event, in the chat and in the panel. It decides whether a clip PLAYS, never whether one is made. The Voice tab greys it out, keeping its position, while spoken replies are off; its strings are `settings.voice.autoPlayAll*`, in the desktop translation files. Selecting the box's own voice (`{action:"select", choice:"local"}`) REPAIRS the wiring when Kokoro is installed but openclaw.json has no `tts-local-cli` entry (`src/lib/voice-local-wiring.ts` writes the same provider JSON install.sh does, asking `clawbox-tts.sh --provider-timeout-ms` for the timeout), and when the pick still cannot be honoured it settles on Auto and answers 200 with `fallback: { requested, reason: "not_installed" | "not_wired" }` instead of a 409 — the panels show that in amber. `tts/install` (owner-only, streamed like the Gemma install, on EVERY edition — the step's Hermes arm registers `clawbox-local`) runs install.sh's `voice_kokoro_install` root step for an absent Kokoro — `step_openclaw_tts --kokoro`, the one path that installs the engine since 2026-09-15 (owner's ruling: install.sh force-installs no model or engine but the llama.cpp runtime and Gemma 4; `openclaw_tts` itself, which every install and update still runs, calls `install-voice.sh --scripts-only`, refreshes the scripts and the units of the engines that are present, publishes the verdict `absent` for a box that never installed Kokoro and treats it as a plain state — one informational line, exit 0, nothing recorded — while `install-voice.sh --whisper`, behind `voice_whisper_install` and `POST /setup-api/whisper {action:"install-engine"}`, is the STT engine's own click) — and for an absent encoder too: `tts_ensure_ffmpeg` runs at the TOP of that step, ahead of the engine because it also has to reach the Hermes arm, which returns before the OpenClaw registration, and it WARNS rather than failing when apt cannot be reached (a box that cannot reach a mirror still has a working chat voice, and losing the whole voice install over one download would be the worse outcome). `openclaw_tts` and the two `voice_*_install` steps are on the WEB root-step list and deliberately not on the UI list, which `install/run-step` serves to the MCP bearer too. `tts/warm` (POST, owner cookie AND same origin — spawning systemctl is the person's doing, not another site's page and not the MCP bearer the middleware also admits; deliberately NOT gated on the edition, since `install-voice.sh` writes the Kokoro unit on every SKU and both harnesses speak through the same script) asks systemd to bring the box's own voice up before anything needs it: `startUserEngine` (`src/lib/local-models.ts`) runs `systemctl --user start --no-block` for `KOKORO_UNIT` and nothing else (allow-listed, and never `enable` — that is Local AI's standing switch, and an engine the owner switched off for good must not come back at the next boot because a chat turn warmed it), answering 200 `{warm:true}` for a unit already up, 202 `{warming:true}` once systemd has the request, 409 `not_installed` where there is no unit and 502 `start_failed`. It exists because the Kokoro server holds the model on the GPU and stops itself after five idle minutes while nothing on the box brings it back, so the first utterance after a quiet spell pays a 13-19 s cold start and usually loses the race to the cloud voice; the two surfaces that KNOW a spoken reply is coming call it the moment the person acts — the chat's microphone button before it starts recording (only while the spoken-replies switch is on, so the recording, the transcription and the agent's turn all run while the model loads) and the Voice tab's "This box" pick, ahead of the write rather than after it, both fire-and-forget so a 409 cannot colour an action that worked. `stt` — speech input: `stt_primary` orders ClawBox cloud transcription and Whisper on the box for BOTH the chat microphone (`chat/transcribe`, which now falls through and reports `engine`) and channel voice notes (`tools.media.models[]`, OpenClaw 2's shared media-model list — audio rows tagged `capabilities: ["audio"]` — tried in order). Microsoft's bundled Edge TTS is switched off at boot on any box with its own voice (`ensureMicrosoftTtsExcluded`), so the speech chain is exactly cloud → Kokoro.

## Server Libraries (`src/lib/`)

- **`stt-preference.ts`** / **`stt-local.ts`** — speech-input ordering (`stt_primary`, the `tools.media.models[]` shapes the boot script recognises as ours) and the on-box Whisper client (temp file, `stt-client.py`, never throws). On OpenClaw 2 that list is shared by every media capability, so rows without `"audio"` — the ClawBox AI video row (`clawai-video-describe.py`, see harness-openclaw.md), an owner's vision row — are neither ordered nor counted as a reason to write by `syncChannelAudio`, which carries them along. `chat/transcribe` falls through to the other engine on ANY failure of the first (4xx, 5xx, network, timeout, a throw) and logs each fallback.
- **`stt-remux.ts`** — the cloud leg's copy-only `ffmpeg` remux of a Matroska/WebM recording (EBML magic) into a temp FILE, because `MediaRecorder` WebM has no duration and the proxy answers it 400 `unsupported_audio`; Opus transcode if the copy fails, the recording as-is if both do. Never throws.
- **`voice-reply-format.ts`** / **`tts-compress.ts`** — spoken REPLIES are compressed, never WAV unless nothing else can be made. `tts/speak` reads `formats` (what the chat's browser said `canPlayType` plays, `playableReplyFormats`) and answers Ogg Opus (`audio/ogg`) where Opus is listed, MP3 (`audio/mpeg`) otherwise and to a request that states nothing. The cloud is asked for that `response_format` (an Opus refusal of 400/404/415/422 is asked once more for MP3); any WAV — Kokoro's only output, a Hermes provider's — is encoded by ffmpeg to temp FILES (mono `libmp3lame` 48k / `libopus` 32k), and no ffmpeg or a failed encode sends the WAV rather than failing the reply. Content-Type and the size floor (`minAudioBytesFor`) follow the sniffed bytes. A Hermes chat clip is stored as MP3, since any browser may replay it. The Voice-tab audition and `generate_audio` (no `format`) stay WAV. A 15 s reply: 722 KB WAV → 91 KB MP3 / 56 KB Opus.
- **`chat-hold-to-talk.ts`** — hold to talk in the mascot chat. Hold the mic button: a release after `HOLD_MIN_MS` (300 ms) sends like Stop, a quicker tap keeps the click-to-start/click-to-stop toggle, and a release dragged off the button cancels, as an abandoned click would. Or hold **F8** while the chat is open: a shorter hold is cancelled (`error: "short"`), key-repeat is ignored, and the key is left to a terminal or a focused canvas (VNC). While held, Escape cancels without closing the chat; blur, a hidden tab, the chat closing or `pointercancel` cancel and release the microphone. `stepHold` is the pure reducer, and ChatPopup performs it with the same stop/cancel the buttons use.

## System Integration (`scripts/`, `config/`)

- **`scripts/kokoro-*.sh`** / **`scripts/kokoro-server.py`** / **`scripts/openclaw/clawbox-tts.sh`** — voice/TTS integration. There is ONE `kokoro-server.py` now: the `scripts/openclaw/` copy nothing deployed is deleted (`install-voice.sh` has always copied the top-level one into the workspace, so the second could only drift, and it had already missed a fix), and the surviving one unlinks `/tmp/kokoro-server.sock` on its idle shutdown — `os._exit` runs no cleanup, so the file outlived every idle exit and the cheap `[ -S … ]` "is the server up?" test kept answering yes for a socket nothing was listening on. `clawbox-tts.sh` reads its ~2.6 GB memory guard on the COLD path only, immediately before the CUDA load the guard protects: in front of the resident server it refused requests that allocate nothing like that, and on this board — ollama keeps its model resident for five minutes after every agent turn, leaving ~2.8 GB — that meant every spoken reply following a chat message went to the cloud voice while the box's own engine was up and idle. After paying for a cold start it asks systemd for `kokoro-server.service` (`warm_kokoro_server`, `--no-block`, unconditionally rather than behind the socket test that was lying, and best-effort AFTER the caller's audio is on disk so it can never turn a good utterance into a failed one), because nothing else on the box restarts a server that stops itself every five idle minutes The Unix socket is bound under `umask 0177` and chmod 0600 (it was 0666 — every legitimate client is the clawbox user, and root bypasses the mode), every accepted connection is checked with `SO_PEERCRED` (uid must be the server's or 0), and a request must name an `output` that is an absolute `.wav` regular file (never a symlink) owned by the server's uid directly under `/tmp` (`resolve_output`; both real clients mktemp the WAV there first), written through `O_NOFOLLOW` — a caller could otherwise have the server truncate any clawbox-owned file with WAV bytes (`openclaw.json`, `data/config.json`). `whisper-server.py` carries the socket half only: its `audio` field is a READ path the gateway hands in from wherever it downloaded a voice note. `install-voice.sh` `try-restart`s both user units after deploying the scripts so a resident server does not keep the old socket until its idle exit.
- **`scripts/stt.py`** / **`scripts/whisper-server.py`** — speech-to-text via Whisper
