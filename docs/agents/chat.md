# Chat

The chat surfaces (`ChatApp` full page, `ChatPopup` mascot chat), cross-device chat tabs and Markdown rendering. Read it when you touch the chat components, `chat-*` libraries or the `chat/*` routes.

## Server Libraries (`src/lib/`)

- **`chat-tabs.ts`** / **`chat-tab-store.ts`** — the chat strip's side conversations as ONE list for every browser signed in to the box (TASK-1159: a tab opened on the phone was missing from the desktop, because the list was each browser's localStorage while the sessions behind it were on the box all along). `chat-tabs.ts` is client-safe — the record, the two tab key shapes (`agent:<id>:clawbox-<id>`, `desktop-<id>`; never main, a channel's or a cron session), the first-message label, and the monotonic merge (add, a placeholder takes its first real name once, a close is final and outlives any device's cached copy, a clashing "Chat N" takes the next N). `chat-tab-store.ts` keeps it in `data/chat-tabs.json` (0600, synchronous read-merge-write, wiped by factory reset) and adopts tab-shaped sessions nothing listed: Hermes transcripts, and OpenClaw session-store rows (read-only; legacy `sessions.json` too). `POST /setup-api/chat/tabs { upsert, close }` is owner-cookie and same-origin only (the MCP bearer gets 403 `owner_only`); `GET` needs the session. `ChatPopup` paints its localStorage cache, then syncs on connect, on every +/close/naming, on focus/visibility and once a minute while open, applying only the latest answer. Which tab is OPEN follows the owner across devices (TASK-1364: a conversation started on the desktop sat on the phone's strip while the phone opened main): the inventory also keeps `active` — `{ key, at }`, key null for main, `at` the BOX's clock and never earlier than the record it replaces — the conversation the owner last sent a turn in; every turn POSTs `activity: { key }` (ChatPopup's `dispatchTurn`, ChatApp's send — main only), the route answers `{ tabs, active }`, and closing the recorded tab clears it. `conversationToFollow` (pure) decides: a device moves only when the record is newer than `seenActiveAt` (localStorage, beside the cached strip — its own turns, the record it last followed, the record current when the owner picked a tab by hand), and only on an ARRIVAL (mount, the chat opening, focus/visibility) — never on the minute tick, never while its own turn runs. The popup GETs the route once at mount so the first bind opens that conversation straight away instead of painting main first. `ChatApp` now subscribes `sessions.messages.subscribe` for main and re-reads on `session.message`, so a turn typed on another device shows without a reload; on a harness with no live connection both chats re-read the transcript on focus/visibility and every `TRANSCRIPT_REFRESH_MS` (5 s) while visible and idle. Pinned by `chat-active-conversation.test.ts`, `chat-continue-across-devices.test.tsx`, the route tests, and `e2e/chat-cross-device.spec.ts` (two browser contexts, one fake gateway via `routeWebSocket`).
- **`chat-markdown.tsx`** — Markdown rendering for chat messages.

## Frontend (`src/components/`)

### Built-in Apps

- **`ChatApp.tsx`** / **`ChatPopup.tsx`** — AI chat, on EITHER harness. Both surfaces resolve which one answers through `useHarnessAdapter` (`src/lib/harness/`) and branch on `capabilities`, never on the harness id; the gateway socket's own lifecycle stays in each component and reaches the adapter through `GatewayLink`, so a box with no gateway opens no socket and renders no connection banner. `ChatApp` is the FULL PAGE (`/app/clawbox`, behind "Open in new tab" and what a phone lands on) and adopted that adapter in TASK-803: it used to fetch `/setup-api/gateway/ws-config` unconditionally, so on the Hermes edition its composer sat disabled behind "Could not connect to gateway" for ever while the mascot popup worked on the same box — two chat implementations and only one of them harness-aware. Its attachments stage through `/setup-api/chat/attachments` like the popup's (the adapter names a file by absolute path, which is also what the shared history projection reads back), and it renders neither a clarify card nor a reasoning disclosure, so a Hermes agent that parks on a question stalls there — answer it from the mascot chat. Escape on the New App card stops at the document (`NewAppWizardCard` calls `stopPropagation`), because the browser flushes the card's close between listeners and the chat's window listener then saw the same key and closed the whole panel; the composer re-measures its height on every change of `input`, so a sent message leaves a one-row box; Dock to right restores the width the panel was undocked at for the session (the desktop persists 0 while undocked). A spoken reply now says what it is doing instead of leaving a gap: `ChatPopup` draws "Speaking the reply… {seconds}s" (`chat.speakingReply`, under the newest bubble, the counter started only once the one-at-a-time queue has let THIS reply through so it never counts an earlier reply's seconds) while `/setup-api/tts/speak` works on a reply that will be PLAYED — by default a typed question's clip is made silently, on its own queue, and claims nothing on screen; with auto-play on (see `tts` above) it takes the spoken path instead — the words land first and a cold Kokoro follows 13-19 s later, so the chat looked finished and then spoke out of nowhere; it labels a clip the CLOUD voice spoke (`chat.spokenByCloud`, kept per object URL from the route's `X-ClawBox-Voice-Engine`, because an owner who picked "This box" has no other way to learn that these particular words went off the box — the sound is the same either way — and an older server sends no header, so nothing is claimed); and it says a refused autoplay out loud (`chat.tapToHearReply` — iOS Safari wants the gesture and the sound in the same tick, and that rejection used to be swallowed whole, so a spoken question was answered in what looked like silence). Both notes are released with the object URLs they belong to. The panel reads `autoReply`, `autoPlayAll` and `engines` from `/setup-api/tts` and nothing else, on open and from `VOICE_SETTINGS_CHANGED_EVENT`, so no reload is needed after a change: it also tested a top-level `supportedOnEdition` the route has never sent (that fact is nested under `channels`) and which named the wrong half anyway — a channel is the gateway's, a reply HERE is `tts/speak`, which a Hermes box answers through its own harness. `engines` is what stops the chat asking a box that has positively reported every engine unconfigured. Settings → Voice is the ONE switch for spoken replies: the composer's speaker button (TASK-782) was taken back out at the owner's word, and the chat only reads that switch now. The yellow cloud-TTS banner is gone from both surfaces. An operator approval card (`chat-approvals.tsx`, `ApprovalPrompt`) offers **Allow all (N)** beside Allow once while more than one approval is waiting (the owner's ask, 2026-09-07 — a turn raised a card per shell command): it answers every waiting card with `allow-once`, one `approval.resolve` each, never `allow-always`, so a request that offers no standing allow is not widened by it; `chat-approval-card-batch.test.tsx` pins that a single card offers no batch and that the per-card decisions stay allow-once and deny. The `clawbox-web-taint` plugin that once raised such a card for every shell call in a turn that had read the web is gone (the owner's decision, 2026-09-15: "no warnings and pop-ups"); `gateway-pre-start.sh` now only removes it from a box in the field, and the card is OpenClaw's own exec approvals'. The transcript FOLLOWS its newest line while the reader is at the bottom (`src/lib/use-stick-to-bottom.ts`: a ResizeObserver on every direct child and a MutationObserver on the subtree, pinned by the reader's own scroll position within 80 px): scrolling only on `messages`/streaming/queued sends left tool pills, the coding-agent card, approval and clarify cards and late-loading pictures growing below the fold; a reader who scrolled up is never moved. The full-page `ChatApp` wires the same hook to its messages area. Every bubble is a memoised row — `ChatMessageRow.tsx` for the popup (with `StreamingReplyBubble`), `ChatAppMessageRow` inside `ChatApp.tsx` for the full page's own markup — compared by VALUE (`samePlainData`, `src/lib/same-plain-data.ts`): the popup renders on every keystroke, streamed chunk and desktop render, a history reconcile rebuilds every message object, and each such render used to parse every reply's Markdown again; now the streaming reply is re-parsed per chunk and nothing else is. The turn clock, "Speaking the reply… Ns" (held as a start time, so a reply whose wait begins in the tick the last one ended still counts from 0) and the microphone clock tick in spans of their own (`ChatStatusClocks.tsx`); a drag or a resize of the popup writes its style directly and commits state once on release — or on a touch the system cancels, which ends it where it stands and snaps nothing (see `scripts/perf/desktop-perf.mjs`); the coding-run poll (`use-coding-agent-activity.ts`) hands back the same array, and an unchanged run the same object, when nothing moved; and a model-state re-read (once a minute and on every focus) equal by value keeps the object on screen — unless a refused reasoning-level push is still owed its retry, or the stored effort differs from the one shown (another window of this browser saved it), when the fresh object goes through exactly as before. A provider-set signal (`onProvidersChanged`) no longer renders the chat to get a hook's effect re-run: `useProviderCatalog` restarts its read inside the effect — one `?refresh=1`, the read in flight aborted, the warming poll dropped and its budget back to zero, plain reads after that, exactly the requests the old counter-driven re-run made — and `useHermesModelOptions` (the Hermes model list the pill and Settings' Hermes provider panel draw) restarts its own the same way, plainly: the read in flight and a booked retry dropped, the retry count back to zero, `refresh=1` only when the read it drops was a Refresh the owner pressed (a signal never sets that flag — a refresh makes the server re-enumerate every provider's live `/v1/models`). It listens only while it HAS a provider, so an OpenClaw box (provider null) is no longer rendered on every signal to ask nothing, and a provider switch inside the signal's 150 ms debounce no longer adds a second read for the new provider, which the switch itself reads. Those two and `useHarnessAdapter` drop an answer equal to what is shown BEFORE it reaches React (`liveRef`, `loadedRef` — the scope compared field by field, every field the route sends — and `factsRef`), because handing a setter the value it already holds can still cost its host — the whole popup — one render; a catalogue re-ask the server says is still pending is a fresh object on purpose, so its chase re-arms from that moment. The popup is `memo()`ed, so it is no longer re-rendered by every desktop render, and the one placement worked out from the window's size in render — the popup hanging above the mascot or the tray, whose `left` is a share of the width — went stale with it (a window narrowed from 1920 to 1280 px left it off screen until the mascot was tapped): `useViewportSize` (`useSyncExternalStore` on `resize`) re-renders it only while that placement reads the size — open, not docked, not dragged or resized by the owner, not on a phone (CSS) — or while it is docked over a row of monitors, whose `mainInsets` are measured against the viewport (a change of the monitors themselves already reaches it through `useDeskScreens`), and the floating rect the notices dodge is reported again once the move has landed, since the `resize` listener measures it where it stood. The picture preview's scrim is a flat `rgba(0,0,0,0.9)` and a picture's download chip a flat `rgba(0,0,0,0.62)`, both without the blur they had.
- **`CodingChatCards.tsx`** — the chat's coding cards, ONE host both chats render (2026-10-30, the Coding Agent UI redesign's step 3): the Create card (`NewAppWizardCard`, the composer's `+` with its `coding-agent/status` gate, `useNewAppCard`/`NewAppToggleButton`/`NewAppCardSlot`; - **Hand-offs into the chat** (`src/lib/ui-events.ts`, three events, three promises): `CHAT_MESSAGE_EVENT` (`dispatchChatMessage(text)`) SENDS the text as the owner's next turn through the popup's one send path (the Coding Agent's New-app wizard, the Fix-error prompt); `NEW_APP_EVENT` (`openNewAppCard`) opens the popup with the Create card in it; and `OPEN_CHAT_EVENT` (`dispatchOpenChat({ draft })`, 2026-10-30) only OPENS the popup (`page.tsx`, the same listener that opens it for the other two) and puts the draft in the composer, focused with the caret at its end, UNSENT — the owner finishes the sentence and presses Send. The Coding Agent run page's **Message in chat** ("Tell coding run <id>: ") and its agent chart's panel use it: the chat composes, the app shows, and that app's no-inputs rule rests on this event. `ui-events-open-chat.test.ts` pins that a draft never fires the send event. The other half of the rule — the Coding Agent app draws no field of its own on home, a project's, a run's or a team's page — is `src/tests/components/coding-agent-no-inputs.test.tsx` (coding-agent-ui.md).
- **"This chat keeps its model"** (`src/lib/chat-model-notice.ts`) — on Hermes from v0.22.4 a resumed session keeps its frozen launch (the route resumes without `-m`/`--provider`), so a model picked in the popup's header mid-conversation applies to the next new chat and the old model goes on answering. That behaviour is kept; `ChatPopup` says so in one polite line over the composer (`chat.keepsItsModel`, `data-testid="chat-model-kept"`) while the header names another model than the one the conversation is held to. The held model is the adapter's `conversationModel(key)`: what the session's turns recorded (`TurnResult.model`/`provider`), kept across a resumed turn that recorded nothing, and null whenever the next turn would open a fresh session — no session threaded yet, a new chat, a closed tab, or a page reloaded into a conversation whose session id it never got back — so the line never claims a switch will not happen when it will. ClawBox AI on both sides is the same pair (no model choice there). `ChatApp` has no model picker and says nothing. Pinned by `chat-model-notice.test.ts`, `hermes-adapter-conversation-model.test.ts` and `chat-hermes-model-kept.test.tsx`.
