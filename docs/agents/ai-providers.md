# AI providers and models

Provider configuration and OAuth sign-ins, the per-provider switch, the ClawBox AI login poll, the Anthropic account pool and the Ollama backend. Read it when you touch `ai-models/*`, `providers/*`, `anthropic/accounts`, `anthropic-accounts.ts`, `ollama/*`, `oauth-*.ts` or a model picker.

## Setup API Routes (`src/app/setup-api/`)

- **AI Models**: `ai-models/configure`, `ai-models/status`, `ai-models/oauth/*` — API key config with OAuth flows (device auth + authorization code). `providers/status` lists every provider (cloud and on-device) with its connection state, whether it is the default, and `enabled`; `providers/enabled` (owner-only) is the per-provider switch — a switched-off provider keeps its credential but is never offered to the chat or written as a fallback, and the current default can never be switched off. Connecting a provider through `configure` switches it back on.
- **Signing out of a provider**: `providers/sign-out` (owner-only POST `{ provider }`, `src/lib/provider-sign-out.ts` with its two halves `provider-sign-out-openclaw.ts` and `provider-sign-out-hermes.ts`) — the "Sign out of <Provider>" with a two-tap confirm on every connected row of the provider list, on OpenClaw and Hermes alike; `ai-models/clawai/sign-out` (#1369) is the same call for ClawBox AI. It removes the row provider's credential everywhere the box and the ACTIVE harness keep it, then reads it back. OpenClaw: every auth profile filed under the provider and every one the gateway's store holds for it goes natively (`openclaw models auth logout <id> --yes`; the Anthropic pool's mirrored `anthropic:clawbox-*` profiles included); what logout leaves — an `auth.profiles` entry with no store row, the provider's `auth.order`, the key inline in `models.providers.<p>.apiKey` (OpenRouter, Google, an Anthropic key) — goes with `config unset`, never a ClawBox AI key that rides in another provider's slot. For ClawBox AI also every other `claw_` key in openclaw.json (`litellm`, the legacy `openai` image slot, the memory search's remote embedder) and the cloud voice the boot script armed with the token (`tts.providers.openai` stamped `clawboxManaged`, whole; only the key out of an owner's own entry). Hermes: every credential-pool row but the fingerprint rows Hermes seeds from config.yaml, through `hermes auth remove <slug> <id>` (which does each source's own cleanup — an env-seeded key out of `.env` — and only suppresses a source another tool owns, such as Claude Code's or the Codex CLI's login) and an OAuth block through `hermes auth logout`; a provider defined in config.yaml loses `providers.<slug>.api_key`; ClawBox AI loses `providers.clawai.api_key`, its copy in `tts.openai.api_key` and `.env`'s `CLAWBOX_AI_TOKEN`, and on the Hermes that answers the chat its whole `providers.clawai` block (base URL, models) and the auxiliary slots pointed at it (vision, title generation, Local AI's compression summariser) too — Hermes counts a provider defined in config.yaml as `authenticated` while its block has a base URL, key or no key, so a block left behind kept it signed in to `GET /setup-api/hermes/models`; on the inactive Hermes of a dual box the block stays, so a default on it there still resolves. Both: the removed values are also cleared out of the config's rotating copies (`openclaw.json.bak*` and `.last-good`, which the gateway rolls back to; Hermes' `backups/config/config.yaml.good.*` and ClawBox's `config.yaml.bak`, `src/lib/credential-copies.ts`) — only a value no live file still holds, so another setting's copy of the same string keeps its backups. ClawBox's records go too: the model picks for the provider (`forgetProviderPicks`), its unavailable-model marks and its verified mark; for ClawBox AI the token, badge and plan in ONE store write, the remembered refusal and the device-login session, so a re-login is read as a NEW account. OpenClaw is hot-applied and confirmed, else restarted; Hermes' dashboard is restarted under the shared claim (and its messaging gateway when one runs); a refused restart is 502 `restart_refused`. A credential still on the box, or a store that could not be read to say it is gone, is 500 `still_signed_in`, never a success. THE DEFAULT: refused 409 `is_default` for every provider but ClawBox AI on OpenClaw (the row's button is locked with the switch's "make another provider the default first" hint), 409 `default_unknown` when the selection cannot be read or names none (an OpenClaw box with no primary, Hermes on `auto`, which answers on whatever credential it resolves); on OpenClaw ClawBox AI keeps #1369's rule — its row stays the default reading "Sign in again" and the chat answers with "Sign in to ClawBox AI again" — and on Hermes it is refused like any other default. The sign-out's task (`src/lib/provider-auth-tasks.ts`) ends its verify step on Hermes by asking Hermes' own list (`hermesStillSignedIn`: the `authenticated` flag `hermes/models` serves, from a live dashboard read of its own — `readLiveProviderAuth`, never the cached catalogue — polled until the dashboard is back): still listed signed in fails the task `still_signed_in`; a dashboard that does not answer in time leaves it succeeded but `verified: false`, with a warning. Refused (409 `sign_in_in_progress`) while a ClawBox AI device login's configure is inside the poll's window; 404 `unknown_provider` for an on-device engine. Offered on a `needs-reauth` row too when the box still holds its credential — the row's `credentialHeld` (a refused token, the default ClawBox AI's included, or a fenced Claude sign-in) — never on the default left with nothing (ClawBox AI's after its own sign-out). The default check and the removal run under `src/lib/provider-change-lock.ts`, which the default's two writers (`chat/model` on OpenClaw, `hermes/models` on Hermes, so `providers/default` too) take as well: a default moved onto the provider in between waits, then finds it signed out; the list holds every Make default and switch while a sign-out runs. On a dual box ClawBox AI is signed out of both harnesses (the inactive one cleaned and read back, not restarted); any other provider's sign-in is the active harness's own. Not touched: keys another setting holds for the same vendor (the cloud voice's own key, the coding agent's OpenAI key, ChatGPT sign-in and Anthropic accounts), the owner's switch (`ai_disabled_providers`) and the fallback chain.
- **Ollama** (chat-provider backend, no UI): `ollama/status`, `ollama/pull`, `ollama/search`, `ollama/delete` — local model management. `search` offers only sizes under the ollama.service memory cap (`OLLAMA_MAX_MODEL_PARAM_B` in `resource-limits.ts`, answered as `maxParamBillions`); `pull` follows the client's abort so a cancelled download stops. The runtime's idle standby (`systemctl stop`, never `disable`, ten minutes after the last proxied use) still applies through `local-ai-runtime.ts`.

- **External AI engine** (TASK-2376): `local-ai/external` (owner-only GET / POST save / DELETE remove, `?probe=1` adds a live `/models` check) `local-ai/external/test` (the probe alone) and `local-ai/external/select` (owner-only POST: makes the already-saved engine the primary again and stands llama.cpp/Ollama down, writing nothing else — the first-boot wizard's Continue) — an OpenAI-compatible endpoint the owner runs as the box's Local AI, provider id `clawext` on both harnesses. `src/lib/external-engine-shared.ts` (ids, limits, the input rule — client-safe), `external-engine.ts` (the store record `external_engine`, the 0600 key file `data/.external-engine-key`, the `/models` probe and its codes `unreachable` / `unauthorized` / `model_not_listed` / `bad_response`), `external-engine-ops.ts` (save/remove into the ACTIVE harness: OpenClaw `models.providers.clawext` + the primary through chat/model's own POST; Hermes `providers.clawext.*` + `model.provider`), `external-engine-hermes.ts` (the Hermes block and the read-path repair `hermes/models` runs). While selected the `local_ai_*` keys name it (`clawext/<model id>`) and the previous values ride in the record for Remove; llama.cpp and Ollama are stopped (and kept down: `standDownChatRuntimesForExternalEngine`, 30 s after boot and every 5 min from `instrumentation.ts`; Remove starts Ollama again when `previous.ollamaRunning`), `local-ai-proxy.ts` answers the `llamacpp`/`ollama` proxies 503 `external_engine_selected`, `bootLlamaCppServer` refuses, and configure (llamacpp/ollama), `local-ai` disable and Local-only answer 409 `external_engine_selected`. The key is never answered (`apiKeySet` only) and a stored key is reused only for the same origin. The outbound probe is bounded (CodeQL request-forgery / file-to-http / http-to-file on `external-engine.ts`): `refusedEngineHost` refuses link-local, metadata and unspecified targets (literal, and again for what a name resolves to) with `address_refused`, redirects are never followed, at most 2 MB is read and only ≤ 50 bounded ids return — proven in `external-engine-ssrf.test.ts` and `local-ai-external-access.test.ts` (403 `owner_only` to a second user and the MCP bearer, real route-auth). Hermes: window ≥ 64,000 enforced; max output tokens and image input not written (Hermes decides them). User docs: `docs-site/guides/local-ai.mdx`, `docs-site/technical/ai-providers.mdx`; board test `69-external-engine`.

## Server Libraries (`src/lib/`)

- **`oauth-config.ts`** / **`oauth-utils.ts`** / **`google-project.ts`** — OAuth provider configuration and flows.
- **`provider-enablement.ts`** — the per-provider switch (`ai_disabled_providers` in the config store): read by `provider-status.ts`, the chat model options, `providers/default` and the fallback writer; refuses to switch off the current default.
- **`anthropic-accounts.ts`** (the Anthropic account pool, Settings → Providers → Anthropic accounts, the `anthropic/accounts` route and the `anthropic_accounts` MCP tool; arithmetic in `anthropic-limit.ts`, Anthropic's `/api/oauth/usage` answer in `anthropic-usage.ts`) — an account becomes `limited` two ways, through ONE write (`setLimited`, then `mutate`'s `settleActive`, so the status, `poolHealth`, the pick, `lastSwap` and the gateway's order agree): a REFUSAL (`markLimited`: a run, the chat or a cron hit the limit), and since TASK-2515 a fresh USAGE READING (`readingPlan` / `recordUsageReading`, wherever a reading is stored: `readAccountUsage` — the owner's card and the tool with `?usage=1` — and the "most room" prefetch `readRoomNow`). A reading whose `exhausted` is true (parseAnthropicUsage's rule: an account window at 100 % or a refusing `severity`, else the session at 90 %+) with a `resetsAt` still ahead limits the account until that reset, and moves the box off it when it is the active one; a spent `weekly_scoped` week is that model's `ModelLimit` only, never the account's; no reset from Anthropic changes nothing. A limit only readings set carries `limitFromUsage` (a model week `fromUsage`): the next reading's reset replaces it and a reading with room lifts it (only one that READ the window the limit is on: a 200 with none, `{}`, lifts nothing), and a lift calls the reset listeners (`wakeNow`: the waiting runs, the gateway's order), since it also takes that end off the wake timer. Every reading is decided IN the chain (`readingPlan` on the pool the queued writes left; `ctx.unchanged` skips the settle and the write). A refusal drops the mark — its limit only grows and only its time or the owner's `clearLimit` ends it. The readRoom pass never awaits the write (markLimited waits on that pass): it queues it in the chain ahead of the pick. `readAccountUsage(id, 0, { record: false })` is for the coding runner's `settleLimitScope`, which records the limit itself with the run's id; in-flight asks are shared only between callers that record alike (`usageAsks` keyed `<id>` / `<id>:quiet`). Tests: `anthropic-usage-limited.test.ts`, `anthropic-model-limits.test.ts`, `anthropic-accounts.test.ts`.
- **`subscription-link.ts`** (TASK-2501) — a ClawBox subscription linked for its PLAN alone, with no ClawBox AI chat model: the device-code handoff in `scope: "entitlement"` (`ai-models/clawai/start` asks the portal for tier `free` so a Free account links instead of a 402; `ai-models/clawai/poll` calls `linkSubscription` inline — no configure route, no Hermes apply, no gateway restart, no provider task). Its own keys, `subscription_link_token` and `subscription_link_plan` (the portal's plan verdict, absent while not known), and its own `device-info` lookup: never `clawai_token` (every cloud feature finds that through `resolveClawaiToken`) nor `clawai_tier`/`clawai_plan_tier` (the boot scripts arm the cloud voice on those), and not `fetchPortalTier`'s caches (they assume one ClawBox AI credential per box). `ai-models/status` refreshes it (`refreshSubscriptionLink`, cached 2 min; an unreachable portal or an unreadable answer keeps the plan on record, while a refusal in the portal's own `invalid_token` envelope forgets it — unlike the ClawBox AI badge, the plan is all a link is for, and a revoked token must not keep unlocking features) and folds its plan into `clawaiPlan` (the better of the two on a box with both), with `subscriptionLinked` / `subscriptionLinkRejected` beside it; `useClawboxLogin` reads `clawaiConfigured || subscriptionLinked` as logged in. `ai-models/subscription-link` GET reads it, DELETE unlinks. The paid-plan gates read `plan-entitlement.ts` (`readPlanEntitlement`, `planEntitlementFromStore`: the ClawBox AI plan/badge pair, then the link), the paid gate's connect card links in this scope, and the portal heartbeat (Remote Control) falls back to the link's token when the box holds no ClawBox AI token.
- **`use-clawbox-login.ts`** — `useClawboxLogin(intervalMs = 30 s, enabled)`: whether the device is signed in to a ClawBox AI account, the account's PLAN and the portal's allowed models, from `/setup-api/ai-models/status`. The plan is the route's `clawaiPlan` — the portal's plan verdict (`mapPortalPlanVerdict`: `"free"`, `"flash"` = Pro, `"pro"` = Max), or the one last recorded in `clawai_plan_tier` when the portal does not answer, and null when neither is known — never `clawaiAccountTier`/`clawai_tier`, which are the MODEL the box defaults to: a Free sign-in stamps those `"flash"`, the same as the Pro plan, and reading them as the plan greeted Free accounts with the Pro celebration. `tier` is the paid plan (null for Free, no account, or not known — every paid gate fails closed on it); `plan` keeps Free and "not known" apart for `TierUpgradeCelebration`, which announces nothing on a plan it cannot tell. However many hooks are mounted — the desktop's and `TierUpgradeCelebration`'s on every idle desktop, plus Settings, the full-page chat and the paid-plan gates — the box is asked by ONE shared poll at the SHORTEST interval any of them asked for; each used to run its own chain, so the most expensive handler the desktop polls answered the same question two to four times a period, a millisecond apart. What each hook sees is unchanged: a mount starts in `loading` and is answered by an ask made for it — a fresh one, or one started together with it (`JOIN_IN_FLIGHT_MS`, 250 ms on `monotonicNow()`: only the page's and `TierUpgradeCelebration`'s mount-asks, in one commit, are the duplicate worth saving, while a hook mounting later asks afresh, because the route is slowest right after a sign-in or a plan change and an ask started seconds before one answered the Coding Agent's paid gate or the Providers pitch card with the old tier until the next poll) — and never by an older ask that lands after it mounted (`Subscriber.fromSeq`, the first ask a hook takes answers from); each hook reduces every answer over its OWN previous state so a failed poll keeps what it had, and the last hook to leave stops the timer and disowns what is in flight. A tick that falls due while the page is hidden is asked on the visible edge — on the box's own screen too, with no exemption: the shield, the paid gates and the tier badge are drawn on the desktop itself and act on nothing while it is away.
