# Files

The Files API (list, upload, move, ZIP downloads), the file guard every file surface shares, the Files app and the one code editor. Read it when you touch `files/*`, `file-guard.ts`, `zip-stream.ts`, `FilesApp.tsx` or `CodeEditor.tsx`.

## Setup API Routes (`src/app/setup-api/`)

- **Files**: `files/` — file list, read, write, upload, mkdir, delete. Its `resolve` action answers `relPath` beside `absPath` — the browse-relative path the Files app navigates by — which is how the Coding Agent's "Open in Files" turns a project folder's absolute path into a Files window opened there (`dispatchOpenApp("files", { forceNew, meta: { path } })` → `FilesApp initialPath`). Uploads are bounded by what the box can spare, not by a size cap (large uploads are the point of the PUT path): `src/lib/bounded-body.ts` meters the body against a budget that re-measures free space on the DESTINATION filesystem every 64 MiB minus `DISK_FREE_RESERVE_BYTES` (`src/lib/disk-reserve.ts`, 512 MiB — the in-app update's build is what a full disk kills; project-import's reserve is the same constant), a chunked or understated body is cut at the reserve with 507 `disk_full` and the partial file unlinked, and the multipart POST carries Busboy limits (`files: 1`, `parts: 4`) with the attachments route's teardown discipline — busboy's `fileSize` TRUNCATES rather than errors, so the `limit` handler destroys the write and answers 507 instead of `ok: true` over a cut file; count limits answer 413 `too_many_parts`; a statfs that fails skips the reserve for that request rather than refusing every upload. The `[...path]` PUT (rename) and DELETE refuse a PROTECTED CONTAINER with 400 `protected_container` (`isProtectedContainer` in `src/lib/file-guard.ts`, judged on the typed path AND its `canonicalPath`): `data/` itself, the checkout, `~/.config` and the browse root — `isProtectedFilePath(DATA_DIR)` stays false so the listing keeps filtering entry by entry, but a rename of `data/` to `data-copy` used to move every credential store out from under the guard in one request. A FOLDER downloads as one ZIP: `GET files/<folder>?zip=1` streams it through `src/lib/zip-stream.ts` (deflate with data descriptors, ZIP64 only where a size or offset needs it, the unix mode kept; each entry judged by `isProtectedFilePath` so it holds exactly what a file-by-file download would; symlinked files followed, symlinked folders not descended; `node_modules`, `.cache`, `.npm`, `__pycache__`, `.venv` left out, `.git` kept; capped at `MAX_ZIP_ENTRIES`, 100,000, with an error mid-stream rather than a partial archive), and `?zip=1&check=1` answers `{ name, entries, files, bytes, tooMany, limit }` — 413 `too_many_entries` past the cap — so the Files app says "too many" before a download starts. A folder without `?zip=1` still answers 400, now with `code: "is_directory"`. TASK-1273..1276 added the Files app's multi-select and moves on the same route: POST `?dir=<dest>` `{ action: "move", paths, conflict }` (`src/lib/files-move.ts`) judges the WHOLE batch before anything moves — every item through `safePath`, a protected container refused as the rename refuses it, a folder into itself or its own subtree refused lexically and through `canonicalPath`, an item already in the destination skipped — and answers 409 `{ code: "conflict", conflicts }` for names the destination already holds unless `conflict` is `rename` (the moved copy becomes `name (2).ext`) or `skip`; then it moves item by item and reports `moved`/`skipped`/`failed`. A selection downloads as one ZIP: POST `{ action: "zip", paths }` answers the `check=1` shape plus a ticket (`src/lib/zip-tickets.ts`, in memory, 10 minutes — the list cannot ride in the link past Node's 16 KiB header limit) and `GET ?zip=<ticket>` streams `zipSelectionStream`, each item re-judged by `safePath` when its bytes are read. The chat composers take dropped files AND folders (`src/lib/use-chat-drop.ts`, `src/lib/dropped-files.ts`): a folder is staged file by file through `chat/attachments` with `batch` and `relativePath` fields sent ahead of the file part (each segment a `safeLeafName`), lands under `<staging>/<batch>/` with its structure, and is sent as ONE attachment naming the folder (`root`); hidden entries and dependency folders are left out, the 25 MB per-file ceiling (`CHAT_ATTACHMENT_MAX_BYTES`) is checked before sending, and one drop is held to 500 files / 250 MB — half the staging retention, whose sweep (`pruneMediaDir` with `folders: true`) treats a staged folder as one item aged by its newest file. The Files window and both chats stop their file drags from reaching the desktop's own drop zone (`page.tsx`, saves to Downloads), which used to take a drop meant for them as well.

## Server Libraries (`src/lib/`)

- **`file-guard.ts`** — the ONE inventory of what the Files API and the MCP file tools may not touch. `canonicalPath(abs)` resolves through the nearest EXISTING ancestor (a leaf that does not exist yet, a deep new path under a link), and every rule — `isProtectedFilePath`, `isProtectedContainer`, and in `mcp/lib/guard.ts` the device/proc/sys and dotenv rules — is applied to BOTH the typed path and that canonical one: a benignly named symlink to `<checkout>/.env` or `/proc/self/environ` passed the lexical rules and file-guard's own list, and `read_file` followed it (security scan #19). The MCP sinks then open the vetted canonical target with `O_NOFOLLOW` (`resolveGuardedPath`), keyed for `recordRead`/`assertNotStale` on that same target, so a link swapped after the check is refused rather than followed. `~/.openclaw` is the one credential store with a carve-out inside it (`isProtectedOpenclawPath`, TASK-1072): the agent's own `workspace/**` and `workspace-<name>/**` are readable and writable, the folder itself is listable so they can be found, and everything else in there — `openclaw.json`, `credentials/`, `agents/*/sessions/`, `extensions/`, `logs/`, `media/` — stays denied, on the typed path and the canonical one. A dotenv or credential BASENAME inside a workspace (`.env`, `.mcp-token`, `id_rsa`) is refused by the MCP tool guard (`isDotenvPath`, `isOpenclawSecretName` in `mcp/lib/guard.ts`); `file-guard.ts` itself refuses only the `PROTECTED_FILE_RES` names there, because the Files API is the owner's own browse surface. `bash` is stricter than the file tools in the one place they differ: its pre-flight judges the `cwd` too (`openclawDeniedCwd`), so a shell may not stand in `~/.openclaw` itself — list-only to `list_directory`, which filters entries, and unfiltered to a shell — nor walk a relative path back out of a workspace. `~/.hermes` has no carve-out, and `PROTECTED_HOME_DIRS` itself is unchanged, so a delegated coding run is still denied the whole folder.
- **`zip-stream.ts`** — a folder as a streamed ZIP (see the Files route above): `walkFolderForZip` (the guard-filtered, name-ordered walk), `summarizeFolderForZip` (the `check=1` count), `zipEntries`/`zipFolderStream` (pull-driven — each file opened before its header is written, closed when a cancelled download returns the generator), and the record writers `localFileHeader`, `dataDescriptor`, `centralDirectoryHeader`, `endOfCentralDirectory`, exported so the ZIP64 thresholds are tested without a 4 GiB file.

## Frontend (`src/components/`)

### Built-in Apps

- **`FilesApp.tsx`** — file browser with upload, rename, delete, mkdir; the status line clears when the folder changes or Refresh is pressed, so a refusal from two folders ago is not still on screen (a same-folder reload keeps an error the owner has not seen answered); `initialPath` (from the window's `meta.path`) is the folder it opens in. Its text viewer edits through the shared editor. A folder's context menu downloads it as a ZIP after asking `?zip=1&check=1`. The trail, Up and phone Back walk the folder tree from Home. (The Projects app — pinned folders, the Projects view and desktop icon, and their GitHub backup — was removed in 4.3.0 by TASK-1556; the owner's folders were never touched. Its three config keys go once, on the first boot that carries the `drop-removed-projects` migration in `src/lib/boot-migrations.ts`, and a saved window of it is dropped by `RETIRED_APP_IDS` in `desktop-state.ts`.)
- **`CodeEditor.tsx`** — the ONE code editor on the device, drawn by the Files app's viewer and the Coding Agent's Files tab alike: a numbered gutter that sticks to the left while long lines scroll, the text coloured by Prism's grammars (`src/lib/code-highlight.ts`, loaded on demand so the desktop bundle carries no grammar; `src/lib/code-language.ts` names the grammar from the file's name; `src/lib/code-lines.ts` is the line shape both share) drawn as React TEXT nodes inside classed spans — never `innerHTML`, since most of what is coloured was written by a run — and, given an `onChange`, a transparent textarea over the coloured text that takes the typing (same font, same padding, so the caret stands on the glyph it moves; Tab indents two spaces, Shift+Tab takes one back, Enter keeps the line's indentation, Ctrl/Cmd+S calls `onSave`). Without `onChange` it is a read-only, selectable view. The palette is the `.tok-*` block in `globals.css` (flat classes, for the parity test's parser); the ground is the host's through `--cb-code-ground`.
- There is NO VS Code app on this build, and no `code-server` route: the launcher has no entry, `/app/vscode` answers "App not found", and neither `VSCodeApp.tsx` nor `src/app/setup-api/code-server/` exists. Code is read and edited in the ONE editor (`CodeEditor.tsx`, the Files app's viewer and the Coding Agent's Files tab) and run from the Terminal. Only `setup/reset` still names it, wiping `~/.local/share/code-server` for a box that ran one before this build.
