# Setup wizard and edition choice

First-boot setup: the wizard's steps, `setup/status`, `setup/complete` and `setup/reset`, and the unified image's edition choice. Read it when you touch `SetupWizard.tsx`, a `*Step.tsx`, the `setup/*` routes or `edition-select.ts`.

## Setup API Routes (`src/app/setup-api/`)

- **Setup**: `setup/status`, `setup/complete`, `setup/reset` — setup flow state, factory reset — `setup/complete` checks `requireSession` in the handler itself (allowBootstrap false; CLAWBOX_TEST_MODE keeps the e2e harness's cookie-less door), the way `setup/reset` does, so it no longer relies on the middleware allow-list alone. `setup/status`'s `update_completed` is a WIZARD-PROGRESS fact — "has the Update step been passed?" — and not the updater's: that step is satisfied by doing nothing on a box already current (it says "System is up to date" and auto-advances), so nothing ran and nothing wrote the config key of the same name, which `src/lib/updater.ts` writes with `update_completed_at` only after a full run and which `update/status` synthesises a `completed` phase from. The route answers the question it was asked instead, from the wizard's own `setup_progress_step` (`updateStepPassed` in `src/lib/setup-progress.ts`), so no surface has to write a completion that never happened.
- **Edition choice**: `setup/edition` (TASK-1149, `reports/clawbox/unified-image-design-2026-09.md`) — the wizard's "Choose your assistant" on a unified-image box, whose root-owned lock reads `CLAWBOX_EDITION=unselected` (both harnesses on disk, neither running). GET answers `{needed, unselected, pending, edition, hint, inProgress, inProgressTarget, serverStartedAt}`; `needed` is true only while the lock is `unselected` or an activation was cut short after the lock flipped (`/etc/clawbox/edition-select.pending` naming the locked agent), so every box with a fixed edition answers false and `setup/status`'s public `edition_choice_needed` with it. POST `{edition}` (bootstrap allow-listed; `requireSession({allowBootstrap:true})` + same-origin in the handler) writes `data/edition-select.env` through the swap's request writer and streams the `edition_select` root step as NDJSON `{phase}` lines (`request → check → lock → provision → cleanup → done`) and one closing `{success, edition, restarting}` or `{error, code, unselected, pending}`. 409 `already_chosen` on any fixed edition (never a free swap — that is `harness/swap` on the Max plan), 409 `setup_complete`, 409 `pending_other`, 409 `update_in_progress`, 409 `busy`. The step ends by restarting clawbox-setup (a transient systemd timer, 10 s), so the client waits for `serverStartedAt` to change and reloads.

## Server Libraries (`src/lib/`)

- **`edition-select.ts`** — the unified image's first-setup choice (TASK-1149), what `/setup-api/setup/edition` reads and starts: `readEditionChoice()` (lock `unselected`, or a pending marker that names the agent the lock already names), the request file (the swap's `writeEditionRequestFile`/`readEditionRequestFile`, on `data/edition-select.env`), the one-at-a-time claim, and the `[edition-select] phase=` follower over this dispatch's journal (`rootStepJournalArgs`). The root side is install.sh's `step_edition_select`: the swap's value gate on its own file, acts only while the recorded lock is `unselected` (or finishes, for the SAME agent, its own cut-short run), proves the agent runs (repairing it once through its install step), writes the pending marker, re-execs `edition_lock` and then `hermes_edition` or `gateway_setup` as the target, removes the other harness (OpenClaw: core package + command, never `~/.openclaw`; Hermes: `~/.hermes` + launcher) as the clawbox user and non-fatally, then schedules the clawbox-setup restart. `readEditionSource()` reports `unselected` as `{edition: "openclaw", defaulted: true, unselected: true, hint?}` — from the lock only, never the env — so every older reader treats the box as one nobody named; install.sh splits its predicates into RUNS (`has_*_harness`: no for both) and INSTALLS (`installs_*_harness`: yes for both).

## Frontend (`src/components/`)

### Setup Wizard (5 steps, then the completion overlay)

- **`SetupWizard.tsx`** — orchestrator, step state management, setup status check. The steps run WiFi → Update → Credentials → AI models → Telegram, and the last one hands over to the completion overlay inside this file rather than to a step of its own — there is no `DoneStep.tsx`, and the dashboard and factory reset it used to carry live in Settings.
- **`WifiStep.tsx`** — WiFi scan, network selection, password entry, Ethernet detection
- **`UpdateStep.tsx`** — system update progress tracking
- **`EditionStep.tsx`** — "Choose your assistant" (TASK-1149): two cards (OpenClaw recommended and preselected unless the lock carries `CLAWBOX_EDITION_HINT`), plain-language copy (`assistant.*` keys), one button. SetupWizard renders it in front of step 2 only while `setup/status` says `edition_choice_needed`; steps are not renumbered. Follows the POST stream, falls back to polling GET when it drops, waits for the restarted server and reloads; failures show a retry (and "choose a different assistant" while the box is still `unselected`).
- **`CredentialsStep.tsx`** — system password + WiFi hotspot configuration
- **`AIModelsStep.tsx`** — AI provider selection with OAuth flows (ClawBox AI, Claude, GPT, Gemini, OpenRouter, Ollama)
- **`TelegramStep.tsx`** — bot token input and validation
