# Coding Agent: routes and runner

The `coding-agent/*` routes, the run lifecycle and everything a run touches on the server: worktrees, systemd scopes, CPU budgets, secrets, deliverables, teams, history, media and inputs. Read it before you change anything under `src/lib/coding-*`, `project-*` or `src/app/setup-api/coding-agent/`.

## Setup API Routes (`src/app/setup-api/`)

- **Coding agent**: `coding-agent/status`, `coding-agent/enable`, `coding-agent/run`, `coding-agent/runs` (the list takes `?slim=1`: every settled run with its free text emptied and `slim: true`, for the app's 5 s live poll — `src/lib/coding-agent-slim.ts`; `?id=` is never slim), `coding-agent/stop`, `coding-agent/kill`, `coding-agent/artifacts`, `coding-agent/projects`, `coding-agent/media/image`, `coding-agent/media/audio`, `coding-agent/tree`, `coding-agent/permissions`, `coding-agent/secrets`, `coding-agent/secrets/names`, `coding-agent/message`, `coding-agent/team`, `coding-agent/team/stop`, `coding-agent/team/message`, `coding-agent/run-notes`, `coding-agent/history`, `coding-agent/history/export` — a headless Claude Code run (`claude-ds -p`) the assistant delegates a whole task to; runs live in the web server and persist in `data/coding-agent-runs.json`. The run HISTORY (TASK-1178, `src/lib/coding-run-history.ts`): `history` GET answers the Settings card's summary (mode, live and older counts, what it weighs, free space and the disk guard, Claude Code's transcript period per settings file) and nothing else — the archive it paged and cleared (`?view=archive`, DELETE), the per-run zip (`history/export?runId=`) and `history/file` (an archived run's evidence) went with the archive mode in SCA2 C1 (2026-10-30). `history/export` is owner-only and STREAMS the whole history as one zip (`src/lib/zip-writer.ts`). `runs?history=1[&offset&limit&project]` pages the older runs — the app's "Show older" on a project's Runs tab asks it with `&project=` — and `runs?id=` finds one of them too; `enable` takes `{ historyRetention: "standard" | "everything" }`, validated before any setter runs (`historyLimit` is answered 400 as since SCA C3; the status carries no `historyLimit` any more). `enable` is owner-only (refuses the MCP bearer) because it is the consent for a delegated shell; `run` answers 409 while the switch is off. Since 2026-09-14 the feature also needs a PAID ClawBox AI plan — Pro or Max, the owner's decision — and `src/lib/paid-plan-gate.ts` is the one place that rule lives (pure and client-safe, so the route and the wizard read the same arithmetic; the internal tier names are off by one, `flash` being the plan marketed as Pro and `pro` being Max, so "Pro or Max" is simply both paid tiers and Free and not-connected are alike `null`). `enable` refuses 402 `paid_plan_required` for a body that would switch the feature ON or mark its wizard finished, and ONLY such a body: a box already enabled when the subscription lapsed is never auto-disabled — its settings, the switch that turns it off included, stay writable — which is why the status carries `planGate: { required, satisfied, plan }` rather than the route quietly flipping anything. `CodingAgentSetupWizard`'s first step draws `PaidFeatureGate` instead of leading on: the device-code handoff on a box with no ClawBox AI account at all, the existing `FreeTierUpgradeCard` on a Free one, and nothing during the login poll's own first tick — a gate that read that tick as Free would flash an upgrade card at a Max subscriber every time the window opened. Each run gets an evidence folder (`data/coding-agent-artifacts/<runId>/`) for the screenshots and test output it saves; when a run settles, its closing message is filed there as `report.md` too (unless the run wrote its own), and the app renders that — and any `.md` a run wrote — as Markdown through the chat's own renderer; `artifacts` serves one such file (images and the WAVs a run can now speak for itself inline — the run's page plays them with a plain `<audio>`, which the desktop's `media-src 'self'` allows — everything else as plain text, because agent-written HTML must never execute in the app's origin), and the runs listing decorates each run with the folder's contents at read time. `projects/delete` (owner cookie AND same origin, for the READ as well as the write — the MCP bearer is refused 403 `owner_only`, because a tool that could remove a project folder would let a prompt-injected run delete the owner's code, and the preview it would otherwise read enumerates a folder's size, its uncommitted files and which secrets are filed against it) is the one gesture in this feature that takes the owner's own code away. `GET ?folder=&kind=` is the dialog's preview (size, `unsaved`, live runs, the project-scoped secret NAMES that would go with it, how many run records are KEPT, and the refusal it would meet right now); `DELETE { folder, kind?, confirm, force?, purgeOldest? }` does it — the two flags are the two consents the preview asks for, `force` for `unsaved_work` and `purgeOldest` for `trash_full`. The project is NAMED TWICE — `confirm` must equal the folder's own name byte for byte, so a dialog opened over one project cannot post over another and a replayed request cannot mean "the current one". **It is a MOVE, not a delete**: `src/lib/coding-project-delete.ts` renames the folder into `<its own root>/.deleted-projects/<folder>--<YYYYMMDDTHHMMSSZ>`. The trash sits in the project's OWN root and not under `data/`, which is a safety property rather than a filing choice: a project is directly inside its root, so the trash is on the same filesystem as it and `rename` is atomic. There is NO copy-then-remove fallback — that path existed only because `data/` can be a different mount from the owner's project folder, and it is the one place this feature could lose a file outright (a run writing into the original during the recursive copy, whose work the remove then took). A rename that still fails is `trash_failed` with the project untouched. A dot name, so `readFolderNames` keeps the trash out of the projects listing, and `resolveProjectTarget` refuses the name outright. The answer says where it went, and the retention rule is 30 days or `MAX_TRASH_ENTRIES` (10) counted ACROSS the roots, whichever is hit first, pruned after each removal — oldest first, and never an entry whose name this module did not write, because the trash is a folder a person can open. TEN refusals, each with a stable `code` every locale words. Five of them are the GUARD refusals — facts about the folder itself, and the ones the preview reports before anything is touched: `live_run` (a run still RUNNING in the folder, a sub-folder or its own copy of it — `isLive` alone, since a paused run and a month-old draft hold a session and not a process), `outside_roots` (the folder is not DIRECTLY inside the owner's project folder or `data/code-projects` — one `path.dirname`, because `~/Projects/shop/node_modules` is "under" a root and is not a project in it), `path_escape` (the entry is a symlink, or its real path is not directly inside the root's REAL path — checked on both ends, so a project reached through a linked root still resolves while a link out of one never does), `protected_checkout` (ClawBox's own checkout, `path.dirname(DATA_DIR)`, checked LAST because the owner's project folder may perfectly well be its parent, in which case every earlier guard passes it), and `unsaved_work` — uncommitted changes, commits no remote has (a NEVER-pushed project's whole history counts, since every one of those commits is only there), or a leftover run copy under `.clawbox/worktrees`. Only that last one is cleared by `force`, and `CodingProjectDeleteDialog.tsx` offers the flag inside the panel that lists exactly what would be lost, never before it. The other five are the REQUEST-SHAPE and STORE codes, stable in exactly the same way because the locales word them too: `invalid` (the name is not one path segment), `not_found` (no project by that name), `confirm_mismatch` (`confirm` is not the folder's own name, byte for byte), `trash_full` (the shelf is full of projects still inside their thirty days, so this removal would delete one of them for good — its own refusal rather than a silent purge, cleared by `purgeOldest` once the dialog has NAMED what would go), and `trash_failed` (the move itself did not happen). What went with the folder is taken down only AFTER the move landed: the project-scoped secrets, keyed by the scope `projectScopeFor` resolves, caught so a store that cannot be written does not undo a removal that is already complete. RUN RECORDS ARE KEPT — a run whose project is gone still renders, with the app deriving that fact from its own folder against the listing (`missingProjectOf`) rather than from a stamp on the record, so the answer survives a reload. `projects` (read-only) lists what the owner can point a run at: every folder directly under the project folder that has a `.git` directory of its own OR that a run has worked in (a run's folder is always a project, git or not, as long as it still exists), plus every code project under `data/code-projects/` except the Test-harness button's `harness-test` scratch project (`kind: "folder" | "codeProject"`), each with its last commit, whether it is on the desktop and its newest run. The last commit costs a `git log` only when it has moved: `lastCommit` (`coding-git.ts`) files each answer under the commit id git printed and hands it back while `.git/HEAD` — read plainly, detached or through a loose ref or `packed-refs` — still names that id, because the Coding Agent window asks this listing every 5 s while a run is live; a linked worktree, a chained symbolic ref, an unborn branch or the reftable store always asks git. Once a project folder is set, EVERY run works in a folder inside it (any depth, never the project folder itself) or in a code project — `resolveWorkingDirectory` refuses anything else, and a run with no folder is refused with a message naming the project folder rather than falling back to it; the Coding Agent home lists projects only (no "runs outside your projects"), the sidebar's recent runs reach every run. The default project folder (`enable { defaultDirectory }`) must be an absolute path — a bare name is a run-folder shorthand, resolved inside the default, and cannot define it; `setDefaultDirectory` validates it with `asDefault`, the one bypass of the inside-the-project-folder rule. `kill` is the settled-run gesture: a run that finished NATURALLY keeps its process group on purpose — the orientation guide tells a run to leave its app's server listening so the desktop can reach it, and a settle that killed the group would break the one pattern the device documents — so the record carries `leftover` and the run's page offers to end it, while a stopped, failed or timed-out run has its group ended for it; a run that is still going is refused with "stop it instead", because Stop already means that. `media/image` and `media/audio` are what the run-only `generate_image` / `generate_audio` tools post to; `src/lib/coding-agent-media.ts` is the WHOLE fence (the MCP tool's own path check is a courtesy for a typo — that process holds the device bearer, and so does a prompt-injected run), the same two-stage containment `vision/describe` uses to decide what may be READ, and the extension is the route's rather than the caller's, since the artifacts route and the desktop decide what a file IS from its name. Both are capped on the RUN RECORD (`MAX_IMAGES_PER_RUN` 20, `MAX_AUDIO_PER_RUN` 40), never per process, because a transient retry and the review pass resume the same record and must not buy the owner's daily allowance twice; every success states how many are left, which is what stops a looping model before the cap has to. `enable` takes `{ generateMedia }` — since SCA C3 ONE switch (`setGenerateMedia`) written to both keys, `coding_agent_generate_images` and `coding_agent_generate_audio`, which a run still reads separately and the status reads back as `generateMedia`, on only when both are; ON when absent, because it is not a consent but a spending preference: the icon pipeline already draws with the same allowance. `{ realBrowser }` (`coding_agent_real_browser`, reported as `realBrowser` in the status) is the third of that kind and the browser route's own reader: on, a run verifies its work in the window on the owner's screen; off, in an invisible browser. It is a preference, not a consent — the run drives Chromium either way — so absent means ON here too, and the first-run wizard's browser step is where a new box says otherwise. `permissions` (owner cookie AND same origin; the MCP bearer is refused 403 `owner_only`, because a tool that could widen its own delegated shell would make the owner's answer temporary) is the owner's ALLOW-LIST of Claude Code permission rules (`coding_agent_allow_rules`, `MAX_ALLOW_RULES` 32): GET the list and the cap, POST `{ rule }` to save one, DELETE `?rule=` to take one back, both writes answering the re-read status. It exists because a headless run cannot be ASKED — anything outside the list it was started with is refused outright and used to reach the owner as a dead sentence on the run's page — so a refusal now carries "Allow next time", which saves the narrowest rule covering it (`deriveAllowRule` → the containing FOLDER, never the one file: the harness writes a handful side by side and a file rule would put the owner back on the same page pressing the same button). The floor a rule must clear is `validateAllowRule` in `src/lib/coding-permission-rules.ts` — pure, so the browser and the server reach the same verdict, with the device's own `fileDenyRules()` passed in as context on the server. It has TWO storeys, because a deny rule outranks an allow rule in Claude Code and a rule inside a denied tree would grant nothing while sitting in the owner's list looking like a permission the box does not honour: **HARD** — the credential and key stores and the box's own state, which no rule may ever reach and whose deny rules ship on every run — and **SOFT**, the harness's own PER-PROJECT state (`~/.claude/projects/<project>/`, `~/.claude-ds/projects/<project>/`, `SOFT_HOME_SUBTREES`), denied only because it is outside the working folder, where ONE named project folder may be unlocked by an explicit rule: `unlockedSoftPaths` is then what makes `fileDenyRules` replace the wholesale tree deny with two entry-by-entry passes, so `HARNESS_STATE_SECRETS` and every project the rule did not name stay shut. The list is box-wide but a run's argv carries only ITS share of it (`runAllowRules`, in `buildRunArgs`, the same filtered list to `--allowedTools` and to `fileDenyRules` so the two halves stay in step): an absolute rule whose concrete folder is gone is left out, and a soft rule is kept only when the project slug it names is the run's own folder's (or the project root's, for a run in a worktree) — measured on the box, six stale rules naming other projects had put 1,680 deny rules (113 KB of argv) on every spawn. Nothing is written back; the Settings card shows the whole list. `suggestAllowRule` offers no rule for a path under a session's own `<sessionId>/tool-results/` folder, since the folder rule would carry that session's UUID and never match again. Every refusal carries a stable `code` beside its English sentence (`ALLOW_RULE_REFUSAL_KEYS`), because a rule the device cannot honour is refused at the door rather than stored and quietly ignored. A run FREEZES the list it started with (`CodingRun.allowRules`, like `effort` and the media switches — the tools a run holds must not change under it), and a RESUME is the one exception: it is the owner's own deliberate act, and "Allow next time" offers Resume in the same breath, so carrying the old list through would hand the run back the refusal just answered. `CodingRunDenials.tsx` is the run-page half and `CodingAgentRulesCard.tsx` the Settings half. `run` and `draft` take a **`deliverable`** — what the run must leave behind before the box calls it finished (`src/lib/coding-deliverable.ts`) — passed through unvalidated to the ONE reader inside `startRun`, which throws `invalid` with the reason so the two routes cannot disagree about what this box accepts and a caller learns its bar was refused rather than silently dropped; `source` is derived from the owner's cookie and never from the body, because that is what decides whether a `command` deliverable is allowed. `run` also takes an **`experience`** (TASK-1348) — the lessons the training cluster's dispatcher selected from its experience store, exactly the JSON `scripts/query-store.mjs` prints, `{ rules: [{ id, rule, applies, evidence?, score? }], skill? }` — read strictly by `readExperienceInput` (`src/lib/coding-experience.ts`: at most 10 rules, ids `^[RC]\d{4}$`, one-line strings, refused 400 `invalid` with a `code` rather than repaired) and rendered as a delimited block at the END of the run's `--append-system-prompt`, never into the task, capped at 8 000 characters with the skill cut first at a line boundary; the record carries `experience: { ruleIds, skill, chars }` (what GET `runs` answers) and the block itself as `experienceBrief`, which every respawn reuses, a resume without one inherits, and `cloneRun` leaves out of every route's answer. Absent or null, the brief is byte-for-byte what it was. Since SCA C3 `enable` no longer takes `{ reviewRounds }`: a pull request gets `DEFAULT_REVIEW_ROUNDS` (3), the key `coding_agent_review_rounds` is still read (an older box's stored value applies) and still on the reset list, and the status no longer reports it. The automatic COMPLETION-ATTEMPT loop is GONE (SCA A2, 2026-10-30; it fired once in 255 runs, at a file the task forbade creating): no attempt-budget config key, no `completionAttempts` on the record, no `startCompletionAttempt` — the box checks the bar ONCE and the only second go is the owner's Resume. `attempts` on the record is still every go at the bar (the run's own first turn, then each Resume), opened by `openAttempt` and closed with the verdict by `closeAttempt`, capped at `MAX_COMPLETION_ATTEMPTS` (6). The gate is the LAST step of the settle chain, after the pull-request step — because for the `pr` kind that is the moment the answer exists — and `deliverableGateApplies` is read by both `finishRun`, which HOLDS the finish notice ("Coding agent finished run-x" over a run about to go back to work is the exact claim the gate removes), and the gate, which sends it, so no run falls between them. A failed check is `gave_up` with the missing item as the reason (`gaveUpReason`, naming how many goes it took), `resumable: true`, and Resume on the card — `resumeRun` accepts `gave_up` beside `paused`, resumes the SAME record in the SAME session (`--resume`, `completionNudge` on stdin naming what is missing, the pull-request step put back to `opening` when none was ever opened, or the resumed go's commit would reach no pull request), and the gate judges that go when it settles exactly as it judged the first. A run with no deliverable and auto-PR off settles exactly as it always did. The token DIET (TASK-1749) is GONE as a setting: `enable` takes no `{ diet }` any more (an unknown body, 400), the status reports none, and `src/lib/coding-diet.ts` keeps only the two pure judgements, `looksVisual` and `mentionsPullRequest`. What it offered and measured, for the record: a `brief` knob (the original ~7,750-character `HEADLESS_BRIEF` or a lean one at under 40% of it that keeps every failure-preventing rule), a `helpers` knob (the delegation sentence — explorer before every edit, tester after each batch, reviewer before the report — or the lean sentence: the checks in the run's own shell, the explorer only for a codebase too large to read, the reviewer once), `visualTools` `always`|`auto`, and `context` `full`|`capped` (`CLAUDE_CODE_AUTO_COMPACT_WINDOW` at 128k instead of near the model's own 1M window). The lean brief, the lean helper sentence and the per-run visual decision did the same work for fewer tokens on bench/diet (2026-10-18) — first-turn context 16,677 tokens for a full run, 13,975 without the brief, 14,375 without the 13 browser and media tools, re-sent every turn — and became the defaults; `capped` cost MORE on the XL spec (126 turns of re-reading after each compaction against 72, 1.35x the tokens and 0.7 of judged quality) and was never in the panel. On 2026-10-29 the knobs were deleted rather than kept configurable: the lean brief (`LEAN_BRIEF_HEAD`/`_MIDDLE`/`_TAIL`, `LEAN_VISUAL_BRIEF`, `LEAN_FINAL_MESSAGE`, assembled by `headlessBrief`; `HEADLESS_BRIEF` is now the visual, no-pull-request one) and `leanHelpersBrief` are the only brief, the full template, `LEGACY_DIET`, `DEFAULT_DIET`, `getDiet`/`setDiet`, `CodingRun.diet` and `coding_agent_diet` are gone (a stale stored value is inert), and the reasons each sentence exists live as comments on the lean constants. What stays is the visual decision: `decideRunVisual(task, directory)` — `looksVisual` over the task and the folder's top-level entries (no visual word in the task, no page, stylesheet, component, front-end config, `public/` or `src/components`) — made once at the first spawn and frozen as `CodingRun.visual`, so a resumed session keeps the tools and the prompt prefix it opened with; a run judged not visual drops the clawbox MCP server's browser and media tools and the brief's browser block (`runHoldsVisualTools(visual)`: `visual !== false`, so an undecided run keeps them); a continuation inherits a `true`. A record from before the decision existed — neither the field nor the `diet` object that arrived with it — reads as `visual = true`, never null, so a resumed old session keeps its browser tools; an EXPLICIT null (a draft's, `newRunRecord`) stays null and decides at its spawn (read as `true`, a restart gave every persisted draft the browser and media tools and skipped `decideRunVisual`) (`routes/coding-agent/diet.test.ts`, `coding-agent-diet.test.ts`). **A run works in a COPY of the project** — a git worktree at `<project>/.clawbox/worktrees/<runId>` on `clawbox/<runId>`, `src/lib/coding-run-worktree.ts` — which is what makes `enable { maxParallelRuns }` (`coding_agent_max_parallel_runs`, default 2, min 1, max `hostMaxParallelRuns()` — 4 on a Jetson or a host under 16 GB of RAM, otherwise floor(RAM GB / 4) capped at 16, answered as the status's `maxMaxParallelRuns` and read by the settings panel's picker; the free-memory guard `TEAM_SPAWN_MIN_AVAILABLE_MB` stays the real safety — refused rather than clamped, and on `CODING_AGENT_RESET_KEYS` because it is the one setting there with a memory cost) safe: the one-run rule and "every run works in the project folder" were the same fact, because two runs in one tree edit each other's half-written files and each settle's `git add -A` commits the other's. `CodingRun.directory` is then the WORKTREE and `CodingRun.worktree` carries `{ path, branch, base, project, removed }`; `projectDirectoryOf(run)` is the ONE reader of that distinction (the projects listing, the project icon's folder id, the desktop registration, the app's `runBelongsTo`), and a record whose `worktree` is half-written is read as having none. Three folders keep the old in-place behaviour and get no copy: one that is not a repository, one that is not its repository's ROOT (a worktree there would be a different folder), and ClawBox's own checkout — which is where every code project lives — plus a team's worker (it has one the TEAM made, `coding-team-worktree.ts`, whose lock and git helper this shares so two operations on one checkout cannot collide) and a read-only planner (it writes nothing and must see the project itself). For those, `assertDirectoryFree` still refuses a second run in the same folder, which is the rule the old limit implied. `assertCanSpawn` RESERVES its slot synchronously with the count it judged and answers the release, which every spawn path holds until its record is visible to `loadRuns()`: the gate counts live runs and a start is not one for several awaits, so two that arrived together both read the same number. Auto-PR ADOPTS the worktree's branch rather than calling `startRunBranch`, whose `checkout -b` in the project checkout is exactly the move that cannot happen once two runs share a repository. The SETTLE (`settleRunWorktree`, the last act of `reviewAndShip`) steps aside while any live run is still in that tree — the review pass, another attempt at the deliverable and the owner's own Resume all work in it — then, since 2026-10-12 (owner's ruling: "the coding agent is not creating many copies of the same project folder"; one project held ten copies of itself, 617 MB), THE FILES GO AND THE BRANCH STAYS whatever became of the merge: nothing on the branch → the tree and the empty branch go (`branchRemoved`); a pull request owns the branch → the tree goes, the branch stays, the work goes home through the request; otherwise the branch is merged home — conservatively, because the project folder is the owner's: only when the checkout is on the run's base branch AND clean, a conflict aborted and named rather than guessed at — and the tree goes either way, with the VERDICT recorded (`RunWorktree.result`: merged into which base at which commit, or unmerged with the blocker — `dirty`, `not_on_base`, `conflict`, `failed` — parsed strictly off disk, so an unrecognised one reads as "nothing decided"). A worktree is only a checkout of commits git already holds: a resume, a review round and a Fix CI continuation all go through `startRun({ resumeRunId })` → `reopenWorktree` → `restoreRunWorktree`, which puts the tree back from the branch in a second. The progress line is `worktreeParked` ("copy removed; its work is kept on <branch> — <reason>"); only two things keep a tree on disk now — git could not say what is on its branch (no answer is never permission to delete), or the removal itself failed (`removeRunWorktree` answers whether the files are actually GONE rather than whether git was happy) — and those are what the run page's **Remove copy** (`coding-agent/worktree`, the lifecycle factory's owner gate) is for; it takes the FILES and leaves the branch. `CodingRunWorktreeCard.tsx` is ONE LINE (`worktreeCardApplies` decides whether it is drawn at all): merged into which base (only while a copy is still on disk — the timeline already says it), open as a pull request from the branch, or "the work is on <branch>, not in the project: <reason>" with nothing to press. The **Bring the work home** button, the copied git commands and the `coding-agent/merge` route were DELETED at the owner's word on 2026-10-12 — a refused merge is answered by the branch name and the Changes tab, never by a second merge path into the owner's folder. `sweepCodingWorktrees()` is the weekly sweep (`coding_agent_worktree_swept_at`, armed from `src/instrumentation.ts` a minute after boot): copies older than a fortnight whose branch is merged — into the base or into `origin/<base>`, since a merged pull request leaves the commits only there — or gone, never one a live run is in, and "git could not say" is never permission to delete. `secrets` (owner cookie for every verb, AND same origin for the writes — the agent is exactly the party a credential store gates) is the owner's SECRET STORE (`src/lib/project-secrets.ts`, `data/secrets.json`): GET the list, the bounds and the master switch, POST `{ injectSecrets }` for the switch itself, POST `{ name, value, scope?, inject? }` to save one or `{ name, scope?, inject }` to tick one, DELETE `?name=&scope=` to take one back, every write answering the re-read payload. The MASTER SWITCH is deliberately HERE and not on `enable` with the feature's other switches: it is the consent for handing credentials to an unattended shell, so it needs the same-origin check as well as the cookie, and `enable` carries only the cookie (reading it is not the half that needs a fence, so the status still reports `injectSecrets`). NO verb anywhere answers with a VALUE — not the list, not the POST that just wrote one, not a refusal — and the store is AES-256-GCM at rest under an HKDF-SHA256 key derived from `data/.session-secret` (a per-entry IV, and the entry's own name and scope as AAD, so a row cannot be relabelled into another project's scope by editing the JSON; a row sealed under a key the box no longer has answers `readable: false` rather than looking corrupt). `secrets/names` is the AGENT's own narrower door (cookie OR the MCP bearer) behind the `coding_secret_list` tool: names, scopes and the two facts that change what a run finds, never a value. A run is handed the box-scoped ticked entries plus its own project's as environment variables, and only while all THREE gates are open — the owner's switch (`coding_agent_inject_secrets`, OFF when absent because it is a consent), the entry's own tick, and the scope (`projectScopeFor` resolves a run's project the way the projects listing names one, so a FOLDER project can have secrets of its own; a project's entry wins over a box-wide one of the same name, and an override this box CANNOT open takes the box-wide value with it rather than silently handing the run the general credential). `BOX_SCOPE` is `@box` and not `box`, because `@` is outside the project alphabet and a project folder can perfectly well be called `box` — with the plain word as the sentinel, a secret saved for that one project was stored as box-wide and handed to every run. A value must be at least `MIN_SECRET_VALUE_CHARS` (8) as well as at most 8,192: the minimum IS the redaction floor, so the store never keeps a value the box would inject and could not scrub. `buildRunEnv` never lets an entry overwrite what the device wrote and drops a reserved name, and `setSecret` refuses one at the door: the `CLAWBOX_`/`CLAUDE_`/`ANTHROPIC_` prefixes decide which account pays for a run, and `LD_*`, the whole of `BASH_*` (`BASH_ENV` is SOURCED by a non-interactive bash before its own body — a way into the `claude-ds` wrapper itself), `NODE_OPTIONS` and their family are code-execution hooks rather than credentials. Everything the run then says is scrubbed of those values on the way onto the record (`src/lib/secret-redact.ts`, `<secret:NAME>`, longest value first, literal bytes not a pattern) — the progress feed, the summary, the harness's stderr — because the record is persisted and answered by a route the MCP bearer reaches; the NAMES go on the record as `CodingRun.secretNames`. The store is deny-listed for a run's own file tools in both inventories, beside the `.session-secret` it is keyed with. `CodingAgentSecretsCard.tsx` is the Settings half. `message` (POST `{ runId, text }`) is how a run that is still going is STEERED rather than stopped — the gap the feature closes is that Stop and Pause were the only two gestures on a live run, and both throw the turn away. On the run-lifecycle factory, so a run the OWNER started answers the MCP bearer 403 here as it does for stop and resume, and OUR PAGE ONLY on top of that (403 `cross_origin`) — every other run route is a lifecycle verb whose worst cross-site outcome is work ended, while this one puts WORDS in front of a shell that edits files, and a `text/plain` form posted from any page carries the cookie and needs no preflight; `isSameOriginRequest` waves a header-less caller through, which is what keeps the MCP bearer working; the text is QUEUED on the record first (`CodingRun.messages`, `src/lib/coding-run-messages.ts`: at most 20 waiting, 4,000 characters each, plain text only, every refusal a stable `code`) because a scoped run outlives the web server and an answer that lived only in a pipe would be a promise the box could not keep across a restart. Two deliveries, and the answer says WHICH happened rather than a flat "sent": every spawn now asks for Claude Code's `--input-format stream-json` and keeps the harness's stdin OPEN, so a message queued mid-run is written as its next user turn (the pipe is closed at the result event, which is what lets a streaming harness exit — safe at any turn, because a plain spawn has had its stdin closed since the first byte and still runs its extra segments); on a box whose harness refuses the flag the same message rides out with the next spawn's own stdin instead — a start, another attempt at the deliverable, or the owner's Resume. The flag is LEARNED from rather than probed for (`noteStreamInputRefused`, the `noteScopeRefused` precedent: a spawn the harness turns away before it ever speaks is remembered for half an hour and the one automatic retry runs plain), because a probe that spawns the harness costs a process on a path several route handlers reach. A message may be sent to anything that still holds a session — running, paused, drafted, and one that GAVE UP, whose page offers Resume for exactly this. `CodingRunMessageBox.tsx` is the run page's half (Queued and Delivered said apart) and MCP `coding_run_message` the agent's. `run` QUEUES a start beyond the limit (202 `{ started: false, queued: true, run }`) and takes `fixCi`; `stop` on a queued run is the owner's cancel (403 `owner_only` for the bearer), as `team/stop` is for a queued team; `message` answers `delivery` (`delivered` / `after_tool_call` / `next_start`) beside `delivered`. The DELIVERY PIPELINE is GONE (SCA A1, 2026-10-30): `coding-agent/pipeline`, `src/lib/coding-pipeline.ts`, `coding-pipeline-store.ts` (the per-project `coding_pipeline_projects` default; `project-switch.ts` stays for the production switch), the driver in `coding-agent.ts` (`attachPipeline`, `pipelineAfterSettle`, `resumePipelines`, `approvePipelineProduction`), the `RUNNER_STEP.pipeline*` feed lines and MCP `coding_agent_run`'s `delivery_pipeline` flag were deleted rather than kept configurable — no deploy target has existed since TASK-1012, so its four deploy-and-verify stages skipped unconditionally, `waiting_owner` had no producer and the production button was unreachable. - **`coding-harness.ts`** — the one name for the `claude-ds` wrapper (Claude Code on the box's ClawBox AI plan) and where install.sh puts it. The wrapper (`scripts/claude-ds`) pre-answers Claude Code's trust dialog for the folder it starts in — whichever folder: a run's project, a code project, the home — because on this appliance every one of them is the owner's own and the dialog's only other answer is "exit" (only `$PWD` is seeded, nothing else in the config is touched). - **`coding-run-unit.ts`** — a run's own transient systemd scope, which is what makes a coding run OUTLIVE the web server. Every run used to be a plain child of `clawbox-setup`, so the `systemctl restart` that ends an in-app update (or a crash, or an OOM kill of the service) took the whole cgroup and a forty-minute run died at minute thirty-nine. `systemd-run --user --scope --unit=clawbox-run-<id>-<token> --collect --quiet -p MemoryHigh=3G -p MemoryMax=4G -p CPUWeight=20 -p IOWeight=20 --nice=10 --` puts the harness in a cgroup of its OWN, outside the service's; `--scope` and not `--service` because systemd-run then execs the command in place, so the pid the web server holds is still the harness's own process group (`pgid`, the Kill button), stdio is inherited rather than journalled and the cwd is the one `spawn` was given, and `buildSpawnArgv`'s capability drop stays untouched behind the `--`. The unit name is rebuilt from a validated alphabet (it reaches `systemctl stop`) with a per-SPAWN suffix, since one record spawns more than once — the transient retry, a resume — and a scope systemd has not finished collecting would refuse the name. `probeSystemdRun()` asks TWO things and spawns nothing — is `systemd-run` installed, and does `$XDG_RUNTIME_DIR/bus` exist as a socket (which is what having a systemd user manager means, and whose absence — no `loginctl enable-linger` — is the failure this is about). It used to create a throwaway scope around `true`, which proved more and cost too much for what readiness is: a journal line per probe on a box whose app polls readiness while its window is open, and a SPAWN on a path several route handlers reach with `child_process` mocked, where it hung until its own deadline (the ai-models configure suites, 111 timeouts). What the two facts cannot prove — that systemd will actually accept the scope — is learned from the real thing instead: `noteScopeRefused` records a spawn systemd turned away (`SCOPE_REFUSED`, judged only when the harness never spoke, so its own failures are never mistaken for one), which makes the one automatic retry run DIRECTLY and makes readiness report systemd's own words for half an hour, and `noteScopeWorked` clears it the moment a scoped harness sends its init event. Reported as readiness's `detachedRuns`/`detachedRunsDetail` — never as a `problem` and never part of `ready`, because a box without it runs exactly as the device always has and refusing a run over it would turn a degradation into an outage. `unitActive` is TRI-STATE, and the two callers read the `null` differently ON PURPOSE: the reattach WATCH treats it as "not gone" (the process group is its second opinion), because reading a bus hiccup as death would settle a live run as lost; the BOOT SWEEP treats it as gone and settles the run, because that process has held no handle on it and the recorded pid may since have been given to a stranger, so nothing can second the answer — and a record left "running" that nothing will ever settle is the worse outcome. `scopeEnv` adds the one variable a `--user` call needs from a SYSTEM service (`XDG_RUNTIME_DIR`, derived and not inherited — the run's environment is still built from nothing).
