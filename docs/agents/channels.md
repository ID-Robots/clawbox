# Telegram and Discord

Channel bot configuration and which Telegram bot the box polls on each edition. Read it when you touch `telegram/*`, `discord/*` or `telegram-bot-identity.ts`.

## Setup API Routes (`src/app/setup-api/`)

- **Telegram**: `telegram/configure`, `telegram/status` — Telegram bot config
- **Discord**: `discord/configure`, `discord/status`, `discord/members` — Discord bot config (token validated live against the Discord API before it is saved), gateway connection state, and the guild-member allowlist picker. Connect-and-go: the token is the ONLY thing the owner enters. `configure` reads the application id (`GET /applications/@me`) and the servers the bot is in with their owners, and on OpenClaw writes them beside the token (`setDiscordToken(token, access)`: `channels.discord.applicationId`, `guilds.<id> = { requireMention: false, users: [owner] }` for a guild not already configured, and the owners' numeric ids in `allowFrom` so they DM without a pairing code — never `dmPolicy`, never `"*"`; `gateway-pre-start.sh` keeps numeric Discord `allowFrom` ids and still strips everything else). It answers `inviteUrl` (built on the box, `discordInviteUrl`) and `needsInvite` when the bot is in no server; the panel then shows "Add the bot to a server" and polls `POST {sync:true}`, which writes nothing until the bot has joined and then gives that server's owner access (`setDiscordAccess`, or the Hermes allowlist when none is chosen) and restarts the channel once. The Application ID field is gone from Settings.

## Server Libraries (`src/lib/`)

- **`telegram-bot-identity.ts`** — which Telegram bot this box polls, asked of the HARNESS on both editions: OpenClaw's `channels.telegram.botToken` in openclaw.json (read through `readConfigStrict`, so an unreadable config cannot pass for "no bot") and Hermes' `TELEGRAM_BOT_TOKEN` resolved the way Hermes' own env bridge resolves it — `~/.hermes/.env` first (the file `hermes config env-path` names), then `~/.hermes/config.yaml`'s top-level scalar for a key `.env` does not define, which is a fallback and never an override (`gateway/run.py`, `hermes_cli/send_cmd.py`); `hermes config get` is NOT that answer, because it routes env-shaped keys to `get_env_value`, which never looks at config.yaml. ClawBox's own `telegram_bot_token` is a mirror `/setup-api/telegram/configure` writes beside the real thing, so a box paired through the harness's own CLI has none — asking it answered "no bot" for a working one. `readActiveTelegramBot()` is the panel's question (the active harness's bot, mirror as the fallback) and is what `/telegram/status`, `/telegram/pairing`, `/setup/status`, `/telegram/configure` and `coding-agent-notify` all ask, so no two surfaces can disagree about whether this box has a bot; `readTelegramBotsInUse()` is the email-approval guard's — EVERY store is read whatever the edition says, so the dual SKU's inactive harness cannot become a collision after a switch; the edition lock decides only which of them may make the answer UNKNOWABLE, so a stray root-owned `~/.hermes/.env` on an OpenClaw box cannot 503 the flagship SKU for good, and an edition nothing on the device actually named (`readEditionSource().defaulted` — no lock file, no `CLAWBOX_EDITION`) counts as both, since "openclaw" is then a guess and a Hermes box with a missing lock would otherwise have waved its own bot through. Both are tri-state — "no bot" and "could not look" are different answers, and only the second makes a save gate refuse: `/email/chat-approval` and `/telegram/configure` both answer 503 `bot_unknown` on it rather than guessing. `telegramBotId()` compares by the id in `<bot id>:<secret>`, because a revoked-and-reissued secret is still the same `getUpdates` stream; a harness value that is not that shape is not a bot.
