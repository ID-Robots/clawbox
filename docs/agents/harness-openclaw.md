# OpenClaw harness

How ClawBox reads and writes OpenClaw: `openclaw.json`, the gateway's auth store, the CLI resolver, the gateway pre-start hook, the persona and onboarding ritual, and the Control UI wrapper. Read it before you touch `openclaw-*.ts`, `gateway-pre-start.sh`, `language-persona.ts` or any OpenClaw config key.

## Server Libraries (`src/lib/`)

- **`openclaw-config.ts`** — read/write OpenClaw gateway config (`~/.openclaw/openclaw.json`). Its three writers (`runOpenclawConfigSet` / `…SetBatch` / `…Unset`) ask the RUNNING GATEWAY first (TASK-1535): the write the CLI would make, computed from the file and sent as ONE exact `config.patch` (`null` for removed keys, every replaced array in `replacePaths` so nothing merges by id), read back from the file, and left to the CLI exactly as before for anything it cannot claim — the CLI's protected-path guard, an unknown flag, a uid/gid other than this process's, no gateway, a refusal. A route that writes several things wraps its request in `withConfigWriteScope` and opens `beginConfigWriteTransaction`: writes are STAGED, `readConfig`/`readConfigStrict` see them, and `commit()` makes them one patch; a write whose failure the caller handles goes through `configWriteBoundary({ onError, onApplied }, body)` (a plain `try`/`catch` outside a transaction), because when the one patch cannot land the commit replays every staged write inside those boundaries. Whole-file writers flush first; a caller about to spawn a CLI that writes the file itself calls `flushConfigWrites()`. The configure route is the one user today. `findOpenclawBin()` is the ONE resolver of the CLI for the web server (every `config set`, `doctor --fix`, version probe, and — through `dirname(bin)/../lib/node_modules/openclaw` — the core's manifest and generation), and it asks the MANAGED prefix `$HOME/.npm-global/bin/openclaw` FIRST: the one `install.sh` installs into (`NPM_PREFIX`), the gateway unit ExecStarts and `gateway-pre-start.sh` migrates with. The node dir used to come first, and on the device node is the distro's `/usr/bin/node`, whose npm defaults to the `/usr` prefix — so one `sudo npm install -g openclaw` left a root-owned second core at `/usr/bin/openclaw` that no update moves. On 2026-09-18 a box ran 2026.7.1-2 from there for every web-server CLI call while its gateway ran the managed 2026.9.3, which had migrated openclaw.json and the state database; the old CLI refused both, `doctor --fix` threw, and every ClawBox AI sign-in was rolled back with "Credential migration failed" (and the box was classified `v1`). Only the managed answer is cached — a fallback is re-probed per call, so a core that lands under a running web server is used without a restart — and no module may freeze the answer at import: `updater.ts` (loaded at boot by instrumentation), the catalog route and `plugins/repair` ask per call through `openclawBin()`, because a captured fallback would be an ENOENT the moment install.sh removes the second core mid-update; the ONE capture left is `configure/route.ts`'s sentinel, whose two uses are `config set` calls `runCommand` reroutes to the live resolver (`openclaw-bin-resolution.test.ts` pins the order, the cache rule and the no-capture rule). The other half is `remove_shadowing_system_openclaw` in install.sh, called by `step_openclaw_install` once the managed core is proven in place (so on every install, in-app update and harness swap): it removes an npm-global OpenClaw under `/usr` or `/usr/local` — the tree whose package.json names `openclaw` and the bin symlinks that resolve into it — and never a dpkg-owned path, a linked tree's target, a hand-written launcher, `$NPM_PREFIX`, or anything while the managed core is absent; the tree is compared by its CANONICAL path (`readlink -f` answers canonical paths, and a prefix behind a link — /usr/local moved to another disk — never matched as typed, which would have cost a box hand-wired onto that core its only one), and it is PARKED with one rename as `lib/node_modules/.openclaw-shadow-removed` before the `rm -rf` and swept at the next run, because `rm -rf` unlinks package.json long before the bulk of the tree and a half-deleted tree under its own name would fail the identity check for ever; it never fails the step, and its prefixes are ARGUMENTS (the suites' seam) rather than an environment variable a caller could point a root `rm -rf` with (`install-shadowing-system-openclaw.test.ts`). ClawKeep's setup card prints `sudo bash ~/clawbox/install.sh --step openclaw_install` for the same reason: the bare `npm install -g openclaw` it used to print fails EACCES as the box's user and, retried with sudo, is exactly how that second core gets there — and the same command with `--prefix ~/.npm-global` would install npm's `latest` rather than the pin under a gateway that restarts into it, which the next update then downgrades over newer-migrated state.
- **`openclaw-auth-store.ts`** — one profile of the gateway's auth store, read and replaced in the row the gateway resolves (the Claude sign-in incident of 2026-10-10). On OpenClaw 2026.9 the shared store is ONE row — `config_machine_state` `authProfiles.store` in `<stateDir>/state/openclaw.sqlite`, the store only when `auth.sharedStore` is exactly `{location:"state-db"}` (else the main agent's `auth_profile_store` row `primary`), with usage stats and cooldowns in a separate row beside it — and `openclaw doctor --fix`'s JSON→sqlite migration only ADDS profile ids that row lacks: for an id already there it keeps the stored profile, archives `auth-profiles.json` and still reports "completed". So every RE-sign-in was discarded while `ai-models/configure` answered 200 (7 of 8 on the box this was found on), and what the store had kept was a failed OAuth refresh FENCE — core swaps a credential for inert markers before each refresh and any refresh error (there a DNS failure right after resume) makes them terminal — which the gateway never uses: every turn died with `No API key found for provider "anthropic"`. `readGatewayAuthProfile(profileId)` answers `no-store | unreadable | absent | present { type, fingerprint, refreshFingerprint, expires, fenced, fence: "failed" | "pending" | null, storeUpdatedAtMs, sharedCopy? }` — fingerprints, never a token; under state-db ownership the main agent's OWN copy of the id is the one answered when it exists, because core resolves it over the shared row (proven against 2026.9.4 in an isolated home) — and `putGatewayOAuthProfile(profileId, bundle)` replaces the profile in one `BEGIN IMMEDIATE` (and an EXISTING agent-local copy in a second), clears that id's `usageStats`, and creates no database, table, row or agent copy. `readGatewayProviderAuth(provider)` is the read-only answer for a whole provider (TASK-1260, the chat on the account pool): every profile a turn could resolve (the main agent's own copies merged over the shared row), core's STORED order and its per-profile failure windows (`usageStats`: cooldown, disable, block) — what `src/lib/anthropic-gateway.ts` reads to learn which pool account core rotated off. The pool's own profiles (`anthropic:clawbox-<id>`, type `token`) are written by core's `openclaw models auth paste-token`, removed by `models auth logout`, and ordered by `models auth order set` (the stored order outranks a config `auth.order`, which `paste-token` writes beside a sign-in of another mode and over which the `models.authOrderSet` RPC refuses), never by ClawBox into the store. The gateway must be STOPPED for the write, and the caller reads back. Its callers: the `configure` route's subscription branch — after doctor answers exactly `completed`, for the Claude sign-in only, it reads back, replaces in place when the store does not hold THIS sign-in (access fingerprint and `expires`, built once with the legacy file's bundle), reads again, and answers 502 `credential_not_stored` before the primary, the session pins or the handoff file are touched when it still does not; "cannot look" (`no-store`, `unreadable`) carries on with one warning, because refusing a sign-in nobody can disprove would lock an owner out on a core generation this code has not met; ChatGPT and Google sign-ins take the same lossy lane and are NOT gated yet (core canonicalises OpenAI profile ids, so a gate needs its own reproduction first) — and `claudeSignInFenced(config)` in `provider-status.ts`, asked by the Providers strip (`needs-reauth` for the Anthropic row) and by `chat/model` (the header option `available: false, reauthRequired: true`, and 409 `provider_reauth_required` for a model picked on it), true only on positive evidence: Anthropic credentialed by oauth-mode profiles alone and the store holding a DEAD marker for each (`failed`, or a `pending` one whose row is older than `ORPHANED_REFRESH_MS`, 150 s — core commits a pending marker before every renewal, so a healthy box holds one for that round trip). The chat's half is `missingCredential` in `chat-error-text.ts` (the gateway's own wording, the provider id captured through a strict alphabet; its own sentence — connect the provider again in Settings, or pick another model in the header — ahead of the `reason === "auth"` rule, whose "not accepting this box's sign-in any more" is false when nobody was asked) and `chat-run-failure.ts`: core 2026.9.4 sends a failed run's `chat` error TWICE, the second about 7 s later with `errorMessage` only, so `RunFailureLedger.settleError()` remembers a run an error frame ended and answers `repeat` — a repeat resets nothing of the turn now in flight, reports nothing to `anthropic/failure` again, and in the mascot chat only puts the failure note back (tagged `failedRun`) when a history re-read dropped it; an `agent` frame from a run at work under that id reopens it, because the account swap's retry runs again under ONE key. `reportAnthropicFailure` (`anthropic-swap.ts`) names the active account in its answer only when the reporting consumer is ON it (`answeredActive`), so the chat no longer says "moved everything that uses Claude to …" over a pool whose only account the gateway cannot carry.
- **`language-persona.ts`** — the UI language as the agent reads it, and the guard that decides when ClawBox may write the persona at all. OpenClaw arms its first-conversation ritual on the agent's FIRST reply by looking at the workspace: a `USER.md` (or `SOUL.md`) that differs from its own template means "someone has already configured this agent", so it stamps the workspace complete and never writes `BOOTSTRAP.md`. ClawBox used to lose that race by minutes — the setup wizard's language pick created `USER.md` before the owner had said hello — and the introduction was suppressed on every box that shipped, invisibly, with no way back short of a factory reset. `personaWritesAllowed()` is the fix: on OpenClaw the persona is off limits until `USER.md` EXISTS (creating it is the suppressing act) and `BOOTSTRAP.md` does NOT (its presence means the ritual is armed and unfinished, and an edit now makes the next turn delete it); Hermes has no such ritual and is never deferred. The guard lives in the `preferences/` route rather than inside `writeLanguagePersona`, because that route is the single door the desktop, the wizard and the agent's own `preferences_set` all arrive through — so the agent cannot suppress its own ritual either. Nothing is lost, only deferred: the pick is still stored, and `scripts/gateway-pre-start.sh` re-applies it once the introduction is over. `openclawWorkspaceDir()` resolves `agents.defaults.workspace` so the guard and the write it guards can never be talking about two different directories. A SET-UP box runs no ritual at all (TASK-1528): a box whose wizard is complete answers its first chat message normally, in every new tab. `retireOnboardingRitual()` runs from `setup/complete` right after the flag is written, on every heartbeat tick, and after `harness/select` persists a switch to OpenClaw. It acts only while OpenClaw is the active harness: on a dual box running Hermes, a USER.md in the OpenClaw workspace would make `clawbox-identity-sync.sh` read it as introduced and overwrite a still-`.provisional` canonical USER.md, the one Hermes keeps, from it. It starts a `USER.md` if the workspace has none (`clawboxUserMd`, which differs from OpenClaw's template, so OpenClaw never seeds its stock ritual; the name comes from `pref:ui_user_name` if the agent ever stored one, since the wizard asks for no name). Then it MOVES `BOOTSTRAP.md` into `<workspace>/.clawbox-retired/`, never deleting it and never over an earlier copy. `onboardingRitualArmed()` answers false once `setup_complete` is true, so the chat never sends its opener.

## System Integration (`scripts/`, `config/`)

- **`scripts/gateway-pre-start.sh`** — gateway pre-startup hooks, and the two halves of the agent's introduction. It seeds `config/clawbox-bootstrap.md` as the workspace's `BOOTSTRAP.md`: OpenClaw adopts a bootstrap file that is already on disk verbatim, which is the supported way to ship one and survives a reinstall of the npm package, and ours is needed because the stock ritual asks what to call the ASSISTANT and never asks the owner's name — with the Settings field gone, that first conversation is the only thing on the device that asks, and it records the answer in `USER.md` and in `ui_user_name` through `preferences_set`. The seed is for a GENUINELY fresh workspace only: "no `BOOTSTRAP.md`" is not the test, because on an introduced box the file is absent precisely BECAUSE the ritual finished, so every trace of a working agent (`USER.md`, `IDENTITY.md`, `SOUL.md`, `AGENTS.md`, `MEMORY.md`, `memory/`) must be absent too. It is also the one write here that may create the workspace, since a factory reset empties `~/.openclaw` wholesale and the gateway would otherwise make the directory on the first turn and seed the stock ritual first. The second half pays back the deferred language: the owner's pick is stored but not written to the persona (see `language-persona.ts`), so this re-applies it under the same two conditions the route uses, at the first gateway start after the introduction is over — byte-for-byte the transformation `writeLanguagePersona()` performs, rewriting nothing when the files already say it, so every later reboot is a no-op. `scripts/setup-shared-identity.sh` and `scripts/clawbox-identity-sync.sh` wait on the same test before copying the canonical identity into an OpenClaw workspace, because on the dual SKU that copy suppressed the ritual exactly as the language write did elsewhere; a switch made before the first hello is picked up by the next sync instead. Since TASK-1528 the seed is only for a box whose wizard is still running. With `"setup_complete": true` in the device store, the same block never seeds. It leaves the workspace alone while the store says `"active_harness": "hermes"`, and otherwise retires a pending ritual: USER.md first, then `BOOTSTRAP.md` moved into `.clawbox-retired/`. It writes byte-for-byte the USER.md that the app's `retireOnboardingRitual()` writes, and this is how a box updated with the ritual still armed stops running it. It also brings OpenClaw 2's three background jobs — check-ins (`agents.defaults.heartbeat.every`), memory dreaming and self-learning — to their defaults ONCE per box (the owner's ruling of 2026-09-15: "Working on its own" is ON by default, reversing TASK-609's opt-outs of 2026-09-03): `data/background-optouts.json` keeps its `{"seeded": [...]}` shape and gains `"generation": 2`, a record at generation 2 naming the half's keys costs one file read and no CLI start, a box the previous build seeded off (no `generation`) or a config restored from an opted-out backup has every key still AT the opt-out literal flipped — check-ins by `config unset`, the same removal the panel's ON performs, never a pinned cadence; dreaming to `true`; the mode to `auto` — while a value the owner set or an absent key is left alone, and an unusable record changes nothing and records nothing. ClawBox never writes `0m` at boot: the panel's ON removes the key and is followed by a gateway restart whose ExecStartPre is this script. `scripts/register-mcp.sh` §4b does the same for Hermes' two booleans, and on a dual box each half is done only when generation 2 names ITS keys — generation-1 rows are not carried forward, so neither half can read the other's completion as its own.
