# Browser

The Chromium that the agent and coding runs drive over CDP (port 18800), its sessions and setup, and the Agent Browser app. Read it when you touch `browser/*`, `browser-*.ts` or the `Browser*` components.

## Setup API Routes (`src/app/setup-api/`)

- **Browser**: `browser/` — Chromium automation via CDP (launch, navigate, click, type, screenshot). WHICH Chromium it drives is the owner's setting, read for EVERY session: with the Coding Agent's real browser on (`coding_agent_real_browser`, absent means on) it uses the device's own window, brought up the way `browser/manage`'s open does, and falls back to a headless Chromium of its own only when that is impossible (a foreign Chromium on port 18800, a launch that failed); with it off it goes straight to the headless one and never touches the owner's screen. Every answer carries `browser: "desktop" | "headless"` — a screenshot from the two is identical, and a run that verified its work where nobody could watch must not report that the owner saw it. The page handles it hands out live in `src/lib/browser-sessions.ts` rather than in the route, because a delegated coding run drives this Chromium too: a run gets a page of its OWN (borrowing `context.pages().at(-1)` steered the tab the owner was reading, and the ten-minute idle sweep then closed it), every session records the run that opened it, and the runner closes exactly those pages when the run settles. `browser/manage` is the device half — install Chromium, the agent link, open/close the desktop window — and answers `serviceSafe: false` for a snap build `clawbox-browser.service` cannot start, refusing the launch at once instead of "check /tmp/clawbox-browser.log" ten seconds later; the same GET also carries `setupComplete`, `autoOpen` and `startUrl`, so the app's face and its state cannot come from two different moments. `browser/setup` (owner-only AND same-origin) writes those three: the auto-open switch exists because `ui_open_app("browser")` is a tool call, and a tool that could switch it back on would make the owner's "no" temporary. systemd starts Chromium, not the web server, so the start page reaches it on disk — `writeBrowserLaunchEnv` (`src/lib/browser-setup.ts`) puts it in `~/.cache/clawbox/browser.env`, which `scripts/launch-browser.sh` sources the way it already sources the VNC display — and only `about:blank` (the default since 2026-09-15 — it loads nothing) or an `http(s)` address survives `normalizeStartUrl`, because Chromium would happily open `file:///etc/shadow` on the screen the agent screenshots.

## Server Libraries (`src/lib/`)

- **`browser-sessions.ts`** — the CDP pages `/setup-api/browser` hands out and who opened each one. A bare Map inside the route was enough while the assistant was the only caller and wrong the moment a delegated run started driving the same Chromium; server-only, and in memory on purpose like the page handles themselves, since a web-server restart takes the CDP connection with it and leaves a persisted record pointing at nothing.
- **`browser-setup.ts`** — what the OWNER decides about the desktop browser (`browser_setup_complete`, `browser_auto_open`, `browser_start_url` in `data/config.json`). The start page is the one setting here that has to reach outside the web server, so it is handed to `scripts/launch-browser.sh` through `~/.cache/clawbox/browser.env` (`DEFAULT_START_URL` is `about:blank`, the same fallback that script carries); `getBrowserSetupComplete` prefers the explicit flag over "it works", or an update would drag an already-working box through onboarding and the wizard would swap its last step for the browser screen at the moment it installed Chromium.
- **`browser-actions.ts`** — the Browser app's two POSTs and `browserErrorText`, shared because three components now write those routes (the app, its wizard, its settings page) and each was free to invent its own English fallback for a refusal that already had a stable `code`; the device's own sentence is the LAST resort, not the first, on a box whose desktop may be in any of ten languages.

## Frontend (`src/components/`)

### Built-in Apps

- **`BrowserApp.tsx`** / **`BrowserSetupWizard.tsx`** / **`BrowserSettingsPanel.tsx`** / **`BrowserDesktopArt.tsx`** — the desktop browser (CDP port 18800), named **Agent Browser** on the desktop (`app.browser`, all ten locales; the id, `/app/browser` and the agent's own "Browser Setup" wording in `mcp/lib/context.ts` are unchanged) and drawn as `AgentBrowserIcon.tsx` — a browser window with the assistant's face, in `currentColor` — on the desktop tile and as the header's mark. ONE header on every face (`browser-header`): the brand mark, the state (home only), Open or Close, **Paste to VNC** (`browser-paste`, the screen's own dialog through `VNCHandle.openPaste()` — the overlay button is hidden), Open in VNC, and Settings or Back; the title bar it used to carry above that repeated the window's own title and is gone. Three faces chosen the way the Coding Agent app chooses its own: the first-run WIZARD until `status.setupComplete`, the embedded SETTINGS page while its button is pressed, and otherwise HOME — which is the browser itself, drawn on the device's own screen by embedding `VNCApp`. Home is the point of the app: opening it used to leave the owner in front of three numbered cards with the window they came for two buttons away, so it now launches Chromium if it is not running, waits, and shows the screen — with a pill while that happens and a stated reason when it cannot. The automatic launch fires once per mount (a ref, set BEFORE the request returns, or the poll would fire a second launch inside the first one's ten-second wait for CDP), never while the owner switched `autoOpen` off, and never while the AGENT is browsing, because `open-browser` terminates the headless browser holding the CDP port — fair when a person asks for it, not as a side effect of `ui_open_app("browser")`. `BrowserStatus` is defined once, in the settings panel, so the three cannot drift, and the settings live IN the app so a phone that landed on `/app/browser` reaches them with no desktop listening. `BrowserDesktopArt` is the wizard's diagram — a deliberate sibling of `MemoryShardArt` and `ClawKeepArt`, same viewBox and palette, with its animation in the `br-art-*` block of `globals.css` under `prefers-reduced-motion: no-preference`.
