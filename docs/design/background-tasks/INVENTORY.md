# Background tasks: inventory of long processes

Every long process a person can start from Settings, how it runs today, what happens to it when the Settings window closes, what progress it reports, and how it can be killed. This is the inventory the background-tasks work is planned from. The goal: every one of these runs detached, survives Settings closing, and shows live progress, both inline in Settings (steps, percentage, time left, a collapsible live log) and in a desktop corner card.

## How this was made

It was re-made for the second slice by reading the code at `origin/beta` (`a2c1718af`), not from memory. The phase-1 version (at `9c7d0a2e9`) served as a checklist, and every one of its rows was re-checked. Five slices of the code were swept one by one:

- Local AI and voice: `LocalAiPanel`, `local-ai/*`, `VoiceOutputPanel`;
- Updates, harness and system: `SystemUpdateApp`, `HarnessPicker`, `DbMaintenancePanel`, `RemoteControlPanel`, `PluginRepairNotice`, `SystemProfilePanel`, `BackgroundJobsPanel`, `PathGuardPanel`, `ComputerUsePanel`, and the system sections of `SettingsApp.tsx`;
- Provider sign-ins and AI settings: `AIModelsStep` and everything it renders, `AiProviderList`, `AnthropicAccountsCard`, the sign-in hooks;
- Messaging channels: the Telegram, Discord, WhatsApp and Email sections of `SettingsApp.tsx`;
- Network, users, devices and appearance: Wi-Fi, hotspot, `UsersPanel`, `MonitorsPanel`, `PetPicker`.

A sixth pass checked coverage. It listed every network call site in `SettingsApp.tsx` and in every component and hook it renders, at any depth (`fetch`, `EventSource`, `WebSocket`, and wrappers like `post()`, `runAction()` and `act()`). Each one was then judged long or instant from its route handler. It found one process the five slices had missed (the system password change, marked *coverage pass*). The 92 calls it judged instant are listed in the appendix.

For every handler that can run longer than a few seconds, the sweep traced:

- the Settings control that calls it;
- the route handler, and how the server runs the work;
- what the client does with the request when the window unmounts;
- where the progress lives;
- how it can be killed.

Rows that two slices both found were merged. Line numbers refer to `a2c1718af`. The files this change edits have moved since, and section 3 names them.

**What "closing Settings" means here.** Settings is a window inside the desktop page, so closing it unmounts `SettingsApp` and does not close the page. A `fetch` keeps running unless the component aborts it in a cleanup. A streamed response that nobody reads any more stays open. Whatever the component held in state is gone, and a reopened Settings starts from its mount effects.

| Verdict | Meaning |
|---|---|
| ✅ survives | The work keeps running, and a reopened Settings shows its state (it re-reads a status the server keeps, or re-attaches to a background task). |
| ⚠️ loses progress | The work keeps running on the server, but its progress and verdict were held by the closed window, and a reopened Settings does not re-attach. A second click is often refused `409 busy`, with no way to see the first run. |
| ❌ dies | Closing the window stops the work or leaves it unable to finish: an aborted request, a client-driven poll that was the only driver, or a server session that is reaped once the polls stop. |
| — n/a | Closing Settings has no bearing on it: the work ends in a reboot that takes the page with it, or it is a read with nothing to lose. |

**How it can be killed** has four parts in every row:

- **UI**: a Cancel or Stop control, and what it does on the server;
- **Cap**: the server-side timeout or limit that ends it;
- **Web-server restart**: what a restart of `clawbox-setup.service` does to work in flight. A child of the web server shares its cgroup, and the unit sets no `KillMode`, so the child is stopped with it. A root step runs in its own `clawbox-root-update@<step>.service` unit and runs on;
- **By hand**: how an administrator stops it, such as a unit to stop or a process group to kill.

How they can be killed, at `a2c1718af`:

- **From the UI**: a handful, each with its own mechanism:
  - the xAI sign-in's Cancel;
  - the Hermes sign-ins' Start over;
  - WhatsApp pairing's Cancel;
  - Remote Access's Cancel while negotiating;
  - the monitor trial's Revert;
  - the approvals bot's switch.

  The confirm dialogs' Cancel buttons (harness swap, rename, user removal) only stop a request that has not been sent. None of the installs or downloads had a Cancel until this change; the Whisper size download is the first.
- **By a cap**: almost all of them. Each root step is capped at 2 h by its unit (`TimeoutStartSec=7200`). CLI spawns are capped at 30 s by default. The fetchers each carry their own cap.
- **By a web-server restart**: everything in-request, every web-server child and every client-driven poll. Root steps run on under systemd.

This change moves two more rows onto the shared mechanism (the memory-search model download and the Whisper size download), adds Cancel and re-adoption after a restart to it, and makes the Voice tab follow the Kokoro install again. Section 3 has the details.

Two processes the phase-1 inventory listed outside Settings were checked again and are still not reachable from it. Neither the Ollama model pull nor the llama.cpp GGUF library download (`POST /setup-api/llamacpp/models`) is reachable: `AIModelsStep` renders their panels only for the `ollama` and `llamacpp` provider ids, which Settings does not pass (`SettingsApp.tsx:4198`, `AIModelsStep.tsx:339-343`). They stay in section 2.

## 3. The shared mechanism, and what is on it

### Phase 1 (merged)

Phase 1 moved the first three Local AI installs that lost their progress onto a shared runner:

- the Gemma 4 / llama.cpp install (`POST /setup-api/llamacpp/install`);
- the Whisper engine install (`POST /setup-api/whisper {action:"install-engine"}`);
- the Kokoro voice install (`POST /setup-api/tts/install`).

All three now read ✅ in section 1.

- **Runner: `src/lib/background-tasks.ts`.**
  - A task is a promise of the web server, never awaited by a request, so a client that leaves cannot end it.
  - Its record holds weighted steps, the headline, byte progress, a 200-line log ring and how it ended. It is persisted atomically to `data/background-tasks.json`.
  - One task per group runs at a time.
  - `backgroundTaskStream` replays a task as the NDJSON the install routes already answered with (`{status}`, `{completed,total}`, then one `{success}` or `{error}`). Its first line names the `taskId`.
- **API**, beside `/setup-api/background-jobs` (the harness's own recurring jobs):
  - `GET /setup-api/background-jobs/tasks`;
  - `POST .../tasks {id, action:"dismiss"}`;
  - `GET .../tasks/follow?id=`.
- **Desktop corner card: `src/components/BackgroundTaskCards.tsx`**, in the top-right notice column of `src/app/page.tsx`. It polls every 2 s while a task runs and every 20 s otherwise.
- **Settings re-attach**: `LocalAiPanel` follows each running install again on its row.

### This change: the second slice

**The mechanism.**

- **Cancel**, for work that can stop safely.
  - A task started with `cancellable: true` gets an `AbortSignal` (`ctx.signal`). `cancelBackgroundTask(id)` aborts it, the record says `cancelRequested` until the work has really stopped, and the task ends in a new state, `cancelled`. That is not `failed`: nothing went wrong.
  - `POST /setup-api/background-jobs/tasks {id, action:"cancel"}` answers `409 not_cancellable` / `not_running` otherwise. Like dismiss, it needs a person's browser on the same origin.
  - A follower's stream closes with `{error, code:"cancelled", cancelled:true}`, so readers that predate Cancel still read it as "not a success", and current ones (`readInstallStream`) tell it apart.
  - Root steps are never cancellable: the web server may start the launcher's steps, not stop them, and none of them has a safe stop half-way.
- **Re-adoption after a restart of the web server.**
  - A root step runs in its own unit, which outlives the web server. `ctx.rootStep(step, …)` follows it (`followRootStep`) and records which run it is on the task: the step, when it was dispatched, and systemd's `InvocationID`, read once while the instance is loaded.
  - A server that finds such a task still `running` adopts it instead of closing it `interrupted`. It follows the same run again (`followRootStepRun`) and closes the task the way the run ended.
  - The run is matched by its invocation. A unit now running another invocation, or a run that was never seen running, reads `interrupted` as before: what happened to it is unknown.
  - What a dead process would have done AFTER the unit cannot be re-run. A task whose unit was its last real work says so (`finishes`, the result it then closes with); one whose unit was not closes `interrupted` with a sentence that says the install itself finished.
  - A task that had already moved past its unit is not adopted.
  - The Kokoro install, the Whisper engine install and the memory-model download follow their root step this way. The llama.cpp install keeps its own inline follow and still reads `interrupted` after a restart.
- **One progress view, two places** (`src/components/BackgroundTaskProgress.tsx`).
  - The view: steps with their states, a bar with the percentage, the time left once there is a rate, the collapsible live log, and Cancel where the task allows it.
  - The desktop card draws it (design 5). So does Settings, inline under the control that started the task (design 3): the Local AI rows, the memory-model card and the Whisper size rows.
  - Settings polls the one task every 1.5 s while it runs (`GET .../tasks?id=`). A Cancel or a re-attach asks again at once.

**The processes moved onto it.** The criterion was the Local AI rows that still lost their progress and download the most: the brief's "model downloads".
