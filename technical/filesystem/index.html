Filesystem Layout

Everything ClawBox cares about lives under /home/clawbox. The app itself is a git checkout; all personal state is deliberately kept outside tracked files so updates can hard-reset the code without touching your data.
Rows marked OpenClaw/dual or Hermes/dual exist only on those editions. Check yours with cat /etc/clawbox/edition.env.

The update mechanism achieves this with git reset --hard <release> + git clean -fd (note: no -x — gitignored paths like data/ and .env are never cleaned). Details: Update System. Every ❌ row above assumes the path really is the directory it names. If one of them has been replaced by a symlink, the factory reset removes the link and leaves whatever it pointed at alone — it never deletes through it — and reports the reset as incomplete, naming the path, without clearing the Wi-Fi, resetting the login password or rebooting. So the box stays reachable and the redirected store is still there to deal with. A plain file where a directory belongs is simply removed and the reset finishes normally.
Do not hand-roll a factory reset over SSH from this table. rm -rf ~/.hermes deletes the agent install (hermes-agent/, installs/, tools/) and bricks the Hermes harness; rm -rf data/* deletes network.env and the offline model weights. The safe procedure is Recovery → D.

~/.hermes/config.yaml is generated state

On the Hermes edition several ordinary product actions rewrite that file end to end:
  • hermes config set, which ClawBox shells out to from Settings → Local AI (three calls per save) and from the Telegram flow;
  • scripts/register-mcp.sh, at every web-server boot;
  • scripts/setup-hermes-dashboard-auth.sh, as the dashboard unit’s ExecStartPre.
Each one does a full load → serialize → save, so hand-added comments and formatting are not preserved — including the commented Security and Fallback-Model blocks the file ships with. Saving a local model in the ClawBox UI is enough to strip them. Treat the file as generated: keep your own notes elsewhere, and let the writers serialise through ~/.hermes/config.yaml.lock rather than editing it under them.

The desktop browser

A ClawBox has one browser. The Chromium you see on the remote desktop and the browser your assistant drives are the same process, on the same profile (~/.config/clawbox-browser) and the same DevTools port (18800), started by clawbox-browser.service:
  • A site you sign in to on the remote desktop is a site the assistant can use, and you can watch what it does there. It keeps your theme, bookmarks and extensions, because it is your browser.
  • The assistant opens tabs of its own and closes only those. It does not navigate or close the tab you are using.
  • The browser is kept running. It comes back after a reboot, and within about twenty seconds if you close its window. Open Browser brings the window forward; Agent Browser (the app called Browser before 4.3) has no Close for it. Close the tabs you no longer need instead.
Updating from a version with two browsers. Earlier versions gave the assistant a hidden browser with a profile of its own under ~/.openclaw/browser/. On the first start after the update, once:
On the boxWhat happens
Only the desktop profile existsNothing changes for you.
Only the assistant’s profile exists (you never opened the Browser app)It is copied to ~/.config/clawbox-browser and becomes the one profile, sign-ins included.
Both existYour desktop profile is used as it is. The assistant’s profile is left on disk, untouched, and no longer used. Sites that only the assistant was signed in to need one sign-in in the shared browser. Agent Browser’s settings show where the old profile is.
Two Chromium profiles cannot be merged safely, which is why the third case asks for a sign-in instead of guessing. The assistant’s old profile is never deleted by the update. It is also not copied when it was written by a newer Chromium than the desktop one. A separate assistant browser (escape hatch). To give the assistant a hidden browser of its own again, with its own sign-ins, add this line to ~/.cache/clawbox/browser.env and restart the box: 
CLAWBOX_BROWSER_AGENT_ISOLATED=1
The desktop browser is then opened and closed by hand from Agent Browser, as before, and the assistant’s old profile under ~/.openclaw/browser/ is used again. Remove the line to go back to one browser. A browser of your own. If you already use a signed-in browser of your own on the remote desktop, make that the one browser in the same file: 
CLAWBOX_BROWSER_PROFILE_DIR=~/.config/my-browser-profile   # its --user-data-dir
CLAWBOX_BROWSER_CDP_PORT=9222                               # its --remote-debugging-port
CLAWBOX_BROWSER_EXECUTABLE=/opt/google/chrome/chrome        # optional: the binary to start it with
ClawBox keeps these lines whenever it rewrites the file (it stores the start page there too), and an environment variable of the same name — for example in the checkout’s .env — overrides each one. A value that is not usable (a relative path, a path with spaces, a port below 1024) is ignored with a warning in the log, and the default is used. With a browser of your own configured, the assistant attaches to it on that port, and:
  • If it is already running on that profile and port, Open Browser brings it forward (or opens your start page as a tab) and the app shows it as running.
  • If it is not running, Open Browser starts it there, with remote debugging on that port.
  • ClawBox never closes a browser on your profile that it did not start itself, and never clears another visible browser off its debugging port; only the assistant’s own background browser is ever cleared.
  • Chrome refuses remote debugging on its default profile, so the profile has to be a directory you pass with --user-data-dir, started with --remote-debugging-port=<the same port>.
  • A factory reset deletes that profile along with ClawBox’s own, if it is a browser profile inside your home directory.
