AI Providers

Edition scope: the provider stack below — ~/.openclaw/… credential files, openclaw.json, and the gateway-pre-start.sh self-heal pass — is OpenClaw / dual only. None of it exists on the Hermes edition, where provider credentials are held by Hermes itself (hermes auth add, stored under ~/.hermes) and the provider ids are Hermes’ own. See AI Providers on Hermes.The Cloud defaults for speech and embeddings and Plan gates sections are ClawBox’s own and apply to every edition.
For choosing a provider as a user, see Choose Your AI Provider. This page is the technical reference: what actually gets written where when you configure each provider, and how the system repairs common broken states.

OpenAI has two distinct lanes, and since OpenClaw 2 they share one namespace. Both are openai/…; what separates them is the credential and one config key. The API key is the auth profile openai:default; the ChatGPT subscription is the OAuth profile openai:chatgpt, and its models carry agents.defaults.models."openai/<id>".agentRuntime.id = "codex", which is what routes the turn through the Codex app-server and your ChatGPT plan. The catalogs still differ: the API lane carries the -pro tiers in addition to gpt-5.4/5.5/5.6, while the subscription serves gpt-5.6-sol/terra/luna, gpt-5.5, gpt-5.4, gpt-5.4-mini and no -pro at all. Mixing them up is the root of most “Incorrect API key” tickets — see self-healing below.The older codex/… and openai-codex/… namespaces are retired: the core answers Unknown model for them and openclaw doctor --fix rewrites them to openai/… while keeping the runtime key. The setup UI still calls the row “OpenAI Codex” — that is a label, not a namespace. A box that signed in before the upgrade holds a codex:default profile the core never consults, and the chat model list shows that row greyed with “Sign in again in Settings”; reconnecting OpenAI in Settings files it where the core looks.

Signing out of a provider

POST /setup-api/providers/sign-out { provider } (owner only; ai-models/clawai/sign-out for ClawBox AI) removes the row provider’s credential everywhere the box and the active harness keep it, then reads the result back. On OpenClaw that is the gateway’s own models.authLogout for every auth profile filed under the provider (OpenClaw 2026.11.3 refuses openclaw models auth logout while the gateway runs; the CLI is used only when no gateway answers), then config unset for what logout leaves (an auth.profiles entry, the provider’s auth.order, an inline apiKey); on Hermes the provider’s entries in the credential pool, config.yaml and .env, followed by a Hermes restart. The default provider’s sign-out is refused (is_default) — make another provider the default first.

Where credentials actually go

Configuring a provider writes up to four places:
  1. ~/.openclaw/agents/main/agent/auth-profiles.json — the real secret. API keys as {type:"api_key", provider, key}; subscriptions as {type:"oauth", provider, access, id, refresh, expires}.
  2. openclaw.json → auth.profiles.<provider>:default — metadata only ({provider, mode}). No secret lives here.
  3. openclaw.json → models.providers.<provider> — the provider definition (baseUrl, API dialect, model list) for lanes that need one (ClawBox AI, Anthropic, Google, OpenRouter, Ollama, llama.cpp).
  4. ~/.openclaw/agents/<agent>/agent/codex-home/auth.json (+ ~/.codex/auth.json) — the ChatGPT-subscription session, synthesized from the auth profile on every gateway start.
The active model is agents.defaults.model.primary (e.g. openai/gpt-5.5), with agents.defaults.model.fallbacks behind it (typically ClawBox AI or a local model). Per-provider credential preference, when a box holds both OpenAI credentials, is the core’s own auth-profile order — written through the gateway’s models.authOrderSet (every profile the store holds for the provider, the preferred one first), or openclaw models auth order set --provider openai <profileIds…> when no gateway runs — stored in the agent’s auth store, revised by whichever OpenAI save happened last, and cleared when only one OpenAI profile is left.

Compatibility routing (why some lanes use “OpenAI-compat”)

Some native OpenClaw provider plugins expect auth stores ClawBox doesn’t populate. ClawBox therefore routes Anthropic via https://api.anthropic.com/v1 and Google via https://generativelanguage.googleapis.com/v1beta/openai — both OpenAI-compatible endpoints with the key inline in the provider definition. Behavior is identical for users; the win is call-time auth that always works. OpenRouter likewise requires an explicit provider definition (https://openrouter.ai/api/v1) — without one, chats silently return empty usage.

ClawBox AI specifics

  • Pairing uses a device-code flow against the portal (clawbox.com) — the wizard shows a short code you confirm in your portal account; the resulting token is stored on-device.
  • Requests proxy through the portal’s AI endpoint to one model, DeepSeek V4.1 Flash (deepseek-v4-flash), on every plan: it answers chat and looks at attached pictures (the box checks that it still can at every start; if not, pictures go to a vision fallback, and when nothing can see the chat refuses a picture in plain words), and advertises reasoning support including X-High effort (mapped upstream to DeepSeek’s maximum reasoning mode).
  • Changing the linked portal account automatically unpairs ClawKeep (backups belong to the account).
  • Two tier values are kept side by side and answer different questions: the device badge (clawai_tier) is what this box should default to, and the plan (clawai_plan_tier) is what the account pays for. Only the second may be read before refusing an entitlement — a Max subscriber whose box is badged Flash is a state the product preserves on purpose.

Cloud defaults for speech and embeddings

On a box linked to ClawBox AI, three capabilities default to the cloud the plan already covers rather than to an engine on the device. The rule is pure and lives in one place (clawai-cloud-defaults-state.ts); the applier runs 45 s after boot and again after any ClawBox AI save, and GET /setup-api/ai-cloud-defaults publishes the verdict and its reason.

¹ and only once POST <proxy>/embeddings has answered a probe (cached 6 h on success, 30 min on failure, cleared when the credential changes). The table is edition-neutral, embeddings included. On the edition where ClawBox owns the memory index itself rather than the agent, the index client accepts exactly two endpoints — the loopback embedder proxy on the device, and this box’s own ClawBox AI embeddings endpoint — checked per request, so the same cloud default applies there. Where that edition records the owner’s pick it does so as a word in ClawBox’s own store (memory_shard_embedder), never an address and never a copy of the credential; the older memory_embeddings_choice_source: "owner" mark is honoured only where that pin stands beside it, so a box that finished the wizard before the cloud option existed is promoted rather than pinned to the device for good. The three rules differ because the three capabilities are not sold the same way: the transcription route has no tier gate, the cloud voice is Max-only on the proxy and would otherwise cost a failed round trip before every fall-back, and moving the memory index invalidates its fingerprint and costs a full reindex — not something to spend on a guess. Two invariants:
  • It only ever promotes. Nothing here moves a capability from the cloud back onto the box; withdrawal is the boot script’s single, plan-gated act.
  • An explicit owner choice is never overwritten. Every surface that lets a person pick records owner beside the pick (tts_choice_source, stt_choice_source, memory_embeddings_choice_source). A box that predates those keys is read by what only a person could have written.
A refusal names one of not_linked, plan, route_unavailable or owner, and the UI prints the matching sentence rather than a bare “not available”. (edition is a fifth word the catalogue still carries and no shipping edition answers with — it is the build-time kill switch for cloud embeddings, kept worded in every locale so flipping it needs no new strings.)

Reasoning effort

The chat header’s reasoning-effort picker is uniform across every cloud provider — Off, Low, Medium, High — so the control behaves the same whichever model you select. The gateway accepts this ladder for all of them and normalizes it per provider.
ProviderLevels offeredDefault
ClawBox AIOff, Low, Medium, HighMedium — a fresh session reasons, and the owner turns it down rather than up. The gateway folds Low/Medium up to DeepSeek’s single reasoning tier
Anthropic, OpenAI, ChatGPT subscription, Google, OpenRouterOff, Low, Medium, HighMedium
xAI GrokOff, Low, Medium, HighMedium
Local llama.cpp (Gemma)Off, and any level above it as thinking onOff
Two consequences worth knowing:
  • The on-device model’s thinking is a switch. Its server takes chat_template_kwargs.enable_thinking per request and has no graded middle, so OpenClaw’s llama.cpp row declares reasoning as binary: every level above Off is sent as thinking on, Off as none. Hermes shows the same switch as Thinking off / Thinking on. A model with only one level shows no control at all.
  • An unsupported level falls back to that provider’s default, not to the nearest neighbouring level. Switching provider mid-conversation therefore resets the effort to the new provider’s default if the current one is not in its list. The selection is remembered per provider.
Provider-specific extras that the gateway vocabulary also accepts (minimal, xhigh, max, adaptive) are deliberately not offered in the picker, to keep the control consistent across models.
Model reasoning capability is declared programmatically, not by hand-editing config. Separately from the picker above, each model entry carries gateway compatibility metadata describing which efforts it accepts. Editing that by hand in openclaw.json does not stick — two mechanisms overwrite it:
  1. The gateway re-applies its expected values on every start. ClawBox’s boot-time configuration step rewrites the reasoning metadata on the ClawBox AI models each time the gateway starts, so a manual edit survives only until the next restart.
  2. System updates replace the bundled model catalog. Updating OpenClaw overwrites the packaged catalog wholesale, so edits made there are lost on the next update. ClawBox re-applies its own values on each boot precisely because of this.
If a level is not declared as supported, the gateway rejects it. Changes must therefore be made in ClawBox’s setup and boot-time configuration code, which is the single source of truth.

Local models (Ollama / llama.cpp)

  • Local lanes authenticate with a per-install bearer token through a local proxy — nothing is exposed unauthenticated, even on localhost.
  • Only one local runtime is active at a time (8 GB Jetson RAM). Ollama gets tuned automatically (quantized KV cache, flash attention, single loaded model).
  • A local model can be the primary or the fallback; the wizard’s fallback chain prefers a configured local model, else ClawBox AI.

Troubleshooting pointers

  • 401 Incorrect API key (sk-proj-…) after switching to the subscription, a missing sign-in, or a spent allowance → Troubleshooting → Chat says the provider refused
  • Config validation failed: … Unrecognized key → stale OpenClaw core; sudo bash install.sh --step openclaw_install
  • Codex chats crash immediately (createDiagnosticTraceContext… is not a function) → @openclaw/codex plugin version skew vs core; re-run sudo bash install.sh --step openclaw_install (re-pins plugins)
  • Model picker rejects a model ID → each lane validates against its own catalog; remember the two OpenAI lanes have different catalogs.

External AI engine

Settings → Local AI → External engine (/setup-api/local-ai/external, owner only) makes an OpenAI-compatible endpoint the owner runs the box’s Local AI. The endpoint is validated with GET {base}/models (8 s, redirects not followed, at most 2 MB of the answer read, only up to 50 bounded model ids passed on) before anything is written; POST /setup-api/local-ai/external/test runs the same check alone, and POST /setup-api/local-ai/external/select makes an engine that is already saved the chat’s model again (the setup wizard’s Continue when the engine was connected before setup). The base URL is http(s) with no credentials, query or fragment, never the box’s own /setup-api/, and never a link-local or cloud-metadata target (169.254.0.0/16, fe80::/10, metadata.google.internal) or the unspecified address (0.0.0.0, ::) — typed as an address in any spelling, or as a name that resolves to one. Loopback, LAN and public servers are what it is for. Refusals carry a code: unreachable, unauthorized (401/403), model_not_listed (with the models the engine does list), bad_response or address_refused.

Where the key goes. data/.external-engine-key (0600) and the harness’s own provider block, as for the other providers whose key is written inline. The /setup-api answers say only apiKeySet; the device store (external_engine in data/config.json) holds the endpoint, model and limits, never the key. A saved key is reused for a re-save or a Test only for the same origin, so a changed address is never sent the key of another. What it replaces. While it is selected, the Local AI store keys name it (local_ai_provider: clawext), so the chat picker, Settings and the provider list show its model as the local model. llama.cpp and Ollama are stopped on save and kept down while it is selected (a check 30 s after boot and every 5 minutes: systemd starts ollama.service at boot, and an update can restart it); Remove starts Ollama again when it was running. The on-device fallbacks leave agents.defaults.model.fallbacks, and the Local AI proxy answers /setup-api/local-ai/llamacpp and /ollama with 503 external_engine_selected instead of starting them — for a stale session override or fallback as much as for a new turn. The gateway pre-start pass keeps the clawext entry and puts it back from the device store when it is missing (a dual box that switched runtime, a restored config). Turning the on-device model on (ai-models/configure with llamacpp/ollama), “turn Local AI off” and Local-only mode answer 409 external_engine_selected while it is selected: Remove (DELETE) is the way back, and it restores the previous Local AI exactly — store keys, the primary, the fallbacks it took out, and on Hermes the on-device registration and selection. The status surfaces report it: setup/status (external_engine), local-models (externalEngine), llamacpp/status (externalEngine), GET /setup-api/local-ai/external?probe=1 (a live /models check) and the agent’s local_ai_status tool. With no engine configured nothing of this runs and the box behaves exactly as before.
