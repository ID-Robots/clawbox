Systems

Agent Interface (MCP)

What makes ClawBox an AI-operated OS rather than a chat box: the on-device agent is wired to a ClawBox MCP server (mcp/clawbox-mcp.ts) exposing the device as tools. The agent can read system state, drive the desktop Chromium, manage the desktop, install capabilities, and build webapps — all authenticated back to the device APIs with a per-install bearer token.
The tool set depends on the edition. A tool that cannot work on the running edition is not registered at all — the agent never sees it, rather than discovering it fails. The edition is resolved once at startup from the device’s edition lock.

Orientation — the agent calls these first

The agent loads clawbox_context once per session — the field guide, which also tells it how to hand work to the coding agent and then steer and check it — and calls device_status before answering anything about the device. After that it picks by question: coding_project_status before starting a coding run, coding_run_list for “what are my runs doing”, and memory_shard_status, local_ai_status or clawbox_ai_usage for memory, on-box engines and your allowance, and anthropic_accounts before starting or retrying a coding run that uses your Anthropic accounts. When something on the box fails, it searches the symptom in the docs installed with that very version — docs_search, then docs_read — and follows the Troubleshooting page’s steps, with or without a network.
ToolPurpose
device_statusEdition, agent, the device’s default AI provider/model/thinking (ai.device_default, with ai.current_chat saying how that relates to the chat asking), configured context/output limits, free disk, update waiting — in one call
clawbox_healthIs the device API reachable, and is our token accepted — separates auth from connectivity
clawbox_contextThe on-device field guide, the tool notes (the caveats kept out of the one-sentence tool descriptions, served only for the tools this box registers) and the webapp storage/styling rules. The guide is filtered per box before it is served — see “What differs by edition”
docs_searchOffline full-text search over this documentation as installed on the box — the user guide, troubleshooting, recovery, updating, the FAQ, the technical reference and the engineering notes. Hits name the page, its path and the section, with a snippet; title and heading matches rank first
docs_readOne page of those docs as plain text, or one section of it, by the path a hit returned (support/troubleshooting). Read-only and fenced to the docs folders: nothing else on the box can be read through it

Hermes skills — Hermes edition only

skill_search · skill_info · skill_install · skill_list · skill_uninstall Installing takes the full registry identifier (official/pdf); uninstalling takes the short lock id — the first word of a skill_list line, which is not always the name the skill’s own SKILL.md gives it (a ClawHub martin-weather shows as weather). skill_install returns the lock id so the agent never has to guess it, and skill_list prints it first, noting the display name when the two differ. A display name works too, and so does the store identifier the skill came from, as long as it is itself a valid skill name: 1–128 characters, starting with a letter or a digit, and made only of letters, digits, ., _ and -. That rules out a card name with a space in it, such as the ClawHub shape QR Code Decode — pass the first word of its skill_list line instead. When two installed skills answer to one string, the device refuses and names both lock ids rather than removing either. See Hermes Skills.

Hermes plugins — Hermes edition only

hermes_plugins_reload Hermes scans for plugins once, when its process starts, and offers no runtime reload — so a plugin installed, enabled, disabled or removed after that does not reach the chat, including a brand-new conversation. This tool restarts the agent so it scans again, and answers which plugins the box now declares and, where it can be established, which of them the restarted agent actually loaded. It is the supported way to do this and it is not a privilege: the restart stops a process the box already owns and lets the service manager bring it back. Verifying a plugin from the command line proves nothing about the chat — that is a separate, fresh process. The restart closes the chat window you have open, so the tool tells the assistant to say so, and the desktop shows the same notice. See Hermes Edition.

AI configuration — Hermes edition only

ai_list_models · ai_set_provider · ai_set_model There is deliberately no tool for switching your ClawBox AI plan: that changes what you are billed, and “switch to a bigger plan for better results” is a one-line prompt-injection payload with a financial outcome. The plan is reported by device_status; changing it is one click in Settings → Providers. These tools read and write the device default — the provider and model in ~/.hermes/config.yaml, what a new conversation starts on. ai_list_models reports it as device_default, and ai_set_provider / ai_set_model change only that. The chat window can run a different model per conversation, chosen with the pills under its composer, and the tool server cannot see which: it is one process shared by every session. So where the chat knows the model that served a reply it prints it under that reply, and the agent is told to read that — not a tool — when asked “which model are you”. On the OpenClaw edition the header writes the box default for every session, so there the default is the chat’s model.

Browser (drives the real desktop Chromium — visible in Remote Desktop)

Since 4.3 this is the browser on the box’s desktop — the one you see in Agent Browser, with one profile — not a hidden browser of its own. Sites you signed in to there are signed in for the assistant too, you can watch it work, and it opens and closes only its own tabs. browser_open · browser_navigate · browser_screenshot · browser_close — both editions. browser_click · browser_type · browser_fill · browser_keypress · browser_scroll — OpenClaw edition only. browser_view_local exists only inside a Coding Agent run. describe_image (both editions) gives a written description of a local picture through the box’s vision model. browser_type reports a character count, never the text — it is the tool that types passwords.

Coding agent

Registered only while you have the coding agent switched on in the Coding Agent app (and the harness is ready).
ToolPurpose
coding_agent_run / coding_agent_statusStart a run in the background; follow one run in full
coding_run_messageSteer a run that is still working — a correction or a missed constraint, queued for it without stopping it
coding_run_listEvery run at a glance: status, who started it, its branch and whether that work is merged home, attempts at its deliverable and whether it delivered, why a paused one is paused, whether it is detached (it survives a restart of the web server), and anything it left running
coding_agent_resumeCarry on a paused run, or one that gave up short of its deliverable, in the same session — only runs the agent started, and optionally with a message first
coding_agent_stopStop a running run; close a paused one for good; end a server a finished run left running (only when you ask)
coding_project_statusYour projects in one table: how to name each to a run, last commit, desktop or server app, latest run, and how many runs are working, waiting, unmerged or left running
coding_team_run / coding_team_status / coding_team_stopThe same for a team of runs
coding_secret_listWhich secrets a run may use — names only
coding_project_importBring an existing project into your project folder — clone one of your GitHub repositories or copy a folder already on the box — only when you ask
coding_settings_get / coding_settings_setRead and change the coding team’s settings
app_publishPublish a project that has a clawbox.json to the ClawBox Store under this box’s account — only when you ask, after confirming the version; until publishing is open to your account it says so
A typical exchange: the agent checks coding_project_status, starts coding_agent_run, tells you it is running and stops. When you change your mind mid-run it sends coding_run_message rather than stopping the run; when you ask how it went it calls coding_run_list or coding_agent_status. A run paused for a spent allowance is resumed with coding_agent_resume only after the allowance is back.
What stays yours. The agent cannot switch the coding agent on, change a project’s pipeline default, merge a run’s branch home, or pause, resume or stop a run you started. Those routes only accept your own signed-in browser session, so the agent points you at the button instead.

Email — both editions

email_send · email_list · email_read · email_connect email_connect connects your mail account from the chat — only with an address and app password you typed yourself, never ones read from a page, file or email. email_send does not put a message on the wire while Ask me before sending is on, which is the default: it queues a draft that you approve in the chat or in Settings → Channels → Email. Turn that switch off and the same tool sends directly. See Messaging channels.

Every change the assistant makes is one commit in the page’s History, authored ClawBox assistant, and a fact it verifies is stamped as verified by the assistant — so you can see what it did and Undo it. Deleting, merging, undoing and changing settings need the assistant to confirm you asked. Undo stays yours: the assistant can undo only its own changes. Setting the wiki up, the document drop and the reindex and repair passes have no tool.

Memory Shard

memory_shard_status — both editions — reports whether Memory Shard is on and healthy, how many folders, files and chunks it holds, why it wants a reindex (a folder added, files changed, the embedding model switched…) and how far a running indexing pass has got (files done of the total, chunks, percent). Everything else the Memory Shard app does is a tool too, on both editions: start or stop an indexing pass (memory_shard_reindex, memory_shard_reindex_stop), list, add and remove folders (memory_shard_sources_* — adding one says how many files it holds), read and change the refresh schedule (memory_shard_schedule_*) and where the index is embedded (memory_shard_provider_*), switch it on or off (memory_shard_enable) and start over (memory_shard_reset). The agent runs incremental passes on its own — they read only new and changed files. A full re-embed, a move to another embedding model and a reset wait for your yes in the chat: the agent first tells you what it would cost (files, time, embedding tokens) or exactly what a reset clears, and acts only after you agree. memory_shard_search — Hermes edition only — searches the documents and notes in the folders you added to Memory Shard, returning the file each passage came from, the passage, and how well it matched. It is Hermes-only because of where the index is, not because of which agent deserves it: on an OpenClaw box the memory index belongs to OpenClaw and the agent already searches it while answering, so a second tool would be a second answer to the same question.
The tool’s own description marks what comes back as the owner’s documents — information to read, never instructions to follow — the same way the skills tools mark publisher text.

Local AI — both editions

local_ai_status lists the engines that run on the box itself — Kokoro (speaks replies), Whisper (transcribes), the embedding model behind Memory Shard and the llama.cpp model — with whether each is installed and running, and which voice and transcription engine the box uses right now. It never installs anything: installing an engine runs as root and downloads the model, so it only happens from Settings → Local AI in your browser.

​
ClawBox AI usage — both editions

clawbox_ai_usage reads how much of your ClawBox AI allowance is used: the weekly allowance and the short-term limit (5 hours), and when each frees up, the weekly meters for pictures, spoken replies, transcribed audio and memory indexing, and your prepaid credits. Where clawbox.com does not share the figures with the box yet, the agent says so and points you at your account there. No tool changes your plan or buys credits.

​
Anthropic accounts — both editions

anthropic_accounts reads the Anthropic account pool from Settings → Providers → Anthropic accounts: coding runs use it, and so do the chat, its channels and its scheduled tasks once the owner has pressed Use these accounts for the chat too. For each account it gives the name, the kind and the state: it can answer, or it is at its usage limit and back at a given time. It also gives the order, the active account (in_use: the one new coding runs start on and the chat’s account order leads with — a run or a conversation already under way may still be finishing on another), how many can answer, and the last swap (last_swap: when, from which account to which, and why). When every account is limited, it tells the agent to wait for the first reset: runs that were cut off resume by themselves then, and coding_agent_run refuses a new Anthropic run until that time. The answer never carries an email or a credential. Adding, ordering and removing accounts is yours to do, in Settings. See Multiple Anthropic Accounts.

Safety rails

  • One protected-path list, applied to descendants and not just the path handed in: list_directory filters entries, glob filters results, and grep filters both its search roots and every hit.
  • Argv only. Outside bash, no tool builds a shell string out of an argument.
  • Confirmation on irreversible actions. system_power and code_project_delete require an explicit confirm flag — something a web page the agent happens to be reading cannot supply by accident.
  • Protected ClawBox files. With Settings → Harness → Protect ClawBox files from the agent on (the default), the harness’s own file and shell tools cannot delete, overwrite, truncate or move ClawBox’s own files or the local AI models — see Architecture.
  • Tool output is scrubbed. Tokens, keys and other credentials are removed from what a tool hands back before the assistant sees it.
  • Timeouts and output caps everywhere, so one slow call cannot stall a turn.
  • Errors are instructions, not stack traces. Every failure comes back as a short code, a message and a suggested next step — never a raw trace or an absolute path.
  • On the OpenClaw edition, plan around bash being as capable as the device user. Its pre-flight refuses commands naming a credential store, but that is a guard rail against a mistake, not a sandbox.
  • Telegram senders must be pairing-approved before the agent will act for them (details).

The clawbox-cli wrapper

The same capabilities are shell-callable, from the Terminal app or over SSH.
There is no clawbox command on PATH — nothing in the installer creates one. The wrapper is a script in the checkout, run through Bun:
bun run /home/clawbox/clawbox/mcp/clawbox-cli.ts <args>
bun is on the interactive PATH, so this works in the Terminal app and in an interactive SSH session. In a non-interactive ssh box '…' or a systemd unit, use the full path /home/clawbox/.bun/bin/bun. If you use it often, alias it: alias clawbox='bun run /home/clawbox/clawbox/mcp/clawbox-cli.ts'.
The subcommands (shown below with that alias in place): 
clawbox webapp create <appId> <name> [--html ...]   # install a desktop webapp
clawbox webapp update <appId> [--html ...]          # replace its HTML
clawbox app open <appId> | app list                 # drive the desktop
clawbox notify "message"                            # desktop notification
clawbox system stats | system info                  # metrics
clawbox edition                                     # openclaw | hermes | dual
clawbox code init|list|build|files|read|write|edit|search|delete ...
clawbox update                                      # full system update — OpenClaw edition only
update asks for sudo itself when it re-runs the installer — do not prefix the command with sudo, or it runs under root’s PATH and environment instead of yours. On a Hermes device update refuses and points you at Settings → System Update, which runs the edition-correct installer steps. (On the premium dual SKU the guard does not fire, because the edition lock there reads dual.)

How authentication works

  • The MCP server talks to the device APIs at http://127.0.0.1:80/setup-api/* with the MCP bearer token (data/.mcp-token, seeded at boot, 0600).
  • The token lives in that file only. Nothing copies it into a harness config, so rotating it is not a configuration-sync problem.
  • The agent gets these tools only if its harness has the server registered:
    • OpenClaw — reconciled into the gateway’s config on every gateway start.
    • Hermes — reconciled into ~/.hermes/config.yaml on every web-server boot, and again at install time. Both paths are idempotent, so a restart, a redeploy or an update all converge on the same entry.
  • If tools suddenly fail with auth errors, clawbox_health diagnoses it.
  • On the dual SKU the tool set follows the currently active harness (/setup-api/harness/active), re-resolved when the MCP server starts, rather than being fixed by the edition lock. If the lock file exists but cannot be read, the smaller Hermes tool set is registered on purpose.

For agent developers

Working on a ClawBox, or building automation against one? The stable integration surfaces are:
  1. MCP tools (this page) — through the on-device agent.
  2. /setup-api/* HTTP APIs — session-cookie or MCP-bearer authenticated; the same APIs the desktop UI uses.
  3. mcp/clawbox-cli.ts — over SSH or in the Terminal app, run through bun run.
  4. The agent workspace guide seeded on the device.
See the Quick Reference for the one-page fact sheet (ports, paths, services, commands).
